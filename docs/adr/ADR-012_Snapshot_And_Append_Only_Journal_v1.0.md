**Область:** транзакционная граница journal↔projection, Domain Event Store contract (`EventSequence` как авторитетный порядок, append-only гарантия, `PayloadHash`, event visibility), compensating-механизм исправления событий, идемпотентность команд (`AppliedCommands`), snapshot contract (определение, триггеры, создание через SQLite Backup API), backup contract на уровне journal-инварианта

# 1. Решение

Odyssey VTT фиксирует единственный авторитетный append-only Domain Event Store, транзакционно связанный с current-state projections, и снимает snapshot кампании по определённому набору триггеров через SQLite Backup API. Журнал и snapshot — разные механизмы с разным назначением и не заменяют друг друга.

Обязательные решения:

1. Авторитетный порядок событий внутри кампании определяется исключительно монотонным `EventSequence`, назначаемым только host в транзакции (`ADR-011` §9.2). Timestamp (`CreatedAtHost`) используется только для отображения и диагностики и никогда не является источником порядка.
2. `DomainEvents` — append-only. Application-код не имеет обычного `UPDATE DomainEvents` и `DELETE DomainEvents`. Единственное исключение — специализированный архивный процесс, перемещающий sealed session events после подтверждённой проверки архива; даже тогда исходная история логически не редактируется: в активной базе остаётся archive index и integrity metadata (раздел 4.2).
3. `PayloadHash` — integrity marker, позволяющий обнаружить физическое изменение event payload. Он явно **не** является криптографической подписью доверенного сервера (раздел 4.3).
4. Event Store хранит полный авторитетный Event. Redaction для сетевых клиентов выполняется исключительно на уровне Networking projections; приватное событие никогда не удаляется и не усекается в базе только потому, что часть клиентов не имеет к нему доступа (раздел 4.4).
5. Одна SQLite-транзакция обязана коммитить одновременно: current-state projection, `DomainEvents`, `GameLogEntries`/`CalculationTrace` (где применимо), network outbox entries и результат `AppliedCommand`. Частичный коммит этой группы запрещён (раздел 5).
6. Исправление уже закоммиченного события выполняется исключительно через компенсирующий механизм `OriginalEvent → CompensatingCommand → CompensatingEvent`. Физическое удаление или `UPDATE` события для обычного Undo, GM Override или воскрешения персонажа запрещены (раздел 6).
7. Повторная доставка команды с тем же `CommandId` не применяет эффект повторно; хост возвращает сохранённый результат из `AppliedCommands`. Это единственный механизм exactly-once effect поверх at-least-once доставки команд (раздел 7).
8. Snapshot — консистентная полная копия `campaign.db`, создаваемая через SQLite Backup API. Это не network snapshot и не domain projection snapshot (раздел 8.1).
9. Snapshot создаётся по фиксированному набору триггеров (раздел 8.2), а не только "по расписанию"; если состояние не изменилось с предыдущего snapshot, новый snapshot не создаётся.
10. Создание snapshot следует обязательному 8-шаговому flow (раздел 8.4). Копирование открытого `campaign.db` вместе с неподтверждённым WAL-состоянием запрещено при любых обстоятельствах.
11. Backup/snapshot не заменяет append-only историю и audit (`PE-INV-008`). Их назначение — disaster recovery и перенос кампании, не альтернативный источник авторитетной истории (раздел 9).
12. Этот ADR не переопределяет физическую структуру `Backups/` или version dimensions, зафиксированные `ADR-011` (раздел 10).
13. Точные числа ротации backup (сколько fast/daily/weekly копий хранить) не фиксируются этим ADR как нормативное решение — они остаются product-настраиваемым baseline, не техническим контрактом (раздел 8.5, явное обоснование).
14. Выбор конкретной SQLite provider-библиотеки наследует статус `[OPEN]` из `ADR-011` §12.1 и не решается здесь (раздел 11.2).
15. Owner key storage mechanism, миграция schema/ruleset и её workflow не входят в этот ADR (раздел 11).

Этот ADR является нормативным authority по Domain Event Store, транзакционной границе journal↔projection, compensating-механизму и snapshot contract. Он реализует и уточняет `05_Persistence_Odyssey_VTT_v0.8.md` разделы 3 (`PE-INV-004`, `PE-INV-005`, `PE-INV-008`), 10–12 и 20–21 применительно к `SLICE-01` без изменения продуктового поведения, описанного там.

# 2. Контекст и проблема

`ADR-011` определяет физический формат кампании (папки, `manifest.json`, версии, SQLite-профиль, принцип схемы), но явно не решает: как именно фиксируется история событий, что именно гарантирует "append-only" на практике, как связаны запись projection и запись события в одной транзакции, как исправляются ошибочные события без нарушения `PE-INV-004`, и какой именно алгоритм используется для snapshot. Без отдельного ADR:

1. Implementation-задачи `SLICE-01` могли бы реализовать transaction pipeline (`05_Persistence` §11.1) неполно — например, закоммитить projection без события или наоборот, нарушив `PE-INV-005`.
2. "Append-only" осталось бы декларацией без явного нормативного запрета `UPDATE`/`DELETE` и без описания единственного законного исключения (архивирование).
3. Не было бы явного, проверяемого правила, отличающего компенсирующее исправление (`PE-INV-004`) от запрещённого редактирования истории задним числом.
4. Snapshot-триггеры (`05_Persistence` §20.2) остались бы product-документом, а не обязательством, которое `ODY-S01-005` (`SP-02`) сможет протестировать на надёжность.
5. Migration runner (`ODY-S01-003`) не имел бы явной точки опоры для требования "snapshot перед migration" — этот ADR фиксирует его как триггер (раздел 8.2), не описывая сам migration workflow.

# 3. Термины

## 3.1 Domain Event Store

Таблица `DomainEvents` и связанная с ней инфраструктура, хранящая полную, неизменяемую (append-only) историю доменных событий кампании.

## 3.2 EventSequence

Монотонно возрастающий integer, уникальный внутри кампании, назначаемый только host в рамках транзакции, фиксирующей событие. Единственный источник авторитетного порядка событий.

## 3.3 Compensating event

Новое событие, логически отменяющее или корректирующее эффект ранее закоммиченного события, без изменения или удаления оригинального события.

## 3.4 Snapshot

Консистентная полная копия `campaign.db`, созданная SQLite Backup API в определённый момент времени, идентифицируемая `BackupId` и связанной `BackupRecord`.

## 3.5 Fast backup / Full backup

Fast backup — snapshot `campaign.db` + `manifest.json` + `backup-manifest.json`, без повторного копирования `Assets/`. Full backup — то же плюс `Assets/` и `checksums.json`.

# 4. Domain Event Store contract

## 4.1 `EventSequence` как единственный авторитетный порядок

Внутри одной кампании `EventSequence` — единственный источник истины о порядке событий. `CreatedAtHost` (timestamp) используется исключительно для отображения пользователю и диагностики и никогда не участвует в определении порядка, разрешении конфликтов или восстановлении состояния. Реализация, использующая timestamp как fallback или дополнительный источник порядка, нарушает этот ADR.

## 4.2 Append-only гарантия и единственное исключение

`DomainEvents` — append-only на уровне application-кода: не существует обычного пути `UPDATE DomainEvents` или `DELETE DomainEvents` в производственном коде приложения.

Единственное исключение — специализированный архивный процесс, который перемещает **sealed session events** (уже закрытую, финализированную игровую сессию) после подтверждённой проверки архива. Даже в этом случае:

- исходная история событий логически не редактируется — перемещённые события физически перестают быть частью активной рабочей таблицы, но их содержимое не изменяется;
- в активной базе остаётся archive index и integrity metadata, достаточные, чтобы доказать, что перемещённые события существовали и не были искажены;
- этот процесс не используется как механизм "очистки" или "исправления" истории — он применяется только к уже sealed, архивным данным, не к активному игровому журналу.

## 4.3 `PayloadHash` как integrity marker

Каждое событие в `DomainEvents` включает `PayloadHash`, вычисляемый над `PayloadJson`. Назначение `PayloadHash` — обнаружение случайного или злонамеренного физического изменения payload на диске (integrity check), а не подтверждение подлинности отправителя. `PayloadHash` явно **не** является криптографической подписью доверенного сервера и не должен интерпретироваться реализацией как таковая.

## 4.4 Event visibility и redaction

Domain Event Store хранит **полный** авторитетный Event для каждого доменного события, независимо от того, какие клиенты имеют право его видеть. Разграничение видимости (`VisibilityClass`) применяется на уровне Networking, которое строит redacted projections для конкретных клиентов. Приватное или скрытое от части игроков событие **не удаляется** и не усекается в базе только из-за отсутствия доступа у части клиентов — база остаётся единственным полным источником истины для GM/host.

# 5. Транзакционная граница journal↔projection

Следующая группа операций обязана фиксироваться **одной** SQLite-транзакцией (`05_Persistence` §11.1, шаги 4–14; `PE-INV-003`, `PE-INV-005`):

```text
1. Изменение current-state projection(s), затронутых командой
2. Запись соответствующей immutable DomainEvent (или нескольких)
3. Запись GameLogEntry / CalculationTrace, если применимо к данной команде
4. Запись network outbox entries, если команда требует уведомления клиентов
5. Запись результата в AppliedCommands (Status, ResultEventSequenceFrom/To, ResultSummary/FailureCode)
```

Нормативное правило: **нельзя** успешно изменить projection без соответствующего события в той же транзакции, и **нельзя** зафиксировать событие, обязанное изменить current state, без соответствующего изменения projection в той же транзакции (`PE-INV-005`). Частичный коммит этой группы — например, успешная запись projection при неудачной записи `DomainEvent`, или наоборот, — является дефектом реализации, а не допустимым частичным состоянием.

Многоагрегатные операции (`05_Persistence` §11.4: attack resolution, transfer item, progression confirmation, member removal/ownership transfer, session end/archive sealing metadata, content import, definition migration, GM Override, fatal action compensation, archive deletion audit, restore metadata) применяются той же единственной транзакцией, не серией последовательных commit'ов.

При ошибке до commit (`05_Persistence` §11.2): транзакция откатывается целиком; ни state, ни event journal не изменяются; клиент получает reject/error; повтор с тем же `CommandId` разрешён, поскольку результат не стал durable.

# 6. Compensating-механизм (`PE-INV-004`)

Исправление уже закоммиченного события выполняется только через:

```text
OriginalEvent
    ↓
CompensatingCommand
    ↓
CompensatingEvent
```

Правила:

- `CompensatingEvent` — новое, отдельное событие с собственным `EventSequence`, ссылающееся на исходное через `OriginalEventId`/`CompensationGroupId` (поля таблицы `DomainEvents`, `05_Persistence` §12.1).
- Физическое удаление события (`DELETE`) или его модификация (`UPDATE`) для обычного Undo, GM Override или "воскрешения" персонажа **запрещены** без исключения.
- Компенсирующая команда проходит тот же транзакционный pipeline (раздел 5), что и любая другая команда — она не является привилегированной операцией, обходящей journal↔projection границу.
- Этот механизм — единственный законный способ "исправить" видимый эффект прошлого события; любая implementation-задача, реализующая GM Override, Undo или Intervention-компенсацию, обязана использовать `CompensatingCommand`/`CompensatingEvent`, а не прямую модификацию `DomainEvents` или projection в обход журнала.

# 7. Идемпотентность команд

## 7.1 `AppliedCommands`

Каждая применённая команда получает запись в `AppliedCommands` (`CommandId` PK, `Status`, `ResultEventSequenceFrom?/To?`, `ResultSummary?`, `FailureCode?`, `CreatedAt`, `CompletedAt`) в той же транзакции, что и связанные события (раздел 5).

## 7.2 Exactly-once effect поверх at-least-once delivery

Повторная доставка команды с тем же `CommandId`:

- не применяет эффект второй раз;
- возвращает сохранённый результат из `AppliedCommands`, а не пересчитывает его заново;
- не расходует повторно action, ammo, resource или Intervention Points.

Это единственный нормативный механизм exactly-once effect поверх сети с at-least-once доставкой команд (`05_Persistence` §11.3). Реализация не должна изобретать альтернативный dedup-механизм (например, client-side debounce как единственную защиту) вместо проверки `AppliedCommands` на хосте.

## 7.3 Ошибка после commit до сетевого ответа

Если commit прошёл успешно, но сетевое подтверждение клиенту не было доставлено, хост при повторном запросе с тем же `CommandId` возвращает уже сохранённый результат, не выполняя команду заново. Сетевое подтверждение успеха никогда не отправляется до успешного commit (`05_Persistence` §11.1, "Сетевое подтверждение успеха не отправляется до успешного commit").

## 7.4 Ошибочный конфликт revision

Несовпадение `ExpectedAggregateRevisions`/`ExpectedCampaignRevision` приводит к `CommandRejected: RevisionConflict` (`05_Persistence` §10.3). Такой reject не создаёт `DomainEvent` (если само отклонение не обязано быть видимо в игровом журнале, `05_Persistence` §10.5) и представляется клиенту как типизированный `Error` по контракту `ADR-004` (категория `Conflict`, стабильный `ErrorCode`, безопасный `SafeReasonCode`), а не как необработанное исключение или сырой SQL-конфликт.

# 8. Snapshot contract

## 8.1 Определение

Snapshot — консистентная полная копия `campaign.db`, созданная через SQLite Backup API. Это принципиально отличается от двух других понятий, которые не должны с ним смешиваться:

- **network snapshot** — полное состояние, передаваемое клиенту по сети при подключении (Networking-контракт, не этот ADR);
- **domain projection snapshot** — исторический срез конкретного aggregate (например, `ItemInstance mechanics snapshot`, `05_Persistence` §8.3), не файловая копия базы.

## 8.2 Обязательные триггеры

Snapshot кампании создаётся при наступлении любого из следующих условий (в порядке того, что наступит раньше):

1. в начале сессии;
2. в конце сессии;
3. каждые 10 минут при наличии изменений с предыдущего snapshot;
4. после 100 подтверждённых событий с предыдущего snapshot;
5. перед database migration (используется `ODY-S01-003`, Migration Runner, как обязательный предварительный шаг — этот ADR фиксирует сам триггер, не workflow миграции);
6. перед потенциально опасными restore/maintenance operations;
7. перед крупным GM Override, если operation policy это требует.

Если состояние кампании не изменилось с момента предыдущего snapshot (нет новых подтверждённых событий), новый snapshot **не** создаётся — повторный snapshot идентичного состояния — не ошибка, но и не обязательное действие.

## 8.3 Обязательные счётчики

Persistence обязана хранить:

```text
LastSnapshotCampaignRevision
LastSnapshotEventSequence
LastSnapshotAt
EventsSinceLastSnapshot
```

Эти счётчики — единственный источник истины для решения "наступил ли триггер раздела 8.2", не пересчёт с нуля при каждой проверке.

## 8.4 Создание

Snapshot создаётся строго по следующей последовательности:

```text
1. Allocate BackupId
2. SQLite Backup API → temporary db
3. Open temporary db read-only
4. Run integrity validation
5. Compute hash and size
6. Write backup manifest
7. Atomic move to final backup path
8. Persist BackupRecord
```

Копирование открытого `campaign.db` обычным файловым копированием (например, `File.Copy`) вместе с неподтверждённым WAL-состоянием **запрещено** при любых обстоятельствах — только SQLite Backup API гарантирует консистентность копии при активном WAL-режиме (согласовано с `ADR-011` §7.1).

## 8.5 Ротация backup — не фиксируется этим ADR как нормативное число

`05_Persistence` §21.3 описывает стандартный baseline ротации (10 последних быстрых копий, 7 ежедневных, 4 еженедельные) и явно отмечает: "Политика может быть изменена в CampaignSettings." Поскольку сам продуктовый документ уже описывает эти числа как настраиваемый baseline, а не фиксированный технический контракт, этот ADR **не** превращает их в обязательное нормативное решение. Обязательными техническими контрактами этого ADR являются: состав Fast/Full backup (раздел 8.6), схема `BackupRecord` (раздел 8.7), и правило `PE-INV-008` (раздел 9) — не конкретные числа хранения копий. Реализующая задача обязана предоставить настраиваемую политику ротации со значениями по умолчанию из `05_Persistence` §21.3, но точные default-числа не требуют amendment этого ADR при изменении.

## 8.6 Состав backup

**Fast backup:** снимок `campaign.db`, `manifest.json`, `backup-manifest.json`. `Assets/` повторно не копируется.

**Full backup:** то же, что Fast backup, плюс `Assets/` и `checksums.json`.

Оба вида backup физически размещаются в структуре `Backups/`, определённой `ADR-011` §4.1 (`Fast/`, `Daily/`, `Weekly/`, `Full/`, `Emergency/`); этот ADR не переопределяет эту структуру.

## 8.7 `BackupRecord`

Минимальная обязательная схема:

```text
BackupRecord
├── BackupId
├── CampaignId
├── BackupKind
├── Reason
├── CampaignRevision
├── EventSequence
├── DatabaseSchemaVersion
├── CampaignFormatVersion
├── RulesetRef
├── CreatedAt
├── CreatedByUserId?
├── RelativePath
├── DatabaseHash
├── AssetsManifestHash?
├── SizeBytes
├── IntegrityStatus
└── SourceOperationId?
```

`DatabaseSchemaVersion` и `CampaignFormatVersion` в `BackupRecord` обязаны совпадать по смыслу с одноимёнными dimensions `ADR-011` §6.1 — этот ADR не вводит альтернативные версии для backup.

## 8.8 Проверка после создания и нехватка места

Каждая DB-копия открывается read-only и проходит базовую integrity validation сразу после создания (раздел 8.4, шаг 4); полный hash всех assets выполняется отдельно для full backup/export. При нехватке места для snapshot допускается удалить только backup, уже подлежащий ротации; при неуспехе после одного повтора backup отменяется с предупреждением, а рабочая команда игры не должна быть повреждена этим сбоем.

# 9. Backup как journal-инвариант (`PE-INV-008`)

Snapshot и backup предназначены для аварийного восстановления и переноса кампании. Они **не заменяют** append-only историю и audit, зафиксированные разделом 4 этого ADR. В частности:

- восстановление из backup не является заменой воспроизведения событий из Domain Event Store для целей audit/diagnostic;
- отсутствие свежего backup не освобождает реализацию от обязательности append-only журнала — журнал остаётся авторитетным источником истины между snapshot'ами;
- backup — точка disaster recovery (потеря/повреждение базы, перенос на другую машину), а не альтернативный или более "лёгкий" источник истории событий.

---

# 10. Граница с `ADR-011`

Этот ADR не переопределяет и не дублирует решения `ADR-011`:

- физическая структура `Backups/Fast|Daily|Weekly|Full|Emergency` (`ADR-011` §4.1) используется как есть, не создаётся заново;
- version dimensions `CampaignFormatVersion`/`DatabaseSchemaVersion`/`RulesetVersion` (`ADR-011` §6.1) используются, но не переопределяются; `BackupRecord` лишь ссылается на них;
- SQLite runtime profile (WAL, single writer, checkpoint, `ADR-011` §7) используется как предпосылка для snapshot через Backup API, не переопределяется;
- обязательный минимальный набор системных таблиц (`ADR-011` §8.2) включает `DomainEvents`, `AggregateRevisions`, `BackupRecords`, `MigrationRecords` — этот ADR детализирует semantics `DomainEvents`/snapshot-related таблиц, но не изобретает новые системные таблицы сверх уже перечисленных в `ADR-011`, кроме уточнения полей `AppliedCommands` (раздел 7.1), которая также входит в минимальный список `ADR-011` §8.2.

# 11. Не входит в ADR-012

- **Owner key storage mechanism** — `ODY-S01-004`; этот ADR не затрагивает хранение секретов.
- **Выбор конкретной SQLite provider-библиотеки** — наследует статус `[OPEN]` из `ADR-011` §12.1. Ничего в snapshot/journal contract этого ADR требует решения этого вопроса именно здесь: SQLite Backup API — часть стандартного SQLite API, доступного независимо от выбора .NET provider-обёртки. Открытый вопрос остаётся открытым, не закрывается молчаливо.
- **Migration runner и его workflow** — `ODY-S01-003`. Этот ADR фиксирует только факт, что migration требует предварительного snapshot (раздел 8.2, пункт 5), не то, как сама миграция выполняется, откатывается или регистрируется.
- **Точные числа ротации backup** — см. раздел 8.5, явно оставлено product-настраиваемым baseline, не нормативным решением ADR.
- **`SLICE-01` вертикальный срез** (создание кампании, импорт карты, сцена, токены и т.д.) — использует этот контракт, но не реализуется здесь.

# 13. Правила для Codex

Codex обязан:

1. Никогда не использовать timestamp как источник авторитетного порядка событий — только `EventSequence`.
2. Не реализовывать `UPDATE`/`DELETE` над `DomainEvents` вне единственного архивного исключения раздела 4.2.
3. Не удалять и не усекать события в базе по причине их недоступности части сетевых клиентов — redaction только на уровне Networking projections.
4. Коммитить projection, `DomainEvent`, `GameLogEntry`/`CalculationTrace`, outbox и `AppliedCommand` результат одной транзакцией (раздел 5), не серией отдельных commit'ов.
5. Исправлять уже закоммиченные события только через `CompensatingCommand`/`CompensatingEvent`, никогда прямой модификацией.
6. Реализовывать проверку `AppliedCommands` до повторного применения эффекта команды при повторной доставке.
7. Создавать snapshot только через SQLite Backup API — никогда обычным копированием файла с активным WAL.
8. Не изобретать дополнительные snapshot-триггеры сверх раздела 8.2 и не пропускать ни один из перечисленных без amendment этого ADR.
9. Не фиксировать точные числа ротации backup как жёсткий контракт в коде без возможности конфигурации (раздел 8.5).
10. Не пинить SQLite provider-библиотеку под предлогом реализации snapshot API — вопрос остаётся открытым (раздел 11).
11. Не решать migration workflow или owner key storage под этим ADR.

# 14. Definition of Done / критерии приёмки ADR-012 implementation

ADR считается реализованным (для той части, которую он определяет), когда:

1. `DomainEvents` не имеет производственного пути `UPDATE`/`DELETE`, кроме архивного процесса раздела 4.2, покрытого тестом.
2. Порядок событий воспроизводится строго по `EventSequence`; тест, сортирующий события по timestamp, не используется как источник истины нигде в production-коде.
3. Транзакционный тест доказывает: успешная projection без соответствующего `DomainEvent` невозможна, и наоборот (раздел 5).
4. Повторная отправка команды с тем же `CommandId` до и после commit не создаёт дублирующий эффект (раздел 7.2–7.3), покрыто тестом.
5. Компенсирующая команда создаёт новое событие со ссылкой на оригинал, не изменяет и не удаляет оригинальное событие (раздел 6), покрыто тестом.
6. Snapshot создаётся при достижении каждого из перечисленных в разделе 8.2 триггеров и не создаётся при отсутствии изменений.
7. Snapshot использует SQLite Backup API; тест, эмулирующий активный WAL с неподтверждёнными данными, подтверждает отсутствие использования простого файлового копирования.
8. `BackupRecord` содержит все поля раздела 8.7 и корректно ссылается на текущие `DatabaseSchemaVersion`/`CampaignFormatVersion`.
9. Restore из backup не создаёт новых `DomainEvent` записей, эквивалентных "переигрыванию" истории — backup остаётся отдельным механизмом от журнала (раздел 9).

# 15. Рассмотренные альтернативы

## 15.1 Timestamp как источник порядка событий

Отклонено: часы на разных машинах/процессах не гарантируют монотонность и синхронизацию; `EventSequence`, назначаемый host-транзакцией, детерминирован и не зависит от системных часов.

## 15.2 Физическое удаление/исправление события вместо compensating-механизма

Отклонено: напрямую нарушает `PE-INV-004`; делает невозможным honest audit/diagnostic истории кампании и усложняет отладку расхождений между клиентами.

## 15.3 Отдельные независимые транзакции для projection и для события

Отклонено: создаёт окно, в котором возможно рассинхронизированное состояние (projection изменена, событие не записано, или наоборот) при сбое между двумя транзакциями — прямое нарушение `PE-INV-005`.

## 15.4 Client-side debounce как единственная защита от дублирования команд

Отклонено: не защищает от повторной доставки на уровне сети/host (at-least-once delivery) и не даёт хосту авторитетного источника истины о том, была ли команда уже применена.

## 15.5 Обычное файловое копирование `campaign.db` для snapshot

Отклонено: при активном WAL-режиме копирование основного файла без учёта `-wal`/`-shm` даёт несогласованную копию; SQLite Backup API — единственный способ, гарантированно дающий консистентный снимок при работающем writer.

## 15.6 Snapshot только "по расписанию" (например, раз в час) без событийных триггеров

Отклонено: не защищает от потери большого числа изменений между плановыми snapshot при высокой активности сессии; событийный триггер "100 подтверждённых событий" (раздел 8.2) дополняет временной триггер именно для этого случая.

## 15.7 Зафиксировать точные числа ротации backup как жёсткий ADR-контракт

Отклонено: сам `05_Persistence` уже описывает эти числа как настраиваемую политику (§21.3), а не технический инвариант; фиксация их в ADR создала бы ложное впечатление, что изменение default-значения требует amendment ADR, хотя продуктовый документ явно говорит обратное.
