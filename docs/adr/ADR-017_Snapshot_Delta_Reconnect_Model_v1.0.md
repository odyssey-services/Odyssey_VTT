**Статус:** Accepted
**Область:** application-level протокол проекции состояния поверх `ISessionTransport` (`ADR-015`) — scene snapshot contract (первичный/chunked snapshot, snapshot identity), формат delta-батчей и операций, gap detection, обработка дублирующихся delta, late join, disconnect/reconnect flow, правило fallback delta-catchup-или-полный-snapshot

# 1. Решение

Odyssey VTT определяет единственный application-level протокол доставки и восстановления projection-состояния поверх `ISessionTransport`'s reliable-канала (`ADR-015` §5.1): каждое подключение получает первичный **ProjectionSnapshot**, затем поток **ProjectionDeltaBatch**, с явным протоколом обнаружения разрывов (gap detection), обработки дубликатов, и явным правилом выбора между delta-catchup и полным snapshot при reconnect.

Обязательные решения:

1. **Snapshot identity**: `ProjectionSnapshot` идентифицируется составной идентичностью — `SnapshotId` (уникальный идентификатор конкретного снимка) **плюс** `BaseSessionSequence`/`ProjectionRevision`/`PermissionRevision` (позиция в потоке событий и ревизия проекции/прав на момент создания) **плюс** `PayloadHash` (integrity-хэш содержимого) — все четыре измерения одновременно, не единственный монотонный номер и не единственный хэш по отдельности. Обоснование: монотонный номер один даёт порядок, но не integrity; хэш один даёт integrity, но не порядок/позицию для delta-catchup сравнения — участнику нужны оба свойства одновременно (раздел 4).
2. **Delta-батч**: минимальная единица сетевой доставки — `ProjectionDeltaBatch` (не отдельная `Operation`) с диапазоном `SequenceFrom`/`SequenceTo`, `ProjectionRevisionBefore`/`After`, списком `Operations[]`, и `BatchHash`. Операции применяются строго в порядке появления внутри `Operations[]`, батчи — строго по возрастанию `SequenceFrom` (раздел 5).
3. **Дедупликация на этом уровне — отдельный, не production-command-идентичный механизм.** Дублирующийся, полностью уже применённый батч подтверждается и молча игнорируется по совпадению диапазона `SequenceFrom`/`SequenceTo` с уже применённым `LastAppliedSequence`, **не** по `CommandId`. Это не альтернатива и не замена `ADR-012` §7's `AppliedCommands`-механизму (host-side exactly-once effect поверх at-least-once command delivery) — это отдельный, more downstream слой: дедупликация доставки уже вычисленной host'ом проекции, а не дедупликация применения команды. Оба механизма действуют одновременно, на разных данных, для разных гарантий (раздел 3, раздел 6).
4. **Gap detection**: если ожидаемый `SequenceFrom` клиента не совпадает с полученным батчем — батч не применяется; клиент запрашивает gap repair за пропущенный диапазон; host отвечает либо недостающими батчами из своего delta-буфера (раздел 8), либо, если диапазон вне буфера, новым полным `ProjectionSnapshot` (раздел 7).
5. **Late join**: участник без предшествующего `LastAcknowledgedSequence` (первое подключение к сессии, не reconnect) всегда получает только первичный `ProjectionSnapshot` — никогда delta-replay истории. Это не отдельный протокол, а частный случай snapshot-протокола при отсутствии предыдущего состояния клиента (раздел 7).
6. **Reconnect**: после успешного transport-уровневого переподключения (`ADR-016` §5 — allocation переиспользуется через join code) application-уровень выполняет 10-шаговый flow (раздел 9), решающим шагом которого является: **delta-catchup, если запрошенный диапазон внутри host'ового delta-буфера; иначе полный переразрешённый snapshot.** Оба пути — нормативная часть протокола, не взаимоисключающий выбор архитектуры (раздел 7/8).
7. **Host обязан вести ограниченный (bounded) delta-буфер на сессию для catchup/gap-repair** — не "всегда полный snapshot" как единственный путь. Обоснование выбора для MVP-класса — раздел 8: полный snapshot при каждом кратковременном разрыве связи (частый случай на мобильных/нестабильных сетях, подтверждено `SP-03`'s собственной оговоркой о непроверенных условиях реального игрока) был бы неоправданно дорог по трафику для рутинного случая; buffered catchup покрывает наиболее частый сценарий дёшево, полный snapshot остаётся corrrect fallback для случая, когда буфер не покрывает разрыв — то есть система не полагается только на дорогой путь и не полагается только на буфер без fallback.
8. **Permission change during disconnect**: при reconnect redaction всегда пересчитывается по текущим (не сохранённым) permissions — отозванный за время отключения доступ не восстанавливается вслепую из старой проекции (raw §18.3, подтверждено без изменений).
9. **`PendingInteraction` reconnect**: активные ожидания пользователя — часть snapshot/delta payload, восстанавливаются интерфейсом в правильном порядке после reconnect (raw §18.4, подтверждено без изменений).
10. Этот ADR **не определяет**: кто что видит в snapshot/delta (visibility/redaction-правила) — `ODY-S02-006` (Permissions Baseline); production-реализацию этого протокола поверх `ISessionTransport` — future implementation task; интеграцию реального Unity Relay SDK — отдельная future задача, заблокированная `ADR-016` §14's эмпирическим гейтом.

Этот ADR является нормативным authority по application-level протоколу проекции состояния. Он реализует и уточняет `06_Networking_and_Session_Sync_Odyssey_VTT_v0.8.md` разделы 15–18 применительно к `SLICE-02` без изменения продуктового поведения, описанного там, и расширяет `ADR-016` §5 ровно в той точке, которую та ADR явно оставила этому ADR.

# 2. Контекст и проблема

`06_Networking_and_Session_Sync` §15–18 описывает намерение протокола проекции состояния (ordering, snapshot, delta, reconnect), но остаётся product-документом, не ADR: он не проходит тот же процесс принятия, что и `ADR-001`–`016`, и не является нормативным authority для реализации. `ADR-015` (`ODY-S02-001`) уже зафиксировала транспортный порт (`ISessionTransport`, reliable/realtime каналы), но явно не определяет, что именно передаётся по reliable-каналу для доставки/восстановления состояния — только сам факт, что канал упорядочен и надёжен. `ADR-016` (`ODY-S02-003`) явно зафиксировала только структурный факт транспортного reconnect (allocation переиспользуется через join code) и явно оставила application-level вопрос "что именно переигрывается/восстанавливается" этому ADR (`ADR-016` §5, дословно: *«что именно переигрывается/восстанавливается после reconnect на application-уровне (missed deltas, snapshot fallback) — предмет `ODY-S02-004`, не этого ADR»*).

Без этого ADR `ODY-S02-005`/`006` (identity/permissions) не могут проектироваться против конкретного snapshot/delta payload-контракта, а будущая implementation-задача была бы вынуждена изобретать gap detection и reconnect-семантику по ходу кода — что противоречит установленному в `SLICE-00`/`SLICE-01`/`SLICE-02` процессу (прецедент `ADR-002`–`016`).

**Разграничение терминологии — критично, не факультативно** (раздел 3.1): слово "snapshot" используется в этой кодовой базе на двух разных, не связанных семантически слоях. `ADR-012` §3.4 (`SLICE-01`, persistence-уровень) определяет `Snapshot` как консистентную полную копию `campaign.db`, созданную SQLite Backup API, идентифицируемую `BackupId` — дисковый артефакт для disaster recovery. Этот ADR вводит `ProjectionSnapshot` (network-уровень, `06_Networking` §16.2) — permission-фильтрованный wire-payload, отправляемый конкретному подключению при первом подключении/reconnect/gap-repair, не связанный напрямую с `campaign.db` или `BackupId`. Ни один из этих двух артефактов не порождает и не заменяет другой; смешение терминологии в реализации запрещено этим ADR (раздел 13).

# 3. Термины

## 3.1 `ProjectionSnapshot` (network snapshot) vs. `Snapshot` (persistence snapshot, `ADR-012`)

**`ProjectionSnapshot`** (этот ADR) — permission-фильтрованный wire-артефакт, отправляемый одному подключению по reliable-каналу, содержащий разрешённое этому подключению состояние проекции на определённый момент (`SessionMetadata`, `VisibleEntities`, `PendingInteractions` и т.д. — `06_Networking` §16.1). Не является копией `campaign.db`.

**`Snapshot`** (`ADR-012` §3.4, отдельное, не связанное понятие) — консистентная полная копия `campaign.db`, созданная SQLite Backup API, идентифицируемая `BackupId`. Дисковый persistence-артефакт для disaster recovery/восстановления.

Эти два артефакта **никогда** не путаются в этом ADR или его реализации: `ProjectionSnapshot` не читается из `BackupRecord`, `Snapshot`/`BackupId` не передаётся по сети как проекция состояния клиенту.

## 3.2 `ProjectionDeltaBatch`

Единица инкрементальной доставки изменений проекции по reliable-каналу, покрывающая непрерывный диапазон `SessionSequence` (`06_Networking` §17.1). Не путать с `DomainEvent`/`DomainEventBatch` (`Odyssey.Application.Commands`, `SLICE-01`-эры) — `ProjectionDeltaBatch` уже редактирован под audience конкретного подключения (permission-filtered), `DomainEventBatch` — сырой, ещё не спроецированный поток авторитетных событий на persistence-уровне.

## 3.3 `SessionSequence` / `AggregateRevision`

`SessionSequence` — сквозной, монотонно возрастающий диапазон (`SequenceFrom`...`SequenceTo`), назначаемый host'ом каждому committed batch событий в порядке commit (`06_Networking` §15.1). `AggregateRevision` — ревизия конкретного aggregate (Token, Scene и т.д.), которую команда может указывать как ожидаемую предпосылку (§15.2) — независимое измерение от `SessionSequence`, не заменяет его.

## 3.4 Delta-буфер (host-side)

Ограниченный (bounded) набор недавних `ProjectionDeltaBatch`, удерживаемый host'ом на сессию (не на кампанию, не персистентно), используемый для gap-repair и reconnect-catchup без необходимости пересобирать полный `ProjectionSnapshot`. Вводится этим ADR (раздел 8) — не упомянут явно как named entity в `06_Networking`, но необходим для реализации §18.2's "delta replay, если окно доступно" буквально.

## 3.5 Late join vs. Reconnect

**Late join** — первое подключение участника к уже активной сессии, без какого-либо предшествующего `LastAcknowledgedSequence` этого участника. **Reconnect** — повторное подключение участника, для которого host уже имеет сохранённые `LastAcknowledgedSequence`/`ProjectionRevision` с предыдущего соединения (`06_Networking` §18.1). Late join **всегда** разрешается только через первичный `ProjectionSnapshot` (раздел 7); reconnect может использовать delta-catchup (раздел 8).

# 4. Snapshot identity

`ProjectionSnapshot` идентичность — составная, поле-в-поле по `06_Networking` §16.2, принята без изменений:

```text
ProjectionSnapshot
├── SnapshotId
├── SessionId
├── AudienceUserId
├── BaseSessionSequence
├── ProjectionRevision
├── PermissionRevision
├── PayloadSections
├── PayloadHash
└── CreatedAtHostTime
```

**Обоснование состава, не только копирование**: `BaseSessionSequence`/`ProjectionRevision` дают клиенту позицию в потоке, с которой последующие `ProjectionDeltaBatch` должны продолжаться (`SequenceFrom` следующего батча должен начинаться сразу после `BaseSessionSequence`) — это то, что делает snapshot и последующую delta-цепочку **согласуемыми** без отдельного out-of-band протокола синхронизации. `PayloadHash` даёт integrity-проверку содержимого независимо от позиции. `PermissionRevision` — отдельное измерение от `ProjectionRevision`, поскольку права могут меняться без изменения игрового состояния (и наоборот) — то же "правило независимости версий", что уже применяется в `ADR-007`/`ADR-011` к другим измерениям версии этой кодовой базы, применённое здесь к сетевой проекции.

---

# 5. Delta-батч и операции

Формат — поле-в-поле по `06_Networking` §17.1, принят без изменений:

```text
ProjectionDeltaBatch
├── SessionId
├── AudienceUserId
├── SequenceFrom
├── SequenceTo
├── ProjectionRevisionBefore
├── ProjectionRevisionAfter
├── Operations[]
└── BatchHash
```

Минимальная единица сетевой доставки — весь `ProjectionDeltaBatch`, не отдельная `Operation` внутри него: клиент не может частично применить один батч (согласуется с `06_Networking` §17.4's правилом об отсутствии partial-patch при частичном пересечении диапазона — раздел 6). `Operations[]` — закрытый, но расширяемый список типов (`AddEntity`, `ReplaceEntity`, `PatchFields`, `RemoveFromProjection`, `AddJournalEntry`, `RemoveCapability`, `AddCapability`, `CreatePendingInteraction`, `ResolvePendingInteraction`, `SetSceneActive`, `SetParticipantState` — §17.2), применяемых клиентом строго в порядке появления внутри массива. Максимальная гранулярность батча (сколько операций/байт на один `ProjectionDeltaBatch`) этим ADR не фиксируется как жёсткое число — implementation-параметр, ограниченный практическими соображениями транспортного payload-лимита (`06_Networking` §11.2, "payload size-limited"), не архитектурное решение этого документа.

# 6. Дубликаты и частичное пересечение

По `06_Networking` §17.4, принято без изменений:

- Батч, диапазон которого **полностью** уже покрыт `LastAppliedSequence` клиента — подтверждается (`Acknowledgement`, §15.4) и **молча игнорируется**, не переприменяется.
- Батч с **частичным** пересечением диапазона (например, клиент уже применил до 105, получает батч 101–108) — **не** применяется как patch поверх уже применённой части; выполняется **resync** (клиент запрашивает недостающий/полный диапазон заново — раздел 7).

**Явное разграничение от `ADR-012` §7's `AppliedCommands`** (раздел 1, пункт 3; отвечает на явный вопрос задачи): это дедупликация другого слоя данных, не альтернатива и не замена. `AppliedCommands` — host-side write-path механизм: предотвращает повторное вычисление эффекта команды при повторной сетевой доставке одной и той же команды с тем же `CommandId`, единственный нормативный exactly-once-effect механизм для команд (`ADR-012` §7.2, явно запрещает изобретать альтернативный dedup вместо проверки `AppliedCommands`). Дедупликация этого раздела — client-side read-path механизм: предотвращает повторное применение уже спроецированного, уже вычисленного host'ом `ProjectionDeltaBatch` при повторной сетевой доставке того же диапазона `SessionSequence`. Ключ дедупликации здесь — диапазон `SequenceFrom`/`SequenceTo` относительно `LastAppliedSequence`, **не** `CommandId` — эти два механизма работают на разных данных, в разных направлениях потока, и оба обязательны одновременно, не взаимозаменяемы.

# 7. Gap detection, late join, и snapshot-fallback

**Gap detection** (`06_Networking` §17.3, принято без изменений): если клиент ожидает `SequenceFrom = 101`, а получает батч, начинающийся с `104` — батч **не применяется**; клиент запрашивает gap repair за пропущенный диапазон (`101`–`103`); host отвечает одним из двух путей (раздел 8 определяет, каким именно):

1. недостающими `ProjectionDeltaBatch` из своего delta-буфера, если диапазон в пределах буфера;
2. новым полным `ProjectionSnapshot`, если диапазон вне буфера.

**Late join** (раздел 3.5): участник без `LastAcknowledgedSequence` **всегда** получает только путь "первичный `ProjectionSnapshot`" — никогда delta-replay истории, независимо от того, насколько короткая история существует. Это не отдельная ветка протокола, а прямое следствие отсутствия точки, с которой delta-replay мог бы начаться.

**Snapshot during active session** (`06_Networking` §16.4, принято без изменений): пока клиент получает (возможно chunked, раздел 8) snapshot, host продолжает сессию и сохраняет delta после `BaseSessionSequence` для отправки клиенту сразу после применения snapshot — snapshot-доставка не приостанавливает сессию для остальных участников.

# 8. Delta-буфер и reconnect fallback-правило — решение и обоснование

**Нормативное решение (отвечает на явный вопрос задачи, раздел 1 пункт 6/7)**: host **обязан** вести ограниченный (bounded) буфер недавних `ProjectionDeltaBatch` на сессию, используемый и для gap-repair (раздел 7), и для reconnect delta-catchup (та же структура данных, не два раздельных буфера). Reconnect flow (раздел 9, шаг 6/7) выбирает между двумя путями:

- **delta-catchup**: если запрошенный клиентом диапазон (от его `LastAcknowledgedSequence` до текущего `SessionSequence`) полностью покрыт буфером — host отправляет недостающие `ProjectionDeltaBatch`, клиент применяет их поверх уже имеющейся локальной проекции;
- **полный snapshot fallback**: если диапазон вне буфера (например, долгое отключение, буфер уже вытеснил нужные батчи) — host строит новый переразрешённый `ProjectionSnapshot` (с текущими, не сохранёнными, permissions — раздел 1 пункт 8) и отправляет его вместо delta-catchup.

**Обоснование выбора "buffered catchup + snapshot fallback" вместо "всегда полный snapshot" для MVP-класса**:

1. **Продуктовый документ сам уже фиксирует оба пути как нормативные**, не альтернативные архитектуры на выбор реализации (`06_Networking` §18.2, шаги 6–7: "Delta replay, если окно доступно. Иначе полный разрешённый snapshot.") — этот ADR формализует уже принятое продуктовое намерение, не изобретает его заново.
2. **"Всегда полный snapshot" был бы неоправданно дорог для наиболее частого случая.** Кратковременные разрывы связи (Wi-Fi roam, мобильная сеть, кратковременная потеря пакетов) — ожидаемо частый, не крайний случай при реальных условиях игрока; `SP-03`'s собственная оговорка (`docs/tasks/active/ODY-S02-002_SP-03_Internet_Connectivity_Report.md`, раздел 9 `ADR-016`) явно отмечает, что реальные условия мобильного/домашнего подключения не были эмпирически проверены — то есть частота коротких разрывов у реального игрока неизвестна, но разумно ожидать её ненулевой. Пересборка полного `ProjectionSnapshot` при каждом таком разрыве расходует трафик и host CPU пропорционально размеру всей видимой участнику проекции, а не размеру фактически пропущенных изменений.
3. **Буфер без fallback был бы небезопасен.** Неограниченный или отсутствующий fallback-путь означал бы, что долгое отключение (превышающее буфер) оставляет клиента без пути восстановления — прямо противоречит `06_Networking` §18.2's собственному явному "иначе" пункту.
4. **Точный размер/длительность буфера — implementation-параметр, не архитектурное решение этого ADR.** Ни продуктовый документ, ни `SP-03` не дают эмпирической основы для конкретного числа (в отличие от `ADR-011`, где `SP-02` дал реальные измерения snapshot size/speed). Фиксация конкретного числа сейчас без данных повторила бы ту же ошибку, которую `ADR-015` §12.1 явно избегает для `TransportTimeoutPolicy` (Provisional default, не выдуманное точное число). **Стартовый ориентир, явно помеченный не финальным**: буфер должен покрывать как минимум типичный transport-уровневый reconnect timeout (`ADR-016` §5's allocation lifetime, само по себе ещё не измеренное эмпирически) плюс разумный запас — implementation-задача обязана выбрать и обосновать конкретное число (по количеству батчей или по времени, что практичнее реализовать) при написании кода, не эта ADR.

# 9. Reconnect flow (10 шагов)

Принято без изменений из `06_Networking` §18.2:

```text
1. Authentication.
2. Проверка SessionId и membership.
3. Замена старого соединения того же аккаунта.
4. Передача LastAcknowledgedSequence.
5. Пересчёт текущих permissions.
6. Delta replay, если окно доступно (раздел 8: буфер покрывает диапазон).
7. Иначе полный разрешённый snapshot (раздел 8: буфер не покрывает диапазон).
8. Asset manifest diff.
9. Scene load.
10. Ready.
```

Шаг 3 ("замена старого соединения того же аккаунта") — транспортно-независимое application-правило: при reconnect с тем же `UserId` предыдущее (возможно ещё формально не разорванное со стороны host) соединение того же аккаунта закрывается host'ом, не остаётся параллельно активным — предотвращает состояние с двумя одновременно "живыми" представлениями одного участника.

Шаг 5 реализует раздел 1 пункт 8 (redaction всегда по текущим permissions, не сохранённым).

---

# 10. `PendingInteraction` reconnect

Принято без изменений из `06_Networking` §18.4: активные `PendingInteraction` — часть payload `ProjectionSnapshot`/`ProjectionDeltaBatch` (уже перечислены в составе snapshot §16.1 и как тип операции `CreatePendingInteraction`/`ResolvePendingInteraction` в §17.2) — отдельного протокола для них не вводится; клиентский интерфейс восстанавливает их в правильном порядке из уже полученного snapshot/delta потока после reconnect.

# 11. Соответствие module boundaries (`ADR-001`) и уже принятым `ADR-015`/`ADR-016`

Этот ADR не вводит новый код и не переопределяет `ADR-001` §6.6 (Networking module boundary), `ADR-015`'s `ISessionTransport`-сигнатуру, или `ADR-016`'s выбор провайдера. Будущая implementation-задача, реализующая этот протокол:

- передаёт `ProjectionSnapshot`/`ProjectionDeltaBatch` как payload внутри уже принятого `NetworkEnvelope` (reliable-канал, `ADR-015` §5.1/§6.1) — не вводит третий канал;
- не даёт `Odyssey.Networking` права читать `campaign.db` напрямую для построения snapshot — построение проекции остаётся ответственностью Application-слоя (сборка `ProjectionSnapshot`/`ProjectionDeltaBatch` из уже спроецированного/redacted состояния), Networking только транспортирует уже готовый payload (`ADR-001` §6.6, `ADR-015` §10);
- не принимает host-authoritative решения о видимости в `Odyssey.Networking` — редакция по permissions (раздел 1 пункт 8) вычисляется до передачи в транспортный слой.

# 12. Не входит в ADR-017

Явно исключено из объёма этого ADR (владеют другие задачи backlog `SLICE-02`, см. `docs/tasks/SLICE-02_BACKLOG.md` §4):

- **Visibility/redaction-правила** — кто конкретно видит какую сущность/поле в `ProjectionSnapshot`/`ProjectionDeltaBatch` (роли Main GM/Player/Observer, permission capabilities, revoked-permission removal) — `ODY-S02-006` (Permissions Baseline). Этот ADR определяет **механику** доставки и восстановления проекции, не то, **кто что получает** внутри неё.
- **Identity baseline** (`UserId`, dev identity, JWT-boundary) — `ODY-S02-005`, не затронуто здесь за пределами упоминания `AudienceUserId`/`UserId` как уже существующих полей других контрактов.
- **Production-реализация этого протокола поверх `ISessionTransport`** (сериализация payload, конкретный код построения `ProjectionSnapshot` из проекции, реальный буфер с конкретным размером) — future implementation task.
- **Интеграция реального Unity Relay SDK** — отдельная future задача, заблокированная `ADR-016` §14's эмпирическим гейтом; этот ADR не зависит от завершения того гейта, поскольку определяет application-level протокол, независимый от конкретного transport-провайдера (тот же принцип "abstraction, не привязка к конкретному SDK", что уже `ADR-015` §4.3 устанавливает).
- **Конкретный численный размер/длительность delta-буфера** — implementation-параметр (раздел 8, пункт 4), не фиксируется здесь как финальное число.
- **Asset manifest diff-протокол** (шаг 8 раздела 9) — упомянут как часть flow, но его собственный контракт (что именно сравнивается, формат diff) — предмет асинхронной/отдельной от этого ADR детализации, не разворачивается здесь подробно, поскольку `06_Networking` не даёт для него отдельного нормативного раздела за пределами упоминания в §18.2.

# 13. Правила для Codex

Codex обязан:

1. Не путать `ProjectionSnapshot` (network, этот ADR) со `Snapshot`/`BackupId` (persistence, `ADR-012` §3.4) — разные артефакты, разные слои, никогда не взаимоподменяемы в коде или комментариях (раздел 3.1).
2. Использовать диапазон `SequenceFrom`/`SequenceTo` (не `CommandId`) как ключ дедупликации `ProjectionDeltaBatch` на клиентской стороне — не путать с `AppliedCommands`'s `CommandId`-дедупликацией на host-стороне (раздел 6); не изобретать третий, альтернативный dedup-механизм для любого из двух слоёв.
3. Не разрешать late join через delta-replay истории — только через первичный `ProjectionSnapshot` (раздел 7, раздел 3.5).
4. Реализовывать buffered delta-catchup **и** полный snapshot fallback оба, не выбирать только один путь как "достаточный" для MVP (раздел 8).
5. Не фиксировать в коде visibility/redaction-логику под этим ADR — она принадлежит `ODY-S02-006`; этот ADR определяет только механику доставки, полагая payload уже отредактированным по permissions до передачи в транспортный слой.
6. Не давать `Odyssey.Networking` прямого доступа к `campaign.db` при реализации построения snapshot — построение проекции остаётся Application-слоем (раздел 11).
7. Не применять частичное пересечение диапазона delta как patch — только resync (раздел 6).
8. Указывать в PR summary implementation-задачи, реализующей этот протокол, выбранный размер/длительность delta-буфера и его обоснование, поскольку это число не фиксируется этим ADR (раздел 8, пункт 4).

# 14. Definition of Done для будущей implementation-задачи

Implementation-задача, реализующая этот протокол поверх `ISessionTransport`, обязана — до открытия своего Draft PR с production-кодом — доказать (тестами, не только прозой):

1. `ProjectionSnapshot`'s четыре измерения идентичности (`SnapshotId`, `BaseSessionSequence`/`ProjectionRevision`/`PermissionRevision`, `PayloadHash`) все присутствуют и проверяются на приёме.
2. Late join всегда получает snapshot, никогда delta-replay (тест: подключение без предшествующего `LastAcknowledgedSequence`).
3. Gap detection корректно определяет разрыв и запрашивает repair (тест: искусственно пропущенный диапазон).
4. Полностью дублирующийся батч подтверждается и игнорируется; частично пересекающийся батч не применяется как patch, вызывает resync (тест на оба случая, раздел 6).
5. Reconnect delta-catchup работает, когда диапазон в буфере; snapshot fallback работает, когда диапазон вне буфера (тест на оба пути, раздел 8).
6. Redaction при reconnect вычисляется по текущим, не сохранённым permissions (тест: право отозвано во время отключения — соответствующие delta не доставляются после reconnect).
7. Ни один тест этого протокола не полагается на visibility/redaction-логику, которая ещё не существует в репозитории на момент этой задачи (она принадлежит `ODY-S02-006`) — payload-фикстуры тестов используют заглушечные/уже-отредактированные данные, не реальную permission-систему, если та ещё не реализована.

# 15. Рассмотренные альтернативы

## 15.1 Единственный монотонный номер как snapshot identity, без хэша

Отклонено: не даёт integrity-проверки содержимого независимо от позиции; продуктовый документ (`06_Networking` §16.2) сам явно требует оба поля одновременно.

## 15.2 Дедупликация delta по тому же `CommandId`, что и `AppliedCommands`

Отклонено: смешивает два разных слоя данных (host-side команда-эффект дедупликация против client-side доставка-проекции дедупликация); `ProjectionDeltaBatch` не имеет прямого 1:1 отношения к одной команде (один батч может агрегировать эффекты нескольких команд, одна команда может породить эффекты в нескольких батчах при разной audience) — `CommandId` структурно не подходит как ключ на этом слое.

## 15.3 "Всегда полный snapshot" при любом reconnect, без delta-буфера

Отклонено (раздел 8): противоречит `06_Networking` §18.2's собственному явному "delta replay, если окно доступно" пункту; неоправданно дорого для частого случая кратковременных разрывов, ожидаемых при реальных сетевых условиях, которые `SP-03` явно не смогла эмпирически проверить (см. `ADR-016` §9's соответствующий операционный риск).

## 15.4 Неограниченный (unbounded) delta-буфер вместо bounded

Отклонено: неограниченная память на сессию — риск ресурсного исчерпания host'а при длинных сессиях с большим числом изменений; продуктовый документ не требует восстановления после сколь угодно долгого отключения через delta — полный snapshot как fallback для этого случая уже покрывает этот сценарий корректно и достаточно.

## 15.5 Фиксировать конкретный численный размер delta-буфера сейчас

Отклонено на этом этапе: ни продуктовый документ, ни `SP-03` не дают эмпирической основы для конкретного числа (в отличие от прецедента `ADR-011`/`SP-02`) — фиксация выдуманного числа без данных повторила бы ту же ошибку, которую этот ADR явно избегает для других значений (раздел 8, пункт 4). Оставлено implementation-задаче с явным минимальным требованием (покрывать типичный transport-reconnect timeout).

# 17. Нормативное действие

Принято как ADR этой задачи (`ODY-S02-004`) без ожидания отдельного эмпирического спайка — обоснование: этот ADR формализует протокол, уже подробно и нормативно описанный продуктовым документом (`06_Networking...` §15–18, разделы помечены `[CONFIRMED]` в исходном документе), не открывает новый архитектурный вопрос, требующий измерения (в отличие от `ODY-S02-002`/`003`'s relay-провайдера). Единственные решения этого ADR, выходящие за буквальный текст продуктового документа — обязательность bounded delta-буфера как механизма (раздел 8) и явное терминологическое разграничение (раздел 3.1) — оба являются прямыми, обоснованными следствиями уже принятого продуктового намерения (§18.2's собственный "delta replay, если окно доступно" пункт), не новыми архитектурными изобретениями, требующими отдельной эмпирической проверки.

С даты принятия (`Accepted`):

- ни одна implementation-задача `SLICE-02`/будущих слайсов не создаёт альтернативный snapshot/delta/reconnect протокол в противоречии с разделами 4–10;
- `ODY-S02-005`/`006` авторизованы опираться на этот ADR как на принятую основу для identity/permissions-полей, уже упомянутых здесь (`AudienceUserId`, `PermissionRevision`), и не обязаны повторно решать вопросы разделов 4–10;
- visibility/redaction-механика (раздел 12) остаётся полностью открытой до `ODY-S02-006` — принятие этого ADR не считается её молчаливым решением;
- конкретный численный размер delta-буфера остаётся implementation-параметром (раздел 8 пункт 4, раздел 15.5) до эмпирически обоснованного выбора будущей implementation-задачей;
- изменение принятого протокола требует amendment этого ADR или нового superseding ADR, не молчаливого отклонения в реализации.
