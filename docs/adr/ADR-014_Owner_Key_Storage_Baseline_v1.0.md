# ADR-014 — Owner Key Storage Baseline

**Документ:** `docs/adr/ADR-014_Owner_Key_Storage_Baseline_v1.0.md`  
**ADR:** ADR-014  
**Версия:** 1.0  
**Дата:** 20 августа 2026 года  
**Статус:** Accepted  
**Область:** конкретный OS-механизм локального хранения owner key material на Windows (Windows Credential Manager, DPAPI CurrentUser scope), формат и область хранимой сущности, ротация, поведение при потере/недоступности ключа, решение открытого вопроса `ADR-012` §12.1 (backup encryption at rest), поведение при переустановке приложения/смене машины/экспорте кампании с точки зрения persistence-слоя  
**Связанные этапы:** Roadmap Этап 2 (`SLICE-01`), Milestone `M2`, backlog `ODY-S01-004`  
**Базовые документы:** `Documentation/21_Security_And_Privacy_Odyssey_VTT_v0.1.md` §5–6, `05_Persistence_Odyssey_VTT_v0.8.md` (`PE-INV-010`, §30–31), `ADR-011_Local_Campaign_Format_v1.0.md` §1 п.13, `ADR-012_Snapshot_And_Append_Only_Journal_v1.0.md` §12.1, `ADR-009_Unity_Project_and_Build_Baseline_v1.1.md` (Windows Standalone x86-64 baseline), `docs/tasks/SLICE-01_BACKLOG.md`

---

# 1. Решение

Odyssey VTT хранит owner key material локально через **Windows Credential Manager** (generic credential, `CRED_TYPE_GENERIC`), доступный через win32 API (`CredWrite`/`CredRead`/`CredDelete`, `advapi32.dll`), в области видимости **текущего пользователя Windows** (`CurrentUser`). Это конкретизирует принцип, уже зафиксированный в `Documentation/21_Security_And_Privacy_Odyssey_VTT_v0.1.md` §5 и `05_Persistence` `PE-INV-010`: owner key никогда не входит в файл кампании.

Обязательные решения:

1. Конкретный механизм хранения — Windows Credential Manager, generic credential type, доступ через win32 `Cred*` API. Не DPAPI напрямую как самостоятельный механизм (см. раздел 4 для обоснования выбора и разницы).
2. Область видимости — `CurrentUser`: секрет привязан к Windows-профилю конкретного пользователя, не доступен другим локальным пользователям той же машины (раздел 4.2).
3. Формат хранимой сущности: непрозрачный (opaque) секретный блок байт (owner key material), адресуемый по `TargetName`, построенному из non-secret локального per-campaign reference identifier (раздел 5).
4. Ротация owner key material в MVP не реализуется автоматически; доступна только явная пользовательская операция "перевыпустить owner key" (regenerate), не периодическая или scheduled ротация (раздел 6).
5. Потеря/недоступность owner key material в MVP — невосстановима на уровне persistence-слоя; кампания и её данные (`campaign.db`, journal) не теряются, теряется только локальный секрет, удостоверяющий владение (раздел 7).
6. Backup encryption at rest (`ADR-012` §12.1) — этим ADR закрывается: backup/snapshot **не шифруется** в MVP, тем же обоснованием, что и отказ от шифрования всей кампании (`21_Security_And_Privacy` §4.1 / `05_Persistence` §30.1). Owner key storage — самостоятельный, отдельный от шифрования контейнера кампании механизм (раздел 8).
7. Этот ADR не расширяет и не сужает границу модели угроз, зафиксированную `21_Security_And_Privacy` §6 (раздел 9).
8. Поведение persistence-слоя при переустановке приложения, смене машины и экспорте кампании описано в разделе 10; UX/networking-уровневое поведение (что видит и что может сделать пользователь при отсутствии owner key на новой машине) явно оставлено `[OPEN]`, не изобретается здесь (раздел 11.3).

Этот ADR является нормативным authority по механизму хранения owner key material. Он реализует принцип `21_Security_And_Privacy_Odyssey_VTT_v0.1.md` §5 без изменения этого принципа.

# 2. Контекст и проблема

`21_Security_And_Privacy_Odyssey_VTT_v0.1.md` §5 фиксирует принцип (owner key хранится через OS secure storage, не в файле кампании), но явно откладывает конкретный механизм на отдельную ADR: *"Конкретный механизм хранения (какой именно OS API, формат, ротация, восстановление при потере) — предмет отдельной ADR owner key storage baseline."* Без этой ADR:

1. Implementation-задачи могли бы выбрать произвольный, несогласованный между собой механизм хранения (например, один разработчик — DPAPI напрямую в `AppData`, другой — Credential Manager), что сделало бы поведение непредсказуемым между установками.
2. Оставался бы нерешённым открытый вопрос `ADR-012` §12.1 (backup encryption at rest), явно привязанный к принятию этой ADR.
3. Не было бы явного, проверяемого решения о том, что происходит при потере ключа — риск, что реализация либо тихо теряет доступ без объяснения пользователю, либо изобретает небезопасный fallback (например, хранение резервной копии ключа в файле кампании, что напрямую нарушило бы `PE-INV-010`).

# 3. Термины

## 3.1 Owner key

Локальный секретный материал, удостоверяющий полномочия владельца/GM Host в отношении конкретной кампании на конкретной машине под конкретной Windows-учётной записью. Точное криптографическое использование (подпись команд, доказательство авторитета, будущая networking-аутентификация) определяется отдельными ADR Этапа 3 (networking/account) и не решается здесь — этот ADR решает только физическое хранение материала.

## 3.2 Windows Credential Manager

Встроенный компонент Windows, предоставляющий per-user хранилище именованных секретов (credentials), защищённых Windows внутренне через DPAPI, доступный приложениям через `Advapi32.dll` API (`CredWrite`, `CredRead`, `CredDelete`, `CredEnumerate`).

## 3.3 `CurrentUser` scope

Область видимости секрета, ограниченная текущим Windows-профилем пользователя: секрет недоступен для чтения другими локальными учётными записями той же машины и не переносится автоматически между машинами.

---

# 4. Выбор конкретного OS-механизма

## 4.1 Решение: Windows Credential Manager (не "голый" DPAPI)

Owner key material хранится как generic credential Windows Credential Manager (`CRED_TYPE_GENERIC`), а не как самостоятельный DPAPI-зашифрованный blob-файл, управляемый приложением напрямую (например, в `AppData`).

Обоснование:

- Windows Credential Manager внутренне использует DPAPI для защиты хранимых секретов — выбор Credential Manager не отказывается от DPAPI, а использует его через готовый, управляемый ОС слой хранения, а не через самостоятельно реализуемый файл.
- Хранение в виде файла, управляемого приложением (даже DPAPI-зашифрованного), создаёт риск, что этот файл будет случайно удалён при очистке `AppData`, антивирусным ПО, ошибкой в коде деинсталлятора или ручной очисткой пользователем — Credential Manager как отдельное системное хранилище не входит в типичные "очистки временных файлов" и переживает переустановку приложения (раздел 10.1).
- Credential Manager не требует от приложения реализовывать собственное шифрование/дешифрование или управление IV/ключами — вся криптографическая работа выполняется ОС; это снижает поверхность для ошибок реализации.
- Не требует новой сторонней зависимости или NuGet-пакета — доступ через P/Invoke к `Advapi32.dll`, уже являющемуся частью Windows, консистентно с Windows Standalone x86-64 MVP baseline (`ADR-009`).

## 4.2 Область видимости: `CurrentUser`

Owner key material сохраняется в области видимости текущего Windows-пользователя (не `LocalMachine`). Это означает: секрет недоступен для чтения другим локальным Windows-учётным записям на той же машине, даже если они запускают то же приложение.

Обоснование: `21_Security_And_Privacy` §6 уже фиксирует, что MVP защищает данные *между пользователями*, но не от локального владельца файла или вредоносного кода, выполняющегося от его имени. `CurrentUser` scope — прямое техническое воплощение этой границы: защита от других локальных пользователей машины, не от компрометации самой учётной записи, под которой работает владелец кампании. `LocalMachine` scope был бы слабее этой уже принятой границы (позволил бы читать секрет любому локальному пользователю машины) и потому отклонён.

# 5. Формат хранимой сущности

Хранимая Credential Manager запись имеет:

- `TargetName` — строка, однозначно идентифицирующая кампанию локально (например, префикс `Odyssey.OwnerKey.` + non-secret локальный per-campaign reference identifier). Сам `TargetName` не является секретом и может быть построен из уже существующего идентификатора кампании или локально сгенерированного opaque identifier — точный источник этого identifier является implementation-деталью, не решаемой на уровне ADR (см. раздел 12.3, открытый вопрос).
- `CredentialBlob` — непрозрачный секретный материал (owner key), которым распоряжается только application-код после чтения через `CredRead`; ADR не специфицирует внутреннюю структуру этого материала (ключ, seed, или производный секрет), поскольку это зависит от криптографического назначения, определяемого будущими Networking/Account ADR.
- `Persist` — `CRED_PERSIST_LOCAL_MACHINE` не используется (это ослабило бы `CurrentUser`-границу раздела 4.2); используется `CRED_PERSIST_ENTERPRISE` или `CRED_PERSIST_LOCAL_MACHINE`-эквивалент, ограниченный текущим пользователем — точный persist-флаг является implementation-деталью в рамках уже зафиксированной `CurrentUser`-границы, не отдельным нормативным решением этого ADR.

Owner key material никогда не сериализуется в `manifest.json`, `campaign.db`, `.odcamp` или любой backup/snapshot — эта граница уже зафиксирована `PE-INV-010` и `ADR-011` §1 п.13 и не переопределяется здесь, только используется как предпосылка.

---

# 6. Ротация

Автоматическая (периодическая, scheduled, или triggered событием) ротация owner key material **не реализуется в MVP**.

Обоснование: без определённого криптографического протокола использования owner key (эта деталь принадлежит будущим Networking/Account ADR Этапа 3), нормативная ротация была бы преждевременной — неизвестно, какие последствия имеет смена ключа для уже установленных доверительных отношений (если таковые появятся в будущем networking-контексте). Фиксировать политику ротации сейчас означало бы либо предвосхищать networking-дизайн, либо вводить ротацию, которая окажется бессмысленной или конфликтующей с ним.

MVP предоставляет только явную пользовательскую операцию "перевыпустить owner key" (regenerate): пользователь может по явному запросу сгенерировать новый owner key material для конкретной кампании, заменяющий предыдущий в Credential Manager. Это не автоматическая ротация, а редкая, explicit, пользователем инициированная операция (аналогично компрометации/предполагаемой утечке). Последствия regenerate для любых будущих networking-доверительных отношений — вне области этого ADR.

# 7. Поведение при потере/недоступности ключа

Если owner key material для кампании отсутствует в Credential Manager при попытке чтения (запись удалена, повреждена, недоступна из-за смены Windows-профиля — раздел 10), это **невосстановимо на уровне persistence-слоя** в MVP:

- Не существует backup, экспорта или resend-механизма owner key material — по определению `PE-INV-010`/§5, оно никогда не покидает защищённое хранилище ОС в открытом или резервируемом виде.
- Потеря owner key material **не означает** потерю самой кампании: `campaign.db`, journal (`ADR-012`), и все игровые данные остаются полностью доступными и целостными — теряется только локальный секрет, удостоверяющий владение/авторитет.
- Persistence-слой обязан явно и безопасно сообщать о недоступности owner key material (используя safe error, `ADR-004`), не тихо продолжать работу так, будто ключ присутствует, и не подставлять пустой/нулевой ключ как эквивалент отсутствующего.

Точное прикладное (UX/application-level) поведение в момент, когда owner key отсутствует — что именно может или не может делать пользователь дальше — зависит от того, как owner key используется в остальной системе (аутентификация GM Host для networking, разрешение GM Override и т.д.), что определяется будущими ADR Этапа 3. Это поведение явно оставлено `[OPEN]` (раздел 11.3), не изобретается здесь.

# 8. Решение `ADR-012` §12.1 — Backup encryption at rest

`ADR-012` §12.1 оставляет открытым вопрос: должен ли backup/snapshot кампании быть зашифрован тем же механизмом, что защищает owner key, и явно откладывает ответ до принятия этой ADR.

**Решение этого ADR: backup/snapshot campaign.db не шифруется в MVP.**

Обоснование:

- `21_Security_And_Privacy` §4.1 и `05_Persistence` §30.1 уже явно и независимо от owner key storage фиксируют: MVP не шифрует кампанию целиком встроенным паролем; защита обеспечивается правами доступа ОС и файловыми permissions, не контейнерным шифрованием.
- Owner key material, хранимое этим ADR, — небольшой непрозрачный секрет (раздел 5), не ключ шифрования многомегабайтного `campaign.db`. Использование owner key material как ключа шифрования backup потребовало бы полностью отдельного дизайна (derivation, IV management, шифрование/дешифрование потоком при snapshot/restore), прямо противоречащего уже принятому решению §30.1 не шифровать кампанию контейнерно.
- Owner key storage (эта ADR) и backup encryption at rest (`ADR-012` §12.1) — логически независимые вопросы: первый защищает удостоверение владения, второй защищал бы содержимое файла на диске. Между ними нет технической зависимости, требующей общего решения.

Таким образом, вопрос `ADR-012` §12.1 закрывается явным "нет" для MVP, а не остаётся открытым дальше. `ADR-012` §12.1 будет считаться удовлетворённым этим разделом с момента принятия этого ADR.

# 9. Граница модели угроз — не расширяется и не сужается

`21_Security_And_Privacy_Odyssey_VTT_v0.1.md` §6 фиксирует, что MVP explicitly не защищает от:

- вредоносного ПО, выполняющегося с правами пользователя;
- физического доступа к незашифрованному диску;
- компрометации самой ОС или её защищённого хранилища secrets;
- действий локального владельца файла кампании в отношении собственных GM-only данных.

Этот ADR **не меняет** эту границу. Выбор Windows Credential Manager (раздел 4) — это выбор конкретного OS-механизма в рамках уже принятой границы ответственности ("ОС/диск — ответственность пользователя и его ОС"), а не попытка расширить защиту за пределы того, что гарантирует сама ОС. В частности:

- Credential Manager не защищает от вредоносного ПО, выполняющегося от имени того же Windows-пользователя (оно технически способно вызвать `CredRead` так же, как и приложение) — это согласуется с уже принятым §6, не является новым или неожиданным ослаблением.
- Компрометация самой Windows-учётной записи (кража пароля пользователя, скомпрометированный профиль) компрометирует и owner key material — это прямое, ожидаемое следствие уже принятой границы §6, не новый риск, вводимый этим ADR.

Если бы содержание этого ADR потребовало изменить (расширить или сузить) §6, это было бы зафиксировано как явный конфликт и вынесено на решение владельца продукта, а не решено тихо. Такого конфликта не обнаружено: выбранный механизм полностью укладывается в уже принятую границу.

# 10. Переустановка приложения, смена машины, экспорт кампании — поведение persistence-слоя

## 10.1 Переустановка приложения (та же машина, тот же Windows-пользователь)

Owner key material, сохранённое в Windows Credential Manager, **не привязано к файлам приложения** и не удаляется автоматически при удалении/переустановке приложения (Credential Manager — системное хранилище, независимое от `AppData` приложения или его установочной папки). При переустановке на той же машине под той же Windows-учётной записью owner key material остаётся доступным без дополнительных действий пользователя.

Явное исключение: если пользователь вручную очистит соответствующую запись через Windows Credential Manager UI/CLI (`cmdkey`, "Диспетчер учётных данных"), это эквивалентно разделу 7 (потеря ключа) — вне контроля приложения.

## 10.2 Смена машины / переустановка Windows-профиля

Owner key material, защищённое через `CurrentUser`-scoped Credential Manager запись, **не переносится** при смене машины и не восстанавливается при полном сбросе/переустановке Windows-профиля пользователя (Credential Manager внутренне полагается на DPAPI, чей master key криптографически связан с конкретным Windows-профилем пользователя на конкретной машине). Это ожидаемое, не аномальное поведение — прямое следствие раздела 4.2 (`CurrentUser` scope) и уже принятого принципа `PE-INV-010`/§5 (owner key не мигрирует вместе с кампанией).

## 10.3 Экспорт кампании на другую машину (`.odcamp`)

При экспорте кампании в `.odcamp` (`ADR-011`) owner key material **не включается** в архив ни при каких обстоятельствах — это прямое следствие `PE-INV-010` и раздела 5 этого ADR (owner key никогда не сериализуется в файлы кампании). При открытии `.odcamp` на другой машине или под другим Windows-профилем локальное owner key material для этой кампании отсутствует по определению — это тот же случай, что раздел 7 (потеря/недоступность ключа), не отдельный сценарий.

Что именно должно происходить на уровне приложения в этот момент (кампания открывается в ограниченном режиме? требуется повторное подтверждение владения? предлагается claim ownership как новому владельцу?) явно оставлено `[OPEN]` — см. раздел 11.3. Persistence-слой лишь гарантирует: отсутствие owner key material корректно и безопасно обнаруживается и сообщается (раздел 7), не приводит к скрытому неопределённому поведению.

# 11. Не входит в ADR-014

- **Формат кампании / `.odcamp`** — определён `ADR-011`, не переопределяется здесь; этот ADR только подтверждает, что owner key material не входит в эти файлы.
- **Snapshot/journal contract** — определён `ADR-012`; этот ADR решает только связанный с ним открытый вопрос §12.1 (раздел 8), не переопределяет остальной snapshot contract.
- **Migration runner** — определён `ADR-013`; не затрагивается этим ADR.
- **Точное криптографическое назначение и использование owner key material** (подпись команд, доказательство авторитета GM Host, участие в будущей networking-аутентификации) — принадлежит будущим ADR Этапа 3 (networking/account); этот ADR решает только физическое локальное хранение материала, не его использование.
- **11.3 UX/application-level поведение при отсутствии owner key на новой машине или после потери** — `[OPEN]`, явно не решается здесь (разделы 7, 10.3). Это требует решения о том, как "владение кампанией" проверяется и используется приложением — вопрос, выходящий за пределы persistence и упирающийся в ещё не определённый Networking/Account дизайн.
- **Кроссплатформенное хранение** (macOS Keychain, Linux Secret Service и т.п.) — не решается. MVP production-платформа — Windows Standalone x86-64 (`ADR-009`); блокировать этот ADR ради гипотетической будущей кроссплатформенности было бы преждевременной абстракцией без реального второго целевого API для сравнения. Если приложение когда-либо получит официальную non-Windows цель, потребуется отдельный ADR (amendment или новый), вводящий platform-abstraction слой поверх принципа §5 — это explicit решение не проектировать такую абстракцию заранее.

# 12. Открытые вопросы

## 12.1 SQLite provider-библиотека — `[OPEN]`, унаследовано

Не относится к этому ADR напрямую (owner key material не хранится в SQLite), но упоминается для полноты: статус остаётся `[OPEN]`, унаследован из `ADR-011`/`ADR-012`/`ADR-013`, не изменяется здесь.

## 12.2 UX/application-level поведение при отсутствии owner key — `[OPEN]`, новое

См. раздел 11.3. Требует решения на уровне будущего Networking/Account ADR: что видит и что может сделать пользователь, когда локальное owner key material отсутствует для открываемой кампании.

## 12.3 Источник non-secret `TargetName` reference identifier — `[OPEN]`, новое

Раздел 5 требует non-secret локальный идентификатор кампании для построения `TargetName` Credential Manager записи. Источник этого идентификатора (например, `CampaignPublicId` из `ADR-011` §12.2, который сам является `[OPEN]`, или отдельный локально генерируемый identifier) не решается здесь — implementation-деталь, зависящая в том числе от разрешения `ADR-011` §12.2.

# 13. Правила для Codex

Codex обязан:

1. Хранить owner key material исключительно через Windows Credential Manager (`CRED_TYPE_GENERIC`, `CurrentUser`-эквивалентная область видимости), не через самостоятельно реализуемый DPAPI-файл в `AppData` и не в виде обычного файла рядом с кампанией.
2. Никогда не сериализовывать owner key material в `manifest.json`, `campaign.db`, `.odcamp`, backup/snapshot, diagnostic bundle или лог любого рода.
3. Не реализовывать автоматическую/периодическую ротацию owner key material в MVP; предоставлять только явную пользовательскую операцию regenerate.
4. При отсутствии owner key material сообщать через safe error (`ADR-004`), не тихо продолжать работу и не подставлять пустой/нулевой ключ.
5. Не реализовывать шифрование backup/snapshot campaign.db под предлогом owner key storage — раздел 8 явно закрывает этот вопрос отрицательно для MVP.
6. Не изобретать UX/application-level поведение при отсутствии owner key на новой машине без отдельного явного решения — раздел 11.3/12.2 остаётся `[OPEN]`.
7. Не реализовывать кроссплатформенное хранение (Keychain, Secret Service) без отдельного ADR — раздел 11 явно ограничивает MVP Windows Credential Manager.

# 14. Definition of Done / критерии приёмки ADR-014 implementation

ADR считается реализованным (для той части, которую он определяет), когда:

1. Owner key material читается/записывается исключительно через Windows Credential Manager API (`CredWrite`/`CredRead`/`CredDelete`), в `CurrentUser`-эквивалентной области видимости; тест/ревью подтверждает отсутствие альтернативных путей хранения (файл в `AppData`, запись в `campaign.db` и т.п.).
2. `manifest.json`, `campaign.db`, `.odcamp`, любой backup/snapshot и любой diagnostic bundle не содержат owner key material ни в каком виде; покрыто тестом, аналогичным существующим redaction-тестам `ADR-010`.
3. Отсутствие owner key material при попытке чтения приводит к safe error (`ADR-004`), не к необработанному исключению или скрытому продолжению с пустым ключом.
4. Backup/snapshot `campaign.db` не проходит через шифрование при создании (соответствует разделу 8 этого ADR и уже принятому `ADR-012` §8.4 flow).
5. Переустановка приложения на той же машине/пользователе не требует повторного создания owner key material (раздел 10.1), если запись в Credential Manager не была удалена независимо от приложения.

# 15. Рассмотренные альтернативы

## 15.1 "Голый" DPAPI-файл в `AppData`, управляемый приложением напрямую

Отклонено: требует от приложения самостоятельно управлять расположением, именованием и жизненным циклом файла; риск случайного удаления при очистке `AppData` или деинсталляции; не даёт выигрыша перед Credential Manager, который решает ту же задачу как готовый системный сервис (раздел 4.1).

## 15.2 `LocalMachine` DPAPI/Credential scope вместо `CurrentUser`

Отклонено: ослабляет уже принятую в `21_Security_And_Privacy` §6 границу "защита между пользователями машины" — `LocalMachine` scope сделал бы owner key material читаемым любым локальным пользователем той же машины, что прямо противоречит цели защиты владения конкретного GM Host (раздел 4.2).

## 15.3 Хранение owner key в зашифрованном виде внутри `campaign.db` с отдельным паролем

Отклонено: прямо нарушает `PE-INV-010` ("секреты не входят в кампанию") и принцип `21_Security_And_Privacy` §5; также потребовало бы вводить пользовательский пароль кампании, что противоречит уже принятому §30.1 (MVP не шифрует кампанию встроенным паролем).

## 15.4 Периодическая автоматическая ротация owner key в MVP

Отклонено: без определённого протокола использования ключа (Этап 3, networking) ротация была бы преждевременной и рисковала бы конфликтовать с ещё не спроектированной моделью доверия (раздел 6).

## 15.5 Шифрование backup/snapshot тем же owner key material

Отклонено: технически несовместимо с решением §30.1 не шифровать кампанию контейнерно; owner key material — небольшой непрозрачный секрет, не предназначенный как ключ шифрования многомегабайтной базы данных (раздел 8).

## 15.6 Проектирование кроссплатформенного абстрактного secure-storage слоя уже сейчас

Отклонено как преждевременная абстракция: у MVP есть только одна production-платформа (Windows Standalone x86-64, `ADR-009`); абстракция без второй реальной реализации для сравнения добавила бы сложность без проверяемой пользы, и могла бы неверно предугадать API будущей платформы (раздел 11).
