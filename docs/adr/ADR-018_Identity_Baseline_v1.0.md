# ADR-018 — Identity Baseline

**Документ:** `docs/adr/ADR-018_Identity_Baseline_v1.0.md`
**ADR:** ADR-018
**Версия:** 1.0
**Дата:** 25 августа 2026 года
**Статус:** Accepted — **в границах, доступных без `18_Account_And_Identity.md`** (см. раздел 2, раздел 12)
**Область:** стабильный, provider-независимый `UserId`, dev/mock identity для локальных и автоматических тестов, граница mock-vs-real Supabase Auth интеграции на этапе `SLICE-02`, правило "JWT никогда не становится частью campaign state", проверяемое правило "service-role key никогда не достигает клиента"
**Связанные этапы:** Roadmap Этап 3 (`SLICE-02`), Milestone `M3`, backlog `ODY-S02-005`
**Базовые документы:** `06_Networking_and_Session_Sync_Odyssey_VTT_v0.8.md` §6 (identity/session directory поля), `21_Security_And_Privacy_Odyssey_VTT_v0.1.md` (данные-классификация, PE-INV-010 паттерн, §7.1 явный stub), `docs/adr/ADR-010_Logging_Diagnostics_and_Redaction_v1.1.md` §10 (data classification), `docs/adr/ADR-011_Local_Campaign_Format_v1.1.md` §9.1 (domain identifier принцип), `docs/adr/ADR-014_Owner_Key_Storage_Baseline_v1.0.md` (структурный/рискологический образец для чувствительных identity-артефактов), `docs/adr/ADR-017_Snapshot_Delta_Reconnect_Model_v1.0.md` §3.3/§4 (`AudienceUserId`, `UserId` — уже принятая основа, не переопределяется), `docs/tasks/SLICE-02_BACKLOG.md`

---

# 1. Решение

Odyssey VTT фиксирует стабильный, provider-независимый `UserId` как единственную нормативную идентичность участника на уровне domain/network слоёв, mock-границу identity-провайдера как достаточную для этапа `SLICE-02` (реальная интеграция — future implementation task), и два проверяемых архитектурных правила о secret-хранении: JWT никогда не становится частью campaign state, service-role key никогда не достигает клиента.

Обязательные решения:

1. **`UserId`** — уже существующий типизированный доменный идентификатор (`Odyssey.Domain.Identity.UserId`, префикс `user_`, canonical hex-формат, без `NewId()` factory в текущем коде) остаётся **не переопределённым** этим ADR по формату. Этот ADR фиксирует его **семантику**: `UserId` — стабильная, provider-независимая идентичность, генерируемая Odyssey (тем же canonical time-sortable принципом, что и остальные доменные идентификаторы — `ADR-011` §9.1), **не равная** и не заимствованная напрямую из идентификатора конкретного auth-провайдера (например, Supabase `auth.users.id`). Между `UserId` и provider-specific ID ведётся отдельное, обновляемое сопоставление (mapping) — не зафиксированное этим ADR в деталях (implementation-параметр, раздел 4). Смена auth-провайдера в будущем меняет только это сопоставление, не переписывает историческую атрибуцию, уже записанную в `campaign.db`/`DomainEvents` под существующими `UserId`.
2. **Dev/mock identity**: для локальных и автоматических тестов без живого auth-провайдера — фиксированный, детерминированный набор dev `UserId` (fixture), не требующий сетевого вызова к какому-либо auth-сервису. Тот же принцип, что уже установлен `InProcessSessionTransport` (`ADR-015` §9) для транспортного слоя — approved mock-граница именно для тестов, не production-путь.
3. **Mock vs реальная Supabase Auth интеграция на этапе `SLICE-02`**: явный mock/approved-boundary **достаточен на этом этапе**, реальная Supabase Auth интеграция — future implementation task, не эта ADR (раздел 5). Обоснование — раздел 5.
4. **JWT никогда не становится частью campaign state**: расширение уже принятого `PE-INV-010`-паттерна (`21_Security_And_Privacy` §4.3, `ADR-014`) на JWT/session-токены — конкретизировано в разделе 6.
5. **Service-role key никогда не достигает клиента**: сформулировано как проверяемое архитектурное правило, с явным указанием, где вообще допустимо использование service-role key (раздел 7).
6. Этот ADR **явно не может** ответственно решить часть смежных вопросов из-за отсутствия `Documentation/18_Account_And_Identity.md` (подтверждено отсутствующим — повторная проверка этой задачей, раздел 2) — эти вопросы зафиксированы как открытые (раздел 12), не изобретены.
7. Этот ADR **не определяет**: permission/role-модель против этого identity (`ODY-S02-006`); production-реализацию Supabase Auth или mock-провайдера (future implementation task); email confirmation, account recovery, multi-device поведение (требуют `18_Account_And_Identity.md`, раздел 12).

Этот ADR является нормативным authority по идентичности участника на уровне domain/network слоёв в границах, перечисленных выше — не полным Account/Identity контрактом, который остаётся ответственностью недостающего продуктового документа.

# 2. Контекст и проблема

`06_Networking_and_Session_Sync` §6.1 фиксирует, что handshake связывает `UserId`/`AuthenticatedSessionId`/`ClientInstanceId`/`ClientVersion`/`ProtocolVersion`, но **явно** оставляет детали ("Email confirmation и дополнительные требования") недостающему `Account/Identity документу`. `Documentation/18_Account_And_Identity.md`, названный этим же разделом продуктового документа и явно упомянутый в `06_Networking...` §6.1 и `21_Security_And_Privacy` §7.1 как источник этой детали — **подтверждён отсутствующим** этой задачей повторно (поиском по `Documentation/`, как и `ODY-S02-000` уже установила ранее): файла не существует нигде в репозитории.

`21_Security_And_Privacy_Odyssey_VTT_v0.1.md` §7.1 сама явно фиксирует этот раздел как **заглушку**: *«Auth, tokens и account identity redaction — Будет добавлено на Этапе 3 (networking), вместе с `06_Networking_and_Session_Sync`, `18_Account_And_Identity.md`, `07_Permissions`»* — то есть даже документ, чья прямая ответственность включает auth/token redaction, сам откладывает наполнение этого раздела до появления недостающего `18_Account_And_Identity.md`, и явно инструктирует "не заполнять преждевременно" (§7, заголовок раздела).

**Это реальный, не устранимый этой задачей информационный пробел**, а не повод откладывать всю ADR. `docs/tasks/SLICE-02_BACKLOG.md` §4's собственная граница `ODY-S02-005` — стабильный `UserId`, dev identity, mock-vs-real Supabase граница, правило JWT/campaign-state, правило service-role-key — оказывается **полностью решаемой** из уже доступных источников (`06_Networking...` §6, `21_Security_And_Privacy` §3–6, `ADR-010` §10, `ADR-011` §9.1, `ADR-014` целиком) без необходимости в содержании `18_Account_And_Identity.md`. То, что действительно требует этого документа — email confirmation, account recovery, multi-device history, полная redaction-таблица auth-полей — явно **не входит** в зафиксированную границу `ODY-S02-005` и зафиксировано как открытый вопрос (раздел 12), не решается изобретением содержания за пределами `docs/tasks/SLICE-02_BACKLOG.md` §4's собственного текста.

# 3. Термины

## 3.1 `UserId`

Стабильный, provider-независимый доменный идентификатор участника (`Odyssey.Domain.Identity.UserId`, уже существующий в коде, префикс `user_`). Генерируется Odyssey тем же canonical time-sortable принципом, что и остальные доменные идентификаторы (`ADR-011` §9.1) — не заимствуется напрямую из auth-провайдера. См. раздел 4.

## 3.2 Provider identity / provider-specific ID

Идентификатор, выдаваемый конкретным auth-провайдером (например, Supabase `auth.users.id`) — отдельное, не путаемое с `UserId` значение. Сопоставление `UserId` ↔ provider identity ведётся отдельно (раздел 4), само сопоставление классифицируется как `Personal`/`Secret`-смежные данные (не входит в campaign state, раздел 6).

## 3.3 Dev identity

Approved mock-набор `UserId`, используемый только для локальных/CI тестов, не требующий живого auth-провайдера. Не production identity source (раздел 5).

## 3.4 JWT / session token

Краткоживущий, выдаваемый auth-провайдером токен, доказывающий текущую аутентифицированную сессию. Отдельная сущность от `UserId` (которая стабильна и долгоживуща) и от `AuthenticatedSessionId` (`06_Networking...` §6.1's handshake-поле, отдельное, session-scoped значение).

## 3.5 Service-role key

Привилегированный, серверный credential (в терминологии Supabase — "service role key"), обходящий row-level security и дающий полный административный доступ к backend-сервису. Принципиально отличается от JWT конкретного пользователя (который несёт ограниченные, привязанные к этому пользователю права).

# 4. `UserId` — стабильная, provider-независимая форма

**Решение (раздел 1, пункт 1) без изменения кода.** Существующий `Odyssey.Domain.Identity.UserId` (canonical `user_` + hex, без `NewId()` в текущем коде — комментарий в `DomainIdentity.cs` называет его "externally assigned") **не меняется** этим ADR. Этот ADR фиксирует правильную интерпретацию "externally assigned": значение генерируется/выдаётся **Odyssey**'s собственным identity-issuance процессом **вне контекста конкретной кампании** (то есть один раз, при первом появлении участника в системе, не заново для каждой кампании/сессии) — не заимствуется буквально из provider-specific ID auth-сервиса. "Externally" в существующем комментарии противопоставляется `MessageId`-подобным идентификаторам, генерируемым заново при каждом использовании (раздел 3.4 `ADR-015`) — не означает "равен provider ID".

**Обоснование стабильности через смену провайдера**: если между `UserId` и provider identity ведётся отдельное сопоставление (раздел 3.2), а не прямое равенство, то смена auth-провайдера в будущем (например, миграция с одного auth-сервиса на другой) требует обновления только этого сопоставления — уже записанные в `campaign.db`/`DomainEvents` ссылки на `UserId` (`CreatedByUserId`, `LastModifiedByUserId`, `AudienceUserId` в `ADR-017` и т.д.) остаются корректными без миграции исторических данных. Прямое использование provider ID как `UserId` сделало бы это невозможным без переписывания истории — прямо противоречит `05_Persistence`/`ADR-012`'s append-only принципу (события не переписываются задним числом).

**Точный механизм и момент создания сопоставления** (какой конкретно API, когда именно `UserId` создаётся при первой регистрации через провайдера) — implementation-параметр, требующий реальной Supabase-интеграции (раздел 5), не фиксируется этим ADR как код.

# 5. Dev identity и mock-vs-реальная Supabase Auth граница

**Dev identity (раздел 1, пункт 2)**: approved, детерминированный набор dev `UserId` для локальных/CI тестов — тот же принцип, что `InProcessSessionTransport` уже установила для транспортного слоя (`ADR-015` §9: "in-process/mock transport только для automated tests"). Конкретный набор fixture-значений (сколько dev-пользователей, их точные canonical ID) — implementation-параметр, не фиксируется этим ADR.

**Mock vs реальная интеграция сейчас — решение и обоснование (раздел 1, пункт 3)**: explicit mock-граница **достаточна** для `SLICE-02` (network prototype prerequisites), реальная Supabase Auth интеграция **явно откладывается**. Обоснование:

1. `SLICE-02_BACKLOG.md` §1 сама фиксирует, что эта ревизия backlog — **не** vertical-slice implementation (roadmap §11.6), а только prerequisites (ADR + spike reports) — реальный auth-код не входит ни в один из семи пунктов exit-criteria этой ревизии (`SLICE-02_BACKLOG.md` §2).
2. `Documentation/18_Account_And_Identity.md` отсутствует (раздел 2) — реальная интеграция, требующая решений о email confirmation, account recovery и т.д., не может быть спроектирована ответственно без этого документа. Откладывание реальной интеграции — не удобство, а прямое следствие реального информационного пробела, не решаемого этой задачей.
3. Прецедент `ADR-015`'s собственного решения: транспортный порт был зафиксирован с mock-реализацией для тестов, реальный provider отложен на отдельные задачи (`ODY-S02-002`/`003`) — тот же паттерн применён здесь: зафиксировать контракт (`UserId`, JWT-границу, service-role-key-правило) сейчас, реальную provider-интеграцию — отдельной future задачей, когда `18_Account_And_Identity.md` появится или владелец продукта явно одобрит объём без него.

**Минимальная форма будущей реальной Supabase Auth интеграции** (не реализуется этой ADR, фиксируется как ориентир для будущей задачи): анонимный или email/password sign-in через Supabase Auth SDK, возвращающий provider-specific ID и JWT; маппинг в стабильный `UserId` (раздел 4) при первом появлении; JWT удерживается только в памяти клиента/защищённом OS-хранилище на время сессии (раздел 6), никогда не персистируется в campaign state.

# 6. Правило: JWT никогда не становится частью campaign state

**Конкретизация (раздел 1, пункт 4, отвечает на явный вопрос задачи)**: расширение `21_Security_And_Privacy` §4.3's уже принятого `PE-INV-010`-паттерна (*«Не хранятся в `campaign.db`, `.odcamp`, backup: OAuth/сессионные токены, пароли, secrets, owner key material»*) — этот принцип **уже дословно включает** "сессионные токены" (JWT — частный случай сессионного токена), явно распространён этим ADR на:

- `campaign.db` (любая таблица, включая `PersistenceMetadata`/системные таблицы);
- `manifest.json`;
- `.odcamp` container;
- любой backup (`Fast`/`Daily`/`Weekly`/`Full`/`Emergency`, `ADR-012` §8);
- diagnostic bundle / crash telemetry (`21_Security_And_Privacy` §4.4, `ADR-010` целиком — уже запрещает токены в diagnostic bundle).

JWT удерживается **только** в оперативной памяти клиентского процесса на время активной сессии, и опционально — в защищённом OS-хранилище (та же категория механизма, что `ADR-014` использует для owner key, не обязательно тот же конкретный API) для авто-переподключения между запусками приложения, но **никогда** как обычный файл рядом с кампанией и **никогда** внутри самой кампании. Это то же самое разграничение "секрет — не campaign artifact", уже установленное `ADR-014`'s owner key принципом, применённое к другому классу секрета.

**Проверяемость правила**: implementation-задача, реализующая auth, обязана иметь тест, доказывающий, что ни один JWT/session-токен не появляется байтово в записанном `campaign.db`, `manifest.json`, `.odcamp` файле или diagnostic bundle после полного цикла аутентификации + сохранения кампании — аналогично тому, как `ADR-014` §14 (Definition of Done) требует доказательства отсутствия owner key в этих же артефактах.

# 7. Правило: service-role key никогда не достигает клиента

**Формулировка как проверяемое архитектурное правило (раздел 1, пункт 5, отвечает на явный вопрос задачи)**:

> Service-role key (или любой эквивалентный привилегированный, RLS-обходящий серверный credential) **никогда** не входит ни в один артефакт, достижимый Unity-клиентом: ни в `Packages/com.odyssey.unity.client`, ни в любой другой `Packages/com.odyssey.*` модуль, компилируемый в клиентскую сборку (`ADR-006`'s dual-compilation modules), ни в Unity `ProjectSettings`/`Assets`, ни в собранный Player build (Mono или IL2CPP), ни в diagnostic bundle, ни в любую конфигурацию, распространяемую вместе с клиентским приложением.

**Где service-role key допустимо использовать, если вообще используется**: только в доверенном, строго серверном execution-контексте, который клиент никогда не выполняет и к которому клиент не имеет прямого доступа (например, backend Edge Function/serverless-функция, выполняемая исключительно на инфраструктуре сервиса) — не как embedded-конфигурация внутри любого артефакта, распространяемого пользователю. Если ни один такой серверный контекст не требуется на этапе `SLICE-02`/будущей implementation-задачи identity — service-role key **не используется вовсе** до появления реальной необходимости в нём, не добавляется "про запас".

**Проверяемость правила**: implementation-задача, вводящая любой Supabase-код, обязана продемонстрировать (тестом или структурной проверкой, аналогично `scripts/verify-test-structure.ps1`'s существующим forbidden-API/forbidden-dependency сканам), что ни один литерал/конфигурационное значение service-role key не присутствует ни в одном файле, входящем в клиентскую сборку — тот же класс проверки, что уже применяется к owner key/секретам в этом репозитории (`ADR-014` §14, `REPO-POLICY-002`'s forbidden-pattern сканирование).

# 8. Данные-классификация (наследуется, не переопределяется)

Per `21_Security_And_Privacy` §3, классификация данных для privacy/security целей наследуется от `ADR-010` §10 без изменений. Этот ADR классифицирует введённые им сущности в терминах этой уже принятой схемы, не вводя новую:

| Сущность | Классификация (`ADR-010` §10) | Причина |
|---|---|---|
| `UserId` | `OperationalSafe` | Стабильный идентификатор без прямой personal-информации; безопасен для логов/diagnostics в отличие от email/имени |
| Provider identity (Supabase `auth.users.id` и т.п.) | `Personal`/`Secret`-смежное | Прямая связь с реальным аккаунтом пользователя; не входит в campaign state (раздел 6, по аналогии) |
| JWT / session token | `Secret` | Прямое доказательство аутентифицированной сессии; правило раздела 6 |
| Service-role key | `Secret`, наивысший уровень чувствительности | Полный административный доступ к backend; правило раздела 7 |

# 9. Соответствие module boundaries (`ADR-001`) и уже принятым `ADR-015`–`017`

Этот ADR не вводит новый код и не переопределяет `ADR-001`'s module boundaries. Будущая implementation-задача:

- размещает `UserId` (уже существует) в `Odyssey.Domain.Identity`, не меняя его формат;
- размещает mock/dev identity provider и, отдельно, реальный Supabase Auth adapter в соответствии с уже установленным паттерном `ADR-015`'s `InProcessSessionTransport` (mock в тестовом/спайковом контексте, реальный provider — Application port + provider-specific implementation, не наоборот);
- не даёт `Odyssey.Networking` или `Odyssey.Persistence` прав самостоятельно решать, что является secret (JWT/service-role key) — эти правила (разделы 6–7) применяются на границе, где секрет мог бы попасть в персистентный/клиентский артефакт, независимо от того, какой модуль формально владеет этим кодом.
- `AudienceUserId`/`UserId`, уже упомянутые `ADR-017` §3.3/§4 как принятая основа для `ODY-S02-005`/`006`, остаются семантически теми же значениями, определёнными разделом 4 этого ADR — не переопределяются.

# 10. Не входит в ADR-018

Явно исключено из объёма этого ADR (владеют другие задачи backlog `SLICE-02`, или требуют недостающего `18_Account_And_Identity.md`, раздел 12):

- **Permission/role-модель против этого identity** (кто что может делать/видеть) — `ODY-S02-006` (Permissions Baseline).
- **Production-реализация** Supabase Auth интеграции или mock-провайдера — future implementation task, отложенная разделом 5.
- **Email confirmation, account recovery, multi-device поведение, регистрационный UX** — требуют `18_Account_And_Identity.md`; не изобретаются этим ADR (раздел 12).
- **Полная redaction-таблица auth-полей** за пределами уже установленного `PE-INV-010`-расширения раздела 6 — `21_Security_And_Privacy` §7.1's собственная заглушка, требующая того же недостающего документа.
- **Конкретный OS-механизм хранения JWT** (Windows Credential Manager vs иной) — implementation-параметр; `ADR-014`'s уже принятый механизм для owner key может быть переиспользован, но это решение future implementation task, не фиксируется здесь как обязательное 1:1 копирование.

# 11. Правила для Codex

Codex обязан:

1. Не заимствовать provider-specific ID (например, Supabase `auth.users.id`) напрямую как `UserId` — использовать отдельное сопоставление (раздел 4).
2. Не персистировать JWT/session-токен ни в `campaign.db`, ни в `manifest.json`, ни в `.odcamp`, ни в backup, ни в diagnostic bundle (раздел 6) — только в памяти/защищённом OS-хранилище на время сессии.
3. Не встраивать service-role key ни в один артефакт, достижимый Unity-клиентом (раздел 7) — если серверный контекст для него не существует на момент задачи, не добавлять key "про запас".
4. Не изобретать содержание `18_Account_And_Identity.md` (email confirmation, account recovery, multi-device история) — эти вопросы остаются открытыми (раздел 12) до появления этого документа или явного решения владельца продукта.
5. Не реализовывать permission/role-проверки под этим ADR — они принадлежат `ODY-S02-006`.
6. Использовать dev/mock identity (раздел 5) для любых тестов, не требующих реальной интеграции — не подключать реальный Supabase Auth в тестовый код без отдельного решения.

# 13. Рассмотренные альтернативы

## 13.1 Использовать Supabase `auth.users.id` напрямую как `UserId`

Отклонено: делает невозможной смену auth-провайдера без переписывания исторической атрибуции в `campaign.db`/`DomainEvents`, прямо противоречит append-only принципу (`ADR-012`); также противоречит уже установленному во всей кодовой базе паттерну "доменные идентификаторы генерируются приложением, не заимствуются из внешней системы" (`ADR-011` §9.1).

## 13.2 Требовать реальную Supabase Auth интеграцию уже на этапе `SLICE-02`

Отклонено: `18_Account_And_Identity.md` отсутствует, что делает ответственное проектирование email confirmation/account recovery невозможным сейчас; `SLICE-02_BACKLOG.md` §1 сама фиксирует эту ревизию как prerequisites-only, не vertical-slice implementation — реальный auth-код не требуется ни одним из семи exit-criteria.

## 13.3 Отложить весь ADR-018 до появления `18_Account_And_Identity.md`

Отклонено: зафиксированная `SLICE-02_BACKLOG.md` §4 граница `ODY-S02-005` полностью решаема из уже доступных источников (раздел 2) — откладывание всего ADR заблокировало бы `ODY-S02-006` (Permissions Baseline) без необходимости, поскольку та задача нуждается именно в стабильном `UserId`-контракте, который этот ADR может дать уже сейчас.

## 13.4 Не формулировать service-role-key-правило как ADR-решение, оставить его "здравым смыслом"

Отклонено: задача явно требует сформулировать его как проверяемое архитектурное правило — "здравый смысл" без нормативной формулировки и явного Definition-of-Done-стиля критерия проверки (раздел 7) не даёт implementation-задаче конкретного, тестируемого требования, тот же принцип, что уже применяется к owner key (`ADR-014`).

# 15. Нормативное действие

Принято как ADR этой задачи (`ODY-S02-005`) в границах, зафиксированных `SLICE-02_BACKLOG.md` §4 — не как полный Account/Identity контракт. Обоснование принятия без ожидания `18_Account_And_Identity.md`: зафиксированная граница этой задачи (`UserId`, dev identity, mock-vs-real граница, JWT-правило, service-role-key-правило) полностью решаема из уже доступных, уже принятых источников (раздел 2); вопросы, действительно требующие недостающего документа, честно зафиксированы открытыми (раздел 12), не изобретены — тот же принцип честности о границах эмпирической/документальной уверенности, что `ADR-016` уже применила к неполному покрытию `SP-03`.

С даты принятия (`Accepted`):

- `UserId` остаётся неизменным по формату; его семантика (стабильность, provider-независимость, отдельное сопоставление) — нормативна для любой будущей auth-реализации;
- mock/dev identity — approved путь для тестов до появления реальной интеграции; реальная Supabase Auth интеграция не начинается без отдельного решения, учитывающего раздел 12's открытые вопросы;
- правила разделов 6–7 (JWT/service-role-key) — нормативны немедленно, даже до появления кода, использующего auth — они ограничивают будущую implementation-задачу с момента её начала, не вводятся постфактум;
- `ODY-S02-006` авторизована опираться на `UserId` (раздел 4) как принятую основу и не обязана повторно решать вопрос его формы;
- открытые вопросы раздела 12 остаются открытыми до появления `18_Account_And_Identity.md` или явного отдельного решения владельца продукта — принятие этого ADR не считается их молчаливым закрытием;
- изменение принятых здесь решений требует amendment этого ADR или нового superseding ADR, не молчаливого отклонения в реализации.
