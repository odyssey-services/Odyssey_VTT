# ADR-013 — Migration Runner

**Документ:** `docs/adr/ADR-013_Migration_Runner_v1.0.md`  
**ADR:** ADR-013  
**Версия:** 1.0  
**Дата:** 20 августа 2026 года  
**Статус:** Accepted  
**Область:** реестр database schema миграций (`SchemaHistory`, immutable identifier, `FromVersion`/`ToVersion`, checksum), нормативный workflow запуска миграции (подтверждение, pre-migration snapshot, temp-copy execution, integrity validation), транзакционность шага миграции, нормативное поведение при ошибке миграции, граница с ruleset migration workflow, read-only compatibility mode для кампании новее приложения  
**Связанные этапы:** Roadmap Этап 2 (`SLICE-01`), Milestone `M2`, backlog `ODY-S01-003`  
**Базовые документы:** `05_Persistence_Odyssey_VTT_v0.8.md` (разделы 6, 25, 26), `ADR-011_Local_Campaign_Format_v1.0.md`, `ADR-012_Snapshot_And_Append_Only_Journal_v1.0.md`, `ADR-004_Result_and_Error_Model_v1.0.md`, `docs/tasks/SLICE-01_BACKLOG.md`

---

# 1. Решение

Odyssey VTT применяет database schema миграции через единый migration runner, работающий над строго упорядоченным реестром миграций, выполняющий каждую миграцию над временной копией базы, никогда не заменяющий рабочую базу до полного успеха всей цепочки, и всегда создающий pre-migration snapshot перед началом. Database schema migration и ruleset migration — раздельные контуры с разной ответственностью.

Обязательные решения:

1. Migration registry — строго упорядоченный список миграций (`0001_Initial`, `0002_...`, ...). Каждая миграция имеет: immutable identifier, `FromVersion`/`ToVersion`, checksum своего кода/скрипта, transaction capability, обязательный validation step и опциональные post-migration rebuild steps (раздел 4).
2. Запуск миграции — нормативный 7-шаговый workflow: показ текущей/целевой версии → подтверждение пользователя → полный snapshot (использует уже принятый триггер `ADR-012` §8.2 "перед migration", не переопределяется здесь) → выполнение миграций по строгому порядку → integrity validation → обновление `SchemaHistory`/`manifest.json` → открытие кампании (раздел 5).
3. Каждый migration step выполняется в транзакции, если это допускает конкретная SQLite-операция; вся цепочка миграций считается успешной только после финальной проверки, не после последнего отдельного шага (раздел 6).
4. Реализационный паттерн: миграция выполняется над temp copy базы; рабочая база заменяется мигрированной копией только после полностью успешной цепочки (раздел 7.1).
5. Поведение при ошибке миграции — нормативное правило, не рекомендация: откат текущего step; исходная рабочая база НЕ заменяется temp copy; pre-migration snapshot сохраняется; пользователю — safe error и diagnostic log; запись новой версией блокируется до успешного завершения (раздел 7.2).
6. `SchemaHistory` — обязательная схема таблицы с полями `MigrationId`, `FromVersion`, `ToVersion`, `CodeChecksum`, `StartedAt`, `CompletedAt?`, `Status`, `ApplicationVersion`, `BackupId`, `FailureCode?` (раздел 8).
7. Изменение `RulesetVersion` НЕ является автоматически database schema migration; ruleset migration — отдельный domain workflow (Rules Engine/Content Domain) с explicit preview/backup/событиями, не решаемый этим ADR (раздел 9).
8. Read-only compatibility mode — нормативное поведение migration runner'а, когда `DatabaseSchemaVersion` кампании новее приложения: write запрещён всегда, попытка safe read-only compatibility, запрет молчаливого игнорирования неизвестных обязательных структур, явный список доступных/недоступных read-only возможностей, запрет automatic downgrade (раздел 10).
9. Этот ADR не переопределяет `.odcamp`/`manifest.json` формат (`ADR-011`), snapshot/journal contract (`ADR-012`), не решает owner key storage (`ODY-S01-004`) и не пинит SQLite provider-библиотеку (наследует `[OPEN]` из `ADR-011`) (раздел 11).
10. Конкретный список будущих миграций (`0001`, `0002`, ...) — implementation-контент, не решение этого ADR (раздел 11).

Этот ADR является нормативным authority по database schema migration runner. Он реализует и уточняет `05_Persistence_Odyssey_VTT_v0.8.md` разделы 25 и 26 применительно к `SLICE-01` без изменения продуктового поведения, описанного там.

# 2. Контекст и проблема

`ADR-011` определяет физический формат и version dimensions; `ADR-012` определяет journal/snapshot contract и явно указывает "перед migration" как один из snapshot-триггеров, не описывая саму миграцию. Без отдельного ADR:

1. Не было бы явного, проверяемого, нормативного (не описательного) правила поведения при сбое миграции — риск оставить кампанию в полуприменённом состоянии.
2. Implementation-задачи могли бы применять миграцию напрямую к рабочей базе вместо temp copy, теряя защиту от повреждения при сбое.
3. Не было бы явной границы между database schema migration и ruleset migration — риск, что реализация Rules Engine попытается провести ruleset migration через тот же migration runner, что и schema migration, смешивая два разных по риску и workflow процесса.
4. Не было бы нормативного поведения для случая "кампания новее приложения" — реализация могла бы либо запретить открытие кампании целиком, либо, хуже, попытаться молча читать неизвестную структуру.

# 3. Термины

## 3.1 Migration

Именованный, упорядоченный шаг преобразования `DatabaseSchemaVersion` кампании с одной версии на следующую, зарегистрированный в migration registry с immutable identifier.

## 3.2 Migration runner

Компонент Persistence, ответственный за определение применимых миграций, их последовательное выполнение над временной копией базы, транзакционность отдельных шагов, integrity validation и обновление `SchemaHistory`/`manifest.json`.

## 3.3 Pre-migration snapshot

Полный snapshot кампании (`ADR-012` §8.1, §8.4), создаваемый по триггеру "перед database migration" (`ADR-012` §8.2 пункт 5), обязательный шаг workflow запуска миграции в этом ADR.

## 3.4 Read-only compatibility mode

Режим открытия кампании, чья `DatabaseSchemaVersion` новее версии, поддерживаемой текущим приложением, в котором запись запрещена и доступно только ограниченное, явно перечисленное подмножество операций чтения.

---

# 4. Migration registry

Миграции образуют строго упорядоченный список:

```text
0001_Initial
0002_AddPendingInteractions
0003_AddEventPayloadHash
...
```

Каждая зарегистрированная миграция обязана иметь:

- immutable identifier (не переиспользуется и не переименовывается после публикации);
- `FromVersion`/`ToVersion` — конкретную пару версий схемы, к которой применяется;
- checksum своего кода/скрипта — используется для обнаружения расхождения между зарегистрированной и фактически выполненной миграцией;
- transaction capability — явное указание, поддерживает ли миграция транзакционное выполнение целиком или требует пошагового транзакционного применения (раздел 6);
- обязательный validation step, выполняемый после применения миграции, до признания её успешной;
- опциональные post-migration rebuild steps (например, перестроение индексов или производных структур), которые не считаются частью самой миграции, но могут быть зарегистрированы как часть её пайплайна.

Порядок миграций строго последовательный: миграция `000N` применяется только после успешного применения всех миграций с меньшим номером, ведущих от текущей версии кампании к целевой версии приложения. Пропуск промежуточной миграции запрещён.

---

# 5. Запуск миграции — нормативный workflow

При открытии кампании со старой версией `DatabaseSchemaVersion`, migration runner обязан выполнить следующую последовательность:

```text
1. Показать пользователю текущую и целевую версию схемы
2. Получить явное подтверждение пользователя перед началом миграции
3. Создать полный snapshot кампании (обязательный snapshot-триггер "перед migration", ADR-012 §8.2 пункт 5)
4. Выполнить миграции строго по порядку регистрации (раздел 4)
5. Запустить integrity validation по завершении цепочки
6. Обновить SchemaHistory и manifest.json
7. Открыть кампанию
```

Нормативные уточнения:

- Шаг 2 (подтверждение пользователя) обязателен и не может быть пропущен автоматическим режимом без явного, отдельно документированного batch/headless workflow — этот ADR не определяет такой headless workflow и не предполагает его существование по умолчанию.
- Шаг 3 использует существующий snapshot contract `ADR-012` целиком (определение, 8-шаговый flow, `BackupRecord`) — этот ADR не переопределяет, как создаётся snapshot, только фиксирует момент, когда он обязателен в рамках migration workflow.
- Шаги 4–6 логически неразделимы для целей учёта успеха: кампания не считается мигрированной, пока не пройдена integrity validation (шаг 5) и не обновлены `SchemaHistory`/`manifest.json` (шаг 6) — см. раздел 6.
- Шаг 7 (открытие кампании) не выполняется, если любой из шагов 3–6 не завершился успешно; в этом случае применяется раздел 7.

---

# 6. Транзакционность

Каждый migration step выполняется в транзакции, если конкретная SQLite-операция это допускает (некоторые DDL-операции SQLite не поддерживают полную транзакционную атомарность — в этом случае применяется temp-copy защита раздела 7.1 как основной механизм безопасности, не заменяемый транзакцией отдельного шага).

Вся цепочка миграций считается успешной только после финальной проверки (integrity validation, раздел 5 шаг 5), не после успешного выполнения последнего отдельного шага. Промежуточный успех отдельных шагов не является основанием для обновления `SchemaHistory` до прохождения финальной проверки.

---

# 7. Поведение при ошибке миграции

## 7.1 Реализационный паттерн — temp copy

Миграция выполняется не над рабочей базой напрямую, а над временной копией базы. Рабочая база заменяется мигрированной копией только после полностью успешной цепочки миграций (все шаги применены, integrity validation пройдена). Это защищает от полуприменённой миграции — рабочая база, находящаяся в реальном использовании, остаётся в исходном, неизменном состоянии до момента, когда мигрированная копия доказанно валидна.

## 7.2 Нормативное правило при сбое

Если миграция завершилась неудачей на любом шаге, обязательны все следующие действия:

- текущий migration step откатывается (используя транзакцию шага, где она применима, раздел 6);
- исходная рабочая база **не** заменяется мигрированной temp copy — рабочая база остаётся в состоянии до начала миграции;
- pre-migration snapshot, созданный на шаге 3 workflow (раздел 5), сохраняется и не удаляется автоматически;
- пользователю показывается safe error (не сырое исключение или диагностика с потенциально приватными данными) и создаётся diagnostic log;
- запись новой версией схемы блокируется — `SchemaHistory`/`manifest.json` не обновляются для незавершённой миграции, кампания не считается находящейся на целевой версии.

Это правило имеет ту же нормативную силу, что и транзакционная граница journal↔projection, зафиксированная `ADR-012` §5: сбой миграции не может привести к состоянию, где рабочая база частично мигрирована, а `SchemaHistory` не отражает реальное состояние базы.

# 8. `SchemaHistory`

Обязательная схема:

```text
SchemaHistory
├── MigrationId
├── FromVersion
├── ToVersion
├── CodeChecksum
├── StartedAt
├── CompletedAt?
├── Status
├── ApplicationVersion
├── BackupId
└── FailureCode?
```

`BackupId` в `SchemaHistory` обязан ссылаться на `BackupRecord` (`ADR-012` §8.7) pre-migration snapshot, созданного на шаге 3 workflow (раздел 5) — эта связь обеспечивает прослеживаемость: для любой записи миграции можно найти snapshot, к которому можно откатиться, если миграция впоследствии окажется проблемной за пределами самого runner'а (например, обнаруженная позже ошибка правильности данных).

`Status` обязан различать как минимум: успешно завершённую миграцию, миграцию с ошибкой (раздел 7.2), и не оставлять записей для миграций, которые не были начаты.

---

# 9. Граница с ruleset migration

Изменение `RulesetVersion` **не является** автоматически database schema migration. Ruleset migration — отдельный domain workflow, принадлежащий Rules Engine и Content Domain, с собственными explicit preview, backup и событиями, не совпадающий с database schema migration runner'ом, определённым этим ADR.

Этот ADR определяет только database schema migration runner (изменение `DatabaseSchemaVersion`). Он не определяет:

- как Rules Engine/Content Domain обнаруживает необходимость ruleset migration;
- как выглядит preview ruleset-изменений для пользователя;
- какие события ruleset migration производит;
- собственный backup-механизм ruleset migration, если он отличается от snapshot contract `ADR-012`.

Точка интеграции, которую этот ADR фиксирует явно: если ruleset migration решает создавать snapshot кампании как часть своего backup-шага, она обязана использовать существующий snapshot contract `ADR-012` (SQLite Backup API, `BackupRecord`), а не изобретать альтернативный механизм копирования базы — по тем же причинам консистентности при активном WAL, зафиксированным `ADR-012` §8.4. Это единственная обязательная точка соприкосновения между двумя workflow, которую фиксирует этот ADR; сам workflow ruleset migration (preview/подтверждение/применение/события) остаётся полностью вне области этого ADR и должен быть определён отдельным ADR или task contract, когда Rules Engine/Content Domain достигнут этой стадии.

# 10. Более новая кампания и read-only compatibility mode

## 10.1 Новая схема — нормативное поведение

Если `DatabaseSchemaVersion` кампании новее версии, поддерживаемой текущим приложением, migration runner обязан:

- запретить write mode безусловно — ни при каких обстоятельствах приложение не открывает кампанию новее себя в режиме записи;
- попытаться открыть кампанию в safe read-only compatibility mode;
- не игнорировать молча неизвестные обязательные структуры — если приложение обнаруживает обязательную структуру данных, которую не распознаёт и не может безопасно интерпретировать, оно не продолжает работу так, будто эта структура не существует;
- если безопасное чтение невозможно (обязательные неизвестные структуры блокируют даже read-only интерпретацию), открытие кампании запрещается целиком, с понятным пользователю сообщением.

## 10.2 Read-only capabilities — явный список

В зависимости от возможностей compatibility adapter, доступны:

```text
- manifest и campaign metadata;
- список персонажей;
- journal/archive просмотр;
- export raw campaign copy;
- diagnostic bundle.
```

Явно недоступны в read-only compatibility mode:

```text
- команды (никакие);
- migration вниз (downgrade миграция);
- GM Override;
- asset mutation;
- backup rotation, меняющая контейнер;
- session hosting.
```

## 10.3 Запрет downgrade

MVP не выполняет автоматический schema downgrade ни в каком режиме, включая read-only compatibility mode. Понижение версии схемы — не операция, которую предоставляет migration runner, определённый этим ADR.

# 11. Не входит в ADR-013

- **Физический формат `.odcamp`/`manifest.json`** — определён `ADR-011`, не переопределяется здесь; этот ADR только ссылается на `manifest.json` как на объект, обновляемый по шагу 6 workflow (раздел 5).
- **Snapshot/journal contract** — определён `ADR-012`; этот ADR использует существующий snapshot-триггер "перед migration" (`ADR-012` §8.2 пункт 5) и существующий `BackupRecord` (§8.7), не переопределяя ни определение snapshot, ни его 8-шаговый creation flow.
- **Owner key storage mechanism** — `ODY-S01-004`; не затрагивается этим ADR.
- **Выбор конкретной SQLite provider-библиотеки** — наследует статус `[OPEN]` из `ADR-011` §12.1 и `ADR-012` §12.2. Ничто в migration runner contract этого ADR требует решения этого вопроса именно здесь.
- **Backup encryption at rest** — наследует статус `[OPEN]` из `ADR-012` §12.1, не решается здесь.
- **Конкретный список будущих миграций** (`0001_Initial`, `0002_...` и далее) — implementation-контент конкретных изменений схемы, создаваемый по мере необходимости в отдельных implementation-задачах, не решение этого ADR.
- **Workflow ruleset migration целиком** (preview, подтверждение, применение, события Rules Engine/Content Domain) — см. раздел 9; определяется отдельно, вне этого ADR.

# 12. Открытые вопросы

## 12.1 SQLite provider-библиотека — `[OPEN]`, унаследовано

См. раздел 11. Статус не изменяется этим ADR. Наследуется из `ADR-011` §12.1 и `ADR-012` §12.2.

## 12.2 Backup encryption at rest — `[OPEN]`, унаследовано

См. раздел 11. Статус не изменяется этим ADR. Наследуется из `ADR-012` §12.1; актуален и для pre-migration snapshot, создаваемого по этому ADR, поскольку это тот же механизм snapshot.

## 12.3 Headless/batch подтверждение миграции — `[OPEN]`, новое

`05_Persistence` §25.2 описывает подтверждение пользователя как обязательный интерактивный шаг. Для сценариев без интерактивного пользователя (например, автоматизированный тест-раннер, о котором идёт речь в `ODY-S01-005`/`SP-02`) остаётся открытым вопрос, какой механизм заменяет интерактивное подтверждение. Этот ADR не решает его — фиксирует только то, что headless-режим не предполагается по умолчанию (раздел 5).

# 13. Правила для Codex

Codex обязан:

1. Реализовывать миграцию над временной копией базы, никогда не изменяя рабочую базу напрямую до полного успеха цепочки (раздел 7.1).
2. Не заменять рабочую базу мигрированной копией, если integrity validation (раздел 5, шаг 5) не пройдена.
3. Не обновлять `SchemaHistory`/`manifest.json` для миграции, не завершённой полностью успешно (раздел 6).
4. При сбое миграции сохранять pre-migration snapshot и не удалять его автоматически (раздел 7.2).
5. Не пропускать шаг создания pre-migration snapshot ни при каких условиях запуска миграции (раздел 5, шаг 3).
6. Не смешивать database schema migration runner с ruleset migration workflow — это разные компоненты с разной ответственностью (раздел 9).
7. Не разрешать write mode для кампании, чья `DatabaseSchemaVersion` новее приложения, ни при каких обстоятельствах (раздел 10.1).
8. Не реализовывать automatic schema downgrade (раздел 10.3).
9. Не изобретать headless/batch-подтверждение миграции без отдельного явного решения — раздел 12.3 остаётся открытым.
10. Не пинить SQLite provider-библиотеку под предлогом реализации migration runner — вопрос остаётся открытым (раздел 11).

# 14. Definition of Done / критерии приёмки ADR-013 implementation

ADR считается реализованным (для той части, которую он определяет), когда:

1. Migration registry содержит миграции со строгим порядком, immutable identifier, `FromVersion`/`ToVersion`, checksum, отмеченной transaction capability и обязательным validation step; тест подтверждает отказ при попытке зарегистрировать миграцию вне порядка.
2. Запуск миграции проходит все 7 шагов раздела 5 в указанном порядке; тест подтверждает, что миграция не начинается без предварительного snapshot.
3. Сбой миграции на любом шаге приводит к состоянию, описанному в разделе 7.2 (rollback шага, сохранённая рабочая база, сохранённый pre-migration snapshot, safe error, diagnostic log, блокировка версии); покрыто тестом, эмулирующим сбой на промежуточном шаге.
4. `SchemaHistory` содержит все поля раздела 8, включая корректную ссылку `BackupId` на pre-migration snapshot.
5. Ruleset migration workflow (когда реализован) не использует этот migration runner напрямую для изменения `RulesetVersion`; тест/ревью подтверждает разделение (раздел 9).
6. Открытие кампании с `DatabaseSchemaVersion` новее приложения не допускает записи ни при каких условиях; read-only compatibility mode предоставляет только перечисленный в разделе 10.2 набор возможностей; тест подтверждает отказ записи.
7. Automatic schema downgrade не реализован ни в каком пути кода.

# 15. Рассмотренные альтернативы

## 15.1 Прямое применение миграции к рабочей базе без temp copy

Отклонено: при сбое на позднем шаге оставляет рабочую базу в неизвестном полуприменённом состоянии; temp-copy паттерн (раздел 7.1) гарантирует, что рабочая база остаётся неизменной до доказанного успеха всей цепочки — прямое требование `05_Persistence` §25.4 `[IMPLEMENTATION]`.

## 15.2 Обновление `SchemaHistory` после каждого успешного шага, а не после финальной проверки

Отклонено: создаёт риск, что `SchemaHistory` покажет кампанию как частично мигрированную, если финальная integrity validation впоследствии провалится — нарушает требование раздела 6, что цепочка считается успешной только после финальной проверки.

## 15.3 Единый migration runner для database schema и ruleset migration

Отклонено: `05_Persistence` §25.6 явно разделяет эти два процесса по ответственности (Persistence vs. Rules Engine/Content Domain) и по workflow (автоматический technical migration vs. explicit preview/backup для игровых данных); объединение усложнило бы обе модели без выигрыша, и потребовало бы либо ослабления гарантий database migration, либо избыточной технической сложности для простого ruleset preview.

## 15.4 Автоматический silent downgrade схемы при открытии более новой кампании

Отклонено: `05_Persistence` §26.3 явно запрещает automatic downgrade в MVP; silent downgrade рискует потерей данных, специфичных для более новой схемы, без явного согласия пользователя.

## 15.5 Полный запрет открытия кампании новее приложения (без read-only mode)

Отклонено: `05_Persistence` §26.1–26.2 явно предусматривает safe read-only compatibility mode с полезным ограниченным набором операций (просмотр, экспорт, diagnostic bundle) — полный запрет лишил бы пользователя возможности хотя бы просмотреть или экспортировать свою кампанию при откате на более старую версию приложения.
