# ODY-S06-105 — Real `IAttackRulesEvaluator` Implementation (Formula + Attributes + Armor + Range)

## 1. Task identity
`ODY-S06-105`; status: In Review (Draft PR, see the backlog row for the link once opened). Fifth task of `SLICE-06`, the first real, production `IAttackRulesEvaluator` implementation -- every predecessor task (`ODY-S05-601`-`611`, `ODY-S06-101`-`104`) exercised only hand-written test fixtures.

## 2. Goal
Build `CoreAttackRulesEvaluator`, computing a real damage/range/hit resolution from a weapon's own real `DamageExpression`, the actor's real attributes (`ODY-S06-102`), the target's real armor (`ODY-S06-103`), and the real actor-target distance (`ODY-S06-104`) -- not a placeholder. Resolve the long-open `AttackRandomSample` single-int limitation (a multi-dice-term formula like "2d6+3" needs more than one independent draw). Wire this real evaluator into the production entry points (`AttackEvaluationService`/`AttackApplyService`) so a real attack, once a real caller exists, produces real numbers.

## 6. Domain contract

## 7. Application contract
`AttackEvaluationService.PreviewAttack`/`EvaluateAttack` gain a private `WithDecodedWeapon` step: `TypedDefinitionCodec.DecodeWeapon` against `ActionMechanics`, building an augmented `AttackEvaluationSnapshot` copy carrying the result (or the original, unaugmented snapshot on decode failure -- not an error, since most existing test fixtures' own action items are not weapons at all). `EvaluateAttack` now draws up to 4 independent `IAuthoritativeRandomStream.NextInclusive(1, 100, drawIndex)` values (a practical MVP cap, not `DiceFormulaParser.MaxDiceCount`/`MaxDiceGroups`) instead of exactly 1, building an `AttackRandomSample` from all of them. No change to `AttackApplyService.cs`, `IAttackStateReader`, or `IAttackApplyRepository` -- `AttackApplyService.ResolveAttack` already forwards the whole `AttackRandomSample` struct opaquely, unaffected by its own internal shape change.

## 8. Persistence boundary
No persistence-layer change. `CoreAttackRulesEvaluator` reads only already-loaded snapshot data (`Actor.AttributeValues`, `ArmorAndEffects.Entries`, `Topology.Entries`, the newly-added `ActionWeapon`) -- no database access of its own, consistent with `ADR-001` §6.2's "Rules receives... external state only through explicit input parameters." `SqliteAttackApplyRepository.cs`'s own existing `ApplyAttackDelta`/`character:{characterId}:{resourceKind}` convention (`ODY-S05-609`, unmodified) applies `CoreAttackRulesEvaluator`'s own `AttackDelta` output exactly as it already applies any other evaluator's output -- the damage resource kind is hardcoded to `"health"` (this task's own MVP decision; `WeaponDefinition` carries no resource-kind field of its own, and `"health"` is this codebase's own established test-fixture convention, e.g. `ODY-S05-609`'s own `AttackAggregateDeltaCommitTests.cs`).

## 18. Change control

### Decisions made during execution

- **`Odyssey.Rules` genuinely cannot reference `Odyssey.Application.Content.TypedDefinitionCodec` -- confirmed by direct `.asmdef`/`.csproj` read (`Packages/com.odyssey.rules/Odyssey.Rules.asmdef`: `"references": ["Odyssey.Domain"]`; `DotNet/Projects/Odyssey.Rules.csproj`: `<ProjectReference Include="Odyssey.Domain.csproj" />` only), not merely assumed from `ADR-001`'s own prose.** `ADR-030` §5 point 1's own text ("decode it as a WeaponDefinition... reusing TypedDefinitionCodec's own existing decode path") reads as if the real evaluator itself performs this decode -- but doing so literally inside `CoreAttackRulesEvaluator` would require `Odyssey.Rules` to reference `Odyssey.Application`, a genuine architecture-boundary violation this task is not authorized to introduce. Resolved by decoding in `AttackEvaluationService` (Application layer, already able to reference `TypedDefinitionCodec`) and passing the result through an extended `AttackEvaluationSnapshot` -- `CoreAttackRulesEvaluator` itself never touches `TypedDefinitionCodec` or any other Application-layer type, verified directly by `Odyssey.Rules.csproj` still listing only `Odyssey.Domain.csproj` after this task's own changes.
- **`AttackEvaluationSnapshot`'s weapon-decode augmentation is a NEW constructor overload (backward compatible), not a change to `SqliteAttackStateReader.Read`'s own snapshot-construction call.** `SqliteAttackStateReader.cs` is explicitly forbidden to modify by this task's own governing ТЗ (`102`/`103`/`104`'s own data source). Since decode failure for a non-weapon action item (the shape of essentially every pre-`ODY-S06-105` test fixture's own action item) must not become a new hard-fail, the augmentation step lives entirely in `AttackEvaluationService` -- the one Application-layer seam every real `IAttackRulesEvaluator` caller already passes through -- leaving `ActionWeapon` null (not an error) whenever decode fails, which only `CoreAttackRulesEvaluator` (this task's own new class) ever actually inspects.
- **`AttackRandomSample`'s extension keeps `Value` as `Values[0]`, not a removed/renamed property.** `SqliteAttackApplyRepository.cs`'s own `randomSample.Value` read (line ~140/155/166) is explicitly forbidden to touch by this task's own governing ТЗ. Preserving `Value` as a computed alias for the first draw, rather than requiring that file to change, keeps its own existing meaning (the single "headline" roll recorded for Game Log/audit purposes) intact with zero edits to a file this task cannot touch.
- **`AttackEvaluationService.EvaluateAttack` always draws exactly 4 values, never fewer/more depending on the actual formula's own term count.** The formula is not decoded until after `WithDecodedWeapon` runs (which itself happens independently of the RNG-draw step) -- the draw loop cannot know in advance how many dice terms a given weapon's formula will need. 4 is a practical MVP cap (this governing ТЗ's own explicit direction), comfortably above any formula this slice's own real content will use, and each draw is cheap (no new stream creation, just additional calls against the one already-open `IAuthoritativeRandomStream`).
- **An unresolved `attributeReference` term throws, rather than silently defaulting to zero or being caught and converted to a "miss."** `ADR-030` §6.2 itself mandates "fail-closed... never a silent zero," but `IAttackRulesEvaluator.Preview`/`Evaluate` return `ProposedAttackResolution` unconditionally with no `Result`-wrapped failure path, and this task is not authorized to change that interface. A thrown exception is the direct, honest translation of "fail-closed" into a signature that cannot itself express failure -- matching this exact codebase's own existing precedent (`DiceFormulaParser.Parse` throws `FormatException` for invalid syntax) rather than inventing a silent, spec-violating zero-substitution.
- **Armor is summed across every equipped piece for a target, never selected by `CoveredBodyPartIds` (this task's own governing ТЗ §3.2, product-owner-approved).** No hit-location model exists anywhere in this codebase yet (`BodyPart` stays `null` on every `ProposedAttackResolution` this evaluator produces, unchanged); inventing a selection criterion (which piece "counts") would mean deciding an un-specified mechanic this task has no authority to invent. Summation is the simplest rule that uses real data without fabricating a rule nothing has defined.
- **`AttackArmorProposal.ArmorRef` uses each contributing piece's own `EquipmentSlotKey` (semicolon-joined when more than one contributes), and the proposal itself reflects only the FIRST target (in `AttackIntent.TargetIds` order) that has any armor at all.** `ArmorDefinition` carries no `ContentDefinitionRef`/identity field of its own (only `EquipmentSlotKey`/`CoveredBodyPartIds`/`Protection`) -- `EquipmentSlotKey` is the closest available identifying string. `AttackArmorProposal`/`AttackRangeResult`/`AttackHitResult` are all single aggregate values on `ProposedAttackResolution` (not per-target, confirmed by direct type inspection before designing anything), so a multi-target intent with different armor per target cannot be fully represented by one `AttackArmorProposal` -- the first-armored-target choice is documented here explicitly as a known simplification of an aggregate-shaped output type, not a silent gap; no required test exercises this specific edge (every armor test in this task's own suite uses one target), so it did not need a stronger resolution.
- **`Range`/`Hit` are single aggregate values for the whole resolution: a miss for the WHOLE attack if ANY target is out of range, even though in-range targets still receive real, independently-computed damage in `DamageDeltas`.** This governing ТЗ's own §3.5 point 2 explicitly named this exact conservative resolution for the aggregate-shape mismatch (`AttackRangeResult` has no per-target list). Confirmed safe by direct inspection: `AttackApplyService`/`SqliteAttackApplyRepository` never read `Hit`/`Range` at all -- only `DamageDeltas`/`CostDeltas`/`EffectCandidates` are ever applied -- so this aggregate simplification has no functional effect on what damage actually lands; it only affects the informational `Hit`/`Range` fields a future UI might display.
- **`Hit.IsHit` is defined as exactly `Range.IsInRange` for this MVP version (governing ТЗ §3.1), explicitly documented as temporary, not a permanent design choice.** No separate to-hit mechanic (an attacker/defender contest, an armor-vs-hit roll) exists anywhere in this codebase yet; inventing one would be deciding an unspecified Ruleset mechanic outside this task's own authority. Range is the only real, currently-computable cause of a miss.
- **`"health"` is hardcoded as the MVP damage resource kind, since `WeaponDefinition` carries no resource-kind field of its own and no other convention exists.** `"health"` is this codebase's own already-established test-fixture convention (e.g. `ODY-S05-609`'s own `AttackAggregateDeltaCommitTests.cs`), reused rather than invented; `CostDeltas` is left empty entirely, since `WeaponDefinition.ActionCost`'s own consumption as a resource delta has no established resource-kind convention either, and this governing ТЗ's own §3.5 computation order never mentions it.
