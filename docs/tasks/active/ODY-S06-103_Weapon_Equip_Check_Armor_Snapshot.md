# ODY-S06-103 — Weapon Equip-Status Check + Armor Wiring Into Attack Snapshot

## 1. Task identity
`ODY-S06-103`; status: In Review (Draft PR, see the backlog row for the link once opened). Third task of `SLICE-06`, second of the block-A data-wiring sequence `ODY-S06-102` reordered.

## 2. Goal
Close two of the three remaining data gaps `ODY-S06-105` (the real `IAttackRulesEvaluator`) will need: (1) an action weapon that is merely owned but not currently `Equipped` must no longer be usable in an attack -- a deliberate, disclosed behavior change, not an oversight; (2) each target's own currently-equipped armor must reach the attack snapshot as a real, decoded `ArmorDefinition`, not a structurally-data-incapable placeholder. This task supplies data and a gate; it does not implement the evaluator or decide which armor a real hit consults.

## 3. Authority
`ODY-S06-102`'s own restructured `SLICE-06_IMPLEMENTATION_BACKLOG.md` row `103` (this task, "Equip Status + Armor Wiring Into Attack State", formerly roadmap block B). `ADR-030` §5 point 2/3 ("resolving any attribute-reference term against `AttackEvaluationSnapshot.Actor`'s own already-loaded attribute state"; naming armor as one of the real evaluator's own future inputs). `TC-ATTACK-025`'s own existing proof that `AttackUnavailableInput`'s constructor structurally rejects any `Availability` but `UnavailableNotBound` -- the direct, code-verified reason `ArmorAndEffects`'s own field type had to change, not merely be populated.

## 4. In scope
`Packages/com.odyssey.persistence/Runtime/Sqlite/SqliteAttackStateReader.cs` -- a new equip-status gate on the action weapon (`GetEquippedEntry` + `InventoryId` cross-check, generic `Rejected(correlationId)` on failure, consistent with every other precondition this method already checks); a new `ReadArmor` step that aggregates every target's own real, decoded armor into the snapshot. `Packages/com.odyssey.domain/Runtime/Combat/AttackPipelineContracts.cs` -- new `AttackArmorAvailability` enum, `AttackTargetArmorEntry` struct, `AttackArmorInput` class (replacing `AttackEvaluationSnapshot.ArmorAndEffects`'s own former `AttackUnavailableInput` typing). `Packages/com.odyssey.application/Runtime/Persistence/InventoryRepositoryContracts.cs` -- new `IInventoryRepository.ListEquippedEntriesByCharacter` method. `Packages/com.odyssey.persistence/Runtime/Sqlite/SqliteInventoryRepository.cs` -- its implementation, by the same join `HasAnyEquippedEntryReferencingBodyPart` already proves is possible against this schema. Existing test fixtures that construct `AttackParticipantState`/`AttackEvaluationSnapshot`/an attack action item directly, mechanically updated to compile and to keep equipping the weapons they need equipped. New tests `TC-ATTACK-105`-`110`. `Tests/Metadata/test-catalog.json`. `docs/tasks/SLICE-06_IMPLEMENTATION_BACKLOG.md` (row `103` to `In Review`).

## 5. Out of scope
The real `IAttackRulesEvaluator`/formula-grammar implementation, and any decision about WHICH of a target's several equipped armor pieces a real hit actually consults -- both `ODY-S06-105`'s own job; this task supplies the raw, decoded list only. `ActivateAbility` (`ODY-S06-106`). `Topology` (the sibling `AttackUnavailableInput` field) -- deliberately untouched, `ODY-S06-104`'s own territory; its type/shape needs are not assumed to match armor's. `IAttackRulesEvaluator`'s own interface signature. `EquipmentService.cs`/`ItemEffectLifecycleService.cs`'s own logic -- called/read, never rewritten. `ADR-030` and earlier ADRs (referenced, not revised). `RulesetDefinitionCatalog`/`SLICE-05_IMPLEMENTATION_BACKLOG.md` (untouched).

## 6. Domain contract
`Packages/com.odyssey.domain/Runtime/Combat/AttackPipelineContracts.cs` gains three new types and retypes one existing field: `AttackArmorAvailability` (`Available`/`UnavailableNotBound`, mirroring `AttackInputAvailability`'s own two-value shape but kept a separate enum, since the two types are not interchangeable); `AttackTargetArmorEntry` (`CharacterId TargetId`, `ArmorDefinition Armor`, one struct per equipped armor piece a target currently has -- a target may appear more than once); `AttackArmorInput` (a sealed class with two static factories, `Unavailable(reason)` preserving the exact prior "not bound" semantics for when no target has any armor, and `Available(entries)` requiring at least one entry). `AttackEvaluationSnapshot.ArmorAndEffects`'s own type changes from `AttackUnavailableInput` to `AttackArmorInput`; its constructor now null-checks the new parameter. No other Domain type changes; `ArmorDefinition` (`Odyssey.Domain.Content`, `ODY-S05-105`) is reused verbatim, zero new fields.

## 7. Application contract
`IInventoryRepository` gains one new method, `ListEquippedEntriesByCharacter(CampaignHandle, CampaignId, CharacterId, CorrelationId) -> Result<IReadOnlyList<EquippedEntryRecord>>` -- narrow, additive, schema-compatible (no migration), returning real rows rather than the existing boolean-only `HasAnyEquippedEntryReferencingBodyPart`'s own existence check. No change to `EquipmentService`/`ItemEffectLifecycleService`'s own public surface; `SqliteAttackStateReader` calls `TypedDefinitionCodec.DecodeArmor` exactly as `ItemEffectLifecycleService.DecodeItem` already does for the identical purpose, by direct reference to the same static codec, not a new decode path.

## 8. Persistence boundary
`SqliteInventoryRepository.ListEquippedEntriesByCharacter` runs one `UNION ALL` SQL query -- `EquippedEntry` joined to `ItemInstance` (owned rows) unioned with `EquippedEntry` joined to `ItemStack` (owned rows), both filtered by `CampaignId`/`OwnerKind`/`OwnerTargetRef` -- reusing the exact join `HasAnyEquippedEntryReferencingBodyPart` already established, just returning full rows instead of a boolean. No new table, no migration. `SqliteAttackStateReader.Read`'s new equip-status gate is a plain `GetEquippedEntry` read (already-existing method, unmodified) plus an in-memory `InventoryId` equality check -- no new query.

## 18. Change control

### Decisions made during execution

- **`AttackEvaluationSnapshot.ArmorAndEffects` needed a genuinely new type, not a populated `AttackUnavailableInput`.** `TC-ATTACK-025` was read before designing anything: `AttackUnavailableInput`'s own constructor throws for any `Availability` value except `UnavailableNotBound`, a real, code-verified, structural block, not a convention that could simply be relaxed. `AttackArmorInput` was designed as a small closed union (two static factories) rather than widening `AttackUnavailableInput` itself, since the latter is also used by `Topology` (`104`'s own territory, deliberately not touched or reshaped here) and by other call sites this task has no authority to change the meaning of.
- **`AttackArmorInput.Available` aggregates ALL of a target's equipped armor pieces (a target may appear more than once in `Entries`), rather than picking "the" armor.** The governing ТЗ was explicit that hit-location-based selection is `ODY-S06-105`'s own job -- `ODY-S06-105`'s own evaluator does not yet exist and the MVP scope treats hit/body-part as unconditional, so there is no location information this task could use to choose even if it wanted to. Passing the raw, complete list is the only choice that does not silently discard real data a future task will need.
- **`Available`/`Unavailable` decision is made once per intent (aggregated across all targets), not once per target.** The governing ТЗ's own §2 point 4 explicitly rejected per-target-selection logic as premature; an aggregate view (empty across every target = `Unavailable`; any real entry anywhere = `Available`, carrying only the real entries) was judged the simplest design that satisfies every one of the six required test scenarios (including the mixed-targets case) without inventing a per-target sub-structure the governing ТЗ never asked for.
- **`ListEquippedEntriesByCharacter` was added as a narrow, single-purpose method returning real rows, not a broader "inventory by character" query surface.** The governing ТЗ's own §2.2 explicitly required this scope discipline, citing `HasAnyEquippedEntryReferencingBodyPart`'s own already-proven-possible join as the direct precedent to reuse (verbatim `CampaignId`/`OwnerKind`/`OwnerTargetRef` filter, `UNION ALL` across `ItemInstance` and `ItemStack`) rather than inventing a different join shape.
- **The weapon equip-status gate reuses the exact generic `Rejected(correlationId)` failure every other `SqliteAttackStateReader.Read` precondition already returns, not a new, more specific error.** The governing ТЗ's own §1 explicitly named this as the required consistency choice, and no existing caller of `Read`/`PreviewAttack`/`EvaluateAttack` branches on which specific precondition failed (confirmed by reading `AttackEvaluationService.AuthorizeAndRead`'s own callers) -- introducing a new, more specific error here would create an asymmetry with every sibling check in the same method for no consumer that needs it.
- **Every pre-existing test file's own `ItemFor` fixture helper was updated to equip the item it creates, rather than leaving `ItemFor` unequipped and inserting a separate `Equip(...)` call at each of the ~40 call sites across 7 files.** All but one of those call sites (`SqliteAttackStateReaderTests.cs`'s own `Fingerprint_changes_when_...` test, which also needed the item to be `Move`-able) wanted the still-legitimate owned-and-equipped path; centralizing the fix in the shared helper was simpler and less error-prone than auditing every call site individually, and the one file whose helper needed a raw, deliberately-unequipped variant (`SqliteAttackStateReaderTests.cs`, for `TC-ATTACK-105` and the fixture Fingerprint fix) got a separate `CreateContainedItem`/`Requip` helper instead of overloading `ItemFor` itself with a boolean flag.
- **The `Fingerprint_changes_when_...` test's item-revision-bump step was changed from a Contained-container `Move` to an unequip/re-equip cycle.** `Move` requires its source to be `Contained` (confirmed by reading `MoveItem<T>`'s own precondition), which is now incompatible with this task's own equip-status gate requiring the action item to stay `Equipped` for the read to keep succeeding. Unequip-then-re-equip produces the same net effect the original test needed to prove (`ItemInstanceRecord.Revision` increases without changing owner or mechanics snapshot) while leaving the item `Equipped` again at the end -- a mechanical fixture repair in response to this task's own governing behavior change, not a weakening of what the test proves.
