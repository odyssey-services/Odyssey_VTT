## 18. Change control

### Decisions made during execution

- **Blocks E and F were combined into one task, per the product owner's own explicit decision recorded in this task's own governing ТЗ §0 -- confirmed by direct repository read before starting that no prior task anywhere in this codebase authors content in one test file for a DIFFERENT test file to consume.** Every prior `ODY-S06-10x` integration test file (`102`-`107`) authors its OWN fixture content, one-shot, inside its own test class -- there is no existing "shared reusable catalog fixture" pattern to follow, and this task does not invent one merely to formally satisfy "block E, then block F" as two separate artifacts. One test file authors real content AND proves the real scenario against it, in the same run.
- **The optional second test named in this task's own governing ТЗ §5 item 2 (a standalone out-of-range-before-movement variant) was deliberately not written**, mirroring `107`'s own governing ТЗ's identical "obligatory minimum only" discretion clause. The required single scenario's own attack #2 already proves the exact same fact directly and non-decoratively: the defender is IN range for attack #1 (distance 3, weapon range 5, real damage lands) and OUT of range for attack #2 after a real `BoardMovementService.MoveToken` call (distance 10), with the miss and the zero damage deltas both asserted exactly. A separate standalone test proving only the mirror-image half of the same fact was judged to add file-and-fixture volume without adding proof value, exactly the same tradeoff `107`'s own governing ТЗ explicitly permitted skipping.
- **`AmmoRequirement.None` was chosen for the weapon, per this task's own governing ТЗ §1 item 2's own explicit simplification instruction ("ammo вне объёма MVP")** -- confirmed by direct `WeaponDefinition` constructor read that `AmmoRequirement.None` requires `CompatibleAmmoKeys` to be empty, which this task's weapon fixture already satisfies without any further change.
- **The ability's own `AdjustResource` primitive was made self-inflicted (`-3` Health on the acting character) rather than target-inflicted, mirroring `TC-ABILITY-001`'s own established precedent for the identical reason: a resource cannot exceed its own `EffectiveMaximum`, and every character in this scenario starts every resource at the hard-fixed 10-point maximum (`ResourceInitializationRules`'s own `InitializeCharacterResource` default, confirmed empirically by every prior `ODY-S06-10x` integration test's own immediate post-`InitResource` assertion, since no literal `ResourceInitializationRules.DefaultBaseMaximum` named constant exists under `DotNet/` -- confirmed by direct repository grep before relying on the value).** A heal-shaped ability targeting an already-full resource would show no observable effect at all, which would make the ability step decorative rather than a real, numerically meaningful proof point. The self-inflicted debuff is later healed back by the consumable item step, giving both the ability AND the item a real, independently observable numeric effect in sequence (10 -> 7 -> 9), rather than only one of the two mattering.
- **The consumable item's own `Instant` effect heals (`AdjustResource +2` Health) rather than damages, chosen specifically because the ability step immediately before it already reduced the acting character's own Health to 7 -- a heal from 7 to 9 stays safely under the 10-point ceiling, so the item step's own numeric effect is real and observable, not silently clamped.** Confirmed by direct `AdjustResourcePrimitive`/interpreter code read that the formula string carries its own sign (`"-3"` for the ability's self-damage, `"2"` for the item's heal) and is added directly to `CurrentValue`, not implicitly negated -- the same convention `105`/`106`'s own fixtures already established for signed `AdjustResource`/damage formulas.
