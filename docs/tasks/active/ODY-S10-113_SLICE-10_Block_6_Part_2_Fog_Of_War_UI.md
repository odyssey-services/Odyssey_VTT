# ODY-S10-113 — SLICE-10 Block 6 Part 2: Fog of War UI (Permanent Map Memory + Live Token Visibility)

## 1. Task identity
`ODY-S10-113`; status: In Review (Draft PR, merge deferred to the product owner). Block 6 of the `SLICE-10` track, part 2 of several. Block 6 part 1 (`ODY-S10-111`/`112`) was purely client-side; this is the first client task where the client must ask the server "what does specifically this player see" (a viewer-scoped read) -- until now every client read (`ListTokens`/`GetScene`/`ListObstacles`) was unfiltered. Part 3 (cover preview, facing/FOV configuration UI) is a separate, later task -- it needs no new server changes, unlike this one.

## 2. Goal
Render two independent, server-authoritative states on the board for a non-MainGm actor: permanent map memory (a darkening overlay, cut out for every explored region the server knows about) and live token visibility (a token outside the server's current line-of-sight result simply does not render). A registered MainGm sees the board fully, unconditionally, exactly as before this task. `RecordExploration` (Block 4, never previously wired anywhere) is wired into the real token-move paths so the feature is demonstrable at all.

## 3. Authority
This task's governing ТЗ; `PlayerVisibilityService.cs`'s own existing `IsPointExplored`/`ComputeVisibleTokens` self-scoped-or-MainGm authorization shape (reused exactly, not reinvented) for the new `ListExploredReveals`; `BoardToolbarPresenter.cs` as the precedent for a small, focused presenter class; `BoardScreenPresenter.cs`'s own established `Refresh()` full-reconciliation pattern (obstacles/tokens already rebuilt from scratch every call) and `BoardCamera` world/pixel transform.

## 18. Change control

### Decisions made during execution
- **Fog rendering technique**: a single `VisualElement` per board (`BoardFogOfWarPresenter`), redrawn from scratch on every `Refresh()` via `Painter2D`/`generateVisualContent` -- an outer board-sized rectangle plus one circle per reveal, all drawn with the same path winding, filled once with `FillRule.OddEven` so any point covered by exactly one shape (a reveal circle) is left unfilled ("punches a hole"). No prior task in this codebase uses `Painter2D`, so this is an original design decision, not a reuse. Chosen over a tile-grid or per-viewer render texture because it needed no new asset pipeline and matches the "readable approximation, not pixel-perfect" explicit non-goal directly.
- **Fog layer z-order**: added to the board area after `RenderObstacles` but before `RenderTokens`, so a currently server-approved-visible token is never itself obscured by the darkness meant for unexplored terrain/obstacles -- the ТЗ does not say token elements must render above or below the fog, but rendering them above matches every VTT's own convention and avoids a confusing "visible token drawn into pure black" look with no product guidance either way.
- **`RecordExploration` wired into both `TryMoveTokenTo` AND `TryMoveSelectedTokenTo`, not only the former** -- see the disclosed finding below; this is a deviation from a literal reading of the ТЗ's own facts section, done because the alternative (wiring only one of the two real move paths) would leave the feature silently non-functional for whichever path a session happens to use.
- **The mutation test for `RecordExploration`'s best-effort invariant uses a MainGm actor** with a `ITokenVisionRepository` that always fails `GetVisionSettings`, specifically so `ComputeVisibleTokens`/fog rendering (which also depend on the same interface, but are skipped entirely for a MainGm) cannot also fail in the same test run and confound the assertion.
- **Board width/height** used for the fog overlay's own sizing are the same `440`/`440` literals `BuildView` already hard-codes for the board area -- pulled into two new named constants (`BoardWidthPixels`/`BoardHeightPixels`) rather than read from `resolvedStyle` at render time, since EditMode tests do not reliably run a full UI Toolkit layout pass and every other coordinate calculation in this class already treats the board's own pixel size as a known constant, not a measured one.

### Findings (reported, not fixed silently)
- **The ТЗ's own facts section states `TryMoveTokenTo` "is called by both the direct-click-move and drag-end paths."** Recon found this is not accurate against the current code: `TryMoveSelectedTokenTo` (the click-to-move path, invoked from `OnBoardPointerUp`) is a separate method with its own direct `BoardMovementService.MoveToken` call; only the drag-end path (`EndTokenDrag`) actually goes through `TryMoveTokenTo`. `RecordExploration` was wired into both methods rather than only the one the ТЗ names, so map memory is built from either move path, not only from dragging.
- **The ТЗ's §2.4 assumes `ApplyDroppedAsset` has a branch that creates a new token**, to be wired the same way. Recon found no such branch exists: `ApplyDroppedAsset` only ever sets an existing token's portrait (`SetTokenPortrait`) or the scene's background (`SetSceneBackground`) -- it never calls `CreateToken`. Nothing was wired there; this is reported rather than invented.
- No file under `Packages/com.odyssey.domain/**`, `Packages/com.odyssey.persistence/**`, `Packages/com.odyssey.rules/**`, or any `Odyssey.Application` file other than `PlayerVisibilityService.cs`, is in this diff. `IFogOfWarRepository`/`SqliteFogOfWarRepository` are used exactly as they already existed -- no port/implementation change.
- The pre-existing `Odyssey.Tests.Persistence.RecoveryHarness` build-ordering gap (a fresh worktree's `dotnet test` on the whole solution fails two `SqliteSavingPipelineTests` cases until that separate harness `.csproj` is built once first) is unrelated to this task's own files -- noted for the record, not fixed (out of this task's scope).
