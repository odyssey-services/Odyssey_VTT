# ODY-S10-108 — SLICE-10 Block 3: Line-of-Sight Service, Token Facing and Vision Parameters

## 1. Task identity
`ODY-S10-108`; status: In Review (Draft PR, merge deferred to the product owner). Block 3 of the `SLICE-10` track, continuing directly from `ODY-S10-107` (Block 2, obstacle data — merged, not modified here). Written from a clean slate with the `ODY-S10-101` stored-membership authorization pattern already in place; no client-supplied flag ever existed here to migrate away from.

## 2. Goal
Add the pure-domain geometry for line-of-sight (segment intersection with the ADR-020 orientation primitive, a directional field-of-view cone, range) and the Application-layer service and storage for per-token facing/FOV/range parameters, plus the `ComputeLineOfSight` read query composing them against real obstacle data. Persistent per-player fog of war (Block 4), a vision-cone/fog UI (Block 6), and combat cover modifiers (Block 5) are explicitly out of scope.

## 3. Authority
This task's governing ТЗ; `ADR-020` (Board Geometry and Movement Determinism) section 6.2 for the mandatory shared orientation primitive and section 6.3 for the fail-closed collinear/touching rule; `SqliteAttackStateReader`/`CoreAttackRulesEvaluator` (`ODY-S07-*`) for the two-layer pure-domain-function-plus-Application-service pattern; `BoardMovementService.CheckAuthorization` (`ODY-S03-004`) for the owner-or-MainGM authorization shape; `ObstacleAuthoringService.CreateObstacle` (`ODY-S10-107`) for the MainGM-only shape and for the "reads stay open" precedent (`ListObstacles`).

## 4. In scope
- **`SegmentIntersection.cs`** (new, `Odyssey.Domain.Geometry`): `Orientation(...)` — the exact ADR-020 section 6.2 formula, classified Left/Right/Collinear via `abs(cross) < GeometryEpsilonV1 * scaleFactor`. ADR-020 leaves `scaleFactor`'s formula unspecified (a qualitative mandate only); this task defines it as `Math.Max(1.0, |PQ|) * Math.Max(1.0, |PR|)` — the product of the two triangle-edge lengths from `P`, each floored at 1 world unit, so the epsilon scales with the segment's own size instead of only its absolute magnitude. `SegmentsIntersect(...)` — the standard four-orientation-test construction, with the ADR-020 section 6.3 fail-closed rule applied only to the genuinely ambiguous collinear/touching sub-case (an epsilon-tolerant `OnSegment` bounding-box containment check), not to "any Collinear result regardless of distance."
- **`LineOfSight.cs`** (new, `Odyssey.Domain.Geometry`): `HasClearLine(...)` — skips obstacles where `ObstacleGeometry.BlocksVision` is false, checks `SegmentIntersection.SegmentsIntersect` for the rest, naive linear scan (ADR-020 section 7 explicitly does not require `SpatialIndexV1` at this task's scale, ≤200 tokens/scene). `IsWithinFovCone(...)` — Atan2-based bearing, normalized to `[0,360)`, shortest angular difference (handles the 0/360 wraparound correctly), boundary-inclusive comparison against half the FOV angle; `fovAngleDegrees >= 360` is always true. `IsWithinRange(...)` — epsilon-tolerant boundary via `BoardGeometry.GeometryEpsilonV1`. `CanSee(...)` — composes the three, returns `false` (not a throw) on any non-finite scalar input.
- **`TokenVisionRepositoryContracts.cs`** (new, `Odyssey.Application.Persistence`): `ITokenVisionRepository`, `TokenVisionSettingsRecord` (with `DefaultFovAngleDegrees=360.0`/`DefaultViewDistance=100.0` constants — no existing sight/attack-range default precedent was found anywhere in this codebase by grep, so these are a deliberately generous, documented placeholder, not a tuned gameplay value), `TokenVisionFailures`.
- **`TokenVisionService.cs`** (new, `Odyssey.Application.Board`, static class): `SetTokenFacing` — owner-or-MainGM, by exact `BoardMovementService.CheckAuthorization` precedent (the token's own controller may always act; anyone else must be the stored MainGm). `SetTokenVisionParameters` — MainGM-only, by exact `ObstacleAuthoringService.CreateObstacle` precedent. `ComputeLineOfSight` — no authorization at all, by exact `ObstacleAuthoringService.ListObstacles` precedent; reads both tokens via `ISceneRepository`, the observer's vision settings via `ITokenVisionRepository`, the scene's obstacles via `IObstacleRepository`; a typed error if observer and target are not in the same Scene.
- **`SqliteTokenVisionRepository.cs`** (new): a new `TokenVisionSettings` table (`CREATE TABLE IF NOT EXISTS`, unversioned schema — this project has never used `ALTER TABLE`, so vision data is a brand-new table, not new columns on `Token`), routed through `SqliteSavingPipeline`, revision-gated exactly like `SqliteObstacleRepository.ToggleDoorState`.
- One sanctioned point-edit to `SqliteSceneRepository.CreateToken`: seeds a default `TokenVisionSettings` row (`FacingDegrees=0`, `FovAngleDegrees=360`, `ViewDistance=100`) atomically in the same transaction as the `Token` row itself (Path A — see §18 for the reasoning against the ТЗ's alternative, Path B).
- Tests, catalogue `TC-PERSIST-080`–`108`, the `SLICE-10` backlog, this contract and its plan.

## 18. Change control

### Decisions made during execution
- **`scaleFactor` in `Orientation`'s epsilon test** (ADR-020 section 6.2 mandates the classification rule but not this factor's exact formula, describing it only qualitatively) was defined as `Math.Max(1.0, |PQ|) * Math.Max(1.0, |PR|)` — the product of the two triangle-edge lengths from `P`, each floored at 1.0 world unit, so the tolerance scales with the segment sizes involved (a long wall needs a looser absolute tolerance than a short one to classify consistently) while never shrinking below the flat `GeometryEpsilonV1` for near-unit-length inputs. No ADR-020 section 6 contradiction was found; this is a genuinely unspecified parameter, not a deviation from the mandate.
- **`TokenVisionSettings` for a token without a row: Path A (auto-create a default row at `CreateToken` time) was chosen over Path B (lazy creation on first `SetTokenVisionParameters`, with `ComputeLineOfSight` returning a typed "not configured" error for a token lacking one)** — the ТЗ offered both as equally acceptable. Path A was chosen because: (1) it matches this codebase's existing convention that every token field (`ZOrder`, `Scale`, `PortraitAssetId`) is populated from the moment the token exists, not left in a special "not yet configured" state a caller must handle; (2) it avoids introducing a whole new error class every future `ComputeLineOfSight` caller (and, eventually, the Block 6 UI) would have to branch on; (3) `CreateToken`'s own public signature is completely unchanged — the seed row is inserted in the same transaction, atomically, via an internal (same-assembly) call to `SqliteTokenVisionRepository.EnsureTokenVisionSettingsTable`, so no existing call site needed updating and the full pre-existing test suite (192 Unit + 901 Persistence at the time of the edit) passed unchanged with zero test-file modifications.
- **`DefaultFovAngleDegrees=360.0`/`DefaultViewDistance=100.0`**: no existing sight/attack-range default was found anywhere in this codebase (confirmed by grep before choosing these values). `360.0` (omnidirectional) was chosen as the facing-agnostic default so a freshly created token is immediately visible-to/from in every direction until a MainGM deliberately narrows its cone, matching the ТЗ's own description of this as the "temporarily omnidirectional" seed state. `100.0` world units was chosen as a deliberately large, documented placeholder range rather than a tuned gameplay value, exactly as the ТЗ's own Path A description anticipated; both constants are documented on `TokenVisionSettingsRecord` itself with this same reasoning.
- **Six error codes/`ERROR_CODES.md` rows** (`PersistenceTokenVisionNotFound`/`IoFailed`/`RevisionConflict`, `TokenVisionSetFacingDenied`/`SetVisionParametersDenied`/`ObserverAndTargetNotInSameScene`) were added to the shared `ErrorCodes.cs` and `docs/errors/ERROR_CODES.md`, following the exact `ODY-S10-107` precedent and disclosure: every error a feature raises needs a registry entry, and `verify-repository.ps1`'s own registry check independently fails the build otherwise.
- **`ObstacleSegment` (Domain-layer struct in `LineOfSight.cs`) is a plain value type distinct from `ObstacleRecord`** (the Application-layer type from Block 2) — `Odyssey.Domain` cannot depend on `Odyssey.Application` (ADR-001), so `TokenVisionService.ComputeLineOfSight` maps each `ObstacleRecord` to an `ObstacleSegment` before calling `LineOfSight.CanSee`.
- **`LineOfSight.HasClearLine` calls `ObstacleGeometry.BlocksVision`, not a reimplementation** — verified directly in `LineOfSightTests.HasClearLine_OpenDoorBetween_DoesNotBlock`/`HasClearLine_WindowBetween_DoesNotBlock`, which exercise exactly the Kind/IsOpen combinations `ObstacleGeometry.BlocksVision` itself governs.
