# ODY-S05-607 — Compensation and Game Log Projections

## 1. Task identity
`ODY-S05-607`; status: In Review (Draft PR https://github.com/odyssey-services/Odyssey_VTT/pull/151).

## 2. Goal
Implement `ADR-029` §1 rule 7 and §6 stages 14-15: a MainGM-only, reason-coded compensating root command that corrects an already-committed attack's Game Log/`AttackOutcome` bookkeeping (roll summary, audience, mis-logged data) without ever deleting or editing the original rows, plus expansion of the attack Game Log entry's audience from the hardcoded binary `PlayerAndGM` to all current combat-encounter participants + GM, via the already-existing `DiceRollAudienceKind`/`DiceRollVisibilityPolicy`/`GameLogReconnectService` mechanism. Does not anticipate `609`'s resource-delta compensation, does not touch `605`/`606`'s own logic, and does not introduce field-level/partial redaction.

## 3. Authority
`ADR-029` §1 rule 7 (compensation is a separate, authorized compensating root command, never a rollback), §6 stages 14-15, §10 (module boundaries); `ADR-012` §5 (`SqliteSavingPipeline`'s single-transaction commit pipeline, `originalEventId`/`compensationGroupId`/`isCompensating` already carried); `ODY-S04-113`'s `RevertCharacterRulesetMigration` (direct structural precedent, copied not reinvented); `ODY-S03-006`'s `DiceRollVisibilityPolicy`/`ODY-S03-007`'s `GameLogReconnectService` (reused unmodified); `ODY-S05-604`'s `AttackOutcomeRecord`/`SqliteAttackApplyRepository` (extended). Three product-owner-approved scope decisions (recorded verbatim in §18) bound compensation scope, trigger/scenario, and the audience model.

## 4. In scope
A new `CompensateAttackOutcome` repository method/contract (`AttackCompensationRecord`, `IAttackApplyRepository.CompensateAttackOutcome`, `AttackApplyService.CompensateAttackOutcome`); its `SqliteAttackApplyRepository` implementation (MainGM-gate first, mandatory reason code, original-record lookup by `ResolveAttackCommandId`, re-compensation guard, new separate transaction/`CommandId`, new corrective `GameLogEntries`/`DiceRolls` rows, `IsCompensating=true`/`CompensationGroupId`/`originalEventId` wiring); audience expansion in `WriteAcceptedAttackGameLogEntry` (`ComputeEncounterAudience`, reading `CombatEncounterParticipant`/`Character` via raw SQL on the same connection/transaction, `SelectedParticipants` with real encounter-participant owning `UserId`s, `GMOnly` fallback for an all-NPC encounter); three new error codes; tests.

## 5. Out of scope
`609`'s resource-delta compensation (no infrastructure anticipated for it -- product-owner decision 1, §18). Any compensation scenario narrower than "MainGM corrects an error in an already-accepted attack" (product-owner decision 2, §18). Field-level/partial redaction -- the disclosure model stays all-or-nothing (product-owner decision 3, §18). `605`'s `ActiveEffectExpiryRules.cs`/`CombatEffectExpiryService`, `606`'s effect-application logic (untouched). New methods on `ICombatEncounterRepository`/rewriting `RecordAttackOutcome`/`ResolveAttackIntervention`/`GetOutcome`. Rewriting `DiceRollVisibilityPolicy`/`GameLogReconnectService`/`SqliteGameLogRepository.ListGameLog` (reused as-is). Any event bus/publisher/subscriber. RNG re-roll of any kind (compensation is pure logging/state-bookkeeping correction).

## 6. Domain contract
No Domain-layer changes. Compensation reuses the existing `DiceRollAudienceKind`/`DiceRollAudience` (`Odyssey.Application.Dice`) and `AttackOutcomeRecord`/`AttackOutcomeKind` (`ODY-S05-604`, unmodified) types as-is.

## 7. Application contract
New `AttackCompensationRecord` (`CompensatingCommandId`, `OriginalResolveAttackCommandId`, `ReasonCode`, `CorrectedSummaryPayload`, `GameLogEntryId`, `CreatedAt`) in `AttackApplyRepositoryContracts.cs`. `IAttackApplyRepository` gains `Result<AttackCompensationRecord> CompensateAttackOutcome(CampaignHandle campaign, CommandId resolveAttackCommandId, string reasonCode, string correctedSummaryPayload, UserId actorUserId, bool actorIsMainGm, CommandId commandId, CorrelationId correlationId)`. `AttackApplyService.CompensateAttackOutcome` delegates unchanged (no new orchestration logic in the Application layer, matching `606`'s own precedent of keeping all mechanism in the Persistence layer's own transaction).

## 8. Persistence boundary
`SqliteAttackApplyRepository.CompensateAttackOutcome`: MainGM-gate as the first check (`PersistenceFailures.AttackOutcomeOperationDenied`, existing code, reused); mandatory non-empty `reasonCode`/`correctedSummaryPayload` (`PersistenceAttackOutcomeCompensationReasonRequired`, new); finds the original `AttackOutcomeRecord` by `resolveAttackCommandId` (`PersistenceFailures.AttackOutcomeNotFound`, existing); requires `OutcomeKind == Accepted` with a non-null `GameLogEntryId` (`PersistenceAttackOutcomeNotAccepted`, new); resolves the committing `CommandId` (`ResolvedByCommandId ?? ResolveAttackCommandId`) to its `DomainEvents.EventSequence` and guards against a second compensation of the same committed event (`PersistenceAttackOutcomeAlreadyCompensated`, new); on success, writes a new `DiceRolls` row (reusing the original's own `RandomSampleValue` verbatim -- never re-rolled) and a new `GameLogEntries` row (`EntryType='AttackCompensated'`, `SummaryPayload=correctedSummaryPayload`, audience recomputed via the same `ComputeEncounterAudience` helper) inside a brand-new `SqliteSavingPipeline.Execute` call with its own `CommandId`, `originalEventId` set to the original committing event's sequence, `compensationGroupId` set to the new `CommandId`, `isCompensating: true`. `WriteAcceptedAttackGameLogEntry` (the original `604` write path) now calls the same `ComputeEncounterAudience(connection, transaction, intent.EncounterId)` helper instead of the hardcoded `'PlayerAndGM'`/`'[]'` literals -- reading `CombatEncounterParticipant` joined to `Character.PrimaryOwnerUserId`/`CoOwnerUserIdsJson` on the same open connection/transaction, no new repository dependency, no constructor change (avoiding a break to `AttackApplyTests.cs`/`AttackEffectApplicationTests.cs`'s existing `new SqliteAttackApplyRepository(_clock)` call sites).

## 18. Change control

### Decisions made during execution

- **Audience computation reads `CombatEncounterParticipant`/`Character` directly via raw SQL on the same open connection/transaction inside `SqliteAttackApplyRepository`, rather than adding `ICombatEncounterRepository`/`ICharacterRepository` as new constructor dependencies.** The governing ТЗ explicitly forbids new methods on `ICombatEncounterRepository`, and adding either interface as a constructor dependency would have broken the two existing test call sites (`AttackApplyTests.cs`, `AttackEffectApplicationTests.cs`) that construct `new SqliteAttackApplyRepository(_clock)` with only a clock argument. This class's own established idiom is already to read/write other repositories' tables directly via raw SQL on its own connection (e.g. `604`'s own `GameLogEntries`/`DiceRolls` writes without calling `SqliteGameLogRepository`'s public methods) -- this decision extends that same idiom to reading `Character`/`CombatEncounterParticipant`, not a new architectural pattern.
- **The audience is computed as `DiceRollAudienceKind.SelectedParticipants` with the real list of encounter-participant owning `UserId`s (via `Character.PrimaryOwnerUserId`/`CoOwnerUserIdsJson`), falling back to `GMOnly` when that list is empty (an all-NPC encounter).** `DiceRollAudience.SelectedParticipants` throws `ArgumentException` if both its user-id and group-id lists are empty, so an all-NPC encounter (no player-owned characters at all) cannot use that audience kind. `GMOnly` is the honest, narrowest available audience for that specific edge case, not a silent widening -- MainGM already sees everything unconditionally via the unmodified `DiceRollVisibilityPolicy`, so no information is lost for the only party who could act on an all-NPC attack's log entry. This is a disclosed, deliberately narrow choice for a genuinely edge case, following the same honesty precedent `605`/`606` already set for their own disclosed limitations.
- **`CompensateAttackOutcome` identifies "the event that committed the current Accepted state" as `original.ResolvedByCommandId ?? original.ResolveAttackCommandId`, then looks up that `CommandId`'s own `DomainEvents.EventSequence` to use as `originalEventId` and as the re-compensation guard key.** This covers both commit paths uniformly: the immediate-accept path (where `ResolveAttackCommandId` itself was the committing command) and the intervention-approved path (where `ResolvedByCommandId`, set by `ResolveAttackIntervention`, was the committing command) -- a single, correct rule rather than two branches.
- **The read/projection side (`SqliteGameLogRepository.ListGameLog`, `GameLogReconnectService.GetVisibleEntries`, `DiceRollVisibilityPolicy`) required zero code changes.** Confirmed by direct reading: `ListGameLog` is public, unmodified, and already reads any `GameLogEntries`/`DiceRolls` row for the campaign regardless of which repository physically wrote it (one physical SQLite table); `GetVisibleEntries`/`DiceRollVisibilityPolicy` already fully support `SelectedParticipants` audience with real `UserId` lists. Correctly populating `AudienceKind`/`AudienceSelectedUserIdsJson` at write time in `SqliteAttackApplyRepository` was sufficient for the entire read/projection side to work correctly -- directly satisfying the governing ТЗ's own "reuse, don't rewrite" requirement (section 2.3) with literally zero lines changed in those three components.
- **No field-level/partial redaction was introduced.** The disclosure model remains all-or-nothing per the existing `DiceRollVisibilityPolicy` (product-owner decision 3, recorded in the original ТЗ) -- `SelectedParticipants` widens WHO is on the list, it does not introduce any new mechanism for filtering WHICH FIELDS a given viewer on that list sees. Verified directly: no new conditional field-masking logic was added anywhere in this task's changes.
- **Compensation scope is strictly Game Log/`AttackOutcome` bookkeeping -- no infrastructure was added or anticipated for `609`'s future resource-delta compensation** (product-owner decision 1). Verified by the architecture guard test (`TC-ATTACK-063`): the `CompensateAttackOutcome` method body contains no reference to `ICharacterRepository`, `SetResourceCurrentValue`, `IInventoryRepository`, or `AttackDelta`.
- **The compensation trigger is general-purpose ("MainGM corrects an error in an already-accepted attack"), not tied to a single narrow scenario** (product-owner decision 2) -- mirroring `RevertCharacterRulesetMigration`'s own general-purpose, mandatory-reason-code shape rather than inventing a narrower, single-purpose command.
