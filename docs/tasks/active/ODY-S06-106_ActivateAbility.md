# ODY-S06-106 — `ActivateAbility` Root Command (Mechanics-Primitive Interpreter, First Implementation)

## 1. Task identity
`ODY-S06-106`; status: In Review (branch `feat/ody-s06-106-activate-ability`, Draft PR to be opened, merge left to the product owner). Sixth task of `SLICE-06`, the first real command mutating character state through `ADR-030` §7's mechanics-primitive schema.

## 2. Goal
Build `ActivateAbility`, a standalone root command letting a character with an activatable `CharacterAbility` spend its resource cost, interpret its `AbilityDefinition.MechanicsPayloadRef` through a real, first-ever `MechanicsPrimitiveEnvelope`/`MechanicsPrimitiveInterpreter` (`ADR-030` §7), and apply the resulting `AdjustResource`/`ApplyEffect` outcomes atomically -- independent of any `CombatEncounter` (`ADR-030` §9.3).

## 3. Authority
`ODY-S06-105`'s own restructured `SLICE-06_IMPLEMENTATION_BACKLOG.md` row `106`. `ADR-030` §7 (mechanics-primitive schema, not yet implemented by any prior task -- independently confirmed by reading `105`'s own delivered code, which implements only the weapon damage formula grammar, not `AdjustResource`/`ApplyEffect`), §9 (`ActivateAbility` architecture, standalone root command, no turn/round binding). Product-owner priority: "ability activation should work like everything else" (this task's own governing ТЗ §0).

## 4. In scope
`Packages/com.odyssey.domain/Runtime/Content/MechanicsPrimitives.cs` (new) -- `MechanicsPrimitiveEnvelope`/`MechanicsPrimitive`/`AdjustResourcePrimitive`/`ApplyEffectPrimitive`, exactly two primitives. `Packages/com.odyssey.application/Runtime/Content/MechanicsPayloadCodec.cs` (new) -- `EncodePrimitives`/`DecodePrimitives`, versioned independently of `TypedDefinitionCodec`. `Packages/com.odyssey.rules/Runtime/Mechanics/MechanicsPrimitiveInterpreter.cs` (new) -- pure interpreter, reusing `AttackDamageFormulaParser`/`AttackRandomSample` by reference. `Packages/com.odyssey.application/Runtime/Persistence/ActivateAbilityContracts.cs` (new) -- `IActivateAbilityStateReader`, `IActivateAbilityRepository`, request/state/record types. `Packages/com.odyssey.application/Runtime/Persistence/ActivateAbilityService.cs` (new) -- the orchestrator. `Packages/com.odyssey.persistence/Runtime/Sqlite/SqliteActivateAbilityStateReader.cs` (new). `Packages/com.odyssey.persistence/Runtime/Sqlite/SqliteActivateAbilityRepository.cs` (new). `Packages/com.odyssey.persistence/Runtime/Sqlite/SqliteAttackApplyRepository.cs` -- visibility-only change (`ApplyAttackDelta`: `private static` -> `internal static`, logic unchanged) for cross-repository reuse. New tests `TC-ABILITY-001`-`009`. `Tests/Metadata/test-catalog.json`. `docs/tasks/SLICE-06_IMPLEMENTATION_BACKLOG.md` (row `106` to `In Review`, interpreter-ownership record).

## 5. Out of scope
Combat-turn-consuming ability activation (`ADR-030` §9.3's own disclosed non-goal -- no `CombatEncounter`/`CombatParticipant`/turn/round/action-slot check anywhere in this task's own code). Item use (`ItemEffectLifecycleService`'s `Instant`-skip, block D -- untouched). `IAttackRulesEvaluator`/`CoreAttackRulesEvaluator`/`AttackDamageFormulaParser` signature or logic changes (read/reuse by reference only). `AcquireAbility`/`AcquireAbilityViaProgressionPurchase` logic changes (read as precedent only). `ADR-030` and earlier ADRs (not revised, including their own stale internal task-number references). `RngContracts.cs` (this task's own finding: `RngPurpose` is a freeform validated string, not a registry -- no edit needed; the new roll purpose is a local constant, exactly mirroring `AttackEvaluationService`'s own `CombatRollPurpose` pattern). A new targeting vocabulary beyond `ContentTargetRule`'s own existing fields. Full atomicity between the resource-delta transaction and `ApplyEffect`'s own `CreateActiveEffect` calls (a disclosed, documented limitation -- see §18).

## 6. Domain contract
`MechanicsPrimitives.cs` (`Odyssey.Domain.Content`): `MechanicsPrimitiveEnvelope` (`int SchemaVersion`, `IReadOnlyList<MechanicsPrimitive> Primitives`, defensively copied), abstract `MechanicsPrimitive`, `AdjustResourcePrimitive` (`ResourceDefinitionId ResourceKind`, `string AmountFormula`, ctor-validated non-empty formula), `ApplyEffectPrimitive` (`ContentDefinitionRef EffectDefinitionRef`). Placed in `Odyssey.Domain` (not `Odyssey.Application`/`Odyssey.Rules`) since both the decode layer (`Odyssey.Application`) and the interpretation layer (`Odyssey.Rules`) need it, and `Odyssey.Rules` cannot reference `Odyssey.Application` (the same layering barrier `105` already confirmed structurally). No change to any pre-existing Domain type except the `SqliteAttackApplyRepository` visibility change (Persistence layer, not Domain).

## 7. Application contract
`MechanicsPayloadCodec.DecodePrimitives(string payloadJson, CorrelationId) -> Result<MechanicsPrimitiveEnvelope>` -- schema-version-gated (mirrors `TypedDefinitionCodec.RequireSupportedSchemaVersion`), per-primitive-kind switch, exception-safe (honest `Result` rejection on malformed JSON or an unsupported version, never a crash). `ActivateAbilityContracts.cs`: `ActivateAbilityIntent` (`ActorId`, `CharacterAbilityId`, `TargetIds`, ctor-validated, deliberately not scene/encounter-scoped), `ActivateAbilityState` (`Actor: CharacterRecord`, `Ability: CharacterAbility`, `Definition: AbilityDefinition`, `Primitives: MechanicsPrimitiveEnvelope`), `ActivateAbilityRequest` (mirrors `AttackRequest`'s own shape: intent + `CommandId`/`CorrelationId`/actor identity/expected revisions), `AbilityActivationRecord` (durable outcome: deltas applied, effect refs applied, timestamp). `ActivateAbilityService.ActivateAbility` orchestrates: idempotency check (`apply.GetActivation`) before any other step -- a replay short-circuits before authorization, state read, or RNG draw; `Authorize` (actor controls the character, or MainGM -- `ADR-019`, unchanged); `reader.Read` (state + decoded primitives); `ValidateTargets` (the first real `ContentTargetRule` runtime check in this codebase -- count within `[MinimumCount, MaximumCount]`, self-targeting gated by `AllowSelf`); `RequiresDice` (genuinely parses each `AdjustResourcePrimitive`'s formula via `AttackDamageFormulaParser.Parse`, checking for an `AttackFormulaTermKind.DiceGroup` term -- not merely primitive-type presence); conditional RNG draw (up to 4 values, mirroring `AttackEvaluationService.EvaluateAttack`'s own pattern, via `IAuthoritativeRandomStreamFactory`/`RandomDecisionContext`, purpose `RngPurpose.Parse("ability.activation.roll")`, a local constant); `MechanicsPrimitiveInterpreter.Interpret`; build a combined `AttackDelta` list (ability cost as a negative delta on the actor + each resolved `AdjustResource` amount applied to every target, evaluated once, not per-target -- a documented MVP decision); `apply.RecordAbilityActivation` (atomic); on success, sequential `ApplyEffect` calls (`catalog.GetContentDefinition` -> validate Version/Status/DefinitionType -> `TypedDefinitionCodec.DecodeEffect` -> `effects.CreateActiveEffect`), each keyed by a deterministic SHA256-derived sub-`CommandId` per effect x target (mirrors `ItemEffectLifecycleService.StableId`).

## 8. Persistence boundary
`SqliteActivateAbilityStateReader` (Persistence layer, can reference `Odyssey.Application`) performs ALL decoding -- both `AbilityDefinition` (via `TypedDefinitionCodec.DecodeAbility`) and `MechanicsPrimitiveEnvelope` (via `MechanicsPayloadCodec.DecodePrimitives`) -- before constructing `ActivateAbilityState`, so `MechanicsPrimitiveInterpreter` (Rules layer) never touches either codec, exactly mirroring `105`'s own resolution of the identical Rules/Application conflict for weapon decoding. Resolves `AbilityDefinitionId -> AbilityDefinition` through `CharacterAbility.SourceRef` (reused additively to carry a serialized `ContentDefinitionRef`), since `AbilityDefinitionId` (`ODY-S04-108`) is a fixture-only Ruleset key with no real backing catalog table anywhere (a genuine architecture gap this task found and resolved -- see §18). `SqliteActivateAbilityRepository` owns a new, standalone `AbilityActivation` table (mirrors `SqliteAttackApplyRepository`'s own standalone-table idiom for a root-command apply pipeline). Every resource-delta write commits through the existing, unmodified `SqliteSavingPipeline`/`PipelineWrite<T>` (`ADR-012` §5) -- the durable `AbilityActivation` row, the DomainEvent, and the AppliedCommands idempotency row land in one SQLite transaction, or none of them do. Reuses `SqliteAttackApplyRepository.ApplyAttackDelta` verbatim (visibility changed to `internal`, logic unchanged) for every resource delta, so insufficient balance for ANY delta rolls back the WHOLE transaction. `ApplyEffect` primitives are NOT part of this transaction -- `IActiveEffectRepository.CreateActiveEffect` manages its own separate connection/transaction internally and cannot be composed in without modifying that repository (forbidden) -- a disclosed limitation, not a silent gap (see §18).

## 9. Tests and validation
`TC-ABILITY-001`-`009` (`DotNet/Tests/Odyssey.Tests.Persistence/ActivateAbilityIntegrationTests.cs` for 001-008, `DotNet/Tests/Odyssey.Tests.Architecture/MechanicsInterpreterScopeTests.cs` for 009), every functional test a real call through `ActivateAbilityService` against a real temp-directory SQLite campaign: (001) constant-formula activation -- exact cost charge and `AdjustResource` application, verified via exact before/after `CharacterResource.CurrentValue`, and a `ThrowingRandomFactory` proves no RNG stream is ever derived; (002) dice-and-attribute formula ("-1d6-Strength") against a fixed RNG stream -- exact resulting value; (003) an `ApplyEffectPrimitive` -- a real `ActiveEffectRecord` is created via the existing, unmodified `IActiveEffectRepository.CreateActiveEffect`; (004) insufficient resource for cost -- the whole command rejected, nothing applied (exact unchanged values for every resource); (005) an actor who neither controls the character nor is MainGM -- rejected by authorization; (006) a repeated call with the same `CommandId` -- idempotent, no second charge, no second RNG derivation (`CountingRandomFactory.CreateCalls` stays 1); (007) an incompatible `MechanicsPayloadRef` schema version -- honest `Result` failure, not a crash; (008) no open `CombatEncounter` anywhere in the campaign -- activation succeeds identically, confirming `ADR-030` §9.3's own independence; (009) `Odyssey.Rules.Mechanics` (this task's own new interpreter folder) never references RNG types or `Odyssey.Application` types directly, scoped to this task's own new code (not the whole `Odyssey.Rules.Runtime` tree, to avoid a false positive against `105`'s own pre-existing, legitimate doc-comment mention of `Odyssey.Application`/`TypedDefinitionCodec` inside the forbidden-to-touch `CoreAttackRulesEvaluator.cs`). ## 10. Compatibility and rollback
No pre-existing public interface changes except `SqliteAttackApplyRepository.ApplyAttackDelta`'s own visibility (`private static` -> `internal static`, logic unchanged -- verified by re-running `105`'s own attack test suite unmodified and green). No schema change to any pre-existing table; `AbilityActivation` is a new, standalone table. `AcquireAbility`/`AcquireAbilityViaProgressionPurchase` are untouched -- an ability acquired without a `SourceRef` carrying a parseable `ContentDefinitionRef` (e.g. legacy `GMGrant` calls with `sourceRef: null`) simply cannot be activated, an honest `Rejected` result, not a crash, and existing callers of `AcquireAbility` keep compiling and behaving identically. Reverting this task's source returns to the pre-`106` state: no `ActivateAbility` command exists, `MechanicsPrimitiveEnvelope`/`MechanicsPayloadCodec`/`MechanicsPrimitiveInterpreter` cease to exist, and no later task has yet been built against them (this is the first task to add them).

## 13. Performance
`MechanicsPrimitiveInterpreter` performs zero I/O -- pure in-memory computation over already-decoded primitives and already-loaded attributes. The RNG draw (when needed) is up to 4 calls against an already-open `IAuthoritativeRandomStream`, mirroring `105`'s own cap. `ApplyEffect` primitives (when present) add one sequential `CreateActiveEffect` call per effect x target -- acceptable given `AbilityDefinition.MechanicsPayloadRef` is expected to carry a small number of primitives per ability.

## 18. Change control

### Decisions made during execution

- **`AbilityDefinitionId` (`ODY-S04-108`) has NO real backing catalog table anywhere -- confirmed by direct doc-comment read (`ContentCatalog.cs`'s own comment explicitly distinguishes itself from `AbilityDefinitionId`'s "fixture-only Ruleset key") and by enumerating every `IContentCatalogRepository` lookup method (only `GetContentDefinition(campaign, ContentDefinitionId, ...)` exists -- no lookup-by-name/human-key method at all).** This is a genuine architecture gap this task found, not assumed from the governing ТЗ. Resolved by reusing `CharacterAbility.SourceRef` (an already-existing, generic `string?` provenance field) to additionally carry a serialized `ContentDefinitionRef` when an ability is meant to be activatable -- a pure usage-convention extension, zero schema/type change, zero modification of the forbidden `AcquireAbility` method. An ability acquired without this convention (e.g. a legacy `GMGrant` call with `sourceRef: null`) simply cannot be activated -- an honest `Rejected` result, not a crash.
- **`MechanicsPrimitiveInterpreter` (Rules layer) never calls `TypedDefinitionCodec`/`MechanicsPayloadCodec` directly -- confirmed the same Rules/Application layering barrier `105` already confirmed structurally (`Odyssey.Rules.asmdef`: `references: ["Odyssey.Domain"]` only) still holds, unchanged by this task.** Resolved identically to `105`'s own resolution for `CoreAttackRulesEvaluator`/weapon decoding: `SqliteActivateAbilityStateReader` (Persistence layer, can reference Application) performs ALL decoding -- both `AbilityDefinition` and `MechanicsPrimitiveEnvelope` -- before constructing `ActivateAbilityState`, so the interpreter only ever receives already-decoded Domain objects.
- **`IActiveEffectRepository.CreateActiveEffect` cannot join `SqliteActivateAbilityRepository`'s own atomic resource-delta transaction -- confirmed by direct interface read: it takes a fully-constructed `ActiveEffectRecord` with no `connection`/`transaction` parameters, meaning it manages its own separate connection internally.** Composing it into the same transaction would require modifying that repository, forbidden by this task's own governing ТЗ. Resolved by matching this codebase's own already-established precedent (`ItemEffectLifecycleService`'s own class doc comment: "sequential repository operations, not an atomic... command") -- the resource-delta transaction (ability cost + `AdjustResource` primitives) is genuinely atomic on its own; `ApplyEffect` primitives are then applied via sequential, individually-idempotent calls (deterministic sub-`CommandId` per effect x target, mirroring `ItemEffectLifecycleService.StableId`'s own pattern) to the existing, unmodified `CreateActiveEffect`. This is a disclosed, documented limitation on cross-repository atomicity, not a silent gap.
- **`RngContracts.cs` requires NO edit, contrary to the governing ТЗ's own §6 allowed-path assumption.** Direct code read of `RngPurpose` (`Packages/com.odyssey.application/Runtime/Random/RngContracts.cs`) shows it is a freeform, format-validated string type (`RngText.IsDottedLowerIdentifier`), not an enum/registry -- `CombatRollPurpose` in `AttackEvaluationService` is simply a locally-declared constant, not a central registry entry. `ActivateAbilityService` declares its own local `AbilityActivationRollPurpose = RngPurpose.Parse("ability.activation.roll")`, exactly mirroring that pattern, with zero edit to `RngContracts.cs` itself -- a smaller footprint than anticipated, documented as a finding, not a violation.
- **`RequiresDice` genuinely parses each `AdjustResourcePrimitive`'s own formula via `AttackDamageFormulaParser.Parse`, checking for an `AttackFormulaTermKind.DiceGroup` term, rather than triggering an RNG draw for any `AdjustResourcePrimitive` regardless of its formula's own content.** Found via real test failures during development: an early, cruder implementation (`primitive is AdjustResourcePrimitive` alone) caused 5 of 8 integration tests to fail against a `ThrowingRandomFactory` deliberately used in constant-formula test scenarios to prove no RNG derivation happens when none is needed. The corrected implementation avoids deriving a random stream at all for constant-only formulas, matching `AttackEvaluationService`'s own "don't roll dice you don't need" discipline.
- **`ValidateTargets` is the first real runtime `ContentTargetRule` validator anywhere in this codebase -- confirmed via direct doc-comment read (`CatalogValidationContracts.ValidateAbility`'s own comment: "target rule shape... already ctor-guaranteed... no live registry to check against yet. This is an explicitly recorded MVP boundary").** Deliberately narrow: target count within `[MinimumCount, MaximumCount]`, self-targeting only when `AllowSelf` is true -- no new targeting vocabulary invented, matching this task's own governing ТЗ §2.6's explicit instruction to reuse the existing `ContentTargetRule` shape rather than inventing one.
- **`AdjustResource` deltas are evaluated once per activation, then applied identically to every target in `TargetIds`, not re-evaluated per target.** The governing ТЗ's own §2.5 point 6 describes charging cost and applying `AdjustResource` deltas without specifying per-target re-evaluation, and no dice-per-target precedent exists anywhere in this codebase's own attack pipeline either (`CoreAttackRulesEvaluator` computes one `AttackRandomSample` for the whole resolution, not per target) -- this MVP decision mirrors that existing precedent rather than inventing a new one.
- **The new `AbilityActivation` table is entirely standalone (no foreign key to `AttackOutcome` or any other table), mirroring `SqliteAttackApplyRepository`'s own standalone-table idiom for the identical architectural reason: a root-command apply pipeline, not general Character CRUD.**
