# ODY-S06-106 — `ActivateAbility` Root Command (Mechanics-Primitive Interpreter, First Implementation)

## 1. Task identity
`ODY-S06-106`; status: In Review (Draft PR [#162](https://github.com/odyssey-services/Odyssey_VTT/pull/162), CI green, merge left to the product owner). Sixth task of `SLICE-06`, the first real command mutating character state through `ADR-030` §7's mechanics-primitive schema.

**Доработка (product-owner-ordered, after independent verification of the original PR #162):** three findings were returned for a real fix, not a textual reformulation -- (1) `ApplyEffect`'s own disclosed cross-repository-atomicity gap left the resource-delta commit genuinely unprotected against a downstream effect-application failure; (2) `CharacterAbility.SourceRef` was repurposed as the `AbilityDefinitionId`→`ContentDefinitionRef` activation bridge, violating that field's own documented provenance-only contract; (3) `ActivateAbilityRequest`/`RecordAbilityActivation` carried no expected-revision optimistic-concurrency parameters at all, contradicting both the governing ТЗ and this contract's own (incorrect) §7 claim that `ActivateAbilityRequest` "mirrors `AttackRequest`'s own shape... expected revisions." All three are now genuinely fixed -- see §18's own "Доработка" subsection for the full decision log.

**Вторая доработка (product-owner-ordered, after independent verification of the first доработка commit `32ccef1`):** the first fix's own `CompensateAbilityActivation` reversed resource deltas but never touched already-created `ActiveEffect` rows -- a real, unfixed atomicity gap of the SAME family, surfaced when a `MechanicsPrimitiveEnvelope` carries 2+ `ApplyEffectPrimitive`s (or one with `MaximumCount > 1`) and the failure lands on a later effect/target, not the first. Now genuinely fixed: `CompensateAbilityActivation` removes every already-created `ActiveEffectId` (tracked in-memory by `ActivateAbilityService`'s own loop, passed in) via the existing, unmodified `IActiveEffectRepository.RemoveActiveEffect`, BEFORE reversing resource deltas. See §18's own "Вторая доработка" subsection.

## 2. Goal
Build `ActivateAbility`, a standalone root command letting a character with an activatable `CharacterAbility` spend its resource cost, interpret its `AbilityDefinition.MechanicsPayloadRef` through a real, first-ever `MechanicsPrimitiveEnvelope`/`MechanicsPrimitiveInterpreter` (`ADR-030` §7), and apply the resulting `AdjustResource`/`ApplyEffect` outcomes atomically -- independent of any `CombatEncounter` (`ADR-030` §9.3).

## 8. Persistence boundary
`SqliteActivateAbilityStateReader` (Persistence layer, can reference `Odyssey.Application`) performs ALL decoding -- both `AbilityDefinition` (via `TypedDefinitionCodec.DecodeAbility`) and `MechanicsPrimitiveEnvelope` (via `MechanicsPayloadCodec.DecodePrimitives`) -- before constructing `ActivateAbilityState`, so `MechanicsPrimitiveInterpreter` (Rules layer) never touches either codec, exactly mirroring `105`'s own resolution of the identical Rules/Application conflict for weapon decoding. Resolves `AbilityDefinitionId -> AbilityDefinition` through `CharacterAbility.ActivationDefinitionRef` (**доработка: a genuinely separate, additive field -- NOT `SourceRef`, which the original PR #162 incorrectly repurposed for this**), since `AbilityDefinitionId` (`ODY-S04-108`) is a fixture-only Ruleset key with no real backing catalog table anywhere, and the real catalog's own `ContentDefinition` table has no indexed human-key column either (confirmed by direct schema read during this доработка -- `Name` is a free-text display string, not a unique key; this rules out a real catalog-index-based bridge, option (a), as a bigger change than this fix warrants). `SqliteActivateAbilityRepository` owns a new, standalone `AbilityActivation` table (mirrors `SqliteAttackApplyRepository`'s own standalone-table idiom for a root-command apply pipeline), now with an additive `CompensatedAt TEXT` column. Every resource-delta write commits through the existing, unmodified `SqliteSavingPipeline`/`PipelineWrite<T>` (`ADR-012` §5) -- the durable `AbilityActivation` row, the DomainEvent, and the AppliedCommands idempotency row land in one SQLite transaction, or none of them do. `RecordAbilityActivation`'s own transaction ALSO re-checks `expectedCharacterAbilitiesRevision`/`expectedCharacterResourcesRevision` fresh (**доработка**, `ADR-022` §5 rule 2) before applying anything. Reuses `SqliteAttackApplyRepository.ApplyAttackDelta` verbatim (visibility changed to `internal`, logic unchanged) for every resource delta, so insufficient balance for ANY delta rolls back the WHOLE transaction. `ApplyEffect` primitives are NOT part of `RecordAbilityActivation`'s own transaction -- `IActiveEffectRepository.CreateActiveEffect` manages its own separate connection/transaction internally and cannot be composed in without modifying that repository (forbidden). **Доработка: this is no longer left as a disclosed, unfixed limitation -- `CompensateAbilityActivation` (a new, additive `IActivateAbilityRepository` method) genuinely reverses `RecordAbilityActivation`'s own already-committed deltas, atomically, in one new transaction, when a downstream `ApplyEffect` fails, and is itself idempotent via the durable row's own `CompensatedAt` column.**

**Вторая доработка:** `CompensateAbilityActivation` FIRST removes every already-created `ActiveEffectId` (via the existing, unmodified `IActiveEffectRepository.RemoveActiveEffect`, `actorIsMainGm: true` -- an internal system rollback of the caller's own failed attempt, not a new capability granted to them, mirroring `ApplyCharacterResourceDelta`'s own established precedent of bypassing a public command's own user-facing authorization for an internal write), THEN reverses resource deltas and marks `CompensatedAt`, exactly as before. Each removal uses its own deterministic sub-`CommandId` (`StableEffectRemovalCommandId`, a DIFFERENT hash input than the creation-time `StableSubCommandId`, so `RemoveActiveEffect`'s own idempotency-ledger entry can never collide with `CreateActiveEffect`'s own -- a collision would make `SqliteSavingPipeline` treat the removal as a replay of the CREATE command and silently no-op). If any single removal fails, the whole compensation attempt returns that failure immediately, without touching resources or `CompensatedAt` -- safe to retry later, since every removal already attempted is itself idempotent.

- **`RequiresDice` genuinely parses each `AdjustResourcePrimitive`'s own formula via `AttackDamageFormulaParser.Parse`, checking for an `AttackFormulaTermKind.DiceGroup` term, rather than triggering an RNG draw for any `AdjustResourcePrimitive` regardless of its formula's own content.** Found via real test failures during development: an early, cruder implementation (`primitive is AdjustResourcePrimitive` alone) caused 5 of 8 integration tests to fail against a `ThrowingRandomFactory` deliberately used in constant-formula test scenarios to prove no RNG derivation happens when none is needed. The corrected implementation avoids deriving a random stream at all for constant-only formulas, matching `AttackEvaluationService`'s own "don't roll dice you don't need" discipline.
- **`ValidateTargets` is the first real runtime `ContentTargetRule` validator anywhere in this codebase -- confirmed via direct doc-comment read (`CatalogValidationContracts.ValidateAbility`'s own comment: "target rule shape... already ctor-guaranteed... no live registry to check against yet. ### Доработка (product-owner-ordered fix, after independent verification of PR #162)

Independent verification found the original implementation strong overall (real integration tests with exact values, correct reuse of `AttackDamageFormulaParser`/`AttackRandomSample`, clean `Odyssey.Rules` layering, an honest `git diff` confined to allowed paths) but returned three specific findings for a genuine fix, explicitly rejecting the original PR's own prose-only "accepted design decision" framing as not a fix:

- **Finding 1 (`ApplyEffect` atomicity): FIXED via a real compensating (saga) mechanism, not a reformulation.** `IActiveEffectRepository.CreateActiveEffect` still cannot join `RecordAbilityActivation`'s own transaction (confirmed again, unchanged fact) -- but leaving the resource-delta commit unprotected against a downstream `ApplyEffect` failure is a real correctness gap, not merely a documented limitation, as the product owner's own review noted (a real failure window: cost/AdjustResource applied, then an effect application fails, leaving the character partially mutated). Considered path (a) -- extending `IActiveEffectRepository` with a same-transaction overload -- but rejected it: that interface lives in `Odyssey.Application`, which must not depend on `Microsoft.Data.Sqlite` (a `SqliteConnection`/`SqliteTransaction`-typed parameter on an Application-layer interface would itself be a layering violation, a bigger and architecturally worse change than this fix warrants). Chose path (b): `IActivateAbilityRepository.CompensateAbilityActivation`, a new, additive method reversing `RecordAbilityActivation`'s own already-committed `ResourceDeltas` by re-applying each one negated, atomically, in a NEW transaction, through the same unmodified `SqliteAttackApplyRepository.ApplyAttackDelta`. Idempotent via a new `AbilityActivation.CompensatedAt` column (a second compensation call for an already-compensated row is a no-op success) and a deterministic derived `CommandId` (`StableCompensationCommandId`, mirroring `ActivateAbilityService.StableSubCommandId`'s own SHA256 pattern). `ActivateAbilityService.ActivateAbility` calls it the moment any `ApplyEffect` application fails, then returns failure -- never the stale success. The top-of-method idempotency check (`apply.GetActivation`) now treats a `CompensatedAt != null` record as a PERMANENT failure on replay (a new `PreviouslyCompensated` error, reusing the already-used `ErrorCodes.ApplicationValidationInvalid` code, no `ErrorCodes.cs` registry edit) -- exactly mirroring the `AppliedCommands` ledger's own "a `CommandId`'s outcome is fixed forever" rule, just with a compensated/failed outcome instead of a successful one. Verified by `TC-ABILITY-010`, which injects a REAL failure (archiving the effect's own `ContentDefinitionRecord` via the existing, unmodified `ContentCatalogLifecycleService.ArchiveDefinition` before activation -- a natural `Status != Published` rejection through the existing decode path, not a fake test double) and asserts exact, fully-reversed `CharacterResource` values plus a permanently-failing retry.
- **Finding 2 (`SourceRef` bridge): FIXED by introducing a genuinely separate field, not by repurposing `SourceRef`.** Investigated path (a) first, as the fix ТЗ itself required -- direct read of `SqliteContentCatalogRepository`'s own `ContentDefinition` table schema confirms `Name` is a free-text, non-unique, non-indexed display column, not a validated human-key -- so a real catalog-index-based lookup of `AbilityDefinitionId -> ContentDefinitionRef` does not exist and would require a materially bigger schema change (a new indexed column, a migration path) than this fix warrants, exactly the caveat the fix ТЗ itself anticipated for path (a). Chose path (b): `CharacterAbility` gains an additive constructor overload and a new property, `ActivationDefinitionRef: ContentDefinitionRef?` (`Ability.cs`, `Odyssey.Domain.Character`) -- entirely separate from `SourceRef`, whose own documented contract (provenance only, null for `GMGrant`/`ProgressionPurchase`) is left fully intact and now verified by a real test (`TC-ABILITY-012`). Since `AcquireAbility`/`AcquireAbilityViaProgressionPurchase`'s own signatures/bodies remain forbidden to change, and neither has a free parameter slot for this field, a NEW, additive, standalone command was added instead: `ICharacterRepository.LinkAbilityActivationSource` (`CharacterRepositoryContracts.cs`) and its sole implementation `SqliteCharacterRepository.LinkAbilityActivationSource` (MainGM-only, mirroring `RemoveAbility`'s own permission gate, reusing the same already-existing `MutateAbilities` private helper `RemoveAbility` itself reuses -- zero new transaction-plumbing code). `SerializeAbilities`/`DeserializeAbilities` gained one additive JSON field (`activationDefinitionRef`, nullable, absent on any pre-existing row deserializes as null) -- `AcquireAbility`/`AcquireAbilityViaProgressionPurchase`'s own bodies are untouched by this change (only the shared serialization helper they already call was extended). `SqliteActivateAbilityStateReader.Read` now resolves the bridge through `ability.ActivationDefinitionRef` directly (a real, already-typed `ContentDefinitionRef?` -- no more string-parsing of an overloaded field). This necessitated touching three files outside the original ТЗ §6 allowed-paths list (`Ability.cs`, `CharacterRepositoryContracts.cs`, `SqliteCharacterRepository.cs`) -- a minimal, additive-only extension of that perimeter, directly implied by the fix ТЗ's own explicit option (b) wording ("add a new, separate, explicitly documented field on `CharacterAbility`"), recorded here rather than silently expanded, and verified by grep that no remaining production code anywhere reads `ability.SourceRef` as an activation bridge.

### Вторая доработка (product-owner-ordered, after independent verification of the first доработка commit `32ccef1`)

Independent re-verification confirmed all three original findings were genuinely fixed, but surfaced a new bug of the SAME family the first fix's own compensation logic missed: `CompensateAbilityActivation` reversed `ResourceDeltas` but never touched `ActiveEffect` rows already created by the `ApplyEffect` loop before the failure point -- exposed only when a `MechanicsPrimitiveEnvelope` carries 2+ `ApplyEffectPrimitive`s (or one with `MaximumCount > 1` targets) and the failure lands on a LATER effect/target, not the first (`TC-ABILITY-010`'s own ability had exactly one effect on one target, so it structurally could not exercise this path).

- **Investigated whether a suitable removal/deactivation method already exists on `IActiveEffectRepository`, per the fix ТЗ's own explicit instruction not to invent an interface-bypassing workaround.** Direct interface read confirms `RemoveActiveEffect(campaign, campaignId, activeEffectId, actorUserId, actorIsMainGm, expectedRevision, commandId, correlationId)` already exists (`ODY-S05-506`, `ADR-028` §9) -- transitions `Status -> Removed`, `Revision`-CAS-guarded, idempotent by `CommandId` via the shared `SqliteSavingPipeline`, MainGM-only, never physically deletes the row (`ADR-012`'s append-only-history discipline). This is exactly the "already-existing, unmodified" method the fix ТЗ asked to find and reuse -- no interface extension was needed, and none was made.
- **`SqliteActivateAbilityRepository`'s own constructor now requires an `IActiveEffectRepository` dependency, and `CompensateAbilityActivation`'s own signature gained `createdEffectIds`/`actorUserId` parameters.** Both are widened, not additive overloads -- safe because this whole feature is still unmerged (`main` has never seen `SqliteActivateAbilityRepository`/`CompensateAbilityActivation` at all), so there is no external caller to preserve backward compatibility for beyond this task's own test fixture, updated in the same commit.
- **`RemoveActiveEffect` is called with `actorIsMainGm: true` regardless of the original activation actor's own permission level.** This is deliberate: it is an internal system rollback of the SAME activation attempt that actor themselves initiated and which failed downstream -- not a new capability being granted to a non-MainGM actor. This mirrors an already-established precedent in this exact codebase: `SqliteAttackApplyRepository.ApplyCharacterResourceDelta` already writes directly to `Character.ResourcesJson` via raw SQL, bypassing the public, permission-checked `ICharacterRepository.SetResourceCurrentValue` entirely, for the identical reason (an internal apply-pipeline write, not a user-facing command).
- **Each effect removal uses its own deterministic sub-`CommandId` (`StableEffectRemovalCommandId`), derived from a DIFFERENT hash input than the creation-time `StableSubCommandId`.** This is not a stylistic choice -- `SqliteSavingPipeline`'s own `AppliedCommands` ledger is a single shared table keyed only by `CommandId`, not scoped per aggregate/repository. Reusing the SAME `CommandId` for a removal that was already used for that effect's own creation would make the pipeline treat the removal call as a REPLAY of the CREATE command (`TryReadAppliedCommandStatus` finding `Status = 'Completed'` already), silently returning the original created record via `SqliteActiveEffectRepository.ReplayByCommandId` instead of ever actually transitioning `Status` to `Removed` -- a genuine footgun this task's own design caught before writing any test, not discovered via a failing test.
- **Compensation now runs in a strict order: remove every already-created effect FIRST, only then reverse resource deltas and mark `CompensatedAt`.** If any single effect removal fails, the method returns that failure immediately without touching resources or `CompensatedAt` at all. This is a deliberate, disclosed simplification: it leaves resources uncompensated in the (untested, and believed rare) case where `RemoveActiveEffect` itself fails for a reason other than "already removed" (e.g. a genuine IO error) -- but it is safely retryable, since every removal already attempted is itself idempotent (a second call is a no-op success or a real, un-worsened retry), and `CompensatedAt` staying null accurately reflects that compensation did not yet fully complete. A deeper fix (e.g. attempting resource reversal regardless of partial effect-removal failure) was considered and rejected as unnecessary scope for this specific finding, which is about effects being left behind on the COMMON path (removal succeeding), not about `RemoveActiveEffect` itself failing.
- **No interface extension to `IActiveEffectRepository`/`SqliteActiveEffectRepository` was needed or made** -- the fix ТЗ's own §4 conditional escalation ("if a suitable method does not exist, raise it explicitly, do not invent a workaround") does not apply, since `RemoveActiveEffect` already existed and already fit exactly.

Verified by `TC-ABILITY-013`: an ability with two `ApplyEffectPrimitive`s on a single self-target -- the first effect's own `ContentDefinitionRef` stays Published (a real `ActiveEffect` gets created), the second's own `ContentDefinitionRef` is archived before activation (a real, natural `Status != Published` rejection, not a fake test double). A retry with the same `CommandId` is confirmed to remain a permanent, honest failure, with the effect list still empty of attached effects (no second removal/creation attempt).
