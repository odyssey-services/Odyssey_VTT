# ODY-S10-111 — SLICE-10 Block 6 Part 1: Obstacle Drawing UI (Walls/Doors/Windows), Door Toggle, Durability

## 1. Task identity
`ODY-S10-111`; status: In Review (Draft PR, merge deferred to the product owner). Block 6 of the `SLICE-10` track, part 1 of several -- the first client-side UI task in this whole track (Blocks 1-5, `ODY-S10-101`-`110`, are entirely server-side; recon confirmed zero client references to any of their commands before this task). Part 2 (fog-of-war rendering, cover preview, facing/FOV UI) is a separate, later task by explicit product-owner decision -- it needs a new "what does this specific player see" query this client does not have yet, and deserves its own focused design.

## 2. Goal
Draw walls/doors/windows on the board by mouse (a new tool-mode mechanic, the first in this client), toggle a door by clicking it, and show/manually apply damage to a destructible obstacle's HP -- all through the existing, unmodified Block 2/5 server commands (`CreateObstacle`/`ToggleDoorState`/`ListObstacles`/`GetObstacleDurability`/`ApplyObstacleDamage`), by exact precedent of every existing board gesture's own direct-call/read-revision/`Refresh()` pattern.

## 3. Authority
This task's governing ТЗ; `BoardScreenPresenter.cs`'s own established conventions (`BoardCamera` for the world/pixel transform, `BoardPointerGesture`/`BoardBoxSelectGesture` for click-vs-drag disambiguation, the direct-call server-command pattern, `HitTestToken`'s own pure-math hit-test precedent); `RoleSelectorPresenter.cs` as the precedent for a small, focused presenter class rather than growing `BoardScreenPresenter.cs` further; `OdysseyPlayModeFoundationSmokeTests.cs`'s own real-mouse-event pattern (`ClickWithMouse`) for the one PlayMode smoke test.

## 18. Change control

### Decisions made during execution
- **A door click both toggles the door AND selects it for the damage panel** -- the ТЗ's own §2.4 (any click on a Door toggles it) and §2.6 (any click on an obstacle with durability selects it for the damage panel) both describe the same gesture without saying which wins for a destructible door specifically. Rather than picking one arbitrarily, this task combines them: the click always selects (so the HP bar/panel state updates), and additionally toggles when the obstacle is a Door. Disclosed here as the ТЗ invited.
- **Escape-to-cancel requires the board area to already have keyboard focus** (e.g. from a prior click on it) -- UI Toolkit's `KeyDownEvent` only reaches a focused element, and this task does not add any new focus-management infrastructure beyond `_boardArea.focusable = true`. A right-click during an active draw gesture is already refused by the pre-existing one-gesture-at-a-time invariant (`HandleBoardButtonDown`'s own `_activeBoardButton != -1` guard), so it was not additionally wired as a second cancel affordance -- it already does nothing during a draw, exactly as before this task.
- **Line-drawing technique**: an absolutely-positioned `VisualElement` whose width is the segment's own pixel length and whose height is a small fixed thickness (4px), rotated via UI Toolkit's `style.rotate`/`style.transformOrigin` (supported at runtime by this project's Unity 6000.4 -- confirmed by the real batchmode compile/test run, not assumed). No prior task in this codebase draws a line with UI Toolkit, so this was an original design decision, not a reuse.
- **Placeholder obstacle colors** (task contract §2.3, not final art): Wall -- solid stone-gray `(0.55, 0.55, 0.58, 1)`; Door -- warm brown `(0.50, 0.32, 0.14, 1)` closed, lighter `(0.75, 0.55, 0.30, 1)` open; Window -- the same blue-gray as a Wall but translucent `(0.55, 0.75, 0.95, 0.45)`. The in-progress draw preview is a translucent gold line `(1, 0.85, 0.1, 0.6)`, matching the existing player-marker's own gold accent color already used elsewhere in this file.
- **HP bar hit-test/damage-panel thresholds**: an 8px pixel hit-test radius for `HitTestObstacle` (`ObstacleHitTestThresholdPixels`), a 40×6px HP bar drawn a fixed 6px above each destructible obstacle's own midpoint, colored green/yellow/red at the 50%/25% HP thresholds -- no visual precedent existed in this codebase for any of these; all are this task's own new design.
- **A new `IObstacleRepository` constructor parameter was added to `BoardScreenPresenter`** (both constructors), mirroring how `ICampaignRepository` is already injected rather than constructed internally -- consistent with the class's own established dependency-injection shape, not a new pattern. All four existing construction call sites needed the same mechanical fix, the same "more files than a narrow scope would suggest" situation this whole SLICE-10 track has already established and disclosed repeatedly for its own server-side constructor changes.
- **A pre-existing PlayMode test-ordering fragility was found and fixed**: `AssertUiInputActionsConfigured` (checking the project-wide Input Actions asset) only ever passed in the pre-existing `RealMouseClick_RoutesThroughUiToolkitInput...` test because that test happened to be the first one in its class to use `InputTestFixture` -- `InputTestFixture.Setup()` resets `InputSystem.actions` to null for the rest of the run, and Unity's own save/restore (confirmed by reading the package source directly) does not cover it. This task's own new `RealMouseClick_DrawWallTool_...` test sorts alphabetically before it and also uses `InputTestFixture`, which turned that latent fragility into a real, reproducible failure. Fixed by moving the check into `[OneTimeSetUp]` (NUnit guarantees it runs once, before every test's own `Setup()`), not by renaming or reordering tests to dodge the symptom -- the same assertion, made order-independent by construction. Verified by an isolated single-test run (passed alone even before the fix, confirming the diagnosis) and by the full suite passing after it.
