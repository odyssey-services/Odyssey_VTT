## 2. Goal
Give `SceneRecord` a real, validated background/map field -- `AssetId? BackgroundAssetId` -- set/cleared through a new `SetSceneBackground` command, fail-closed against the campaign's own `AssetManifestEntries`, and put the previously-reserved-but-unused `AssetReferences` table to its first real production use. ## 6. Domain contract
No new Domain-layer type. `SceneRecord.BackgroundAssetId` (`AssetId?`, `Odyssey.Application.Persistence`) is validated in the constructor exactly like every other optional reference field on this record set (`TokenRecord.CharacterId`'s own precedent): `IsValid` checked only when a value is supplied, `null` accepted as a first-class, non-error state (a Scene with no background is valid). No origin/scale/placement type is introduced (§5).

## 7. Application contract
`ISceneRepository.SetSceneBackground(CampaignHandle campaign, SceneId sceneId, AssetId? backgroundAssetId, long expectedRevision, CommandId commandId, CorrelationId correlationId) -> Result<SceneRecord>` -- by exact precedent of `MoveToken`: `expectedRevision` for optimistic concurrency, `CommandId` for idempotent replay through the same `SqliteSavingPipeline` journal-projection transaction every other mutating method in this repository already uses. `backgroundAssetId: null` is accepted and clears an existing background -- the same command handles set and clear, per this task's own governing ТЗ §1 decision 6.

## 8. Persistence boundary
`SqliteSceneRepository.SetSceneBackground`: inside the `SqliteSavingPipeline.Execute` transaction -- (1) read the Scene row by `SceneId` (fails with the existing, unmodified `SceneNotFound` if absent); (2) atomic optimistic-concurrency check against `expectedRevision` (fails with the new `SceneRevisionConflict` on mismatch, by exact precedent of `MoveToken`'s own `TokenRevisionConflict` check, `ADR-002` §10.2); (3) if `backgroundAssetId.HasValue`, a real existence check against `AssetManifestEntries` in this same campaign's own database (fails closed with the new `AssetNotFound` if absent -- since each campaign owns a separate `campaign.db` file, "exists in `AssetManifestEntries`" and "exists in this campaign" are the same single lookup, covering both the plain-missing and cross-campaign cases with one query); (4) `UPDATE Scene SET BackgroundAssetId = ..., Revision = Revision + 1, ...`; (5) `AssetReferences` sync -- unconditionally `DELETE FROM AssetReferences WHERE ReferencedByType = 'Scene' AND ReferencedById = $sceneId`, then, only if a non-null background was set, `INSERT` the new `(AssetId, 'Scene', SceneId)` row -- delete-then-optionally-reinsert keeps exactly one current row per Scene, never accumulating a stale/duplicate one across repeated changes or a reset to `null` (this task's own governing ТЗ §1 decision 4, the first real production consumer of this previously-reserved, nowhere-else-used table). The `Scene` table's own `CREATE TABLE IF NOT EXISTS` DDL (`EnsureSceneTokenTables`) gains one new nullable `BackgroundAssetId TEXT` column -- see §18 for the disclosed `ADR-013` boundary this required.

## 9. Tests and validation
`TC-BOARD-016`-`023` (`SqliteSceneRepositoryTests.cs`). `016`: a valid, campaign-registered `AssetId` succeeds, `BackgroundAssetId` is set, `Revision` increments. `017`: a non-existent `AssetId` fails with `AssetNotFound`. `018`: an `AssetId` registered under a genuinely different campaign (its own separate temp campaign/database, created and torn down within the test) fails with the same `AssetNotFound` -- the cross-campaign case. `019`: `backgroundAssetId: null` after a prior successful set really clears the field. `020`: a mismatched `expectedRevision` fails with `SceneRevisionConflict`. `021`: retrying with the same `CommandId` replays without a second `Revision` advance and without a second `AssetReferences` row (proven by a direct SQL count, not an indirect inference). `022`: a direct SQL read of `AssetReferences` after a successful call confirms the row really exists. `023`: replacing the background with a different `AssetId` removes the old `AssetReferences` row and leaves exactly one current row for that scene. Full solution `dotnet test` and `verify-format.ps1`/`verify-repository.ps1`/`verify-test-structure.ps1` all green (see §17 for exact counts).

## 10. Compatibility and rollback
`SceneRecord`'s constructor gains one new optional parameter (`backgroundAssetId = null`) appended at the end -- every existing positional/named call site compiles unchanged. `ISceneRepository` gains one new method; no existing method's signature or behavior changes (confirmed: `CreateScene`'s own `INSERT` statement is untouched -- the new nullable column defaults to `NULL` for a row that does not reference it). Reverting this task's source returns `SceneRecord`/`ISceneRepository` to their pre-`105` shape; `AssetReferences` returns to being reserved-but-unused, exactly as it already was.

No new PII surface -- `AssetId` is an opaque identifier, and the fail-closed existence check never exposes the raw campaign/asset path to a caller (`AssetNotFound`'s own safe user message).

## 18. Change control

### Decisions made during execution

- **`Packages/com.odyssey.application/Runtime/Results/ErrorCodes.cs` and `Packages/com.odyssey.application/Runtime/Persistence/CampaignRepositoryContracts.cs`/`docs/errors/ERROR_CODES.md` were touched even though none appears in this task's own governing ТЗ §5 allowed-paths list -- an under-naming in that list, not a deliberate exclusion, disclosed here rather than silently worked around, by the exact precedent `ODY-S07-102`'s own task contract §18 already established for its five new error codes.** The governing ТЗ's own §2.2/§4 explicitly require typed, fail-closed errors for a missing/cross-campaign `AssetId` and a revision conflict, and no existing `PersistenceFailures` entry covers either -- `SceneNotFound`/`TokenRevisionConflict` are for different aggregates/conditions. Two new, strictly additive entries (`AssetNotFound`, `SceneRevisionConflict`) were the minimum needed; `scripts/check-repository-policy.ps1`'s own `REPO-POLICY-005` check (which fails the whole repository-policy gate if any production `ErrorCode.Parse` literal lacks a matching, test-verified `ERROR_CODES.md` row) confirmed both rows are correctly registered and reference real, passing tests (`TC-BOARD-017`/`018`/`020`).
- **`Packages/com.odyssey.persistence/Runtime/Sqlite/MigrationRegistry.cs` was deliberately NOT touched, even though it is the concrete artifact `ADR-013` §4 calls a "migration registry."** Direct code read, before implementation, confirmed the actual migration RUNNER (temp-copy execution, per-step transactions, real schema-version-transition tracking) does not exist anywhere in this codebase -- `MigrationRegistry.cs`'s own doc comment states outright that it is "not the migration runner itself" and holds exactly one degenerate identity entry (`FromVersion == ToVersion`, both pinned to `SqliteCampaignRepository.DatabaseSchemaVersion`, a single hardcoded constant this task's own allowed-paths list does not include and has no reason to bump). Registering a second entry with the identical `FromVersion == ToVersion` pair would misrepresent a real schema change as another identity no-op; fabricating a version bump this project does not yet track at that granularity would be a worse, silent workaround than disclosing the gap plainly. Given that constraint, the new `BackgroundAssetId` column is added directly to `Scene`'s own `CREATE TABLE IF NOT EXISTS` DDL (`EnsureSceneTokenTables`) -- the exact mechanism by which every existing column on `Scene`/`Token` already reached the schema, since no `ALTER TABLE` precedent exists anywhere in this codebase to violate, and none is added here either. This covers every campaign this task can actually create or that this test suite exercises; it does not retroactively add the column to a hypothetical pre-existing `campaign.db` file created by an older build, since no such migration-application mechanism exists to do that safely today -- that gap belongs to whichever future task actually builds the `ADR-013` runner, not this one.
- **The `AssetId` existence check for `SetSceneBackground` is a single `AssetManifestEntries` lookup, deliberately not two separate checks for "does not exist" vs. "exists in a different campaign."** Confirmed by direct schema read: `AssetManifestEntries` carries no `CampaignId` column at all, because each campaign already owns its own separate `campaign.db` file (`ADR-011`) -- an `AssetId` "registered in a different campaign" lives in a database this repository never opens for the current `CampaignHandle`, so a single existence lookup against the current campaign's own table already and only ever finds assets that are genuinely scoped to it. `TC-BOARD-018` proves this concretely with a second, real, temporary campaign, not a mocked scenario.
