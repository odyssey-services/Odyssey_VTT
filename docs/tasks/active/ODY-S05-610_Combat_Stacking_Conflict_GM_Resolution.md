# ODY-S05-610 — Combat Stacking Conflict GM Resolution

## 1. Task identity
`ODY-S05-610`; status: In Review (Draft PR https://github.com/odyssey-services/Odyssey_VTT/pull/154).

## 2. Goal
Give `ODY-S05-503`'s own `ActiveEffectStackConflict` (the pending record `ActiveEffectStackingRules.ResolveStacking` already produces for `EffectStackPolicy.RequestGMResolution`) durable, cross-session persistence, and provide a real command a MainGM can use to resolve it (`ActiveEffectStackConflictResolution.ApplyAsIndependentInstance`/`Replace`/`Ignore`, already defined by `ODY-S05-503`). This closes the gap `ODY-S05-606` found and disclosed: a combat-sourced `RequestGMResolution` collision previously created no row and reached no GM at all.

## 3. Authority
`ADR-028` §7 rule 7 (`RequestGMResolution`'s own pending-conflict/resolution-command requirement); `ODY-S05-503`'s own `ActiveEffectStackConflict`/`ActiveEffectStackConflictResolution`/`ActiveEffectStackingRules.ResolveActiveEffectStackConflict` (unmodified, reused exactly as-is); `ODY-S05-606`'s own task contract ("Post-review amendment" section, 2026-09-15) for the finding that created this task; `ODY-S05-604`'s own `AttackOutcome`/pending-intervention idiom (CAS-guarded, `CommandId`-idempotent, routed through `SqliteSavingPipeline`) as the directly analogous precedent this task reuses the *pattern* of.

## 4. In scope
A new, standalone `CombatStackConflict` table inside `SqliteAttackApplyRepository` (by direct analogy to `AttackOutcome` -- not under `SqliteActiveEffectRepository`, since the gap is combat-specific: `ActiveEffectStackingRules.ResolveStacking` has exactly one call site in the entire codebase, `606`'s own `ApplyEffectCandidates`); persistence of a pending conflict inside that same call's own atomic-apply transaction; a new root command, `ResolveStackConflict`, letting a MainGM apply `ActiveEffectStackConflictResolution` via the existing, unmodified `ActiveEffectStackingRules.ResolveActiveEffectStackConflict`, reusing the existing create/replace/ignore mutation logic (now extracted into a shared `ApplyStackDecisionMutation` helper both callers use); tests.

## 5. Out of scope
`ODY-S05-605`'s own territory (combat duration expiry). `ODY-S05-607`'s own territory (compensation, audience-filtered Game Log projections). `ODY-S05-609`'s own territory (`AttackDelta` application). Rewriting `ODY-S05-502`/`503`/`604`/`606`'s own already-accepted behavior -- `ActiveEffectStackingRules`'s own two pure functions are called, never modified. Appending a method to `ICombatEncounterRepository`/`IInventoryRepository`/`ICharacterRepository`. Revising `ADR-028`/`ADR-029`.

## 6. Domain contract
No new Domain type. `ActiveEffectStackConflict`/`ActiveEffectStackConflictResolution` (`Odyssey.Application.Effects`, `ODY-S05-503`) are reused exactly as-is; no new Domain-level identity type is introduced for the persisted conflict record (see §18 -- keyed by the existing `CommandId`/`ActiveEffectId` types instead).

## 7. Application contract
New `CombatStackConflictRecord` (Application-layer, `AttackApplyRepositoryContracts.cs`): `RaisingCommandId`, `CampaignId`, `CandidateApplication` (`ActiveEffectRecord`), `ConflictingActiveEffectId`, `RaisedAt`, `IsResolved`, `ResolvedAt`, `ResolvedByCommandId`, `Resolution`. `IAttackApplyRepository` gains one new method: `Result<CombatStackConflictRecord> ResolveStackConflict(CampaignHandle campaign, CommandId raisingCommandId, ActiveEffectId conflictingActiveEffectId, ActiveEffectStackConflictResolution resolution, UserId actorUserId, bool actorIsMainGm, CommandId commandId, CorrelationId correlationId)`. `AttackApplyService.ResolveStackConflict` delegates unchanged (no new orchestration logic in the Application layer, matching `606`'s/`609`'s own precedent of keeping all mechanism in the Persistence layer's own transaction).

## 8. Persistence boundary
`SqliteAttackApplyRepository` gains the `CombatStackConflict` table, embedding the candidate `ActiveEffect`'s own full shape via `SqliteActiveEffectRepository`'s existing `AddParameters`/`SelectColumns`/`ReadRecord` (reused verbatim -- no duplicated serialization logic), plus conflict-specific columns (`ConflictingActiveEffectId`, `RaisedAt`, `ConflictStatus`, `ResolvedAt`, `ResolvedByCommandId`, `Resolution`). `ApplyEffectCandidates`'s own `RequestGmResolution` branch (previously a bare `break`) now calls `RecordStackConflict`, writing this pending row inside the SAME `SqliteSavingPipeline` transaction as the rest of the triggering attack's own commit -- never a second connection/transaction. `ResolveStackConflict` is a brand-new root command with its own `SqliteSavingPipeline.Execute` call: MainGM-gate first, reads the pending row, CAS-guards via a conditional `UPDATE ... WHERE ConflictStatus='Pending'`, then reconstructs `ActiveEffectStackConflict` and calls the existing `ActiveEffectStackingRules.ResolveActiveEffectStackConflict`, applying the result through the shared `ApplyStackDecisionMutation` (extracted from `606`'s own switch, now called by both producers of an `ActiveEffectStackDecision`) -- never the public `IActiveEffectRepository.CreateActiveEffect`.

## 9. Tests and validation
`TC-ATTACK-084`-`092` (continuing the existing series): a `RequestGMResolution` candidate creates a durable pending record in the same transaction as the rest of apply (direct SQL check); an unresolved conflict still commits the rest of the attack (`TC-ATTACK-054`'s own invariant, reconfirmed) and now additionally persists a pending record; MainGM resolution with each of the three outcomes (`ApplyAsIndependentInstance`/`Replace`/`Ignore`) produces the exact mutation `ActiveEffectStackingRules.ResolveActiveEffectStackConflict` itself decides; a non-MainGM attempt is denied with zero mutation; resolving an already-resolved conflict a second time (different resolving `CommandId`) is a CAS failure; retrying the same resolving `CommandId` is idempotent via `SqliteSavingPipeline`'s own replay; an architecture guard confirms `ResolveStackConflict`'s own method body never calls the public `CreateActiveEffect`. Full `dotnet test` (992 pre-existing + 9 new = 1001 total) and the repository validation scripts are green.

## 10. Compatibility and rollback
`IAttackApplyRepository` gains one new method (backward compatible for every existing caller); `SqliteAttackApplyRepository`'s constructor is unchanged. `ApplyEffectCandidates`'s own `RequestGmResolution` branch behavior change (bare no-op -> persisted pending row) is additive -- verified via the full pre-existing regression suite (14 tests from `604`/`606`) passing unchanged, since `TC-ATTACK-054` never asserted the ABSENCE of a row in a different table, only the absence of a second `ActiveEffect` row (still true). One new standalone table (`CombatStackConflict`); no change to `ActiveEffect`/`AttackOutcome`'s own existing schema. Reverting this task's source and table leaves `602`-`609` unaffected -- an unresolved conflict would simply return to today's (pre-`610`) silent-no-durable-record behavior, not a data-loss condition.

## 11. Security and privacy
MainGM-only gate is the first statement in `ResolveStackConflict`, checked before any read of the pending record (established project convention, matching `ResolveAttackIntervention`). No new information disclosure -- the pending record's own candidate application is already visible information (the same `ActiveEffect`-shaped data that would have been created had stacking not required GM resolution).

## 12. Observability
Per this task's own product-owner-directed design (§2 decision 4): two new DomainEvent types, `odyssey.persistence.combat_stack_conflict_raised` (appended directly via `SqliteSavingPipeline.AppendDomainEvent`, inside the SAME transaction as the triggering attack's own `attack_outcome_recorded`/`resolved` event -- `ODY-S04-107`'s own "more than one event per transaction" precedent) and `odyssey.persistence.combat_stack_conflict_resolved` (the new command's own single `PipelineWrite`-driven event, matching `attack_outcome_resolved`/`attack_outcome_compensated`'s own convention).

## 13. Performance
One extra `SELECT`/`INSERT` (pending-conflict persistence, only when `RequestGMResolution` actually fires -- a rare policy outcome) inside the already-open atomic-apply transaction; the resolution command is a rare, MainGM-only, explicit administrative action with the same cost profile as `ResolveAttackIntervention`.

## 14. Dependencies
`ODY-S05-606` (source of `RequestGmResolution` stacking decisions needing persistence, extended), `ODY-S05-503` (`ActiveEffectStackConflict`/`ActiveEffectStackConflictResolution`/`ActiveEffectStackingRules.ResolveActiveEffectStackConflict`, unmodified), `ODY-S05-502`/`606` (`SqliteActiveEffectRepository`'s own internal SQL helpers, reused).

## 15. Dependencies (packages)
None new.

## 16. Implementation plan
Implemented directly (ExecPlan-equivalent scope, matching this contract's own §16 original expectation) -- see §18 for the design decisions made.

## 17. Completion evidence
Implemented the `CombatStackConflict` table (embedding the candidate `ActiveEffect` via `SqliteActiveEffectRepository`'s own reused serialization helpers), wired `ApplyEffectCandidates`'s own `RequestGmResolution` branch to persist a durable pending record in the same transaction as the rest of attack apply, extracted the shared `ApplyStackDecisionMutation` helper (reused by both `ApplyEffectCandidates` and the new `ResolveStackConflict`), and implemented `ResolveStackConflict` as a MainGM-only, CAS-guarded, `CommandId`-idempotent root command mirroring `ResolveAttackIntervention`'s own shape. Verified: a pending record is created atomically with the rest of attack apply; an unresolved conflict still lets the attack commit; each of the three resolution outcomes produces exactly the mutation `ActiveEffectStackingRules.ResolveActiveEffectStackConflict` itself decides; a non-MainGM attempt mutates nothing; a second resolution attempt on an already-resolved conflict is rejected; a retry with the same resolving `CommandId` is idempotent; no reference to the public `CreateActiveEffect` exists in the resolution's own method body; the full solution test suite (1001 tests) remains green.

## 18. Change control

### Decisions made during execution

- **The new persisted conflict record lives inside `SqliteAttackApplyRepository` (a new `CombatStackConflict` table), not a wholly separate standalone repository/contract, resolving this contract's own previously-open question (§18, original draft).** Direct verification (this task's own governing ТЗ §1) confirmed `ActiveEffectStackingRules.ResolveStacking` has exactly one call site in the entire codebase -- `606`'s own `ApplyEffectCandidates` -- and neither `505`'s item-triggered creation nor `506`'s direct-command path ever reaches it (both fail earlier for a non-trivial stacking policy, per their own contracts). The gap is genuinely combat-specific, not a general cross-cutting one; placing the record in the combat-specific `SqliteAttackApplyRepository` (by the same "new standalone table, same repository as the closely-related aggregate" precedent `AttackOutcome` itself already set) is architecturally more honest than a "general" table for a scenario with no other live producer today. If a future non-combat producer of `RequestGMResolution` conflicts appears, that would be its own separate task's own decision, not preempted here.
- **The persisted record's identity is a composite key of (raising `CommandId`, conflicting `ActiveEffectId`) -- not the raising `CommandId` alone, and not a new synthetic ID type.** The governing ТЗ's own §2 decision 2 directed keying by the raising attack's own `CommandId`, by direct analogy to `AttackOutcome`'s own `CommandId`-only primary key. However, `AttackEffectCandidate` is `IReadOnlyList<AttackEffectCandidate>` -- a single attack can, in principle, carry more than one candidate that independently resolves to `RequestGmResolution` against different existing `ActiveEffect` rows (e.g., an attack hitting multiple targets, or one target with two independently-conflicting effects). A bare `CommandId` primary key would make a second such candidate's own `INSERT` throw a primary-key violation, aborting the whole attack's own transaction outright -- a correctness regression, not merely a narrower feature. The composite key still introduces no new ID TYPE (both `CommandId` and `ActiveEffectId` already exist), stays fully faithful to "no new ID type," and closes this real, easily-triggered correctness gap. `ResolveStackConflict`'s own signature targets a conflict by the same pair for the same reason.
- **`ApplyEffectCandidates`'s own switch statement was extracted into a shared `ApplyStackDecisionMutation` helper, called by both `ApplyEffectCandidates` itself (for an immediate `ResolveStacking` decision) and the new `ResolveStackConflict` (for a `ResolveActiveEffectStackConflict` decision).** This is the governing ТЗ's own explicit, non-discretionary requirement (§3.2: "переиспользовать этот switch, не дублировать логику"). The extracted helper still contains all six `ActiveEffectStackDecisionKind` cases (including `RequestGmResolution`, which throws `InvalidOperationException` if reached there) rather than only the three kinds `ResolveActiveEffectStackConflict` can actually produce -- `ApplyEffectCandidates` itself intercepts `RequestGmResolution` BEFORE calling the shared helper (to persist a new pending conflict, a fundamentally different action than mutating an `ActiveEffect` row), so the shared helper's own `RequestGmResolution` branch is unreachable from either caller today; it exists as a fail-loud safety net, matching this class's own existing "unrecognized state throws" convention (its own pre-existing `default: throw new ArgumentOutOfRangeException`).
- **Two new DomainEvent types were introduced (`combat_stack_conflict_raised`, `combat_stack_conflict_resolved`), not one.** The governing ТЗ's own §2 decision 4 named both explicitly as examples and stated the general project convention ("каждая новая команда... вводит свой тип события"). `combat_stack_conflict_resolved` is the new `ResolveStackConflict` root command's own single event, exactly matching `attack_outcome_resolved`/`attack_outcome_compensated`'s own shape. `combat_stack_conflict_raised` is NOT its own root command (the raise happens inside the ALREADY-existing `RecordAttackOutcome`/`ResolveAttackIntervention` commands, which already emit their own `attack_outcome_recorded`/`resolved` event) -- it is appended as an ADDITIONAL `DomainEvents` row in the SAME transaction via `SqliteSavingPipeline`'s own `internal static AppendDomainEvent` (the exact mechanism `ODY-S04-107`'s own precedent already established for "more than one event per transaction"), purely for independent observability/audit-trail purposes (so a durable conflict's own existence is queryable via `DomainEvents` without cross-referencing the triggering attack's own event). This is a deliberate choice to follow the ТЗ's own explicit instruction literally, erring toward more observability rather than less; `606` itself did not need an analogous event for plain `ActiveEffect` creation, but this task's own governing ТЗ specifically called for one here.
- **`ResolveStackConflict` does not write any `GameLogEntries` row.** Unlike `ResolveAttackIntervention` (which narrates the attack's own resolution in the Game Log, since that IS the attack's own visible outcome), a stacking-conflict resolution is bookkeeping about HOW an effect was ultimately applied, not a new narratable game event in its own right -- the governing ТЗ's own required tests/DoD never named a Game Log requirement for this command, and no precedent in this block writes a Game Log entry for a command that doesn't itself represent a player-visible in-fiction event.
