# ODY-S10-109 — SLICE-10 Block 4: Fog of War (Persistent Map Memory + Live Token Visibility)

## 1. Task identity
`ODY-S10-109`; status: In Review (Draft PR, merge deferred to the product owner). Block 4 of the `SLICE-10` track, continuing directly from `ODY-S10-108` (Block 3, merged — line-of-sight service, not modified here) and from `ODY-S10-101` (Block 1 — campaign membership).

## 2. Goal
Two independent per-player states, both keyed directly on `UserId` (this codebase's established convention): (1) live token visibility, a thin composition over Block 3's `TokenVisionService.ComputeLineOfSight`, no new storage; (2) persistent map memory, an append-only (INSERT-only) set of circular "reveals" in a new `FogReveal` table. No UI (Block 6), no combat cover (Block 5).

## 3. Authority
This task's governing ТЗ; the product decision of 2026-09-29 (two independent states: monotonic persistent memory + live, non-persistent token visibility); `TokenVisionService.ComputeLineOfSight` (`ODY-S10-108`) as the reused, unmodified building block; `CampaignMembershipAuthorization.IsMainGm` (`ODY-S10-101`) for both the MainGM-sees-everything shortcut and the self-scoped read check; `VisibilityPolicy.IsVisible` (`Odyssey.Application.Networking.Projection.SceneProjectionContracts`, an unrelated networking-projection model) as the precedent for "MainGM sees everything unconditionally" as a product principle already established elsewhere in this codebase.

## 18. Change control

### Decisions made during execution
- **§1.1's MainGM shortcut is keyed on `targetUserId`, not `requestingUserId`.** The ТЗ's own §1.3 wording ("если requestingUserId/targetUserId — MainGM ... возвращать видно всё") is ambiguous between the two. Resolved as: the unconditional bypass applies when the user *whose state is being computed* (`targetUserId`) is MainGM — because that is whose perspective the method returns. If it were keyed on `requestingUserId` instead, a MainGM asking about a specific player's own state (the explicit debug/support use case §1.4 itself names) would get "sees everything" instead of that player's actual, narrower state — defeating the feature. `requestingUserId` only gates the self-scoped authorization check (§1.4); it plays no role in which visibility rule is applied. Flagged here explicitly, as the ТЗ invited, rather than silently picking one reading.
- **`RecordExplorationRequest` gained a `CommandId` the ТЗ's own prose signature (`RecordExploration(campaign, sceneId, observerTokenId, correlationId)`) did not list**, and dropped the `sceneId` parameter that prose signature did list. `CommandId`: every mutating write in this codebase routes through `SqliteSavingPipeline`, which requires one for idempotent command replay -- omitting it would make `RecordExploration` the only writer in the entire codebase without idempotent-replay support, an inconsistency the ТЗ's shorthand signature (which also omits `CommandId` from every other example, including reads) does not appear to have intended as a deliberate design choice. `SceneId`: dropped as redundant, by exact precedent of Block 3's own `ComputeLineOfSightRequest`, which likewise derives Scene from the token records it reads rather than taking a separately supplied, cross-checkable parameter.
- **`RecordExploration` performs no authorization of its own**, exactly as the ТЗ's literal signature implies (no actor parameter at all): the exploring user is read directly from the observer token's own `ControllerUserId`. The ТЗ's own §1.2 says this method is invoked by "whatever orchestrates token movement (UI/networking, out of this task's scope)" — the authorization decision (who may act through this specific token) already happened at that orchestration layer, via Block 1/3's own `MoveToken`/`SetTokenFacing` checks, before this method is ever reached.
- **The circle-containment math lives as a private helper inside `PlayerVisibilityService.cs`, not a new Domain-layer file.** The allowed-path list (§5) names no new file under `Odyssey.Domain.Geometry` for this task, unlike Block 2/3's own `ObstacleGeometry.cs`/`LineOfSight.cs`; adding one anyway would repeat the very "opportunistic scope creep" this track's own established discipline (confirmed by the earlier `ODY-S10-107` doc-fix task, which deliberately left an identical out-of-scope defect untouched) counsels against. `BoardGeometry.EuclideanDistance`/`GeometryEpsilonV1` are called, not duplicated.
- **`FogRevealId` added to the shared `DomainIdentity.cs`, two error codes to `ErrorCodes.cs`, and two matching rows to `ERROR_CODES.md`**, none named in the ТЗ's allowed-path list — the exact same, disclosed, mechanical shared-infrastructure pattern `ODY-S10-107`/`ODY-S10-108` already established and disclosed for `ObstacleId`/token-vision's own error codes.
