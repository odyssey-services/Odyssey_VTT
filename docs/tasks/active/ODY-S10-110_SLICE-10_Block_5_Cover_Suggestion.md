# ODY-S10-110 — SLICE-10 Block 5: Cover (Damage Reduction) + Destructible Obstacles — v3

## 1. Task identity
`ODY-S10-110`; status: In Review (Draft PR, merge deferred to the product owner). Block 5 of the `SLICE-10` track, continuing directly from `ODY-S10-108`/`ODY-S10-109` (Blocks 3/4, merged). **This is the v3 ТЗ, which replaces the original hint-only scope this task ID started with** (Part A below, already implemented, is unchanged from that original scope) with two additional parts: Part B (destructible obstacles) and Part C (cover as a real, wired-in combat damage reduction). Same branch/PR throughout — the task identity and number did not change, only its scope, per the v3 ТЗ's own explicit instruction to stop and use the new version wholesale rather than opening a second task.

## 2. Goal
Three parts, one cohesive Block 5:
- **Part A** (unchanged from the original scope): a graduated (`None`/`Half`/`ThreeQuarters`/`Full`) cover *degree*, computed from Block 2's obstacle geometry via a 4-sample-around-the-target model, exposed as a standalone read-only hint (`CoverSuggestionService.SuggestCover`) for callers outside combat (e.g. a UI showing cover before an attack is even decided).
- **Part B** (new): obstacles gain optional HP/armor (`ObstacleDurability`) and a MainGM-only `ApplyObstacleDamage` command; a destroyed obstacle is excluded from `ListObstacles`, the single integration point with all downstream geometry (line-of-sight, cover) -- no separate synchronization.
- **Part C** (new, product decision 2026-09-29): cover now really reduces attack damage, the same additive way armor `Protection` already does, computed once per attack inside `SqliteAttackStateReader.ReadTopology` and consumed by `CoreAttackRulesEvaluator.Resolve`. It never affects `Hit`/`Range` (there is no to-hit roll to modify -- `Hit == Range` remains this codebase's own documented MVP stub, confirmed by recon and left alone).

## 3. Authority
The v3 ТЗ (supersedes the original hint-only ТЗ for this same task); the product decisions of 2026-09-29 (graduated cover; a hint for Part A; a real damage reduction for Part C); `ADR-020` section 12.4 (cover must reuse `ObstacleGeometry.BlocksVision`, never invent a separate blocking interpretation); `LineOfSight.cs`/`SegmentIntersection.cs` (`ODY-S10-108`) as reused, unmodified building blocks; `CoreAttackRulesEvaluator.cs`'s own existing `AggregateProtection`/`finalDamage = Max(0, formulaValue - protection)` shape as Part C's direct precedent; `SqliteAttackStateReader.ReadArmor`/`WithDecodedWeapon` as the precedent for "decode/compute once in Persistence or the one Application-layer seam, before the snapshot reaches `Odyssey.Rules`, which cannot reference `Odyssey.Application`/`Odyssey.Persistence`" (ADR-001).

## 4. In scope

### Part A (unchanged)
- **`Cover.cs`** (`Odyssey.Domain.Geometry`): `CoverDegree` enum, `CoverGeometry.ComputeCoverDegree` (one attacker point, four fixed diagonal sample points around the target at `DefaultTargetRadius = 0.5`, each tested via `SegmentIntersection.SegmentsIntersect` against `ObstacleGeometry.BlocksVision`-passing obstacles).
- **`CoverSuggestionService.cs`** (`Odyssey.Application.Board`): `SuggestCover`, no authorization, typed cross-Scene error.

### Part B (new)
- **`ObstacleRepositoryContracts.cs`**: `CreateObstacle` gains optional trailing `long? maxHp = null, long protection = 0`; new `ObstacleDurabilityRecord`; `IObstacleRepository` gains `ApplyObstacleDamage`/`GetObstacleDurability`; new `ObstacleFailures.ApplyDamageDenied`/`DurabilityNotConfigured`.
- **`ObstacleAuthoringService.cs`**: new `ApplyObstacleDamage` (MainGM-only, exact precedent of `CreateObstacle`'s own check), `ApplyObstacleDamageRequest`; `CreateObstacleRequest` gains `MaxHp`/`Protection`.
- **`SqliteObstacleRepository.cs`**: new `ObstacleDurability` table (`CREATE TABLE IF NOT EXISTS`, no `Revision`-vs-`Obstacle` coupling -- its own independent revision counter); `CreateObstacle` optionally seeds a durability row in the same transaction as the `Obstacle` row; `ApplyObstacleDamage` (`effectiveDamage = Max(0, damageAmount - Protection)`, `CurrentHp = Max(0, CurrentHp - effectiveDamage)`, `IsDestroyed = (CurrentHp == 0)`, revision-gated); `ListObstacles` `LEFT JOIN`s `ObstacleDurability` and excludes a destroyed row.
- Two new `ErrorCodes.cs`/`ERROR_CODES.md` entries.

### Part C (new)
- **`AttackPipelineContracts.cs`**: new `AttackCoverAvailability`/`AttackTargetCoverEntry`/`AttackCoverInput` (exact `AttackTopologyInput` shape); `AttackEvaluationSnapshot` gains a `Cover` property and a new 12-arg constructor (the 10-arg and 11-arg overloads are preserved, defaulting `Cover` to `AttackCoverInput.Unavailable`, for every pre-existing caller/test fixture).
- **`CoreAttackRulesEvaluator.cs`**: new `CoverPenaltyTable` (`None`=0, `Half`=2, `ThreeQuarters`=5, `Full`=10 -- documented MVP placeholders); `Resolve` subtracts `coverPenalty` alongside `protection` (`finalDamage = Max(0, formulaValue - protection - coverPenalty)`), never touching `Hit`/`Range`; `Modifiers` (previously always empty) gains one `AttackModifierEntry("cover", coverPenalty)` per target whose cover penalty is nonzero.
- **`SqliteAttackStateReader.cs`**: new required constructor parameter `IObstacleRepository obstacles`; `ReadTopology` (renamed in effect to return both `AttackTopologyInput` and `AttackCoverInput`, computed from the same already-read actor/target positions, no second token-position pass) also calls `_obstacles.ListObstacles`/`CoverGeometry.ComputeCoverDegree` per same-Scene target.
- Tests, catalogue `TC-PERSIST-130`–`137` (Part B) and `TC-ATTACK-130`–`135` (Part C), the `SLICE-10` backlog, this contract and its plan.

## 18. Change control

### Decisions made during execution
- **Reconstructing Part A/Part B's own allowed-path list from the v3 ТЗ's self-contained description**, since the ТЗ says Parts A/B are "unchanged from v2" but this task never received a v2 document directly -- only this v3 text, which fully specifies Part B's own behavior inline (§3 of the ТЗ). The file set touched for Part B (`ObstacleRepositoryContracts.cs`, `ObstacleAuthoringService.cs`, `SqliteObstacleRepository.cs`, their existing test files, two new error codes) was inferred directly from that inline description, following the exact same "necessary shared-infra/existing-file touch, disclosed" pattern every prior SLICE-10 task in this track already established. Flagged here explicitly since it could not be cross-checked against a v2 document this task never had.
- **A one-line, disclosed necessary edit to `AttackEvaluationService.WithDecodedWeapon`** (not named in the ТЗ's own §8 allowed-path list, which explicitly expected *zero* edits to this file per §4.5's own claim): the 11-arg `AttackEvaluationSnapshot` constructor this method calls defaults `Cover` to `Unavailable`, so re-wrapping the reader's own snapshot to attach the decoded `ActionWeapon` was silently discarding the real, already-computed `Cover` data on every real `Evaluate`/`Preview` call -- a genuine, previously-unnoticed bug the ТЗ's own plan did not anticipate. Fixed by passing `snapshot.Cover` through explicitly, mirroring how every other pre-existing field on that same line is already threaded through. This finding is exactly the kind of ТЗ/reality contradiction this track's own standing instructions ask to be stopped and reported on, not silently worked around.
- **`SqliteAttackStateReader.ReadTopology` was restructured to return both `AttackTopologyInput` and `AttackCoverInput` together** (`Result<(AttackTopologyInput, AttackCoverInput)>`), rather than adding a second, separate `ReadCover` method with its own token-position lookups -- the ТЗ's own §4.2 explicitly suggested computing cover "inside `ReadTopology` or a neighboring method... not discarding the raw X/Y as today," and reusing the same already-resolved positions avoids a second `ListTokensByCharacter` round-trip per target.
- **Nine test files, not the three the ТЗ's own §8 explicitly named** (`AttackEvaluationServiceTests.cs`, `CoreAttackRulesEvaluatorIntegrationTests.cs`, `AttackPipelineIntegrationFixtureTests.cs`), needed the same one-line mechanical `SqliteAttackStateReader` constructor-argument fix (a new `IObstacleRepository` parameter) -- `AttackAggregateDeltaCommitTests.cs`, `AttackApplyTests.cs`, `AttackCompensationAndAudienceTests.cs`, `AttackEffectApplicationTests.cs`, `CombatStackConflictResolutionTests.cs`, `MvpTwoCharacterCombatScenarioTests.cs`, `SqliteAttackStateReaderTests.cs` were the other six. The exact same "more files than the ТЗ named needed a mechanical constructor-argument fix" situation this track's own `ODY-S10-105`/`106` tasks already established as accepted practice -- disclosed, not silently expanded scope. `AttackEvaluationServiceTests.cs` itself needed no new tests beyond this: its own hand-written fixtures never construct a real, decodable weapon, so `WithDecodedWeapon`'s re-wrap path (where the Cover-loss bug lived) is never exercised there -- the real, decodable-weapon path is already fully covered by `CoreAttackRulesEvaluatorIntegrationTests.cs`'s own new Part C tests, which would have caught a regression of that fix.
- **`Source: "cover"` on every `AttackModifierEntry` from cover** (not per-target-tagged) -- the ТЗ's own §4.4 example used the literal string `"cover"`; for a multi-target attack, several `AttackModifierEntry` values with the same `Source` but different `Value`s may appear in `Modifiers`, one per affected target, rather than a single aggregate entry -- kept simple, matching the ТЗ's own literal example rather than inventing a richer tagging scheme not asked for.

### Findings (reported, not fixed silently)
- **`AttackEvaluationService.WithDecodedWeapon` required a one-line edit the ТЗ's own §4.5 explicitly said would not be needed** -- see the decision above; without it, cover would have been silently and permanently lost on every real attack evaluation, defeating this task's entire Part C purpose. This is the one place this task's implementation diverges from the ТЗ's own stated plan, and it does so to make the plan's own goal (§4.5: "PreviewAttack automatically gets cover for free") actually true.
