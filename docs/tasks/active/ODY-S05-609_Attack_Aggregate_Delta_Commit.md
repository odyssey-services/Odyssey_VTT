# ODY-S05-609 — Attack Aggregate Delta Commit

## 1. Task identity
`ODY-S05-609`; status: In Review (Draft PR, see the backlog row for the link once opened).

## 2. Goal
Close `604`'s own disclosed gap (`ADR-029` §1 rule 5, §6 stage 13, §12 item 4): apply an accepted attack outcome's own already-computed `AttackDelta.Value` (`DamageDeltas`/`CostDeltas`, `ODY-S05-603`, unmodified) against concrete Character resource state, in the same atomic-apply transaction as `604`'s own outcome/Game Log commit. This task never chooses, evaluates, or invents a Ruleset formula -- `AttackDelta.Value` is already computed by the time it reaches here; this task's own work is (a) a new, explicit `TargetRef` addressing convention (deltas were never actually persisted or resolved before this task -- see §18's correction of this contract's own original, inaccurate draft) and (b) the Persistence-layer orchestration that resolves and writes the already-computed value.

## 3. Authority
`ADR-029` §1 rule 5, §6 stage 13 (atomic apply's own affected-aggregate list), §10 (`character:`/`item:` identity-resolution boundary, not a Ruleset-formula boundary), §12 item 4 (Definition of Done); `ODY-S05-604`'s own task contract ("Post-review amendment" section, 2026-09-14) for the finding that created this task; `ODY-S05-603`'s `AttackDelta`/`ProposedAttackResolution` (unmodified); `ODY-S05-604`'s `AttackOutcomeRecord`/`IAttackApplyRepository` (extended, the same "persist across the pending/resolved round trip" shape `606` already established for `EffectCandidates`); `ODY-S04-109`'s `CharacterResource`/`ResourceDefinitionId`/`SetResourceCurrentValue` (identity/value-range rules reused, public method itself not called -- see §18).

## 4. In scope
- A new, explicit `TargetRef` addressing convention: `"character:{characterId}:{resourceKind}"` / `"item:{itemInstanceId}:{itemResourceKind}"` (product-owner-approved, §18) -- identity resolution only, reusing the existing `ResourceDefinitionId` type for `resourceKind`, not inventing a new one.
- Persisting `DamageDeltas`/`CostDeltas` on `AttackOutcomeRecord`/`AttackOutcome` (new `DamageDeltasJson`/`CostDeltasJson` columns, mirroring `606`'s own `EffectCandidatesJson` precedent exactly) -- the mandatory prerequisite this contract's own original draft missed (§18).
- Resolving a `character:`-addressed `TargetRef` to a `CharacterId`/`ResourceDefinitionId` pair and applying the already-computed `Value` against `Character.ResourcesJson`, embedded directly inside `SqliteAttackApplyRepository`'s own atomic-apply transaction (never the public `ICharacterRepository.SetResourceCurrentValue` -- see §18).
- One new `internal`-visibility change on `SqliteCharacterRepository` (`SerializeResources`/`DeserializeResources`), mirroring `606`'s own `SqliteActiveEffectRepository` internal-helper precedent.
- Escalating (not silently building) the `item:`-addressed path as a disclosed blocker (§18) -- `ItemInstanceRecord` has no numeric mutable field at the Domain level.
- Tests proving deltas apply exactly once, atomically, only on actual commit (immediate or approved-intervention), never on Pending/Rejected.

## 5. Out of scope
- Choosing, evaluating, or inventing any Ruleset formula (hit/damage/cost/armor/body-part) -- `AttackDelta.Value` is already computed by the time this task touches it.
- `609`'s own resource-delta compensation infrastructure for `609` itself is not this task's concern; nor does this task anticipate `609`-triggered compensation being layered on top later (that stays a separate future task, by the `604`→`609` precedent already established in the backlog).
- `ODY-S05-605`'s own territory (combat duration expiry). `ODY-S05-606`'s own territory (`ActiveEffect` creation/stacking). `ODY-S05-607`'s own territory (compensation commands, audience-filtered Game Log projections). `ODY-S05-610`'s own territory (stacking-conflict GM resolution).
- Rewriting `ODY-S05-602`/`603`/`604`/`606`/`607`'s own already-accepted production behavior.
- Adding any method to `ICombatEncounterRepository`. Adding more than the zero new `IInventoryRepository` methods this task actually ended up needing (see §18 -- the item-side method the original contract anticipated was never built; the blocker was escalated instead).
- Building a numeric mutable field on `ItemInstanceRecord`/the Domain `ItemInstance` model -- a real, deeper Domain gap, escalated as a blocker (§18), not silently invented within this task's own scope.
- Revising `ADR-008`/`ADR-012`/`ADR-028`/`ADR-029`.

## 6. Domain contract
No Domain-layer changes. `AttackDelta` (`Odyssey.Domain.Combat`, `ODY-S05-603`) is reused exactly as-is (`TargetRef: string`, `Value: int`); `ResourceDefinitionId` (`Odyssey.Domain.Character`, `ODY-S04-109`) is reused exactly as-is as the `resourceKind` segment of the new `TargetRef` convention -- no new Domain type is introduced.

## 7. Application contract
`AttackOutcomeRecord` gains `IReadOnlyList<AttackDelta> DamageDeltas`/`CostDeltas` (mirroring `EffectCandidates`'s own addition by `606`); `IAttackApplyRepository.RecordAttackOutcome` gains the same two parameters. `AttackApplyService.ResolveAttack` passes `evaluated.Value.DamageDeltas`/`.CostDeltas` through unchanged -- no new decision logic in the Application orchestration layer itself (all delta-resolution/application logic lives in the Persistence layer's own atomic-apply transaction, matching `606`'s own architectural precedent exactly, per §18).

## 8. Persistence boundary
`SqliteAttackApplyRepository` gains two new columns (`DamageDeltasJson`/`CostDeltasJson`, JSON-serialized, `NOT NULL DEFAULT '[]'`) and, inside its own existing `apply:` transaction lambdas (both `RecordAttackOutcome`'s immediate-accept path and `ResolveAttackIntervention`'s Approve path, right alongside the existing `ApplyEffectCandidates` call), a new `ApplyAttackDeltas` step: for each delta (`DamageDeltas` then `CostDeltas`, in order), `ApplyAttackDelta` splits `TargetRef` on `:` into exactly three segments and dispatches on the first (`"character"` or `"item"`; anything else, or a segment that fails to parse as its own identity type, or a segment count other than three, is `PersistenceAttackOutcomeDeltaTargetRefInvalid`). A `character:{characterId}:{resourceKind}` delta is applied by `ApplyCharacterResourceDelta`: a minimal, targeted raw SQL `SELECT ResourcesJson, CharacterResourcesRevision, CharacterRevision FROM Character WHERE CharacterId = ...` on the same connection/transaction, deserialized via `SqliteCharacterRepository.DeserializeResources` (now `internal`), the matching `CharacterResource` located by `ResourceDefinitionId`, `CurrentValue + delta.Value` checked against `[MinimumValue, EffectiveMaximum]` (rejected, never clamped, as `PersistenceAttackOutcomeDeltaValueOutOfRange` if out of range), then written back via a targeted `UPDATE Character SET ResourcesJson = ..., CharacterResourcesRevision = CharacterResourcesRevision + 1, CharacterRevision = CharacterRevision + 1, ...` using `SqliteCharacterRepository.SerializeResources` (now `internal`). Multiple deltas targeting the same character within one attack are applied strictly sequentially -- each call re-reads the row fresh from the same open transaction, so the second delta's own revision increment is always correct with no risk of two independent CAS-guarded calls conflicting. An `item:{itemInstanceId}:{itemResourceKind}` delta always fails as `PersistenceAttackOutcomeDeltaItemTargetUnsupported` (§18's disclosed blocker). Any delta failure is returned from the `apply:` lambda itself, so `SqliteSavingPipeline` rolls back the entire transaction -- including the just-inserted `AttackOutcome` row -- exactly like any other guard failure in this class; no partial commit is possible.

## 9. Tests and validation

## 18. Change control

### Decisions made during execution

- **This contract's own original draft (written by `604`'s post-review amendment) was factually wrong about `604`'s starting state, and this task corrected it before implementing anything.** The original §2 claimed `AttackDelta` values were "already computed... and persisted by `ODY-S05-604`'s `AttackOutcome`" -- direct code inspection at activation time showed this was false: `AttackApplyService.ResolveAttack` passed only `EffectCandidates` to `RecordAttackOutcome`; `evaluated.Value.DamageDeltas`/`.CostDeltas` were computed and immediately discarded; `IAttackApplyRepository.RecordAttackOutcome` had no delta parameter at all; the `AttackOutcome` table had no `DamageDeltasJson`/`CostDeltasJson` column (only `EffectCandidatesJson` existed, from `606`). Persisting the deltas first -- by the exact `EffectCandidatesJson` precedent `606` already established -- was therefore this task's own mandatory first step, not an already-satisfied precondition. This governing ТЗ's own §1 flagged this discrepancy explicitly and instructed treating the contract's prose as unreliable pending direct verification; that verification is recorded here.
- **The `TargetRef` addressing convention (`"character:{characterId}:{resourceKind}"` / `"item:{itemInstanceId}:{itemResourceKind}"`) is a product-owner-approved, explicit design decision, not left to this task's own discretion.** `AttackDelta.TargetRef` is a fully opaque string with no accepted production producer anywhere in the codebase (the only existing usage was test-fixture placeholder data, a bare `CharacterId.ToString()`, which never carried resource-kind information and was never actually resolved or applied before this task). `resourceKind` reuses the existing `ResourceDefinitionId` type (`Odyssey.Domain.Character`, `ODY-S04-109`) rather than inventing a new identifier -- this is identity-resolution vocabulary, not a Ruleset-formula choice, matching `ADR-029` §10's own boundary.
- **Delta application never calls the public `ICharacterRepository.SetResourceCurrentValue`; it embeds a minimal, targeted raw SQL SELECT/UPDATE directly inside `SqliteAttackApplyRepository`'s own atomic-apply transaction, reusing only `SqliteCharacterRepository.SerializeResources`/`DeserializeResources` (made `internal` for this purpose).** Two independent, non-discretionary reasons, both confirmed by direct code inspection before implementing: (1) `SetResourceCurrentValue`'s own `MutateResources` opens its own `SqliteConnection`/`SqliteSavingPipeline.Execute` call -- a second, independent transaction that cannot be atomic with the attack's own commit; (2) `SetResourceCurrentValue` hard-requires `actorIsMainGm == true` as its own first check, but an immediate (non-intervention) attack accept is not necessarily GM-initiated. This is the exact same shape of problem `606` already solved for `IActiveEffectRepository.CreateActiveEffect` (by making `SqliteActiveEffectRepository`'s own SQL helpers `internal`) -- this task follows that precedent for `SqliteCharacterRepository` instead of duplicating the `CharacterResource` JSON-serialization shape a second time. Only `SerializeResources`/`DeserializeResources` needed the visibility change (a same-assembly, non-public-contract change) -- the full 36+-column `SelectForUpdate`/`CharacterRecord` round trip `MutateResources` uses was deliberately NOT reused, since delta application only ever reads/writes three columns (`ResourcesJson`/`CharacterResourcesRevision`/`CharacterRevision`); a minimal, targeted SQL statement was judged clearer and cheaper than forcing a full-record round trip through machinery built for a different (public, MainGM-gated, single-resource-per-call) use case.
- **Multiple deltas targeting the SAME character within one attack (e.g. a `DamageDeltas` entry and a `CostDeltas` entry on the same actor) are applied strictly sequentially inside the loop, each re-reading `Character.ResourcesJson`/`CharacterResourcesRevision` fresh from the same open transaction.** Because SQLite transactions are single-writer/serialized, this guarantees the second delta's own revision increment is always correct relative to the first -- there is no risk of the conflict that two independent, separately-CAS-guarded calls to the public `SetResourceCurrentValue` (each computed against its own separately-read `expectedCharacterResourcesRevision`) would have produced. Verified directly by `TC-ATTACK-071`.
- **An `item:{itemInstanceId}:{itemResourceKind}`-targeted delta is a disclosed, escalated blocker -- `PersistenceAttackOutcomeDeltaItemTargetUnsupported`, always -- not a silently-invented Domain field.** Direct inspection of `ItemInstanceRecord`/the Domain `ItemInstance` model (`Odyssey.Domain.Inventory`) confirmed no numeric mutable field exists anywhere (only an opaque `RuntimeState: string`, with no established internal numeric convention inside that string either) -- there is no durability/charges/ammunition field to write a resource delta into. This governing ТЗ's own §4 explicitly named this exact possibility and required treating it as a blocker to escalate rather than a field to invent within this task's own scope; per that instruction, `IInventoryRepository` gained ZERO new methods (the one-method allowance the original ТЗ granted was never exercised, since there is no existing numeric field to write through in the first place). A future task that wants item-targeted attack deltas must first decide and add the missing Domain field -- an explicit, separate, larger decision (what numeric state an item even has) that this task does not make on its own.
- **No field-level clamping is performed: a delta that would push `CurrentValue` outside `[MinimumValue, EffectiveMaximum]` is rejected outright (the whole apply transaction rolls back), never silently clamped to the boundary.** This mirrors `SetResourceCurrentValue`'s own existing behavior exactly (`PersistenceFailures.CharacterResourceValueOutOfRange`, `ODY-S04-109`) -- consistency with the already-accepted convention for the same underlying condition, not a new design choice.
- **Three pre-existing test fixtures' own placeholder `AttackDelta` values were updated, not left broken.** `AttackApplyTests.cs`, `AttackEffectApplicationTests.cs`, and `AttackCompensationAndAudienceTests.cs` each had an identical `Rules` fixture line producing `new AttackDelta(intent.TargetIds[0].ToString(), 1)`/`new AttackDelta(intent.ActorId.ToString(), 1)` -- placeholder data satisfying `ProposedAttackResolution`'s own non-null-list constructor requirement, never actually applied or asserted upon before this task (since `604`'s own apply logic discarded deltas entirely). Once this task made delta application real, these placeholder values (a bare `CharacterId.ToString()`, one colon-segment, not three) became genuinely resolved and correctly rejected as an invalid `TargetRef` -- breaking all 16 of those files' own pre-existing tests. Replacing the placeholder values with empty delta lists (`Array.Empty<AttackDelta>()`) fixed this: none of those three files' own tests assert anything about delta values, only about apply atomicity/idempotency/intervention (`604`), `ActiveEffect` application (`606`), and compensation/audience projection (`607`) respectively -- confirmed by direct inspection before editing. All 24 of those tests pass unchanged after this fix, proving this was a fixture-data correction, not a rewrite of `604`/`606`/`607`'s own already-accepted behavior (the governing ТЗ's own explicit prohibition).

### Blockers

- **Item-targeted attack deltas cannot be applied today.** `ItemInstanceRecord` has no numeric mutable field at the Domain level (only an opaque `RuntimeState` string) to write a durability/charges/ammunition-style delta into. This is a genuine, deeper Domain-modeling gap this task does not resolve on its own (per the governing ТЗ's own explicit instruction to escalate rather than invent) -- a future task must first decide what numeric state an `ItemInstance` even carries before an item-targeted `AttackDelta` can ever be applied through a real write path.
