# ODY-S06-107 — `UseItem` Root Command (Item `Instant`-Effect Application, Block D)

## 1. Task identity
`ODY-S06-107`; status: In Review (branch `feat/ody-s06-107-use-item`, Draft PR to be opened, merge left to the product owner). Seventh task of `SLICE-06`, roadmap block D ("using one active item once"). Built from the start to `ODY-S06-106`'s FINAL, thrice-revised idempotency/compensation rigor (full atomicity, full compensation of every side-effect category, resumable-after-partial-compensation-failure) -- not a simpler first pass deferred to a later доработка round, per this task's own governing ТЗ §0's explicit instruction.

## 2. Goal
Build `UseItem`, a standalone root command letting a character consume exactly one unit of an inventory item (a stack unit, or a whole non-stackable instance) and apply every `Instant`-duration built-in effect it declares, atomically, with the same idempotency/compensation guarantees `ActivateAbility` reached only after three independent-verification rounds.

## 3. Authority
`ADR-030` §10 (item use, named/reserved by `ODY-S06-101`, never previously scoped). `Packages/com.odyssey.application/Runtime/Effects/ItemEffectLifecycleService.cs`'s own `Instant`-skip (line ~113) and its own doc comment ("Instant creates no persistent row; its immediate mechanics are outside this service") -- this task is the first real implementation of that "outside this service" mechanics. `ODY-S06-106`'s own final, thrice-revised `ActivateAbilityService`/`SqliteActivateAbilityRepository` shape -- this task's own governing ТЗ §0 explicitly requires building to that same rigor from the start.

## 7. Application contract
`UseItemContracts.cs`: `UseItemIntent` (`ActorId`, `Item: InventoryItemRef`, `ExpectedItemRevision`/`ExpectedInventoryRevision`/`ExpectedCharacterResourcesRevision`, ctor-validated >= 1, deliberately self-only -- no target list, since items have no `ContentTargetRule` concept anywhere in this codebase, confirmed by direct code read: `ItemDefinition` carries no target rule, and `EffectDefinition.TargetRule` has zero runtime consumers even for `ActivateAbility`; a used item's `Instant` effects always target the actor who used it, a documented MVP decision, not an implied default), `UseItemState` (`Actor`, `InventoryId`, `Definition: ItemDefinition`, `InstantEffectPrimitives: IReadOnlyList<MechanicsPrimitiveEnvelope>` -- deliberately a LIST, one envelope per `Instant` built-in effect, not one merged envelope, since one item can carry several distinct `Instant` effects each with their own independent formula), `ItemUsageRecord` (mirrors `AbilityActivationRecord`'s own final shape exactly: `CompensatedAt`/`CompensationStartedAt` both present from this task's first version), `IUseItemRepository` (`GetUsage`/`RecordItemUsage`/`CompensateItemUsage`, mirroring `IActivateAbilityRepository`'s own final three-method shape). `UseItemService.UseItem` orchestrates, in order: three-branch idempotency check (built from the start, not added by doработка -- `CompensatedAt != null` -> permanent failure; `CompensationStartedAt != null` -> resume compensation, always report failure; else -> existing success); `Authorize` (actor controls the item's own owning character, or MainGM); `reader.Read`; `RequiresDice` across ALL `InstantEffectPrimitives` envelopes (a single RNG derivation covers every effect on the item, mirroring `ActivateAbility`'s own no-needless-draw discipline); `MechanicsPrimitiveInterpreter.Interpret` once PER envelope, resource adjustments and effect-application intentions accumulated across all of them; `apply.RecordItemUsage` (atomic: revision re-checks + item consumption + resource deltas); sequential `EffectApplicationHelper.ApplyEffect` calls (self-targeted, deterministic sub-`CommandId` per effect index only -- no per-target loop, unlike `ActivateAbility`), tracking `createdEffectIds`; on any failure, `apply.CompensateItemUsage` reverses everything, and the overall call returns failure regardless of the compensation's own outcome.

## 8. Persistence boundary
`SqliteUseItemStateReader` resolves the item's own `ItemDefinition` straight from its already-pinned `ItemMechanicsSnapshot.Payload` (a `DecodeItem` switch mirroring -- not calling, since it is `private` in the forbidden-to-touch `ItemEffectLifecycleService.cs` -- that method's own established pattern) -- a genuine simplification versus `AbilityDefinitionId`: no catalog-bridge gap exists for items at all, since the snapshot already carries everything the item itself needs. Each `BuiltInEffectRefs` entry DOES need a real catalog round-trip (the item's own snapshot only pins the item's own shape, not its referenced effects'), filtered to `EffectDurationType.Instant` only -- the SAME criterion `ItemEffectLifecycleService.cs`'s own line ~113 already applies for the opposite purpose (skipping `Instant` during equip), confirmed by direct code read before designing this filter so both call sites agree on what "Instant" means. `SqliteUseItemRepository` owns a new, standalone `ItemUsage` table (mirrors `AbilityActivation`'s own final schema exactly: `CompensatedAt`/`CompensationStartedAt`/`CreatedEffectIdsJson` all present from the start, plus a new `ConsumedItemUnitJson` column carrying everything needed to fully restore the consumed item unit on compensation). `RecordItemUsage`'s own transaction re-checks all three expected revisions fresh (item's own row revision, its `InventoryId`'s own `InventoryRecord.Revision`, and the actor's own `CharacterResourcesRevision` -- there is no dedicated "inventory" `CharacterSectionRevisions` field; inventory has its own, separate per-aggregate revision counters, confirmed by direct code read), consumes the item unit via `SqliteInventoryRepository.ConsumeItemUnitInTransaction` (internal, reused by reference), and applies resource deltas via `SqliteAttackApplyRepository.ApplyAttackDelta` (internal, unmodified, from `ODY-S06-106`) -- all in one transaction. `CompensateItemUsage` reverses, in order: already-created effects (via `IActiveEffectRepository.RemoveActiveEffect`, unmodified), then resource deltas, then the consumed item unit (via `SqliteInventoryRepository.RestoreConsumedItemUnitInTransaction`, internal, reused by reference) -- durably marking `CompensationStartedAt`/the created-effect-id list/the consumed-item snapshot BEFORE any reversal, exactly mirroring `106`'s own final, third-доработка resolution.

## 18. Change control

### Decisions made during execution

- **Items have NO target-rule concept anywhere in this codebase -- confirmed by direct code read before designing `UseItemIntent`, not assumed.** `ItemDefinition` carries no `ContentTargetRule`-shaped field, and `EffectDefinition.TargetRule` has ZERO runtime consumers even for `ActivateAbility` (`ActivateAbilityService.ApplyEffect` decodes the effect but never reads its own `TargetRule`; `ItemEffectLifecycleService` likewise never reads it, taking the target from its own caller instead). Resolved by making `UseItem` deliberately self-only: a used item's `Instant` effects always target the actor who used it (the item's own holder) -- a documented MVP decision recorded directly in `UseItemIntent`'s own doc comment, not an implied default. This also makes `UseItemService` simpler than `ActivateAbilityService` in one respect: no per-target loop, since exactly one target (the actor) always exists.
- **An item's own `ItemDefinition` is resolved straight from its already-pinned `ItemMechanicsSnapshot`, never from today's catalog entry -- mirroring, not calling, `ItemEffectLifecycleService.DecodeItem`'s own established pattern (that method is `private` in a file this task must not modify, so the identical switch logic is repeated in `SqliteUseItemStateReader`, not shared by reference).** This is a genuine simplification versus `AbilityDefinitionId`: no `AbilityDefinitionId`-style catalog-bridge gap exists for items at all, since `ItemStackRecord`/`ItemInstanceRecord` already carry a full `ItemMechanicsSnapshot` (`SourceDefinitionRef`, `DefinitionSnapshotVersion`, `ContentType`, `Payload`) pinned at creation time -- confirmed by direct type-shape read before assuming a bridge was needed the way `106` needed one.
- **`ItemDefinition.HasCharges`-bearing items are rejected honestly at the state-read step, before any consumption is attempted -- confirmed by direct doc-comment read that `HasCharges`/`MaxCharges` are definition-level capability declarations only, with no runtime current-charge state anywhere in this codebase.** Building real per-instance charge tracking is a separate, larger task explicitly out of this one's scope, per the governing ТЗ's own §2.3.
- **`IInventoryRepository.ConsumeItemUnit`'s own standalone idempotency cannot use the usual re-select-based `TryReplay<TRecord>` pattern `SqliteInventoryRepository` already established elsewhere, since a fully-consumed row may no longer exist to re-select.** Resolved with a small, dedicated `ItemConsumptionLedger` table recording the outcome itself (kind, id, whether fully consumed, remaining quantity), read back directly on replay -- a genuinely different idempotency shape than this file's own existing `InventoryCommandLedger`-based pattern, disclosed here rather than silently forced into an ill-fitting existing mechanism.
- **`ConsumeItemUnitInTransaction`/`RestoreConsumedItemUnitInTransaction` are `internal` static methods on `SqliteInventoryRepository`, reused by `SqliteUseItemRepository` for its own atomic transaction, exactly mirroring `106`'s own `SqliteAttackApplyRepository.ApplyAttackDelta` visibility-widening precedent.** The PUBLIC `IInventoryRepository.ConsumeItemUnit` (own connection/transaction/ledger) is a separate, thinner entry point built on the SAME internal core, for standalone testability (`TC-INVENTORY-193`-`196`) independent of `UseItem`.
- **`RestoreConsumedItemUnitInTransaction` restores by RE-INSERTING the exact prior row (same id, same every field) when the row was deleted, or incrementing a still-live stack's own `Quantity` back by 1 (CAS-guarded) otherwise -- never "create a new stack with the same quantity," per this task's own governing ТЗ §2.6's own explicit instruction that a fully-compensated inventory be indistinguishable from its pre-`UseItem` state.** The restored row's own `Revision` legitimately advances by 2 across a full consume-then-restore round trip (once for the consume, once for the restore) -- an accepted, disclosed consequence, mirroring how `ActivateAbility`'s own resource-delta reversal already advances a `CharacterResource`'s own revision on both the forward and reverse application, never rolling the revision counter itself back to its exact prior number. A test's own FIRST DRAFT assumed exact revision equality after a full round trip and had to be corrected once this was understood -- caught during test-writing, not left as a wrong assertion.
- **`ConsumeItemUnitInTransaction`'s own captured "prior record" is serialized into a new `ItemUsage.ConsumedItemUnitJson` column via Newtonsoft's DEFAULT parser settings caused a REAL bug during test-writing: Newtonsoft auto-detects ISO-8601-looking date strings on `JObject.Parse` and silently reformats them (via a culture-specific `DateTime.ToString()`) on read-back, corrupting `UtcInstant.Parse`'s own strict format.** Found via a real failing test (`FormatException` on a genuinely round-tripped date), not by inspection. Fixed by reusing `SqliteCharacterRepository.ParseJsonPreservingStrings` (`internal`, same assembly, already exists specifically to disable Newtonsoft's own date auto-detection via `DateParseHandling.None`) rather than inventing a second such helper.
- **`ActivateAbilityService.ApplyEffect` was extracted into `Odyssey.Application.Mechanics.EffectApplicationHelper`, per this task's own governing ТЗ §2.5 point 9's own explicit preference, rather than duplicating the exact code `106`'s own three doработка rounds already proved easy to get subtly wrong.** The extraction is behavior-preserving byte-for-byte (identical `Error.Create` calls, identical `ActiveEffect` construction) -- verified by re-running the full, unmodified `TC-ABILITY-*` suite green before writing any `UseItem`-specific code, so any regression from the extraction itself would have been caught in isolation from this task's own new logic.
- **`InventoryStackOperationServiceTests.ThrowingInventoryRepository`'s own new `ConsumeItemUnit` stub was a necessary, purely mechanical fix, not a scope choice -- adding any interface method to `IInventoryRepository` requires every implementer, including test fakes, to implement it.** This is the same category of unavoidable consequence `106`'s own second доработка already accepted for `ActivateAbilityIntegrationTests.cs` when `IActivateAbilityRepository.CompensateAbilityActivation`'s own signature grew new parameters.
