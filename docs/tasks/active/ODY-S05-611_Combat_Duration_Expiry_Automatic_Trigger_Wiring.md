# ODY-S05-611 — Combat Duration Expiry Automatic Trigger Wiring

## 1. Task identity
`ODY-S05-611`; status: In Review (Draft PR https://github.com/odyssey-services/Odyssey_VTT/pull/155). Final task of the full attack pipeline block (`ADR-029`).

## 2. Goal
Give `ODY-S05-605`'s own `CombatEffectExpiryService.EvaluateAndExpireIfDue` a real, automatic production call site, so a combat-duration-bound `ActiveEffect` genuinely expires as encounters are played, closing the gap `605` itself disclosed, `606` did not pick up, and `608` independently reconfirmed still open.

## 3. Authority
`ADR-029` §7 (the six combat duration boundary mechanisms, unmodified); `ODY-S05-605`'s own `CombatEffectExpiryService.cs` class-level doc comment ("wiring that call site is explicitly out of this task's own scope"); `ODY-S05-608`'s own task contract (§18 decision log and "Product-owner decision" note, 2026-09-16) for the finding that created this task; the `ODY-S05-604`→`609` and `ODY-S05-606`→`610` precedent this backlog already established.

## 4. In scope
Wiring inside `SqliteCombatEncounterRepository.Advance` -- not `CombatEncounterService.Advance` (a pure authorization wrapper with no transaction/data access of its own) -- that, after the round/turn advance's own transaction commits, enumerates the encounter's current participants' combat-bound `Active` effects and calls the existing, unmodified `CombatEffectExpiryService.EvaluateAndExpireIfDue` for each. Two new optional constructor parameters on `SqliteCombatEncounterRepository` (`IActiveEffectRepository`, `ICombatEncounterLifecycleReader`, both defaulting to real implementations) so none of the 9 existing single-argument call sites break. Tests.

## 5. Out of scope
Any change to `CombatEffectExpiryService`/`ActiveEffectExpiryRules` (`605`, called only). Any change to `SqliteActiveEffectRepository.ExpireActiveEffect`'s signature or connection strategy (`502`, called only). `606`/`607`/`609`/`610`'s own territory. Any new event bus/publisher/subscriber. A new `ICombatEncounterRepository`/`IActiveEffectRepository` method beyond what already exists. Batching/caching/scheduling the enumeration (§18 -- a deliberate non-goal, matching `605`'s own "no polling loop, no scheduler, no cache" precedent). Revising `ADR-028`/`ADR-029`.

## 6. Domain contract
No new Domain type. `EffectDurationType`/`CombatDurationBinding`/`ActiveEffect` (`605`/`502`, unmodified) are reused exactly as-is.

## 7. Application contract
No new Application-layer contract or method. The wiring calls `IActiveEffectRepository.ListActiveEffectsByTarget` (`502`, unmodified), `TypedDefinitionCodec.DecodeEffect` (`105`, the exact same already-established source `ItemEffectLifecycleService`/`505` already uses to recover a real `ActiveEffect`'s own `EffectDurationType` from its pinned mechanics snapshot payload -- not a newly-invented source), and `CombatEffectExpiryService.EvaluateAndExpireIfDue`/`IsCombatDurationType` (`605`, unmodified).

## 8. Persistence boundary
`SqliteCombatEncounterRepository.Advance` commits its own existing round/turn-advance transaction exactly as before (unchanged), then -- outside that transaction, since `ExpireActiveEffect` opens its own separate `SqliteConnection` and cannot share it -- calls a new private `ExpireDueCombatEffects` helper. For each current participant, it lists that participant's `ActiveEffect` rows, filters in-memory to `Status == Active && CombatBinding.HasValue && CombatBinding.Value.EncounterId == encounter.EncounterId`, decodes each candidate's own `EffectDurationType`, and (only for one of the six combat duration types) calls `EvaluateAndExpireIfDue` with a freshly-synthesized `CommandId` per candidate (see §18 for why reusing `Advance`'s own single incoming `CommandId` across multiple candidates would be incorrect). A read, decode, or expiry failure for one candidate is skipped, never thrown, and never rolls back the already-committed round/turn advance.

## 9. Tests and validation
`TC-ATTACK-093`-`100` (continuing the existing series, no new `TC-COMBAT-*` prefix -- see §18): a real `Advance` call (not a direct `EvaluateAndExpireIfDue` call) expires a real `ForRounds` effect once its boundary round is crossed; an effect not yet due stays `Active`; a non-combat effect and an already-terminal effect are untouched; the round/turn advance still commits and a sibling candidate still expires even when one candidate's own processing fails; multiple due candidates across different participants in one `Advance` call are all handled; an effect on a character outside the current roster is not expired (documented residual gap); a non-MainGM `Advance` attempt is still denied (regression); both a round-boundary (`ForRounds`) and a turn-boundary (`UntilTargetTurnStart`) duration type are evaluated by the same wiring. One pre-existing architecture test (`CombatScopeTests.cs`, `602`) required updating -- see §18. Full `dotnet test` (1001 pre-existing + 8 new = 1009 total) and the repository validation scripts are green.

## 10. Compatibility and rollback
`SqliteCombatEncounterRepository`'s constructor gains two new OPTIONAL parameters (backward compatible -- all 9 existing single-argument call sites keep compiling unchanged, verified directly). `ICombatEncounterRepository`'s own public `Advance` contract/return type is unchanged (per this task's own explicit constraint) -- test observability of expiry is via direct repository/database state queries after calling `Advance`, not a widened result type (see §18). No schema change (`ActiveEffect`'s existing table is reused as-is). Reverting this task's source leaves `602`-`610` unaffected -- combat-bound effects simply stop auto-expiring again, returning to the pre-`611` (already-accepted, if incomplete) behavior, not a data-loss condition.

## 11. Security and privacy
No new authorization gate: `Advance` already requires `ActorIsMainGm` before this wiring's own code ever runs; the wiring itself is a system-driven consequence of an already-authorized command, not a new player-facing action.

## 12. Observability
No new DomainEvent type; `ExpireActiveEffect`'s own existing `odyssey.persistence.active_effect_expired` event (`502`, unmodified) is emitted exactly as it already was for a direct call -- this task changes only who calls it, not what it records.

## 13. Performance
Per `Advance` call: one `ListActiveEffectsByTarget` read per current participant (typically a handful), plus, only for a due candidate, one `EvaluateAndExpireIfDue`/`ExpireActiveEffect` call. No batching/caching/scheduler is introduced -- a deliberate choice (§18), matching `605`'s own "no polling loop, no scheduler, no cache" precedent for what remains a per-turn, non-hot-path command.

## 14. Dependencies
`ODY-S05-605` (`CombatEffectExpiryService`/`ActiveEffectExpiryRules`/`ICombatEncounterLifecycleReader`, unmodified, now actually wired), `ODY-S05-602` (`SqliteCombatEncounterRepository`/`ICombatEncounterRepository`, extended), `ODY-S05-502`/`105` (`SqliteActiveEffectRepository`/`TypedDefinitionCodec.DecodeEffect`, unmodified, reused via the same source `505` already established).

## 15. Dependencies (packages)
None new.

## 16. Implementation plan
Implemented directly (ExecPlan-equivalent scope, matching this contract's own §16 original expectation) -- see §18 for the design decisions made.

## 17. Completion evidence
Implemented `ExpireDueCombatEffects` inside `SqliteCombatEncounterRepository`, called from `Advance` after its own transaction commits. Verified: a real `Advance` call (not a direct service call) expires a due `ForRounds` effect; an effect not yet due stays `Active`; non-combat and already-terminal effects are untouched; the round/turn advance commits regardless of a sibling candidate's own processing failure, and that sibling still expires correctly; multiple due candidates across participants are all handled; an effect on a character outside the current roster is left alone (documented gap); the pre-existing MainGM gate is unaffected; both a round-boundary and a turn-boundary duration type are evaluated by the same wiring. `SqliteCombatEncounterRepository`'s constructor gained two optional parameters with real defaults -- all 9 pre-existing call sites compile unchanged. One pre-existing architecture test (`CombatScopeTests.cs`) was updated to reflect this task's own deliberate, narrow `Odyssey.Application.Effects` exception. Full solution test suite (1009 tests) green.

## 18. Change control

### Decisions made during execution

- **Wiring point: inside `SqliteCombatEncounterRepository.Advance`, not `CombatEncounterService.Advance`.** Direct code read confirmed `CombatEncounterService.Advance` is a pure two-line authorization wrapper (`if (!ActorIsMainGm) return Denied; return repository.Advance(...);`) with no transaction and no data access of its own -- the real work, and the only place a transaction is already open with the full participant list already known, is the `Sqlite`-layer implementation. This governing ТЗ's own §2.1 made this decision explicit; verified, not merely assumed.
- **Transactional strategy: NOT atomic with `Advance`'s own round/turn-advance commit -- a separate, immediately-following step after that transaction commits.** `SqliteActiveEffectRepository.ExpireActiveEffect` opens its own separate `SqliteConnection` (confirmed by direct code read), an architectural fact this task does not change (forbidden path: no signature/connection-strategy change to `ExpireActiveEffect`). `ADR-029` §7 itself imposes no atomicity requirement between round/turn advancement and dependent-effect expiry. Rolling back an already-committed round/turn advance because one effect's own expiry failed would be a materially more disruptive failure mode than a briefly-late expiry, so `Advance`'s own transaction commits first and unconditionally; the expiry wiring runs after, and a failure there never unwinds it.
- **Enumeration: by the encounter's own current participants, `ListActiveEffectsByTarget` per participant, filtered in-memory by `CombatBinding.EncounterId`.** `IActiveEffectRepository` has no "all effects for encounter X" method, and this task is explicitly forbidden from adding one. A brute-force full-campaign scan was rejected as unacceptable and precedent-less; per-participant enumeration bounds the read to the encounter's own real size.
- **`EffectDurationType` is recovered by decoding each candidate's own `EffectMechanicsSnapshot` via `TypedDefinitionCodec.DecodeEffect`, exactly the established source `ItemEffectLifecycleService` (`505`) already uses for the identical purpose -- not a newly-invented source.** `ActiveEffect`/`CombatDurationBinding` do not themselves carry `EffectDurationType` as a field (confirmed by direct code read); it lives only on the content-catalog `EffectDefinition`, recoverable from the already-pinned mechanics snapshot payload every real `ActiveEffect` carries. A decode failure, or a decoded type outside the six combat duration types (`CombatEffectExpiryService.IsCombatDurationType`), causes that one candidate to be silently skipped (not thrown), consistent with this task's own "one candidate's failure never disturbs the rest" invariant.
- **A fresh, internally-synthesized `CommandId` is generated per expiring candidate -- never `Advance`'s own single incoming `CommandId` reused across multiple candidates.** `SqliteActiveEffectRepository.ExpireActiveEffect` routes through `SqliteSavingPipeline`, whose idempotency is keyed by `CommandId` alone. Reusing one `CommandId` for a second candidate's own `ExpireActiveEffect` call would make `SqliteSavingPipeline` treat it as a replay of the FIRST candidate's already-applied result, silently skipping the second candidate's own real expiry -- a genuine correctness bug the governing ТЗ's own text did not explicitly flag but that direct inspection of `SqliteSavingPipeline`'s own replay mechanism revealed. Since `Advance` itself never re-executes this wiring on its own replay (the `Replay()` check short-circuits before reaching it), synthesizing a fresh internal `CommandId` per candidate carries no idempotency risk of its own.
- **`SqliteCombatEncounterRepository`'s constructor gained two new OPTIONAL parameters (`IActiveEffectRepository`, `ICombatEncounterLifecycleReader`), both defaulting to real, unmocked implementations, rather than a required breaking change.** Direct search found 9 existing call sites across the test suite using the single-argument constructor; the same "optional parameter, real default" precedent this codebase already uses for a comparable situation was applied here rather than forcing all 9 to change. `ICombatEncounterLifecycleReader`'s own default (`new SqliteCombatEncounterLifecycleReader(this)`) passes the repository itself, which already fully implements `ICombatEncounterRepository` -- no circularity at runtime, just a self-reference.
- **`Advance`'s own public result type (`Result<CombatEncounterRecord>`) is NOT widened to report which effects expired.** The governing ТЗ's own §3.2 explicitly allowed "just observability through a direct DB/repository state query in tests" as an acceptable alternative to changing the result shape. `CombatEncounterRecord` is used pervasively; adding an expiry-report field to it (or introducing a parallel out-parameter) for a rarely-relevant diagnostic would be a disproportionately invasive change for what every test in this task's own suite can already observe directly via `IActiveEffectRepository.ListActiveEffectsByTarget` after calling `Advance` -- exactly the same pattern every predecessor task in this block already uses to verify state.
- **One pre-existing architecture test, `CombatScopeTests.Production_scope_has_no_attack_rng_effect_ui_or_network_surface` (`602`), required updating -- renamed to `..._no_attack_rng_ui_or_network_surface`, with `"using Odyssey.Application.Effects"` removed from its own forbidden-string list.** This test predates this task and asserted that `SqliteCombatEncounterRepository.cs` never references `Odyssey.Application.Effects` at all -- a real, direct architectural conflict with this task's own explicit, governing mandate to call `CombatEffectExpiryService`/`IActiveEffectRepository` (both in that namespace) from exactly that file. This is a deliberate, narrow, now-documented exception (composition of an already-accepted service for a governing-ТЗ-mandated purpose), not a silent widening of combat encounter timeline's own scope -- RNG, Networking, UI, Game Log, and attack-specific (`DiceRoll`/`DamageResult`) surfaces remain forbidden in the updated test exactly as before. A fixture correction in response to an approved design decision, by the same precedent `609` already established for its own three pre-existing test-fixture fixes.
- **Test-ID: continues `TC-ATTACK-*` (`093`-`100`), not a new `TC-COMBAT-*` prefix -- even though a live `TC-COMBAT-*` prefix does in fact already exist** (`TC-COMBAT-016`/`017`, `602`'s own `CombatScopeTests.cs` entries in `Tests/Metadata/test-catalog.json` -- a correction to this task's own governing ТЗ's §1 claim that no such prefix exists, confirmed by direct grep). This does not change the outcome: `TC-COMBAT-016`/`017` are `602`'s own pre-existing entries for a different test file's own different tests, not a reason to introduce a THIRD naming scheme for this task's own new tests. The governing ТЗ's own reasoning for continuing `TC-ATTACK-*` stands on its own merits (this whole work item belongs to the `ADR-029` full attack pipeline block by subject matter, independent of which package a given task's code happens to live in -- `609`/`610` already established this same precedent for code living in `SqliteAttackApplyRepository`), so `093`-`100` continue that series as directed.
