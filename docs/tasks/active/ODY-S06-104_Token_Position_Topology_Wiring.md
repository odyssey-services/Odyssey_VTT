# ODY-S06-104 — Character↔Token Link + Attack Participant Position/Distance Wiring

## 1. Task identity
`ODY-S06-104`; status: In Review (Draft PR, see the backlog row for the link once opened). Fourth task of `SLICE-06`, third and final of the block-A data-wiring sequence `ODY-S06-102` reordered.

## 2. Goal
Close the third and final data gap `ODY-S06-105` (the real `IAttackRulesEvaluator`) will need: `WeaponDefinition.Range`-style range checks require real position/distance data, which today does not exist anywhere in the codebase (`TokenRecord` has no `CharacterId`, and `CombatEncounter` is scene-agnostic). This task links a token to a Character at creation time, resolves an attack participant's position through that link, and computes each target's real distance from the actor -- passed through `AttackEvaluationSnapshot.Topology` as raw data, not a final range verdict. This task supplies data; it does not implement the evaluator or decide what counts as "in range."

## 18. Change control

### Decisions made during execution

- **`ListTokensByCharacter` is campaign-wide, not Scene-scoped, and is a genuinely new query shape -- not the literally-proposed-and-rejected `GetTokenByCharacter(campaign, sceneId, characterId, correlationId)`.** Direct inspection confirmed `CombatEncounter` carries no `SceneId` anywhere (`CreateCombatEncounterRequest`/`CombatEncounterRecord`, both read in full before deciding) and `ISceneRepository` has no campaign-wide "list every scene" method either -- so a Scene-scoped lookup cannot be constructed by the caller in the first place; the only version of "ListTokens + in-memory filtering" that can actually run without already knowing a SceneId is a query filtered by `CampaignId`+`CharacterId` directly. This is a narrow, single-purpose, additive method (one SQL `WHERE` clause, no join, since `CharacterId` now lives directly on `Token`), consistent with `ODY-S06-103`'s own `ListEquippedEntriesByCharacter` precedent for scope discipline, even though the exact shape differs from what was informally sketched as a starting point.
- **Range units: `WeaponDefinition.Range` and `AttackTargetDistanceEntry.Distance` are the same "world units (meters)" scale `BoardGeometry.GeometryEpsilonV1`'s own doc comment already establishes, with no conversion factor.** No other unit anchor exists anywhere in the codebase (confirmed by the originating research); introducing a second, unexplained scale would create an ambiguity this task has no authority or need to resolve. Recorded explicitly in `AttackTargetDistanceEntry`'s own doc comment so a future reader does not need to re-derive this.
- **`Topology`'s computed value is a distance (`double`), not the two raw `TokenPosition` values.** Computing a Euclidean distance is a pure, deterministic operation with no Ruleset/business meaning of its own -- it belongs in this data-wiring layer (this task), not duplicated inside `ODY-S06-105`'s own future evaluator. Passing raw positions instead would force every future evaluator call to re-invoke `BoardGeometry` itself for no benefit, and would leak two internal coordinate values into a Rules-facing snapshot that only ever needs their relationship.
- **A target that could not be resolved (no linked token, or a cross-Scene pair) is simply absent from `AttackTopologyInput.Entries`, not an error and not a synthetic "infinite distance" placeholder.** This mirrors `ODY-S06-103`'s own established precedent for armor exactly (a target with no equipped armor is absent from `AttackArmorInput.Entries`, not a zero-`Protection` fabrication) -- and per the governing ТЗ's own explicit instruction, missing position data must NOT become a new hard-fail the way `ODY-S06-103`'s own deliberate equip-status gate was. `Unavailable` is returned only when the AGGREGATE across every target is empty (mirroring `ReadArmor`'s own aggregate-level decision), not per-target.
- **`SqliteAttackStateReader`'s constructor gained a required fifth parameter (`ISceneRepository scenes`), not an optional one.** Direct grep found exactly seven call sites, all in tests, all straightforward to update in this same task/PR -- small enough that a required parameter (matching this codebase's own established precedent from `ODY-S06-102`'s `AttackParticipantState` and `ODY-S06-103`'s interface-member addition) was judged clearer than a defaulted one nothing else would ever omit.
- **`CreateToken`'s new `characterId` parameter IS optional (unlike the `SqliteAttackStateReader` constructor case above), because its own call-site count (10, across production and test code, most having nothing to do with Character linkage) made a required parameter a needless mass edit for a genuinely optional concept (`08_Scenes_And_Board`'s own "a token need not represent a Character" vocabulary) -- the governing ТЗ itself specified this as optional for exactly this reason.** The asymmetry between this decision and the `SqliteAttackStateReader` constructor decision above is deliberate, not an inconsistency: one is a genuinely optional domain concept with many unrelated callers; the other is a required collaborator with few, all-related callers.
- **`MoveToken` now also reads and preserves the moved token's own `CharacterId` in its returned `TokenRecord`.** `MoveToken`'s own `UPDATE` statement never touches the `CharacterId` column, so the link survives a move in the database regardless -- but the in-memory `TokenRecord` `MoveToken` previously constructed and returned did not carry it forward (it wasn't part of that record's own shape before this task). Fixed as a direct, minimal consequence of this task's own field addition, not a new feature -- a `TokenRecord` object should not lie about a field the database itself still has correct.
