# ODY-S10-105 — Stored MainGM Check in the Dice/Inventory Subsystem

## 1. Task identity
`ODY-S10-105`; status: In Review (Draft PR, merge deferred to the product owner). Step MG-5 of the "replace the client-supplied MainGM flag" sub-track (`docs/tasks/SLICE-10_IMPLEMENTATION_BACKLOG.md`) — the fifth and final subsystem of the track.

## 2. Goal
Make the four strictly-MainGM-only dice points and the eight strictly-MainGM-only inventory points depend on the stored campaign membership (`CampaignMembershipAuthorization.IsMainGm`) instead of a caller-supplied flag, and make `SqliteInventoryRepository.ApplyItemDefinitionMigration`'s existing MainGM check real — all without inverting the two dice methods' pre-existing "own roll, then MainGM" fast path, and without adding an authorization gate to `ConsumeItemUnit`, which deliberately has none.

## 3. Authority
This task's governing ТЗ; `ODY-S10-101`'s Application-layer pattern (`BoardMovementService`), reused for the seven Application-layer dice/inventory points; `ODY-S10-102`'s Persistence-layer pattern (`SqliteCharacterRepository`), reused for `SqliteInventoryRepository`.

## 4. In scope
- **Dice (Application layer):** `DecideModifierRequest`/`ApplyOverrideRequest`/`RequestFullRerollRequest`/`CancelRollRequest` gain `CampaignHandle Campaign` (none had one); `DiceRollService.DecideModifier`/`ApplyOverride`/`RequestFullReroll`/`CancelRoll` gain an `ICampaignRepository` parameter and a real `CampaignMembershipAuthorization.IsMainGm` check. `RequestFullReroll`/`CancelRoll` keep their existing order exactly: the cheap "is this my own roll" check still runs first, and the (now real) MainGM lookup runs only when that check does not already pass — proved by a poisoned-repository test showing zero lookup calls for the roll's own actor. `SubmitRoll`'s own `ActorCanCreateRoll` gate is untouched (a different, non-MainGM permission).
- **Inventory (Application layer):** `InventoryStackOperationService.Split`/`.Merge`, `InventoryMovementService.MoveItemInstance`/`.MoveItemStack`, `EquipmentService.Equip`/`.Unequip`, `InventoryCreationService.CreateItemInstanceFromDefinition`/`.CreateItemStackFromDefinition` each gain an `ICampaignRepository` parameter and the same real check, fail closed, no alternative "it's my item" path added (recon confirmed none exists today). Six request types (`SplitItemStackRequest`, `MergeItemStacksRequest`, `MoveItemInstanceRequest`, `MoveItemStackRequest`, `EquipRequest`, `UnequipRequest`) had a constructor `actorUserId` parameter that was validated but never stored — all six gained a real `ActorUserId` property. `EquipRequest.EquippedByUserId` (a provenance label, not an actor) is untouched.
- **Inventory (Persistence layer):** `SqliteInventoryRepository` gains a required `ICampaignRepository` constructor dependency (`ArgumentNullException` on `null`, `SqliteCharacterRepository`'s own precedent); `ApplyItemDefinitionMigration` now performs the real lookup instead of trusting its `actorIsMainGm` parameter (kept the interface's own already-had `actorUserId`). `ConsumeItemUnit` lost both `actorUserId` and `actorIsMainGm` — neither was read for anything beyond a bare validity check, and the interface's own doc comment already says this layer deliberately does not authorize; removing two truly dead parameters follows this whole track's "no dead parameters" convention. No gate was added inside `ConsumeItemUnit` itself.
- **Client:** `RollPanelPresenter.cs`'s constructors now take a real `CampaignHandle`/`ICampaignRepository` pair instead of a bare `CampaignId` (recon found the presenter itself had no such pair in scope, only its one production caller did); the four dice-service call sites pass them through. `TrialScreenPresenter.cs` — its only production caller — passes `demo.Value.Campaign`/`demo.Value.CampaignRepository` (already held from the `ODY-S10-101` demo-campaign pattern) instead of `demo.Value.Campaign.CampaignId`. Two Unity Editor tests that construct `RollPanelPresenter` directly (`GameLogPresenterTests.cs`, `RollPanelPresenterTests.cs`) needed the same real pair; `RollPanelPresenterTests.cs` did not have one at all before this task and now builds its own real, registered campaign the same way `GameLogPresenterTests.cs` already did.
- Tests, catalogue `TC-DICE-024`–`028`/`TC-INVENTORY-197`–`200`, the `SLICE-10` backlog, this contract and its plan.

## 9. Tests and validation
New: `TC-DICE-024` (`DecideModifier` denies an unregistered user, a registered Player and a registered Observer, and lets the host and a second, separately-registered MainGm through); `TC-DICE-025`/`026` (fail-closed for `DecideModifier`/`ApplyOverride` via a poisoned membership repository, even for the host); `TC-DICE-027` (`RequestFullReroll`: a registered Player is still denied for someone else's roll, a real MainGm succeeds, and the roll's own actor needs zero lookup calls — proved with a poisoned repository that would fail loudly if reached); `TC-DICE-028` (same registered-Player-still-denied/real-MainGm-succeeds shape for `CancelRoll`). `TC-INVENTORY-197`/`198` prove the six newly-added `ActorUserId` properties are genuinely read, not merely accepted: a registered-but-not-MainGm Player is denied on `Split`/`Merge` and on `Equip`/`Unequip`, and a different, separately-registered MainGm succeeds. `TC-INVENTORY-199`/`200` mirror the same denied/allowed shape plus a fail-closed case for `MoveItemInstance`. A deliberate mutation (`DecideModifier`'s denial short-circuited) made `TC-DICE-024` fail (`Expected: True, But was: False`) and was reverted.

**Existing tests changed, and why:** every construction of the four dice request types and the eight inventory request types lost their `bool` flag argument; every one of the twelve service-method calls (plus `SqliteInventoryRepository`'s own constructor) gained the campaign repository. Where a request's own actor argument was previously an unregistered/random `UserId` paired with a self-claimed `true`, it became the campaign's registered host (`DevIdentityProvider.AssignHost()`) or, for `false`/denial cases, stayed unregistered — the same "claim becomes real judged-by-role" rewrite every prior task in this track made. `Odyssey.Tests.Unit.dll`: 183/183 (was 178). `Odyssey.Tests.Persistence.dll`: 883/883 (was 881, both pre-task baselines after `ODY-S10-104` merged to `main`).

## 18. Change control

### Decisions made during execution
- **A real, user-facing scope gap was found and, per instruction, escalated rather than routed around:** the ТЗ itself anticipated that `RollPanelPresenter.cs` might not already have a `CampaignHandle` in scope, and said to record the finding and ask rather than invent a workaround. Recon confirmed exactly that: the presenter held only a bare `CampaignId`; the real `CampaignHandle`/`ICampaignRepository` pair existed one level up, in `TrialScreenPresenter.cs` (already using the `ODY-S10-101` demo-campaign pattern), plus in two Unity Editor test files not named in the ТЗ's allowed-path list. The product owner was asked and chose to expand scope to cover `TrialScreenPresenter.cs` and the two test files, minimally and mechanically, following the existing demo pattern — done as approved.
- **`ConsumeItemUnit`'s `actorUserId`/`actorIsMainGm` were removed outright, not just the flag.** The ТЗ asked for a judgment call here: `actorIsMainGm` clearly had to go, and `actorUserId` was already unused for anything but a bare validity throw (no audit row, no ledger reference, nothing) — keeping a parameter nobody reads contradicts the "no dead parameters" convention this whole track has followed since `ODY-S10-102`. Confirmed safe: the only callers of this exact public overload are the two allowed test files; `UseItemService`'s own compensation path calls the separate, unaffected internal `ConsumeItemUnitInTransaction` helper, never this one.
- **`SqliteInventoryRepository`'s constructor becoming a required dependency broke ~14 test files outside the ТЗ's 10 named ones** (attack/combat/check fixtures that also happen to construct this shared repository as unrelated setup). This is the same shape `ODY-S10-102` already hit and the product owner already accepted as necessary, mechanical collateral of a shared-class signature change — handled identically here: only the constructor argument (and, in a few files, an unregistered "MainGM" fixture variable that needed registering to keep meaning what its name already claimed) changed, no production file of those subsystems was touched.
- **A scoping mistake was caught and fixed before it reached the diff:** an early mechanical pass, matching `NewUserId(), actorIsMainGm: true,`, briefly touched two legitimate, still-untouched `ActivateAbilityRequest`/`UseItemRequest` constructions in `MvpTwoCharacterCombatScenarioTests.cs` that happen to share that exact text shape (`MG-3b`, forbidden). Caught immediately by the resulting compile errors (`ActivateAbilityRequest`/`UseItemRequest` missing their real, still-in-scope `actorIsMainGm` argument), reverted, and the whole diff was re-swept for `actorIsMainGm`/`ActorIsMainGm` afterward to confirm no other such collision survived.

### Findings (reported, not fixed silently)
- `UseItemService.cs`/`ActivateAbilityService.cs`/`AttackEvaluationService.cs`/`SqliteActivateAbilityRepository.cs` (`MG-3b`) and `RedactCharacterForExport.cs`/`CharacterExportContracts.cs` remain exactly as `ODY-S10-103` left them — not touched by this task, both already tracked in the backlog as separate future work.
- No file of the characters/board/combat-effects/content-catalog subsystems is in this diff.
- Unity Editor test files were edited by direct code reading and reasoning, not a Unity Editor compile — this environment has no Unity Editor available; the change is plain C# against already-established types (`CampaignHandle`, `ICampaignRepository`, `SqliteCampaignRepository`) the same assembly already references via `BoardScreenPresenter.cs`'s own demo-campaign helper.
