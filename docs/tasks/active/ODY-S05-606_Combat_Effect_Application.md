# ODY-S05-606 — Combat Effect Application (`EffectApplicationDecision`)

## 1. Task identity
`ODY-S05-606`; status: In Progress.

## 2. Goal
Implement `ADR-029` §8: when an attack's atomic apply commits (immediately or via an approved intervention), every candidate whose final `EffectApplicationDecision` is `Apply` creates/stacks an `ActiveEffect` row -- routed through the existing `ADR-028` `EffectStackPolicy` decision layer (`ODY-S05-503`), in the same transaction as the rest of atomic apply. `DoNotApply`/unresolved `RequiresIntervention` candidates never create a row. This task does not decide `EffectApplicationDecision` itself (Rules already does, `ODY-S05-603`, unmodified) and does not implement `AttackDelta`/Character-Item state application (`ODY-S05-609`'s own territory).

## 3. Authority
`ADR-029` §1 rule 8, §8 (verbatim: candidate composition, "Apply only" rule, `Instant` non-representation, standalone-repository/shared-pipeline/atomic-apply requirement), §9 (module boundaries, no nested handler calls); `ADR-028` §7 (`EffectStackPolicy`, reused via `ODY-S05-503`'s existing `ActiveEffectStackingRules`, unmodified) and §10 (creation authorization paths); `ODY-S05-603`'s `AttackEffectCandidate`/`EffectApplicationDecision` (extended, not rewritten); `ODY-S05-604`'s `AttackOutcomeRecord`/`SqliteAttackApplyRepository` (extended); `ODY-S05-605`'s `CombatDurationBinding` (reused verbatim).

## 4. In scope
Backward-compatible extension of `AttackEffectCandidate` (reason category, host-only reason detail, `CombatDurationBinding`, `EffectStackPolicy`, `EffectMechanicsSnapshot`); persistence of `EffectCandidates` on `AttackOutcomeRecord`/`AttackOutcome` (new `EffectCandidatesJson` column); combat `ActiveEffect` row creation/stacking embedded directly in `SqliteAttackApplyRepository`'s own atomic-apply transaction, reusing `SqliteActiveEffectRepository`'s internal SQL helpers; tests.

## 5. Out of scope
Deciding `EffectApplicationDecision` (`ODY-S05-603`'s own Rules-layer job, unmodified). `605`'s expiry mechanism (`ActiveEffectExpiryRules.cs`/`CombatEffectExpiryService`, untouched). `607`'s compensation/audience-filtered Game Log projections. `609`'s `AttackDelta`-to-Character/Item-state application. Calling the public `IActiveEffectRepository.CreateActiveEffect` from the combat apply path (architectural decision, §18). Any new method on `IActiveEffectRepository`/`ICombatEncounterRepository`. Durable persistence of `ActiveEffectStackConflict` (`RequestGMResolution`'s own pending state) -- `ODY-S05-503` never built one; this task does not either (disclosed limitation, §18).

## 6. Domain contract
`AttackEffectCandidate` (existing type, `ODY-S05-603`) gains, via a new constructor overload (the original 4-argument constructor is preserved verbatim for every existing caller): `EffectApplicationReasonCategory ReasonCategory` (new small public-safe enum, `TriggerConditionMet`/`TriggerConditionNotMet`/`RequiresInterventionChoice`), `string HostOnlyReasonDetail`, `CombatDurationBinding? DurationBinding` (`ODY-S05-605`, reused), `EffectStackPolicy StackPolicy` (`ADR-028`, reused), `EffectMechanicsSnapshot MechanicsSnapshot` (see §18 for why this field was added beyond the ТЗ's own explicit list).

## 7. Application contract
`AttackOutcomeRecord` gains `IReadOnlyList<AttackEffectCandidate> EffectCandidates`; `IAttackApplyRepository.RecordAttackOutcome` gains the same parameter. `AttackApplyService.ResolveAttack` passes `EffectCandidates` through unchanged (no new decision logic in the Application orchestration layer itself -- all effect-application logic lives in the Persistence layer's own atomic-apply transaction, per §18's architectural decision).

## 8. Persistence boundary
`SqliteAttackApplyRepository` gains one new column (`EffectCandidatesJson`, JSON-serialized) and, inside its own existing `apply:` transaction lambdas (both `RecordAttackOutcome`'s immediate-accept path and `ResolveAttackIntervention`'s Approve path), a new `ApplyEffectCandidates` step: for each `Apply`-decided candidate, reads any existing conflicting `ActiveEffect` row on the same connection/transaction, calls the existing `ActiveEffectStackingRules.ResolveStacking`, and executes the resulting mutation (insert/update) via `SqliteActiveEffectRepository`'s own now-`internal` SQL helpers (`InsertColumns`/`InsertPlaceholders`/`AddParameters`/`SelectColumns`/`ReadRecord`/`EnsureActiveEffectTables`) -- never the public `CreateActiveEffect` method, which would open its own separate connection/transaction. No new table; the existing `ActiveEffect` table (with `605`'s own `Combat*` columns) is reused as-is.

## 9. Tests and validation
`TC-ATTACK-047`-`055`: Apply/DoNotApply/RequiresIntervention-approved/RequiresIntervention-rejected row-creation behavior, candidate persistence across the pending/resolved steps (direct SQL column check), atomicity under a guard failure (whole-database row-count check), two stacking-collision scenarios (`IncreaseStacks`, `RequestGMResolution`), and an architecture guard proving `CreateActiveEffect` is never called from the combat apply path. Full `dotnet test` and the repository validation scripts must be green.

## 10. Compatibility and rollback
`AttackEffectCandidate`'s original constructor is preserved (backward compatible); `AttackOutcomeRecord`/`RecordAttackOutcome`/`IAttackApplyRepository` gain a required new parameter, but the only callers are this same PR's own files and tests (verified directly -- no external caller exists). One new nullable-safe column on the existing `AttackOutcome` table; the existing `ActiveEffect` table's own schema is unchanged (`605` already added the `Combat*` columns this task writes into). Reverting this task's source and column leaves `602`-`605` unaffected.

## 11. Security and privacy
No new authorization gate is added: combat effect creation inherits the already-authorized attack command's own authorization (immediate accept was already actor/MainGM-authorized in `603`'s `AuthorizeAndRead`; intervention approval is already MainGM-gated by `604`). See §18 for the explicit citation and reasoning behind this choice, as the governing ТЗ required.

## 12. Observability
No new Game Log entry or diagnostic event; the existing `AttackResolved` Game Log entry (`604`) already narrates the committed attack. Per-effect logging is `607`'s own audience-filtered-projection territory.

## 13. Performance
At most one existing-conflict SELECT and one INSERT/UPDATE per `Apply`-decided candidate, inside the already-open atomic-apply transaction; no additional connection, no polling, no scheduler.

## 14. Dependencies
`ODY-S05-603` (`AttackEffectCandidate`/`EffectApplicationDecision`, extended not rewritten), `ODY-S05-604` (`AttackOutcomeRecord`/`SqliteAttackApplyRepository`, extended), `ODY-S05-605` (`CombatDurationBinding`, reused verbatim), `ODY-S05-503` (`ActiveEffectStackingRules`, reused verbatim, unmodified), `ODY-S05-502` (`SqliteActiveEffectRepository`'s own SQL helpers, made `internal` for reuse -- its public `IActiveEffectRepository` contract is unmodified).

## 15. Dependencies (packages)
None new (`Newtonsoft.Json`, already used elsewhere in `Odyssey.Persistence`, is reused for `EffectCandidatesJson`).

## 16. Implementation plan

## 17. Completion evidence
Implemented the backward-compatible `AttackEffectCandidate` extension, `AttackOutcomeRecord`/`IAttackApplyRepository` candidate persistence, and `SqliteAttackApplyRepository`'s own embedded combat-effect apply step (reusing `SqliteActiveEffectRepository`'s internal SQL helpers, never its public `CreateActiveEffect`). Verified: `Apply` creates a row with `CombatDurationBinding` intact; `DoNotApply` and an unresolved `RequiresIntervention` create none; an approved intervention creates its row on that deferred step; a rejected intervention creates none; candidates survive the pending-to-resolved round trip; a guard failure leaves no partial `AttackOutcome`/`ActiveEffect` row; `IncreaseStacks`/`RequestGMResolution` collisions route through the existing `ActiveEffectStackingRules`, not a duplicated decision.

## 18. Change control

### Decisions made during execution

- **Combat `ActiveEffect` rows are inserted directly inside `SqliteAttackApplyRepository`'s own `SqliteSavingPipeline.Execute` transaction, reusing `SqliteActiveEffectRepository`'s own SQL helpers made `internal` for this purpose -- the public `IActiveEffectRepository.CreateActiveEffect` is never called from the combat apply path.** This is the governing ТЗ's own explicit, non-discretionary architectural mandate (its section 5): `SqliteSavingPipeline.Execute` opens its own connection/transaction per call, confirmed by direct inspection, so calling `CreateActiveEffect` from inside `SqliteAttackApplyRepository`'s own transaction would open a SECOND, independent transaction -- breaking `ADR-029` §8's own "as one participant in the attack's atomic apply transaction" requirement and `ADR-012`'s single-commit rule. `ADR-028` §6's own "no new method on `IActiveEffectRepository`" rule is honored (no method was added or changed on that interface); `ADR-029` §8's own literal text ("through the standalone `IActiveEffectRepository` and shared `SqliteSavingPipeline`") is honored at the level of abstraction it actually matters at -- the same standalone table, the same `SqliteSavingPipeline` machinery, the same shared internal SQL shape -- not the specific C# public method call, exactly as `ODY-S05-604` already established for writing directly into `GameLogEntries`/`DiceRolls` (tables `SqliteGameLogRepository` owns) without calling that repository's own public method. `SqliteActiveEffectRepository`'s five private helpers (`InsertColumns`, the new `InsertPlaceholders`, `AddParameters`, `SelectColumns`, `ReadRecord`, `EnsureActiveEffectTables`) were changed to `internal` -- a same-assembly visibility change, not a public contract change -- specifically so this reuse is a real shared helper, not a duplicated SQL string (the governing ТЗ's own preferred resolution over documented duplication).
- **A self-identified gap, closed beyond the governing ТЗ's own explicit field list: `AttackEffectCandidate` also gained `EffectMechanicsSnapshot MechanicsSnapshot`, not only the four fields the ТЗ named (reason category, duration bindings, stacking key/options).** Building a real `ActiveEffect` row requires a full `EffectMechanicsSnapshot` (`SourceDefinitionRef`, `DefinitionSnapshotVersion`, `ContentType`, a non-empty `Payload`) -- the pre-existing `MechanicsRef` field is only a `ContentDefinitionRef` (identity + version), not snapshot content, and `ADR-029` §8 itself requires the candidate to travel with its own already-pinned snapshot ("not discovered by loading the latest content definition"). Without this field, no valid `ActiveEffect` could be constructed from a candidate at all -- the same category of self-caught, pre-review gap as `ODY-S05-605`'s own `CombatDurationBinding` persistence fix. The original 4-argument `AttackEffectCandidate` constructor synthesizes a placeholder snapshot (`ContentType.Effect`, `Payload = "{}"`) purely for its own backward-compatibility contract, matching this codebase's own pervasive "{}" placeholder-payload convention in every test fixture that has no real Ruleset content to supply.
- **Rights/authorization (governing ТЗ section 7): combat effect creation inherits the already-authorized attack command's own authorization; no separate MainGM (or any other) gate is added for `ApplyEffectCandidates` itself.** The immediate-accept path was already actor/MainGM-authorized by `AttackEvaluationService.AuthorizeAndRead` (`ODY-S05-603`, unmodified) before `RecordAttackOutcome` is ever called; the deferred path is already MainGM-gated by `ResolveAttackIntervention` (`ODY-S05-604`) before its own Approve branch runs. `ADR-028` §10's two creation-authorization paths (authorized item-use vs. direct MainGM-only) do not cleanly describe a combat-triggered effect at all -- it is authorized by a third, already-established path this ADR-029 attack pipeline itself created (`ODY-S05-603`/`604`'s own authorization chain), not a new instance of either §10 path. Adding a redundant permission check here would duplicate, not strengthen, an already-enforced authorization boundary.
- **`RequiresIntervention` candidates are approved/rejected as a group with the overall attack outcome, not individually.** `ODY-S05-604`'s own architecture has exactly one Approve/Reject/Cancel decision per attack (no per-candidate resolution mechanism exists or is introduced here) -- approving the intervention applies every `Apply` candidate plus every `RequiresIntervention` candidate from that same attack; rejecting or cancelling applies none of them, including any candidate that was plain `Apply` from the start (the attack as a whole did not land). Inventing per-candidate intervention resolution is a materially larger feature this task does not build.
- **A `RequestGMResolution` stacking collision creates no row for that candidate, and the rest of the attack's own atomic apply still commits.** `ODY-S05-503`'s own `ActiveEffectStackConflict` has no durable, cross-session persistence anywhere in this codebase -- its own doc comment explicitly defers that to "whichever future task actually needs it." Inventing a new persistence mechanism for it here would be new scope beyond `ADR-029` §8's own text (which only requires routing stacking through the existing `EffectStackPolicy` handling, not resolving every possible pending state durably). This is a disclosed limitation, not a silent gap: a future task must add `ActiveEffectStackConflict` persistence before a combat-sourced `RequestGMResolution` collision can actually reach a GM for resolution.
- **`SqliteActiveEffectRepository.cs`'s five newly-`internal` helpers required fixing a line-ending regression** a text-processing script introduced while making that visibility change (the whole file was rewritten with CRLF line endings against this repository's own LF convention) -- caught by `verify-format.ps1` before this PR was opened, not left for review to find.
