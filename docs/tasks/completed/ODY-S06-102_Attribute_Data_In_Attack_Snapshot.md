# ODY-S06-102 — Attribute Data in Attack Snapshot

## 1. Task identity
`ODY-S06-102`; status: Done (PR #158, merged into main). Second task of `SLICE-06`, first of the block-A reordering this task itself performs.

## 2. Goal
Make `AttackParticipantState` carry the acting/target character's own real, already-purchased attribute `EffectiveValue` readings, so `ADR-030` §6.2's `attributeReference` formula term (`1d6+STR`) has real data to resolve against once a future task (`ODY-S06-105`) implements the real `IAttackRulesEvaluator`. Today `AttackParticipantState` carries only `CharacterId`/`LifecycleStatus`/`ApprovalState` -- no attribute value at all -- even though `SqliteAttackStateReader.Read` already loads the full `CharacterRecord` (attributes included) for every actor/target. This task closes that gap; it does not interpret formulas or implement the evaluator.

## 3. Authority
The governing ТЗ (`ODY-S06-102`, this task) restructures `docs/tasks/SLICE-06_IMPLEMENTATION_BACKLOG.md`'s own block-A sequence, per direct product-owner instruction recorded there (section 10): build all missing attack-snapshot input data first (attributes, this task; armor, `103`; position/range, `104`), then build the real evaluator once (`105`), rather than a minimal evaluator first and three retrofits after. `ADR-030` §6.2 (the `attributeReference` term, "resolved... against a small resolution context the caller supplies: for the attack evaluator, the acting/target `AttackParticipantState`'s own already-loaded attribute snapshot"). `ADR-030` §5 point 2 ("resolving any attribute-reference term against `AttackEvaluationSnapshot.Actor`'s own already-loaded attribute state -- no new database read").

## 4. In scope
`Packages/com.odyssey.domain/Runtime/Combat/AttackPipelineContracts.cs` -- `AttackParticipantState` gains an `AttributeValues` property (`IReadOnlyDictionary<AttributeDefinitionId, long>`, the existing Domain attribute catalog-key type, reused verbatim -- no new attribute-representation format), defensively copied in the constructor. `Packages/com.odyssey.persistence/Runtime/Sqlite/SqliteAttackStateReader.cs` -- its private `State(CharacterRecord)` mapping now also copies `record.Attributes`' own `EffectiveValue` readings, keyed by `AttributeDefinitionId`, into the new field; no new database read (the `CharacterRecord` this reads from is already loaded by the surrounding `Read` method for `LifecycleStatus`/`ApprovalState`). The two existing direct constructor call sites (`SqliteAttackStateReader.cs` itself, and `AttackEvaluationServiceTests.cs`'s own `Participant` fixture helper) updated to the new 4-argument shape. New tests (`TC-ATTACK-101`-`104`). `docs/tasks/SLICE-06_IMPLEMENTATION_BACKLOG.md` restructured per its own section 10 entry. `Tests/Metadata/test-catalog.json`.

## 5. Out of scope
The formula grammar/parser, the mechanics-primitive interpreter, and the real `IAttackRulesEvaluator` implementation itself -- all `ODY-S06-105`'s own territory; this task supplies data, it does not interpret it. `ActivateAbility` (`ODY-S06-106`). Armor/equipment data (`ODY-S06-103`) and position/range data (`ODY-S06-104`) -- named, reserved, not touched here. `IAttackRulesEvaluator`'s own interface signature. `ADR-030` itself (referenced, not revised). `RulesetDefinitionCatalog`/`RulesetMigrationRules.cs` (`ADR-025`'s own territory). Fail-closed behavior for an unresolvable/missing attribute reference at formula-evaluation time -- `ADR-030` §6.2 itself assigns that decision to the future formula-evaluator/parser task, not to this data-wiring task.

## 6. Domain contract
`AttackParticipantState` (`Odyssey.Domain.Combat`) is the only Domain type changed: its constructor gains a fourth parameter, `IReadOnlyDictionary<AttributeDefinitionId, long> attributeValues` (null rejected; defensively copied into an internal `Dictionary`, exposed as `IReadOnlyDictionary`). No new Domain type is introduced -- `AttributeDefinitionId` (`Odyssey.Domain.Character`, `ODY-S04-105`) is reused verbatim as the dictionary key, and `long` (matching `AttributeValue.EffectiveValue`'s own type) as the value, exactly mirroring how the Character aggregate itself already represents a resolved attribute value.

## 7. Application contract
No new Application-layer type or method. `AttackEvaluationService.PreviewAttack`/`EvaluateAttack` are unchanged -- they already pass whatever `IAttackStateReader.Read` returns straight to `IAttackRulesEvaluator`; this task only changes what `SqliteAttackStateReader.Read`'s own snapshot carries.

## 8. Persistence boundary
`SqliteAttackStateReader.Read` performs no new SQL query. `CharacterRecord.Attributes` (`IReadOnlyList<AttributeValue>`, `ODY-S04-105`) is already returned by the existing `_characters.GetCharacter` calls this method already makes for the actor and every target; the private `State(CharacterRecord)` helper now also folds each `AttributeValue.EffectiveValue` into the new `AttackParticipantState.AttributeValues` dictionary, keyed by `AttributeValue.AttributeDefinitionId`.

## 9. Tests and validation
`TC-ATTACK-101`-`104` (`DotNet/Tests/Odyssey.Tests.Persistence/SqliteAttackStateReaderTests.cs`), each a real call through `AttackEvaluationService.PreviewAttack`/`EvaluateAttack` (not an isolated `SqliteAttackStateReader.Read` unit test) against a real temp-directory SQLite campaign: (101) the actor's own real purchased attribute values (via `PurchaseAttributeIncrease`) appear correctly in `ProposedAttackResolution.Snapshot.Actor.AttributeValues`; (102) the same for a target, not only the actor; (103) a character with no purchased attributes yields an empty, non-null `AttributeValues` (no crash); (104) `EvaluateAttack`'s own authoritative-RNG path also carries the values (not only the RNG-free `Preview` path). The two pre-existing direct-constructor call sites were updated to compile against the new 4-argument shape and continue to pass (`AttackEvaluationServiceTests.cs`'s `Participant` helper now passes an empty dictionary, since none of that file's own tests depend on a concrete attribute value). Full solution `dotnet test` and `verify-format.ps1`/`check-repository-policy.ps1`/`verify-test-structure.ps1` all green.

## 10. Compatibility and rollback
`AttackParticipantState`'s constructor gains a fourth, REQUIRED parameter -- a source-breaking change to a `readonly struct` with exactly two known call sites in the whole repository (verified by direct grep before making the change), both updated in this same task/PR. `IAttackStateReader`/`IAttackRulesEvaluator`'s own public interfaces are unchanged. No schema change -- `CharacterRecord.Attributes` is read, not written, and no new table/column is introduced. Reverting this task's source leaves `ODY-S06-101` and all of `SLICE-05` unaffected; `AttackParticipantState` simply stops carrying attribute data again, returning to the pre-`102` (already-accepted, if incomplete) shape.

## 11. Security and privacy
Not applicable -- attribute values are already-authorized Character aggregate data the acting user (or MainGM) can already read via `GetCharacter`; this task only copies already-accessible data one hop further into an in-memory snapshot, not a new read path or a new exposure surface.

## 12. Observability
No new DomainEvent, no new log line -- a pure in-memory data-shape extension of an existing read-only snapshot.

## 13. Performance
Zero additional database reads -- `record.Attributes` is already part of the `CharacterRecord` the surrounding `Read` method already loaded. The added work is one in-memory dictionary build per participant (actor + each target), bounded by that character's own typically-small attribute count.

## 18. Change control

### Decisions made during execution

- **The new field's type is `IReadOnlyDictionary<AttributeDefinitionId, long>` (`EffectiveValue` readings keyed by the Character aggregate's own existing catalog-key type), not a `string`-keyed dictionary and not a copy of `IReadOnlyList<AttributeValue>` itself.** `CharacterRepositoryContracts.cs`/`DevelopmentEconomy.cs` were read in full before deciding: `AttributeDefinitionId` (`ODY-S04-105`) is already a validated, string-backed catalog key (e.g. `"Strength"`) with `Equals`/`GetHashCode` -- a directly usable dictionary key, not something needing a new representation. Copying the full `AttributeValue` objects (which also carry `SpentDevelopmentPoints`/`Revision`, mutation-tracking fields irrelevant to a read-only attack snapshot) was rejected as carrying unrelated Character-aggregate bookkeeping into a Rules-facing snapshot; exposing only the already-computed `EffectiveValue` (`BaseValue + PermanentAdjustment`) is what `ADR-030` §6.2's own `attributeReference` term actually needs to resolve against, and matches this class's own doc-comment convention ("effective values... computed, never hand-edited").
- **The constructor's new parameter is required, not optional/defaulted, and the two existing call sites were updated directly rather than adding a backward-compatible overload.** A direct repository-wide grep before making the change confirmed exactly two call sites (`SqliteAttackStateReader.cs`'s own production mapping, `AttackEvaluationServiceTests.cs`'s own test fixture helper) -- small enough that updating both directly is clearly simpler and more honest than introducing a second, would-be-legacy constructor overload nothing else would ever call.
- **Tests were added to `SqliteAttackStateReaderTests.cs`, calling through the real `AttackEvaluationService.PreviewAttack`/`EvaluateAttack`, not as an isolated `SqliteAttackStateReader.Read`-only test.** The governing ТЗ's own §6.1/§6.2 explicitly required this distinction. A fixed-outcome `IAttackRulesEvaluator` stand-in (`RecordingRules`, structurally identical to `AttackEvaluationServiceTests.cs`'s own `Rules` fixture) stands in for the not-yet-built real evaluator (`ODY-S06-105`'s own job) purely so the full, real `AttackEvaluationService` → `SqliteAttackStateReader` → real `SqliteCharacterRepository` pipeline actually runs end-to-end, proving the attribute data genuinely reaches the snapshot the production code path produces -- not merely that a hand-built `AttackParticipantState` object has the right shape.
- **Attribute values were seeded via the real `GrantDevelopmentPoints`/`PurchaseAttributeIncrease` commands, not by hand-constructing a `CharacterRecord`.** `CharacterRecord.Attributes` has no public setter and no test-only constructor bypass; `CharacterAbilityInstancesTests.cs`'s own established fixture pattern (grant points, then purchase) was reused verbatim rather than inventing a second way to populate the same data.
- **No fail-closed/error-handling logic for a missing or unresolvable attribute is added by this task.** The governing ТЗ's own §2.3 explicitly assigns that decision to the future `AttackDamageFormulaParser`/`CoreAttackRulesEvaluator` task (`ODY-S06-105`) -- this task's own job is only to ensure real data, when it exists, physically reaches the snapshot; `TC-ATTACK-103` proves the no-attributes case produces an empty dictionary, not a crash, which is as far as this task's own scope goes.
- **The backlog restructuring (§3 of the governing ТЗ) redefines `102`, inserts `103`/`104`, and renumbers the former `102`→`105`/`103`→`106`, with an explicit `SLICE-06_IMPLEMENTATION_BACKLOG.md` section 10 change-control entry recording the reasoning -- not a silent renumbering.** Direct inspection confirmed no separate file-based task-contract stub ever existed for the old `102` ("real evaluator") reservation -- it was a backlog-table row only (per `ODY-S06-101`'s own creation of the table, not a pre-activation reservation task in the `605`/`608` sense) -- so, per the governing ТЗ's own §3 point 5, nothing needed renaming or deleting beyond the backlog document's own table and prose.
