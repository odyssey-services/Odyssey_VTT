# ODY-S07-103 — Skill Catalog (`SkillDefinition` as publishable content, block 2)

## 1. Task identity
`ODY-S07-103`; status: Done (PR #168, merged into main). Third task of `SLICE-07`, the first decomposition of block 2 (skill catalog).

## 2. Goal
Give `ContentDefinitionType.Skill` (today a bare, unused enum value, `Skill = 11`) a real, publishable content type -- a typed `SkillDefinition` plus `TypedDefinitionCodec.EncodeSkill`/`DecodeSkill`/`CatalogValidationContracts.ValidateSkill` -- so it can flow Draft→Published through the already-existing, unmodified `SLICE-05` catalog-authoring/validation/publish pipeline, by the exact precedent `AbilityDefinition`/`EffectDefinition` (`ODY-S05-105`) already established.

## 6. Domain contract
`Packages/com.odyssey.domain/Runtime/Content/TypedDefinitions.cs`: `SkillDefinition`, a `sealed class`, Domain-layer, no serialization/persistence/Unity dependency, by direct precedent of `AbilityDefinition`/`EffectDefinition`'s own file/namespace placement and constructor-validation idiom. **Finding, not an oversight (governing ТЗ §2.1's own explicit anticipation, confirmed true by implementation):** `SkillDefinition` carries zero fields beyond what the generic `ContentDefinitionRecord` envelope (Name/Description/Tags/RulesetCompatibility) already covers. It has no `MechanicsPayloadRef` (unlike `AbilityDefinition`/`EffectDefinition`) -- a skill is never executed as a mechanic; `ODY-S07-102`'s `CoreCheckRulesEvaluator` reads it as a bare named modifier, not a `ContentBlockGraph` reference. It has no governing-attribute field -- no existing consumer (`CheckParticipantState`/`CoreCheckRulesEvaluator`/`CharacterSkill`) reads such a relationship; the check-resolution system treats attributes and skills as independent named peers. Adding either field now would be a speculative extension with no consumer; both are deliberately withheld, per the governing ТЗ §1 points 1-2.

## 7. Application contract
`TypedDefinitionCodec.EncodeSkill(SkillDefinition) -> string` / `DecodeSkill(ContentDefinitionType actualType, string propertiesJson, CorrelationId correlationId) -> Result<SkillDefinition>`, by exact precedent of `EncodeAbility`/`DecodeAbility`: `EncodeSkill` writes only the shared `schemaVersion` envelope (there is nothing type-specific to write, since `SkillDefinition` has no fields); `DecodeSkill` checks `actualType != ContentDefinitionType.Skill` first (returns `TypedDefinitionCodecFailures.WrongDefinitionType`, no JSON parsed), then `JObject.Parse` under the same `try`/`catch` over `IsMalformedPayloadException`'s already-established exception set, calls the existing, unmodified `RequireSupportedSchemaVersion`, and constructs a bare `new SkillDefinition()` on success. No new `ErrorCodes`/`ERROR_CODES.md` entries are needed -- `WrongDefinitionType`/`MalformedPayload` are already fully generic (parameterized only by `CorrelationId`), confirmed by direct code read before writing `DecodeSkill`, the identical two failures every other `DecodeX` in this file already reuses.

`CatalogValidationContracts.ValidateSkill(record, correlationId, issues)`: calls `TypedDefinitionCodec.DecodeSkill`, adds a codec-failure issue and returns early on decode failure (`AddCodecFailureIssue`, the same helper `ValidateAbility`/`ValidateEffect`/`ValidateAmmo` already use), and otherwise performs no further check -- there is no `ValidateMechanicsPayloadRef`-style call (no such field exists on `SkillDefinition`, per §1 decision 1) and no other field to validate. Decodability is the entire skill-specific check, the same shape `ValidateAmmo` already has for a type with no post-decode business rule.

## 8. Persistence boundary
None. `ContentCatalogAuthoringService.CreateDraftDefinition`/`ContentCatalogLifecycleService.PublishDefinition`/`SqliteContentCatalogRepository` are already fully generic by `DefinitionType` (confirmed working for Weapon/Armor/Ability/Effect/Item in every prior `SLICE-05`/`ODY-S06`/`ODY-S07` task) and are not modified by this task.

## 18. Change control

### Decisions made during execution

- **No new `ErrorCodes`/`ERROR_CODES.md` entries were added, unlike `ODY-S07-102`'s own five new rows for genuinely new failure semantics.** Confirmed by direct code read of `TypedDefinitionCodecFailures.WrongDefinitionType`/`MalformedPayload` before writing `DecodeSkill`: both are already fully generic, parameterized only by `CorrelationId`, with no type-specific error code baked in -- the same two failures every existing `DecodeX` (Item/Weapon/Armor/Ammo/Ability/Effect) already reuses as-is. `Skill`'s decode failure modes (wrong type, malformed JSON, unsupported schema version) are structurally identical to every other type's, so no new error taxonomy is required.
- **`SkillDefinition` was implemented with literally zero domain-specific fields, confirmed correct by direct comparison against `AbilityDefinition`/`EffectDefinition`'s own constructors (`TypedDefinitions.cs`) before writing the type.** Every field either type carries (target rule, entry point/trigger/action cost/resource costs, duration type/value, stack policy, `MechanicsPayloadRef`) is either explicitly excluded for Skill by the governing ТЗ's own §1 decisions (no `MechanicsPayloadRef`, no governing-attribute field) or simply has no analog for a skill (a skill is not an activatable/appliable mechanic with a trigger or duration). This is reported here as the governing ТЗ's own §2.1 explicitly anticipated finding, not a shortened implementation -- no artificial field was invented to avoid an "empty" type.
- **The five minimum tests (governing ТЗ §4 points 1-5) were split across two existing test files by test *level*, not consolidated into one new file, matching this codebase's own established convention:** the full Draft→Published cycle (point 1) went into `MinimalTestCatalogFixtureTests.cs` (the file that already hosts every other type's own end-to-end authoring/validation/publish fixture test), while the pure codec-level round-trip/wrong-type/malformed/schema-version tests (points 2-5) went into `TypedDefinitionCodecTests.cs` (the file that already hosts the identical four tests for `Ability`/`Effect`). Both files are named explicitly in the governing ТЗ §5's own allowed-paths list ("existing test file where Ability/Effect catalog round-trips are tested"); this task interprets that as covering both, since Ability/Effect round-trips are themselves already split the same way between these two files.
- **Test list item 6 (governing ТЗ §4 point 6, "if `SkillDefinition` carries at least one specific field, add a constructor-validation test for it") was not applicable and no such test was added.** Follows directly from the zero-fields finding above -- there is no field-specific constructor validation to test, since `SkillDefinition`'s constructor takes no parameters.
