# ODY-S07-104 — Body-Part/Anatomy Catalog (`BodyPartDefinition` + `AnatomyProfileDefinition`, block 3)

## 1. Task identity
`ODY-S07-104`; status: Done (PR #169, merged into main). Fourth task of `SLICE-07`, the first decomposition of block 3 (body-part/anatomy catalog).

## 2. Goal
Replace today's hardcoded, test-fixture-only `AnatomyInitializationRules.DefaultHumanoidBodyParts()` with two real, publishable content types -- `BodyPartDefinition` (a reusable named part) and `AnatomyProfileDefinition` (a bundle referencing a specific published set of `BodyPartDefinition`s) -- flowing Draft→Published through the already-existing, unmodified `SLICE-05` catalog pipeline. This task builds the catalog/authoring side only; `InitializeCharacterAnatomy` is not wired to the new catalog (a deliberate scope-narrowing decision, not a risk-driven deferral -- see §5/§18).

## 6. Domain contract
`Packages/com.odyssey.domain/Runtime/Content/ContentCatalog.cs`: `ContentDefinitionType.AnatomyProfile = 15` -- the first new enum value added since the original `ODY-S05-101` set (`BodyPart = 12` already existed, unused until now).

`Packages/com.odyssey.domain/Runtime/Content/TypedDefinitions.cs`: **`BodyPartDefinition`** -- `Name` (string, non-blank, ≤128 chars), `DamageLimit` (long, `> 0`), `Properties` (opaque string, ctor-required non-null) -- exactly the personal-character `Odyssey.Domain.Character.BodyPart`'s own Name/DamageLimit/Properties shape, no more; deliberately no current-HP/armor/attack-penalty/targeting-visibility field (§5). **`AnatomyProfileBodyPartRef`** -- `BodyPartRef` (`ContentDefinitionRef`, exact-version, by direct precedent of `ItemDefinition.BuiltInAbilityRefs`/`AmmoDefinition.EffectContributionRefs` -- every existing cross-type catalog reference uses exact-version `ContentDefinitionRef`, never inline data), `AttachedToIndex` (`int?`, a positional index into the owning `AnatomyProfileDefinition.BodyPartRefs` list, not a `BodyPartId` -- at authoring time no per-character `BodyPartId` exists yet for a catalog part; this task's own explicit decision, §1 point 5 of the governing ТЗ, not left for implementation to discover). **`AnatomyProfileDefinition`** -- `BodyPartRefs` (`IReadOnlyList<AnatomyProfileBodyPartRef>`), ctor-validated: non-empty; no `AttachedToIndex` equal to its own element's index (no self-reference); every `AttachedToIndex` within `[0, Count)`; and no cycle in the `AttachedToIndex` chain starting from any element (a plain internal graph-walk with a per-start visited set) -- a structural, single-definition invariant, distinct from and in addition to the cross-definition `ValidateReferencesAndCycles` mechanism (§7), which the governing ТЗ explicitly requires both of, not one instead of the other.

## 7. Application contract
`TypedDefinitionCodec.EncodeBodyPart`/`DecodeBodyPart` and `EncodeAnatomyProfile`/`DecodeAnatomyProfile`, by exact precedent of `EncodeSkill`/`DecodeSkill`/`EncodeAbility`/`DecodeAbility`: `schemaVersion` embed, `actualType` mismatch checked first (returns `WrongDefinitionType`, no JSON parsed), `JObject.Parse` under the same `try`/`catch` over the already-established `IsMalformedPayloadException` set, `RequireSupportedSchemaVersion`, and constructor validation (any `ArgumentException`/`ArgumentOutOfRangeException` the `AnatomyProfileDefinition`/`BodyPartDefinition` constructor throws is itself caught by `IsMalformedPayloadException` and surfaces as `MalformedPayload`, the same way every other typed constructor's validation already does). `AnatomyProfileBodyPartRef`'s own JSON shape is `{"bodyPartRef": "<ContentDefinitionRef.ToString()>", "attachedToIndex": <int|null>}`, an array of these under `bodyPartRefs`. No new `ErrorCodes`/`ERROR_CODES.md` entries -- `WrongDefinitionType`/`MalformedPayload` are already fully generic, confirmed by direct code read before writing either new codec pair.

`CatalogValidationContracts.ValidateBodyPart` -- decodes via `DecodeBodyPart`, reports a codec-failure issue on failure (`AddCodecFailureIssue`), otherwise nothing further -- every field is already ctor-guaranteed, by exact precedent of `ValidateSkill`. `ValidateAnatomyProfile` -- decodes via `DecodeAnatomyProfile`, reports a codec-failure issue on failure, otherwise nothing further -- `BodyPartRefs`' own internal shape (non-empty, no self-reference/out-of-range/cycle) is already ctor-guaranteed; each `BodyPartRef`'s existence/exact-version/target-type/ruleset-compatibility is checked by the existing, unmodified `ValidateReferencesAndCycles`, not duplicated here. A new `CollectOutgoingRefs` branch for `ContentDefinitionType.AnatomyProfile` emits `(BodyPartRefs[i].BodyPartRef, ContentDefinitionType.BodyPart, "properties.bodyPartRefs[i]")` for each entry, by exact precedent of the existing `Ammo`/`Item` branches -- this is the first case in this codebase of one authored type's `CollectOutgoingRefs` branch referencing another type through the *same* generic mechanism used for Item→Ability/Effect, proving the mechanism is genuinely type-agnostic, not extended.

## 18. Change control

### Decisions made during execution

- **The product owner's own explicit `AskUserQuestion` confirmation -- that connecting `InitializeCharacterAnatomy` to the new catalog is out of this task's scope -- was consumed as a fixed input before implementation began, not re-litigated during execution.** The governing ТЗ's own §0 already recorded this decision and its rationale (deliberate scope-narrowing, not risk avoidance, since `AnatomyProfileVersion` already pins a profile as an immutable snapshot at copy time); this task did not reopen it.
- **No new `ErrorCodes`/`ERROR_CODES.md` entries were added, matching `ODY-S07-103`'s own precedent.** Confirmed by direct code read of `TypedDefinitionCodecFailures.WrongDefinitionType`/`MalformedPayload` before writing either new `DecodeX`: both are already fully generic. `BodyPart`/`AnatomyProfile`'s decode failure modes are structurally identical to every other type's.
- **`AnatomyProfileDefinition`'s own cycle check is a plain internal graph-walk in its own constructor, deliberately separate from and in addition to `ValidateReferencesAndCycles`'s cross-definition cycle detection -- not a reuse of that mechanism and not a replacement for it.** The governing ТЗ's own §2.2 explicitly distinguishes the two: `AnatomyProfileDefinition`'s own constructor check is a same-definition, `AttachedToIndex`-chain invariant (structurally impossible to express as a `ContentDefinitionRef`, since `AttachedToIndex` is a positional index, not a definition reference), while `ValidateReferencesAndCycles` checks cross-*definition* reference cycles (e.g. two published `AnatomyProfileDefinition`s referencing each other via the generic `DependencyRefs` field) -- a completely different graph. Both are required; neither substitutes for the other.
- **`BodyPartDefinition.DamageLimit` validates `> 0`, not `>= 0` like the personal-character `BodyPart.DamageLimit`.** This is the governing ТЗ's own explicit §2.2 instruction (not independently chosen): a catalog-authored body-part template with a zero damage limit is not a meaningful piece of content to publish, even though the personal-character runtime value (which can reach zero through gameplay) legitimately allows it.
