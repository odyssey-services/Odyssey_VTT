## 18. Change control

### Decisions made during execution

- **`DiceRollService.SubmitRoll`'s own formula-parsing code was read in full before the dice-substrate decision was made -- it parses `request.Formula` through the ORIGINAL `DiceFormulaParser` (`ADR-009`), not `AttackDamageFormulaParser` (`ADR-030`), confirmed by a direct line-level code read, not an assumption from the two parsers' similar names.** This is the concrete finding that produced the formula-split requirement (`ADR-031` §5.2): a check formula's dice-group and attribute/skill terms cannot be submitted to `SubmitRoll` as one string, so the check command must itself split them, submitting the dice-only sub-formula to `SubmitRollRequest.Formula` and the resolved modifier via the already-existing `AutomaticModifierRequest` mechanism. Without this direct code read, a plausible but wrong assumption (that `SubmitRoll` could simply accept `"1d20+Strength"` unchanged) would have been baked into the ADR.
- **`DiceRollService.SubmitRoll` was independently confirmed, by a whole-repository grep for this task, to have zero real production callers today -- exercised only by its own test suite.** This is the concrete evidence cited for choosing it over a direct `IAuthoritativeRandomStream` draw (`ADR-031` §5.1/§16.1): reusing a real, already-accepted, currently-unused feature was judged preferable to building a second, independent roll mechanism beside it.
- **`AttackDamageFormulaParser`'s own `attributeReference` resolution code (`CoreAttackRulesEvaluator`'s private formula-evaluation helper) was read directly to confirm it performs a bare, unqualified dictionary lookup by parsed identifier name, with no attribute-specific validation anywhere in the parser itself.** This is the direct evidence for concluding a skill name resolves through the identical grammar production without any parser change -- not an assumption based on `SkillDefinitionId`'s similar validation pattern to `AttributeDefinitionId`'s alone.
- **Two of this ADR's own eight design questions -- degrees of success, and advantage/disadvantage/dedicated contest support -- are recorded as explicit, disclosed, product-confirmation-pending decisions, not silently resolved either way, per the governing ТЗ's own explicit instruction that a product-level decision made within this task must be flagged for confirmation, not asserted as settled.** `ADR-031` §17 records both by name, alongside a recommendation (before `ODY-S07-102`'s own contract is finalized) rather than leaving them for an indefinite future task to notice on its own.
- **`RecordCriticalSuccessEvidence`'s own doc comment and `ODY-S04-106`/`114`'s own task-file wording were quoted verbatim, not paraphrased from memory, before being cited as this ADR's own authority (section 3) and Definition-of-Done requirement (§15 point 4).** Direct file reads confirmed the exact "no real trigger... this task provides only the durable recording primitive" sentence and `ODY-S04-114`'s own test's synthetic `"roll_vertical_slice_001"` literal, giving this ADR's own decision 8/§10 a concrete, citable gap to close rather than a restated assumption.
- **`SLICE-07_IMPLEMENTATION_BACKLOG.md` and `ADR-031` were created in the same task/PR, explicitly reusing `ODY-S06-101`'s own already-accepted one-ADR-then-backlog simplification for `SLICE-06`, itself a divergence from `SLICE-05`'s own two-phase precedent.** The governing ТЗ explicitly authorized this by direct reference to the `ODY-S06-101` precedent ("по прямому прецеденту `ODY-S06-101`"), and the backlog document's own section 1/5 record the reasoning so a future reader does not mistake the absence of a separate prerequisite backlog for an oversight.
- **A factual correction was made during research, before it could be written into the backlog incorrectly: `CharacterRecord` already carries a `PortraitReference` field -- the governing ТЗ's own premise that "ни `TokenRecord`, ни `CharacterRecord` не несут поля под портрет" is only true for `TokenRecord`.** Confirmed by direct field read (`CharacterRepositoryContracts.cs`, constructor parameter `portraitReference`, property `PortraitReference { get; }`) before writing `SLICE-07_IMPLEMENTATION_BACKLOG.md`'s own block 5 description, which is phrased to describe the REAL gap (an unvalidated, unlinked opaque string on `CharacterRecord`, and a wholly missing field on `TokenRecord`) rather than repeating the ТЗ's own slightly inaccurate premise verbatim.
- **Доработка (product-owner-confirmed): `ADR-031` §17's own two originally-open decisions are now closed, not left pending.** The product owner confirmed, after PR #165's own independent verification, that both degrees of success (§8.2) and advantage/disadvantage/dedicated contest support (§8.3) are out of scope for the first check/contest implementation. `ADR-031` §1 decision 6, §8.2, §8.3, §13 (Non-goals), §16.4, and §17 itself are updated from "flagged for product-owner confirmation"/"not yet confirmed" to "confirmed non-goal for v1, 2026-09-22" -- each edit explicitly preserves the "disclosed, revisitable non-goal, not an architectural prohibition" framing `ADR-030` §12 already established as this codebase's own convention for non-goals, per this доработка's own explicit instruction not to silently convert a disclosed-but-open decision into a permanent ban. No other section of `ADR-031`, and neither `SLICE-07_IMPLEMENTATION_BACKLOG.md` nor `PLANS.md`, was touched -- both already had zero open questions of their own.
