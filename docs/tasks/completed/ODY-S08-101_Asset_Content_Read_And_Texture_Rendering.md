## 2. Goal
Make the scene background and token portraits that `SLICE-07` already stores actually visible on the board. Two things were missing: an asset read API (`RegisterAsset` had no paired read; nothing in the codebase returned an asset's bytes) and texture rendering in `BoardScreenPresenter` (tokens were solid colored squares, the board a solid fill). ## 7. Application contract
`Result<byte[]> ReadAssetContent(CampaignHandle, AssetId, CorrelationId)` -- the whole file as `byte[]`, chosen over a stream because the only current consumer is small images and a stream abstraction would have no consumer. Fail-closed: an `AssetId` absent from this campaign's own `AssetManifestEntries` -> the reused `AssetNotFound`; manifest row present but file missing on disk -> new `AssetFileMissing`; stored SHA-256 differing from the hash of the bytes read, a `NULL` stored hash, or a manifest path resolving outside the campaign's `Assets/Objects` directory -> new `AssetIntegrityFailed`; other I/O -> the existing `SceneIoFailed`. Placed on `ISceneRepository` beside `RegisterAsset`/`SetSceneBackground`/`SetTokenPortrait`, the default the ТЗ named; no better home exists (`IContentCatalogRepository` is unrelated, and a new interface would have one method).

`Result<SceneRecord> GetScene(CampaignHandle, SceneId, CorrelationId)` -- read-only counterpart of `GetToken`, existing `SceneNotFound` for an unknown scene. See §18 for why this second method was required.

## 8. Persistence boundary
`SqliteSceneRepository.ReadAssetContent`: one `SELECT RelativePath, Hash FROM AssetManifestEntries WHERE AssetId = $id` on the campaign's own `campaign.db` (physical isolation: campaigns are separate database files, so this single lookup is also the cross-campaign check, the same property `SetSceneBackground`/`SetTokenPortrait` rely on); the path is resolved with `Path.GetFullPath` and required to lie under `<root>/Assets/Objects` before any file access; the file is read with `File.ReadAllBytes`; SHA-256 is recomputed with the same `ToLowerHex` helper `RegisterAsset` used and compared (case-insensitive) with the stored value. No write, no pipeline, no journal event -- a pure read like `GetToken`. `SqliteSceneRepository.GetScene` mirrors `GetToken` (`EnsureSceneTokenTables`, single `SELECT`, `BackgroundAssetId` read).

## 9. Tests and validation
Backend (`dotnet test`): `TC-BOARD-033` exact bytes and matching hash; `034` unknown `AssetId` -> `AssetNotFound`; `035` `AssetId` from a genuinely separate temp campaign -> `AssetNotFound` (and still readable in its own campaign); `036` real file deletion -> `AssetFileMissing`; `037` file overwritten with different bytes -> `AssetIntegrityFailed`; `038` manifest path rewritten to `Assets/Objects/../../<file>` with a byte-identical file placed there, so the hash would match and only path confinement can reject; `039` `GetScene` with/without background and for an unknown scene. ## 10. Compatibility and rollback
Two added interface methods; no existing signature or behavior changes. The only implementer of `ISceneRepository` is `SqliteSceneRepository` (searched `Assets/`, `DotNet/`, `Packages/`). `BoardScreenPresenter`: with no `BackgroundAssetId`/`PortraitAssetId`, the produced visual state is identical to before (no image style is applied; the token fill and board fill code paths are unchanged); an unknown scene still renders as an empty board and still returns `Success`. Reverting removes the two methods, the two error codes, and the presenter additions.

## 11. Security and privacy
The manifest is data in a local database file, so `ReadAssetContent` never trusts its `RelativePath`: it must resolve inside the campaign's own `Assets/Objects` directory (defense against a tampered manifest reading an arbitrary local file; a `../` traversal test proves it). Error responses expose no path, hash or `AssetId`. No new permission concept (matches `GetToken`).

## 12. Observability
None new (pure reads). The presenter surfaces an asset failure through the existing status label (`"Asset load failed: <safe reason>"`) and the returned `Result`.

## 13. Performance
`ReadAssetContent` reads the whole file once. The presenter caches each decoded `Texture2D` for its lifetime, so `Refresh()` (called on every selection change and move) never re-reads disk or re-decodes an already-loaded asset -- proven by `TC-BOARD-044`. `GetScene` adds one small `SELECT` per `Refresh`. The cache holds successful loads only, so an asset that failed is retried on the next `Refresh`; textures are destroyed on `Dispose`.

## 18. Change control

### Decisions made during execution

- **A second new `ISceneRepository` method (`GetScene`) was added, although the ТЗ §2/§5 allowed exactly one new read method.** The ТЗ requires the presenter to render the scene background when `SceneRecord.BackgroundAssetId` is set, but `ISceneRepository` had no way to read a Scene back at all (`CreateScene` and `SetSceneBackground` return it, nothing reads it; `ODY-S07-105` noted this). Without `GetScene` the presenter cannot know the background id. It is a small, additive, read-only mirror of `GetToken`. Same class of disclosure as `ODY-S07-102`/`105`/`106`.
- **Two new error codes (`persistence.asset.file_missing`, `persistence.asset.integrity_failed`) instead of reusing existing ones -- checked first, as the ТЗ §1.2 requires.** `persistence.scene.io_failed` covers generic file/SQLite I/O failures and is `ManualRecoveryRequired`, but a manifest row whose file is gone, or bytes that differ from the recorded hash, are data-integrity conditions a caller may need to distinguish from a transient I/O error; `persistence.integrity.check_failed` is documented as the `Open`-time quick-check/`SchemaHistory` failure and reusing it would stretch its meaning. Both are strictly additive; `REPO-POLICY-005` verifies their registry rows and test references.
- **Path confinement was added beyond the ТЗ.** Not requested, but reading a path taken from a database row without confining it would let a tampered manifest read any local file; it costs one comparison and has its own test (`TC-BOARD-038`).
- **`Refresh()` semantics for asset failures.** An asset that cannot be loaded (missing file, integrity failure, undecodable bytes) never stops the board: the element falls back to today's solid visual, and `Refresh()` returns the first such error as a typed `Failure` after rendering everything (the ТЗ asks for the decode error to be propagated as a typed error). This can only happen when an asset id is set, so no existing flow changes. An unknown scene (`SceneNotFound`) deliberately keeps returning `Success` with an empty board, exactly as before.
- **Image decoding error reuses `ApplicationValidationInvalid` with a new user-message key** (`errors.board_screen.texture_decode_failed`), the same pattern `BoardScreenErrors.RenderFailed`/`NoTokenSelected` already use; no new error-code literal.
- **Token portrait replaces the ownership color rather than tinting.** Per the ТЗ (`вместо текущей сплошной заливки`); the ownership border/selection border remain.
- **Presenter tests were previously uncatalogued in `test-catalog.json`** (the four existing `BoardScreenPresenterTests` have no entry). The new presenter tests use `TC-BOARD-*` (the ТЗ default, no separate UI prefix exists) with runner `Unity EditMode`, matching the runner string other Unity tests already use. The four pre-existing tests were left as they were.
- **`AssetId` is minted fresh by every `RegisterAsset` (`AssetId.NewId`)** -- confirmed by reading it, as the ТЗ asked -- so the texture cache needs no invalidation for asset replacement.

### Findings (reported, not fixed -- out of scope by the ТЗ's own invariants)

- **The Unity project on `main` does not compile, for a reason that predates this task, and nothing in CI detects it.** `Odyssey.Persistence`'s Unity `.asmdef` references only `Odyssey.Domain`, `Odyssey.Content` and `Odyssey.Application`, and `scripts/verify-test-structure.ps1` encodes exactly that as the allowed set (no `Odyssey.Rules`). But `SqliteCharacterRepository.cs` (added by the character-economy tasks) uses `Odyssey.Rules.Character.*` types directly (`using RulesAttributeCostRules = Odyssey.Rules.Character.AttributeCostRules;` etc.). `dotnet` compiles it only because SDK-style project references flow transitively through `Odyssey.Application`; Unity asmdef references do not, so a batchmode compile fails with `CS0234`/`CS0246`/`CS0012` in that file. Reproduced by running Unity against this branch. Verifying the presenter therefore required temporarily adding `"Odyssey.Rules"` to that `.asmdef` locally, then reverting it -- the committed diff contains no `.asmdef` change, because the correct resolution is an architectural decision (amend the ADR-001 dependency matrix to allow `Persistence -> Rules`, or refactor `SqliteCharacterRepository` so persistence no longer uses Rules types) that belongs to the product owner/architecture, not to a rendering task. Until it is resolved the Owlbear-style board work (this whole slice) cannot be run in the Unity client at all. Secondary observation: with that workaround Unity compiled and ran cleanly, and running Unity also auto-generates many untracked `.meta` files for `Packages/` sources, which suggests those sources have not been opened in the Editor for some time.

- **`RegisterAsset` aliases same-named files.** It copies the source only `if (!File.Exists(destinationPath))` and computes the hash from the destination file. Registering a second file with the same file name but different content therefore returns a new `AssetId` whose `RelativePath` and `Hash` are the FIRST file's (verified empirically with a throwaway probe: distinct ids, same path, same hash, and `ReadAssetContent` on the second id returns the first file's bytes). For the intended board UX this means importing two different maps that are both called `map.png` silently shows the first one for both. The tests here use unique file names and are unaffected. Fixing it changes `RegisterAsset`, which this task's invariants forbid; it should be its own task (a content-addressed or uniquified destination name is the likely shape).
- **CI does not execute Unity tests.** The `unity-project-package-static` job explicitly does not run the Unity Editor. The presenter tests (`TC-BOARD-040`-`047`) were therefore executed locally in batchmode against Unity 6000.4.0f1, not by CI; see §17 and the PR description.
