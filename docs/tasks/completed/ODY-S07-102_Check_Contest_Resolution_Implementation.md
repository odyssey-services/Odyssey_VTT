## 6. Domain contract
`Packages/com.odyssey.domain/Runtime/Checks/CheckContracts.cs` (new): `CheckParticipantState` (a `readonly struct`, `CharacterId`/`AttributeValues`/`SkillValues`, both dictionaries defensively copied, mirroring `AttackParticipantState`'s own idiom but deliberately without `LifecycleStatus`/`ApprovalState`, `ADR-031` §7/§16.3); `CheckResultKind` (`Pass`/`Fail`); `CheckOutcome` (`Result`/`IsNaturalMaximum`/`ResolvedModifier`/`FinalTotal`/`DifficultyClass`), living in `Odyssey.Domain` rather than `Odyssey.Rules` so it can flow into `Odyssey.Application`/`Odyssey.Persistence` without either needing an extra `Odyssey.Rules` type reference, the same "Rules produces a Domain-shaped result" precedent `ProposedAttackResolution`/`AttackRandomSample` already establish.

## 7. Application contract
`CheckContracts.cs` (`Odyssey.Application.Checks`): `CheckIntent` (`ActorId`, `Formula`, `DifficultyClass: long` (validated `>= 0`), `Audience: DiceRollAudience`, required not defaulted -- `DiceContracts.cs`'s own established "never leave this implicit" rule); `CheckRequest` (`Intent`/`ActorUserId`/`CommandId`/`CorrelationId` -- deliberately NO `ActorIsMainGm`/`expectedXxxRevision` field, an explicit, disclosed divergence from `ActivateAbilityRequest`'s own shape, recorded in this task's own §18: a check mutates no `CharacterRecord` section, and its only potential write, `RecordCriticalSuccessEvidence`, itself takes no revision parameter and performs no permission gate); `ICheckStateReader.Read` (no `CanControlActor` method, for the identical reason); `CheckOutcomeRecord` (the durable idempotency-read record, no `CompensatedAt`/`CompensationStartedAt` -- a check has no resource delta or created effect to reverse); `ICheckRepository` (`GetCheckOutcome`/`RecordCheckOutcome`). `CheckService.PerformCheck` orchestrates, in this fixed order (this task's own governing ТЗ §1.6, not left to independent judgment): (1) `apply.GetCheckOutcome` BEFORE any RNG derivation -- mandatory, since `DiceRollService.SubmitRoll` itself performs no `CommandId`-keyed replay (confirmed by direct code read); (2) `reader.Read`; (3) `AttackDamageFormulaParser.TryParse`; (4) `ICheckRulesEvaluator.TryResolveFormula` (fail-closed on an unresolved/ambiguous reference or more than one dice-group/attribute-reference term, before any RNG is spent); (5) build `AutomaticModifierRequest` entries (`FormulaConstant` when the formula's own constant sum is non-zero, `AttributeModifier`/`SkillModifier` for the at-most-one resolved reference term) and call the real, unmodified `DiceRollService.SubmitRoll` with `actorCanCreateRoll: true` (this task's own explicit, disclosed simplification -- no session/permission model exists for checks, mirroring `SubmitRollRequest`'s own already-established `ActorCanCreateRoll`/`ActorIsMainGm` caller-supplied-boolean convention); (6) `ICheckRulesEvaluator.Evaluate` against the real `DiceRoll.FinalTotal`/`NaturalResults`; (7) conditionally `ICharacterRepository.RecordCriticalSuccessEvidence` with the real `DiceRoll.RollId` (only when `IsNaturalMaximum && ResolvedSkillId.HasValue`, a deterministic sub-`CommandId` derived the same `StableSubCommandId` way `ActivateAbilityService` already established); (8) `apply.RecordCheckOutcome`.

## 8. Persistence boundary
`SqliteCheckStateReader.Read` mirrors `SqliteAttackStateReader.Read`'s own `State(CharacterRecord)` helper exactly -- one `GetCharacter` call, then a plain `foreach` copy of `record.Attributes`/`record.Skills` into two dictionaries, zero extra database reads. `SqliteCheckRepository` owns a new, standalone `CheckOutcome` table (mirrors `SqliteActivateAbilityRepository`'s own standalone-table idiom), committing through the existing, unmodified `SqliteSavingPipeline.Execute` (`ADR-012` §5) -- the durable row, the DomainEvent (`"odyssey.persistence.check_performed"`), and the `AppliedCommands` idempotency row land in one transaction or none do. No compensation logic anywhere in this repository -- a check has no resource delta or created effect to reverse (`ADR-031` imposes no such requirement, unlike `ADR-030`'s own eventual doработка requirement for `ActivateAbility`).

## 18. Change control

### Decisions made during execution

- **`DiceRollService.SubmitRoll`'s own formula parameter is parsed by the ORIGINAL `DiceFormulaParser` (`ADR-009`), not `AttackDamageFormulaParser` (`ADR-030`) -- confirmed by a direct line-level code read (`DiceRollService.cs`, `DiceFormulaParser.TryParse(request.Formula, ...)`) before writing a single line of `CheckService`.** This is the concrete finding that makes the formula-split (§1.3 of the governing ТЗ) a real necessity, not a stylistic choice: a check formula's dice-group and attribute/skill terms cannot reach `SubmitRoll` as one string, so `CheckService` itself parses the FULL formula through `AttackDamageFormulaParser`, submits only the reconstructed dice-only sub-formula, and passes the resolved modifier via `SubmitRollRequest.AutomaticModifiers` -- a mechanism `DiceRollService` already had, built for exactly this shape.
- **`Odyssey.Rules` cannot reference `Odyssey.Application.Dice.NaturalResult`, confirmed by direct `.asmdef` read before designing `ICheckRulesEvaluator.Evaluate`'s own signature.** Rather than pass the Application-layer `NaturalResult` type across the module boundary (forbidden by `ADR-001` §6.2's own dependency matrix, the identical constraint `CoreAttackRulesEvaluator`'s own doc comment already discloses for `WeaponDefinition`), `Evaluate` takes plain `IReadOnlyList<int> dieValues`/`int dieSides` -- primitives any layer can pass, with `CheckService` doing the one-line extraction from `DiceRoll.NaturalResults` before the call. This is the same "Rules receives already-derived values as explicit parameters, never the Application type that produced them" discipline `CoreAttackRulesEvaluator.Evaluate(intent, snapshot, randomSample)` already models (`randomSample` itself is a `Odyssey.Domain.Combat` type, not an `Odyssey.Application` one).
- **`CheckRequest` deliberately has no `ActorIsMainGm`/`expectedXxxRevision` field, and `CheckService.PerformCheck` passes `actorCanCreateRoll: true` to `DiceRollService.SubmitRoll` unconditionally -- an explicit, disclosed simplification, not an oversight.** Confirmed by direct signature/doc-comment read of `ICharacterRepository.RecordCriticalSuccessEvidence` ("No permission gate -- recording an observed game fact is not a discretionary decision") and by `ADR-031` §7's own explicit statement that a check mutates no `CharacterRecord` section, so there is no revision to declare/re-check. This governing ТЗ's own §1.6 contract snippet already omitted these fields, confirming the omission was intentional, not an accidental gap this task silently perpetuated.
- **A disclosed, accepted limitation, not designed away: if `RecordCriticalSuccessEvidence` fails AFTER a real dice roll already happened but BEFORE `RecordCheckOutcome` durably lands, a retry of the same `CommandId` re-enters the flow (since `GetCheckOutcome` finds nothing yet) and derives a genuinely NEW dice roll.** `RecordCriticalSuccessEvidence` itself is idempotent by its own deterministic sub-`CommandId` (so a duplicate evidence row is never created), but the check's own dice roll is not saga-protected across this narrow window the way `ActivateAbility`'s three доработка rounds eventually protected resource+effect side effects. This is accepted because `ADR-031` imposes no compensation requirement on checks (a check has no resource delta or created effect to reverse, unlike `ActivateAbility`), and the governing ТЗ's own step ordering (§1.6, `RecordCriticalSuccessEvidence` before `RecordCheckOutcome`) does not ask for a saga/compensation mechanism here -- disclosed explicitly rather than silently risked.
- **`docs/tasks/SLICE-07_IMPLEMENTATION_BACKLOG.md`'s own block 1 description and row 1 (`ODY-S07-101`) previously stated `ADR-031` §17's two product questions as still open, pending resolution "before or during" this task -- stale wording written the same day as `ADR-031`'s own first version, before its own доработка confirmed both.** Corrected here (block 1 description, row 1's own entry, and a new §10 change-control entry) to state plainly that both were already confirmed before this task started, and that this task consumed that confirmed decision as a fixed input -- per this task's own governing ТЗ §0's explicit instruction not to re-raise already-settled questions.
- **`Packages/com.odyssey.application/Runtime/Results/ErrorCodes.cs` and `docs/errors/ERROR_CODES.md` were touched even though neither appears in this task's own governing ТЗ §4 allowed-paths list -- an omission in that list, not a deliberate exclusion, disclosed here rather than silently worked around.** The governing ТЗ's own §1.3/§1.4 explicitly require four distinct, typed, fail-closed validation errors (`RequiresExactlyOneDiceGroup`/`RequiresAtMostOneAttributeReference`/`AmbiguousReference`/`UnresolvedReference`) plus a fifth for a malformed formula string -- and `scripts/check-repository-policy.ps1`'s own `REPO-POLICY-005` check (confirmed by direct script read before making this change) fails the whole repository policy gate if any production `ErrorCode.Parse` literal lacks a matching row in `docs/errors/ERROR_CODES.md`. There is no way to satisfy the governing ТЗ's own explicit fail-closed requirement without adding both files' own new, strictly additive entries (five new `ErrorCodes.cs` lines, five new `ERROR_CODES.md` rows, zero existing rows/lines changed) -- the same class of "the allowed-paths list under-names a location this task's own explicit requirement cannot avoid touching" gap `ODY-S06-101`'s own task contract §18 already disclosed for `ActivateAbilityService.cs`'s own folder placement, handled here the identical way: disclosed explicitly, not silently expanded scope.
