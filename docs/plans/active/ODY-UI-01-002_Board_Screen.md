## Investigation performed

1. Read `DeveloperShellPresenter.cs` in full: confirmed the established pattern — a plain C# class (not `MonoBehaviour`), constructor-injected dependencies, view built entirely from code-created `VisualElement`s over an already-configured `UIDocument`, no dedicated `.uxml` of its own.
2. Read `RuntimeCompositionAndDiagnosticsTests.cs`'s `DeveloperShellDisplaysBuildIdentityAndUnavailableFallback` test in full: confirmed a bare `GameObject` + `UIDocument` component works in EditMode with no scene/Player. `Grep`'d the whole EditMode test assembly for `ClickEvent`/`SendEvent`/`.clicked(` — zero matches, confirming no existing test simulates a UI Toolkit pointer event.
3. Decided (task contract §3): expose `SelectToken`/`TryMoveSelectedTokenTo` as public methods on the presenter, with UI Toolkit click callbacks as thin wrappers — lets tests exercise the presenter's own logic directly and robustly, since no proven simulated-click precedent exists in this repository to build on.
4. Decided (task contract §3): render tokens as plain absolutely-positioned `VisualElement`s inside the existing `UIDocument`, not a GameObject/SpriteRenderer scene hierarchy — `ADR-001` §6.7 already names "UI Toolkit views" as the expected pattern; a second rendering technology would need its own camera/coordinate-space setup for a screen this slice's own backlog keeps deliberately minimal.
5. Decided (task contract §3): `BoardScreenDemoCampaign.CreateFresh` programmatically creates a throwaway campaign/scene/two-tokens fixture, so a human can press Play with no manual setup step.
6. Confirmed `Odyssey.Unity.Client.Runtime.asmdef` already references every needed assembly (`Odyssey.Application`, `Odyssey.Persistence`, `Odyssey.Domain`) — no new project reference needed.
7. Ran `scripts/test-unity.ps1` for real (Unity 6000.4.0f1 is installed locally). Batch compile failed with `CS0234`/`CS0246` across every `Packages/com.odyssey.persistence/Runtime/Sqlite/**` file — `Microsoft.Data.Sqlite` unresolved inside Unity's own compiler. Confirmed this is pre-existing and unrelated to this task's own two new files: the identical code passes `dotnet build`/`dotnet test` (261/261) outside Unity; `Odyssey.Persistence.asmdef`'s `precompiledReferences` is empty and no `Plugins/` folder anywhere carries the needed DLLs; dozens of previously-uncommitted `Packages/**.meta` files were freshly auto-generated by this very run, direct evidence no prior task ever opened this project in the real Unity Editor; `check-repository-policy.ps1`'s own `TC-CI-006` line confirms CI's Unity check is static-only, never a real compile. Removed the auto-generated `.meta` churn from this task's own diff via `git clean -f -- Packages/`, without deciding whether those files should eventually be committed by whichever future task fixes the underlying gap.
8. Decision: do not attempt to fix the `Odyssey.Persistence` Unity-SQLite-plugin gap in this task — explicitly out of this task's own scope (`SLICE-UI-01_IMPLEMENTATION_BACKLOG.md` §5 forbids any `Packages/com.odyssey.persistence` change here); reported honestly in the task contract instead, with a recommendation that a dedicated, separate follow-up task add the missing Unity Plugin references before further `SLICE-UI-01` work can get real Unity Editor validation.
