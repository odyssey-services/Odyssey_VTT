# ExecPlan — ODY-S07-101 ADR-031 Check / Contest Resolution Architecture

## 1. Purpose
Close the gap a direct product-owner question, independently verified against the tracked repository, found: an attribute/skill check (roll + modifier vs. a target difficulty) does not exist anywhere in this codebase, in code or in any prior ADR. Decide, in one accepted ADR, HOW that roll happens (substrate), HOW its formula is parsed and resolved (grammar, attribute AND skill values), HOW its result is judged (a new pass/fail evaluator), WHETHER it needs `CombatEncounter` state (no), and HOW it finally wires the long-dormant `RecordCriticalSuccessEvidence` recording primitive for real -- as one coherent architecture, not left for a future task to improvise piecemeal. Open `SLICE-07` (the whole gap-closure track: checks plus four smaller content/asset gaps) with a backlog naming all five blocks in the product owner's own priority order. This task produces the ADR and the backlog; it implements nothing.

## 2. Scope
`docs/adr/ADR-031_Check_Contest_Resolution_Architecture_v1.0.md` (19-section ADR, `ADR-030`'s own template, extended for more design sections): the dice-substrate decision (`DiceRollService.SubmitRoll`, with the required formula-split since `SubmitRoll`'s own formula parameter uses the ORIGINAL `DiceFormulaParser`, confirmed by direct code read to lack an attribute-reference term); the formula-grammar decision (`AttackDamageFormulaParser` reused verbatim); a new check snapshot (`CheckParticipantState`) carrying both attribute and skill dictionaries, by the `ODY-S06-102` zero-extra-read precedent; a new, standalone `Odyssey.Rules` pass/fail evaluator; degrees of success and advantage/disadvantage/contests named as explicit, product-confirmation-pending non-goals; the `CombatEncounter`-unbinding decision; the real `RecordCriticalSuccessEvidence` wiring requirement; confirmation no new `RngPurpose` is needed. `docs/tasks/SLICE-07_IMPLEMENTATION_BACKLOG.md` (new, modeled on `SLICE-06_IMPLEMENTATION_BACKLOG.md`'s own structure): five blocks named/reserved in priority order (checks, skill catalog, body-part catalog, scene background, portraits), none decomposed beyond this task. `PLANS.md` §13.3 amendment recording `SLICE-07`'s insertion. ## 4. Architecture
The deliverable is entirely documentation; there is no runtime architecture to build in this task. The ADR's own architecture decisions (recorded in `ADR-031` itself, not repeated here) are: (a) a new check root command routes its dice roll through `DiceRollService.SubmitRoll` (`Odyssey.Application.Dice`, `ODY-S03-005`, unmodified), never a direct `IAuthoritativeRandomStream` draw; (b) the command itself parses the full check formula through `AttackDamageFormulaParser` (`Odyssey.Rules`, `ADR-030` §6.2, unmodified), splitting it into a dice-only sub-formula (submitted to `SubmitRoll`) and a resolved attribute/skill modifier (submitted via `SubmitRollRequest.AutomaticModifiers`); (c) a new `CheckParticipantState` type (`Odyssey.Domain`, structurally parallel to `AttackParticipantState` but independent) carries both `AttributeValues`/`SkillValues` dictionaries, populated with zero extra database reads from an already-loaded `CharacterRecord`; (d) a new `ICheckRulesEvaluator`/`CoreCheckRulesEvaluator` pair (`Odyssey.Rules`, structurally parallel to `IAttackRulesEvaluator`/`CoreAttackRulesEvaluator` but independent) resolves the check formula's own non-dice terms and compares the real `DiceRoll.FinalTotal` against a caller-supplied difficulty class, producing pass/fail plus a natural-maximum-roll flag; (e) the check command is a standalone `ADR-002` root command, never requiring `CombatEncounter` state; (f) a genuine natural-maximum roll on a skill check calls `ICharacterRepository.RecordCriticalSuccessEvidence` with the real `DiceRoll.RollId`, never a synthetic identifier.
