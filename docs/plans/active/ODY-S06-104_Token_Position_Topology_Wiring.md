# ExecPlan — ODY-S06-104 Character↔Token Link + Attack Participant Position/Distance Wiring

## 1. Purpose
Close the third and final data gap blocking `ODY-S06-105` (the real `IAttackRulesEvaluator`): real position/distance data for range checks. `TokenRecord` has no `CharacterId` today and `CombatEncounter` is scene-agnostic, so an attack participant's position cannot be resolved at all. Third task of the product-owner-directed block-A reordering (`102` wired attributes, `103` wired equip-status/armor, this task wires position/distance; `105` will then build the full evaluator once, consulting all three).

## 2. Scope
`TokenRecord`/`ISceneRepository.CreateToken` gain an optional `CharacterId` link. `ISceneRepository.ListTokensByCharacter` (campaign-wide) added. `AttackEvaluationSnapshot.Topology` retyped from `AttackUnavailableInput` to a new `AttackTopologyInput` union (`Odyssey.Domain.Combat`). `SqliteAttackStateReader.Read` resolves the actor's and each target's position and computes real distances. Seven existing test files updated for the new required constructor parameter. Eight new tests (`TC-BOARD-014`/`015`, `TC-ATTACK-111`-`116`). `SLICE-06_IMPLEMENTATION_BACKLOG.md` row `104` moved to `In Review`.

## 3. Non-goals

A token re-linking command. Adding `SceneId` to `CombatEncounter` -- it stays scene-agnostic. `AttackRangeResult` itself, `IAttackRulesEvaluator`'s own interface, `BoardMovementService`/`BoardGeometry`'s own logic (called/read only). `ADR-030` and earlier ADRs (referenced, not revised).

## 6. State and data flow
`CreateToken` optionally receives a `CharacterId`, persists it in the new `Token.CharacterId` column, and returns it on the `TokenRecord` -> `MoveToken` reads it back from the row it is updating and carries it forward into the returned record unchanged (the `UPDATE` statement never touches that column). Separately, `SqliteAttackStateReader.Read`, after building `targets`, calls a new `ReadTopology(campaign, intent.ActorId, intent.TargetIds, correlationId)`: `ListTokensByCharacter` resolves the actor's own token (campaign-wide, first match by `CreatedAt`) -> if found, the same lookup runs per target -> for each target whose own token resolves AND whose `SceneId` equals the actor's, `BoardGeometry.EuclideanDistance` computes a real distance from the two `TokenPosition` values, wrapped in an `AttackTargetDistanceEntry` tagged with that target's `CharacterId` -> the aggregate list, empty or not, becomes `AttackTopologyInput.Unavailable("...")` or `.Available(entries)` and travels in the snapshot exactly where `AttackUnavailableInput` used to.

## 7. Error handling
A failed `ListTokensByCharacter` call (an infrastructure-level read failure) propagates its own real `Error` up through `Read`'s `Result<AttackEvaluationState>` -- not converted to the method's generic `Rejected(correlationId)`, which is reserved for business-precondition checks. A Character with no linked token, or an actor/target pair on different Scenes, is NOT an error at all -- per the governing ТЗ's own explicit instruction, missing position data is not a new hard-fail (unlike `ODY-S06-103`'s own deliberate equip-status gate); that target (or every target, if the actor itself has no token) is simply absent from `AttackTopologyInput.Entries`.
