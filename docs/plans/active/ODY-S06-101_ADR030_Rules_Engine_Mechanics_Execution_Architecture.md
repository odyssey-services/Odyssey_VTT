# ExecPlan — ODY-S06-101 ADR-030 Rules Engine / Mechanics Execution Architecture

## 1. Purpose
Close the gap `ADR-029` §10 explicitly disclosed and left open ("without selecting a game system's hit formula ... or content payload schema"): decide, in one accepted ADR, HOW `IAttackRulesEvaluator` gets a real implementation, HOW `WeaponDefinition.DamageExpression`/`AbilityDefinition.MechanicsPayloadRef`/`EffectDefinition.MechanicsPayloadRef` are interpreted, and HOW a future `ActivateAbility` command activates an ability -- as one shared Rules Engine, not three unrelated mechanisms -- and open `SLICE-06` (the MVP "two characters, gear, abilities, combat, movement, repeated combat" scenario) with a backlog naming the whole roadmap. This task produces the ADR and the backlog; it implements nothing.

## 2. Scope
`docs/adr/ADR-030_Rules_Engine_Mechanics_Execution_Architecture_v1.0.md` (18-section ADR, `ADR-028`/`029`'s own template): one-engine/three-call-sites decision; the real `IAttackRulesEvaluator` implementation's architecture (not code); a formula-grammar decision for `DamageExpression`, based on a genuine read of `DiceFormulaParser`'s own code, not assumption; a minimal, closed two-primitive (`AdjustResource`/`ApplyEffect`) schema for `MechanicsPayloadRef`; a `RulesetId@RulesetVersion` rules registry reusing `CatalogValidationContracts.cs`'s own existing cache-key convention; the `ActivateAbility` root-command architecture, explicitly decided non-combat-bound for MVP; item-use (roadmap block D) named as a future consumer of the same engine, not designed here. `docs/tasks/SLICE-06_IMPLEMENTATION_BACKLOG.md` (new, modeled on `SLICE-05_IMPLEMENTATION_BACKLOG.md`'s own structure): Rules Engine block (`101`-`103`) fully decomposed, roadmap blocks B-G named/reserved only. `PLANS.md` §13.2 amendment recording `SLICE-06`'s insertion. This task contract and this ExecPlan themselves.

## 3. Non-goals

## 4. Architecture
The deliverable is entirely documentation; there is no runtime architecture to build in this task. The ADR's own architecture decisions (recorded in `ADR-030` itself, not repeated here) are: (a) one `Odyssey.Rules`-layer Mechanics Execution Engine consumed by three call sites -- the real `IAttackRulesEvaluator` implementation, an `ActivateAbility` root command, and (named, not built) future item-use; (b) a new superset formula-grammar parser living in `Odyssey.Rules`, referencing `DiceFormulaParser`'s own published constants (`MaxDiceCount`/`MaxDiceGroups`/`MinSides`/`MaxSides`) by direct reference rather than duplicating or modifying `Odyssey.Domain`'s own accepted `DiceFormula.cs`; (c) a mechanics-primitive JSON envelope, versioned like `TypedDefinitionCodec`'s own `schemaVersion` convention, decoded by a new method kept separate from `DecodeAbility`/`DecodeEffect`; (d) an in-process, code-registered `RulesetId@RulesetVersion` dictionary registry with zero I/O, per `ADR-001` §6.2's own module-boundary rule; (e) `ActivateAbility` mirroring `AttackApplyService`'s own existing orchestration shape, explicitly unconditional on `CombatEncounter` state.
