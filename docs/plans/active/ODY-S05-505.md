## 4. Proposed approach

- No further production-code changes to `ItemEffectLifecycleService.cs`/`SqliteActiveEffectRepository.cs` were needed — the prior session's implementation, after independent verification (fresh build, fresh full-suite test run, direct API-signature cross-checks against `IInventoryRepository`/`IContentCatalogRepository`/`ErrorCodes`), held up completely. This closeout's own value-add is verification, documentation, and process completion (catalog registration, task/plan docs, validation scripts, commit/push/PR), not new implementation.
- `ItemEffectLifecycleService.OnItemEquipped` reads the item's pinned `ItemMechanicsSnapshot` (never today's catalog state), decodes its `BuiltInEffectRefs`, and for each ref not already covered by a retained `WhileItemEquipped` row from the same source, fetches and validates the target `EffectDefinition` (must be `Published`, `Effect`-typed, non-`Instant`, non-combat-duration), builds a candidate `ActiveEffectRecord`, and either resumes an existing `Suspended` row (via `SetItemEffectEquipped`) or creates a new one (via the unmodified `CreateActiveEffect`). A non-`IndependentInstances` `StackPolicy` collision fails the whole reaction rather than silently bypassing `503`'s own decision layer, since `503` provides decisions only, not an atomic write path this service can safely compose with today.
- `ItemEffectLifecycleService.OnItemUnequipped` lists every effect sourced from the item (both `ForItem`/`ForEquippedItem` kinds), filters to `Active`+`WhileItemEquipped` (decoded from each row's own pinned snapshot, never the current catalog), and transitions each via `SetItemEffectEquipped`.
- `SetItemEffectEquipped` mirrors `ExpireActiveEffect`'s own structure: `Revision`-CAS UPDATE inside `SqliteSavingPipeline.Execute`, with a durable, fixed-order JSON command-summary payload (campaign/effect/actor/expected-revision/target-status) used both as the `DomainEvents` payload and the `AppliedCommands.ResultSummary`, so a replay can be verified byte-for-byte against the original semantic inputs rather than merely trusting a matching `CommandId`.
- Verification approach for this closeout's two open findings: re-derive each from source, not from the prior session's own narrative. The Unity/IL2CPP gap: diff `Odyssey.Persistence.asmdef`'s `references` array against `SqliteCharacterRepository.cs`'s own `using` statements, then repeat identically against `origin/main` to prove it predates this task. The `CharacterAbility` gap: read `ICharacterRepository`'s own contract directly to confirm no suspend/resume method of any shape exists.

No change to `EquipItem`/`UnequipItem`/`EquipmentCommandLedger`, `ActiveEffectStackingRules.cs`/`ActiveEffectExpiryRules.cs`, `SqliteCharacterRepository.cs`, or any `.asmdef`/`.csproj`.

## 10. Recovery and rollback

Rollback of THIS PR is a normal revert before merge. `SetItemEffectEquipped` never physically deletes a row (`ADR-012`'s append-only-history discipline, already established by `ExpireActiveEffect`). Each `ItemEffectLifecycleService` reaction is its own set of independent, individually-idempotent transactions — a host that retries a partially-failed reaction with identical inputs before issuing the next equipment operation recovers cleanly; equipment itself is not automatically rolled back if a later effect write fails.
