# ExecPlan — ODY-S06-106 `ActivateAbility` Root Command

## 1. Purpose
Build `ActivateAbility`, the first command letting a character actually activate an acquired `CharacterAbility` -- authorizing the actor, charging the ability's own resource cost, interpreting `AbilityDefinition.MechanicsPayloadRef` through `ADR-030` §7's mechanics-primitive schema (the first real implementation of it anywhere in this codebase), and applying the outcome atomically, standalone from any `CombatEncounter` (`ADR-030` §9.3). Last block-A item from the product owner's explicit priority ("ability activation should work like everything else").

## 2. Scope
`MechanicsPrimitives.cs` (new, `Odyssey.Domain.Content`) -- the two-primitive schema. `MechanicsPayloadCodec.cs` (new, `Odyssey.Application.Content`) -- versioned decode/encode. `MechanicsPrimitiveInterpreter.cs` (new, `Odyssey.Rules.Mechanics`) -- pure interpreter reusing `AttackDamageFormulaParser`/`AttackRandomSample`. `ActivateAbilityContracts.cs`/`ActivateAbilityService.cs` (new, `Odyssey.Application.Persistence`) -- the command and its read/apply contracts. `SqliteActivateAbilityStateReader.cs`/`SqliteActivateAbilityRepository.cs` (new, `Odyssey.Persistence.Sqlite`) -- the implementations. `SqliteAttackApplyRepository.ApplyAttackDelta` -- visibility-only change for reuse. Nine new tests (`TC-ABILITY-001`-`009`).

**Доработка (product-owner-ordered fix, after independent verification):** `IActivateAbilityRepository.CompensateAbilityActivation` (new, additive) -- real compensating reversal of `RecordAbilityActivation`'s own committed deltas when `ApplyEffect` fails downstream. `CharacterAbility.ActivationDefinitionRef` (new field, `Ability.cs`) + `ICharacterRepository.LinkAbilityActivationSource` (new, additive, `CharacterRepositoryContracts.cs`/`SqliteCharacterRepository.cs`) -- replaces the original `SourceRef`-repurposing bridge. `ActivateAbilityIntent.ExpectedCharacterAbilitiesRevision`/`ExpectedCharacterResourcesRevision` (new required fields) + a fresh in-transaction re-check in `SqliteActivateAbilityRepository.RecordAbilityActivation`. Three new tests (`TC-ABILITY-010`-`012`).

## 6. State and data flow
`ActivateAbilityService.ActivateAbility(reader, apply, catalog, effects, random, clock, campaign, keyEpochId, request)`: idempotency check first (`apply.GetActivation(campaign, request.CommandId, ...)` -- a replay returns the prior record without touching authorization, state, or RNG, **and, доработка, a replay whose own record has `CompensatedAt != null` returns a permanent honest failure instead**) -> `Authorize` (`reader.CanControlActor` or MainGM) -> `reader.Read(campaign, intent, ...)` (loads `CharacterRecord`, finds the `CharacterAbility`, resolves+decodes `AbilityDefinition` via **(доработка) `ActivationDefinitionRef`->catalog->`TypedDefinitionCodec.DecodeAbility`**, decodes `MechanicsPayloadRef` via `MechanicsPayloadCodec.DecodePrimitives` or builds an empty envelope if null) -> `ValidateTargets` (count + self-targeting against `Definition.TargetRule`) -> `RequiresDice` (parses each `AdjustResourcePrimitive.AmountFormula` via `AttackDamageFormulaParser.Parse`, checks for a `DiceGroup` term) -> if true, draw up to 4 independent RNG values via `random.Create(...)`/`RandomDecisionContext`, purpose `"ability.activation.roll"`, building one `AttackRandomSample` -> `MechanicsPrimitiveInterpreter.Interpret(primitives, actorAttributes, randomSample)` -> resolved `ResourceAdjustments`/`EffectsToApply` -> build a combined `List<AttackDelta>` (ability's own `ResourceCosts` as negative deltas on the actor, each resolved adjustment applied to every `TargetIds` entry) -> `apply.RecordAbilityActivation(..., request.Intent.ExpectedCharacterAbilitiesRevision, request.Intent.ExpectedCharacterResourcesRevision, ...)` (one SQLite transaction: **(доработка) fresh revision re-check first**; every `AttackDelta` via `SqliteAttackApplyRepository.ApplyAttackDelta`, all-or-nothing; then the durable `AbilityActivation` row; then the DomainEvent, via `SqliteSavingPipeline`) -> on success, sequential `ApplyEffect` calls per effect x target (deterministic sub-`CommandId`, catalog resolve + decode + `CreateActiveEffect`) -> **(доработка) if any fails, `apply.CompensateAbilityActivation` reverses the just-committed deltas atomically before returning failure** -> `AbilityActivationRecord` returned.

## 7. Error handling
Any state-read failure (ability not found, not enabled, no `ActivationDefinitionRef` set, catalog lookup failure, wrong `DefinitionType`/`Status`/`Version`, incompatible `MechanicsPayloadRef` schema version) surfaces as an honest `Result` failure, never a crash -- `SqliteActivateAbilityStateReader.Read` and `MechanicsPayloadCodec.DecodePrimitives` are both exception-safe. Authorization failure and target-validation failure short-circuit before any RNG draw or transaction. **(доработка) A stale `ExpectedCharacterAbilitiesRevision`/`ExpectedCharacterResourcesRevision`, re-checked fresh inside `RecordAbilityActivation`'s own transaction, rejects the whole command before any delta is applied -- `PersistenceFailures.CharacterRevisionConflict`, reused, no new error code.** Insufficient resource for any single `AttackDelta` (the ability's own cost, or any resolved `AdjustResource` amount) rolls back the WHOLE `RecordAbilityActivation` transaction via `ApplyAttackDelta`'s own existing `OutOfRange` rejection semantics -- nothing partially applied. A retried `CommandId` short-circuits at the very first step (`apply.GetActivation`), before authorization or any RNG derivation, guaranteeing no double charge and no reroll. **`ApplyEffect` failures (after the resource-delta transaction has already committed) are no longer a disclosed-but-unfixed limitation (доработка): `CompensateAbilityActivation` genuinely reverses the already-committed deltas, atomically, and is itself idempotent (a second compensation call for an already-compensated row is a no-op success via the `CompensatedAt` column) -- a retried `CommandId` after compensation is a PERMANENT honest failure (`PreviouslyCompensated`), never a silent success.**

## 8. Test strategy
`ActivateAbilityIntegrationTests.cs` (`Odyssey.Tests.Persistence`): every test a real call through `ActivateAbilityService.ActivateAbility` against a real temp-directory SQLite campaign, using `ContentCatalogAuthoringService`/`ContentCatalogLifecycleService` (not raw repository calls) to author and publish real `Ability`/`Effect` content definitions, mirroring `MinimalTestCatalogFixtureTests.cs`'s own established fixture pattern. `ThrowingRandomFactory` (throws if `Create` is ever called) proves constant-only formulas never derive an RNG stream. `FixedRandomStreamFactory` (prescribed raw values per draw index) proves dice-and-attribute formulas produce an exact, hand-computed expected value. `CountingRandomFactory` (wraps a real `DeterministicRandomStreamFactory`, counts `Create` calls) proves a retried `CommandId` never re-derives randomness. All `AdjustResource` test formulas are damage-shaped (negative), since a freshly initialized `CharacterResource`'s `CurrentValue` already equals `EffectiveMaximum` (`RulesResourceInitializationRules.DefaultBaseMaximum` = 10) -- a heal-shaped formula would exceed the maximum and trigger the same `OutOfRange` rejection real overheal already triggers, a real bug this task's own test-writing found and fixed by recomputing every affected test's own expected value. `MechanicsInterpreterScopeTests.cs` (`Odyssey.Tests.Architecture`): a text scan of only `Packages/com.odyssey.rules/Runtime/Mechanics` (this task's own new folder, not the whole `Odyssey.Rules.Runtime` tree) for forbidden RNG/Application-layer substrings -- deliberately scoped narrower than `RulesScopeTests.cs`'s own whole-tree RNG-only scan, since this test's own broader forbidden list (including the bare substring `"Odyssey.Application"`) would otherwise false-positive against `105`'s own pre-existing, legitimate `CoreAttackRulesEvaluator.cs` doc comment, a file this task cannot modify.

## 10. Recovery and rollback
`SqliteAttackApplyRepository.ApplyAttackDelta`'s visibility change (`private` -> `internal`) is the only modification to a pre-existing file's own logic-bearing surface, and it is logic-unchanged -- `105`'s own full attack test suite re-run unmodified and green confirms this. `ICharacterRepository.LinkAbilityActivationSource` (доработка) is a new, additive interface method -- `SqliteCharacterRepository` is its only implementer (confirmed by repository-wide search), so no other implementer needed updating. No schema change to any pre-existing table beyond the additive `CompensatedAt` column on the brand-new `AbilityActivation` table (no migration needed, nothing has shipped yet). `AcquireAbility`/`AcquireAbilityViaProgressionPurchase`/`RemoveAbility` are untouched -- every existing caller keeps compiling and behaving identically; an ability acquired without a subsequent `LinkAbilityActivationSource` call simply cannot be activated (an honest rejection). Reverting this task's source returns to the pre-`106` state: no `ActivateAbility` command exists, the mechanics-primitive schema ceases to exist, and no later task has yet been built against it (this is the first task to add it).
