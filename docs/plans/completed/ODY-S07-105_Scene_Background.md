# ExecPlan — ODY-S07-105 Scene Background/Map

## 1. Purpose
Give `SceneRecord` a real, validated background/map field (`AssetId? BackgroundAssetId`) through a new `SetSceneBackground` command, fail-closed against `AssetManifestEntries`, and put the reserved-but-unused `AssetReferences` table to its first real use -- the real-catalog counterpart of what `CharacterRecord.PortraitReference` should have been.

## 2. Scope
`SceneRepositoryContracts.cs` -- `SceneRecord.BackgroundAssetId`, new `ISceneRepository.SetSceneBackground`. `SqliteSceneRepository.cs` -- implementation, `Scene` DDL column, `ReplayScene` update. `ErrorCodes.cs`/`CampaignRepositoryContracts.cs`/`ERROR_CODES.md` -- two new additive error entries (disclosed allowed-paths gap). `SqliteSceneRepositoryTests.cs` (`TC-BOARD-016`-`023`). `test-catalog.json`. `SLICE-07_IMPLEMENTATION_BACKLOG.md` (block 4 status, row 5). This task's own contract and ExecPlan.

## 3. Non-goals
Origin/scale/placement metadata (`ADR-020`'s own future implementation task). A new `ContentDefinitionType`/publishable catalog type. Token/character portraits (block 5, confirmed separate via `AskUserQuestion`). `CreateScene`/`CreateToken`/`GetToken`/`MoveToken`/`ListTokens`/`ListTokensByCharacter`/`RegisterAsset`'s existing signatures/behavior. Any ADR revision. `SLICE-05_IMPLEMENTATION_BACKLOG.md`/`SLICE-06_IMPLEMENTATION_BACKLOG.md`. `ODY-S07-102`-`104` files.

## 4. Architecture
`SceneRecord.BackgroundAssetId` (`AssetId?`, optional ctor param defaulted to `null`, validated only when supplied -- mirrors `TokenRecord.CharacterId`'s own precedent). `ISceneRepository.SetSceneBackground(campaign, sceneId, backgroundAssetId, expectedRevision, commandId, correlationId)` mirrors `MoveToken`'s own shape exactly (`expectedRevision` for atomic-inside-transaction optimistic concurrency, `CommandId` for `SqliteSavingPipeline`-mediated idempotent replay). Implementation order inside the pipeline's `apply` delegate: read Scene row (fail `SceneNotFound`) -> check `expectedRevision` (fail new `SceneRevisionConflict`) -> if non-null, check `AssetManifestEntries` existence in this same campaign's db (fail new `AssetNotFound` -- covers both "never existed" and "exists in a different campaign" with one lookup, since each campaign is its own database file) -> `UPDATE Scene` -> `DELETE FROM AssetReferences` for this scene, then conditionally `INSERT` the new row -- delete-then-optionally-reinsert, never accumulating. The `Scene` table's own `CREATE TABLE IF NOT EXISTS` DDL gains one new nullable `BackgroundAssetId TEXT` column.

## 6. State and data flow
`SetSceneBackground` -> `SqliteSavingPipeline.Execute` -> `tryReplay`: `ReplayScene` by `LastCommandId` (now also selecting/returning `BackgroundAssetId`) -> `apply`: read current Scene row -> optimistic-concurrency check -> conditional `AssetManifestEntries` existence check -> `UPDATE Scene` (new revision, new `BackgroundAssetId`, `LastCommandId`) -> `AssetReferences` delete-then-optionally-reinsert -> `PipelineWrite<SceneRecord>` with a new `"odyssey.persistence.scene_background_set"` DomainEvent, committed atomically with the `AppliedCommands` idempotency row (`ADR-012` §5).

## 7. Error handling
Missing Scene -> existing, unmodified `SceneNotFound`. Revision mismatch -> new `SceneRevisionConflict`, checked atomically inside the same transaction (`ADR-002` §10.2), by exact precedent of `TokenRevisionConflict`. Non-existent or cross-campaign `AssetId` -> new `AssetNotFound`, a single lookup covering both cases since `AssetManifestEntries` has no `CampaignId` column and each campaign is its own database file. I/O failure -> existing, unmodified `SceneIoFailed`.

## 8. Test strategy
`SqliteSceneRepositoryTests.cs`, real SQLite-backed, temp-directory campaign (this file's own established `SetUp`/`TearDown` pattern): a `RegisterTestAsset` helper (real file write + `RegisterAsset` call, mirroring `RegisterAsset_CopiesFileIntoAssetsObjects...`'s own fixture style) and two direct-SQL `AssetReferences`-row-count helpers (own short-lived `SqliteConnection`, mirroring `CatalogValidationServiceTests.MarkPublishedDirectly`'s own direct-SQL precedent for test-only assertions the public API cannot express). `TC-BOARD-018`'s cross-campaign case creates and tears down a second, genuinely separate temp campaign within the test itself -- not a mocked/faked campaign boundary.

## 10. Recovery and rollback

Reverting this task's source returns `SceneRecord`/`ISceneRepository`/`AssetReferences` to their pre-`105` state exactly; no later task depends on `SetSceneBackground`/`BackgroundAssetId` (this is the first task to add them).
