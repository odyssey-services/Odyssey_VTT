# ExecPlan — ODY-S07-102 Check/Contest Resolution Implementation

## 1. Purpose
Build the first real implementation of `ADR-031`'s check/contest resolution architecture: a new command that resolves an attribute/skill formula through the already-accepted shared grammar, rolls through the real, unmodified `DiceRollService.SubmitRoll`, judges pass/fail through a new pure `Odyssey.Rules` evaluator, and finally closes the multi-task-old, explicitly-disclosed `RecordCriticalSuccessEvidence` trigger gap (`ODY-S04-106`/`114`).

## 4. Architecture
`CheckParticipantState` (`Odyssey.Domain.Checks`) mirrors `AttackParticipantState`'s own copy-defensive-dictionary idiom, carrying both `AttributeValues`/`SkillValues`, deliberately without `LifecycleStatus`/`ApprovalState`. `CheckOutcome`/`CheckResultKind` live in the same Domain namespace (not `Odyssey.Rules`) so both `Odyssey.Application`/`Odyssey.Persistence` can reference them without an extra `Odyssey.Rules` dependency, mirroring `ProposedAttackResolution`/`AttackRandomSample`'s own established "Rules produces a Domain-shaped result" pattern. `ICheckRulesEvaluator`/`CoreCheckRulesEvaluator` (`Odyssey.Rules.Checks`) is structurally parallel to, but independent of, `IAttackRulesEvaluator`/`CoreAttackRulesEvaluator`: `TryResolveFormula` (pure, `TryParse`-shaped, no `Result<T>` since `Odyssey.Rules` cannot reference `Odyssey.Application.Results`, confirmed by direct `CoreAttackRulesEvaluator` doc-comment read) and `Evaluate` (pure, takes plain `int[]`/`int` for die results rather than the Application-layer `NaturalResult` type, since `Odyssey.Rules`'s own `.asmdef` only references `Odyssey.Domain`). `CheckService.PerformCheck` (`Odyssey.Application.Checks`) is the orchestrator, mirroring `ActivateAbilityService.ActivateAbility`'s own idempotency-first shape but routing its own roll through `DiceRollService.SubmitRoll` (a new caller, zero changes to that service). `SqliteCheckStateReader`/`SqliteCheckRepository` (`Odyssey.Persistence.Sqlite`) mirror `SqliteAttackStateReader`/`SqliteActivateAbilityRepository`'s own established shapes exactly, including `SqliteSavingPipeline.Execute`'s tryReplay/apply idiom.

## 6. State and data flow
`CheckService.PerformCheck(reader, apply, characters, diceRollStore, random, clock, campaign, rulesetVersion, keyEpochId, request)`: `apply.GetCheckOutcome` (idempotency, BEFORE any RNG derivation -- mandatory since `DiceRollService.SubmitRoll` has no `CommandId`-keyed replay of its own) -> `reader.Read` (real `CheckParticipantState`, zero extra DB reads) -> `AttackDamageFormulaParser.TryParse` (the shared grammar, unmodified) -> `ICheckRulesEvaluator.TryResolveFormula` (exactly one `DiceGroup` term reconstructed into a dice-only string; at most one `AttributeReference` term resolved fail-closed against both dictionaries; every `Constant` term summed) -> build `AutomaticModifierRequest` entries (`FormulaConstant` if non-zero; `AttributeModifier`/`SkillModifier` for the resolved reference) -> real `DiceRollService.SubmitRoll` (`actorCanCreateRoll: true`, the request's own `Audience`) -> `ICheckRulesEvaluator.Evaluate` against the real `DiceRoll.FinalTotal`/`NaturalResults` -> conditionally `characters.RecordCriticalSuccessEvidence` (real `DiceRoll.RollId`, a deterministic sub-`CommandId`) when `IsNaturalMaximum && ResolvedSkillId.HasValue` -> `apply.RecordCheckOutcome` -> `CheckOutcomeRecord` returned.

## 7. Error handling
An unresolved/ambiguous reference, or a formula with zero/more-than-one `DiceGroup`/more-than-one `AttributeReference` term, is a typed, fail-closed `Result` failure BEFORE `DiceRollService.SubmitRoll` is ever called -- zero RNG consumed, zero durable writes, proven in tests by a `ThrowingRandomFactory` test double that fails the test if `Create` is ever invoked. A `RecordCriticalSuccessEvidence` failure (after a real roll already happened) short-circuits before `RecordCheckOutcome`, leaving `GetCheckOutcome` unable to find a record on retry -- a disclosed, accepted limitation (this task's own §18) since `ADR-031` imposes no compensation requirement on checks and `RecordCriticalSuccessEvidence` itself is already idempotent by its own deterministic sub-`CommandId`.

## 8. Test strategy
`CheckIntegrationTests.cs` (`Odyssey.Tests.Persistence`): every test a real call through `CheckService.PerformCheck` against a real temp-directory SQLite campaign and a real, unmodified `DiceRollService.SubmitRoll`/`DiceRollStore`, mirroring `ActivateAbilityIntegrationTests.cs`'s own established `Active`/`GrantAttribute`/`Command`/`User`/`FixedRandomStreamFactory`/`ThrowingRandomFactory` helpers verbatim, plus a new `GrantSkill` helper (`PurchaseSkillLevel`, mirroring `GrantAttribute`'s own shape) and a new `CountingRandomFactory` wrapper (mirroring `ActivateAbilityIntegrationTests.cs`'s own identical-purpose double) for the idempotency test's own "exactly one RNG derivation across two calls" assertion. `FixedRandomStreamFactory`'s own fixed value is used directly as the natural die result (`DiceRollService`'s own `NextInclusive` passes the raw sample through unmodified, unlike the modulo-mapped d6 convention `CoreAttackRulesEvaluator`'s own tests use) -- `FixedRandomStreamFactory(20)` on a `1d20` formula deterministically produces a natural maximum, `FixedRandomStreamFactory(10)` deterministically does not.
