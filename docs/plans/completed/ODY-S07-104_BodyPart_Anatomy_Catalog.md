# ExecPlan — ODY-S07-104 Body-Part/Anatomy Catalog

## 1. Purpose
Replace today's hardcoded, test-fixture-only `AnatomyInitializationRules.DefaultHumanoidBodyParts()` with two real, publishable content types -- `BodyPartDefinition` and `AnatomyProfileDefinition` -- flowing Draft→Published through the unmodified `SLICE-05` catalog pipeline. Catalog/authoring only; `InitializeCharacterAnatomy` is not wired to the new catalog (a deliberate, product-owner-confirmed scope decision, not a risk deferral).

## 4. Architecture
`BodyPartDefinition` (`Odyssey.Domain.Content`): `Name`/`DamageLimit` (`> 0`)/`Properties`, mirroring the personal-character `BodyPart` shape exactly, no more. `AnatomyProfileBodyPartRef`: `BodyPartRef` (exact-version `ContentDefinitionRef`, by precedent of `ItemDefinition.BuiltInAbilityRefs`) + `AttachedToIndex` (`int?`, positional into the owning list -- not a `BodyPartId`, since none exists yet at authoring time). `AnatomyProfileDefinition`: `BodyPartRefs` (non-empty, ctor-validated against self-reference/out-of-range/cycle in the `AttachedToIndex` chain -- a same-definition structural invariant, distinct from cross-definition reference validation). `TypedDefinitionCodec.EncodeBodyPart`/`DecodeBodyPart`/`EncodeAnatomyProfile`/`DecodeAnatomyProfile` follow `EncodeSkill`/`DecodeSkill`'s exact shape (schemaVersion embed/check, wrong-type-first, malformed-payload try/catch, ctor validation folded into the same catch). `CatalogValidationContracts.ValidateBodyPart`/`ValidateAnatomyProfile` decode-and-report, by precedent of `ValidateSkill` (no post-decode business rule beyond decodability). A new `CollectOutgoingRefs` case for `AnatomyProfile` emits each `BodyPartRefs[i].BodyPartRef` with expected type `BodyPart`, feeding the existing, unmodified `ValidateReferencesAndCycles` -- the actual existence/version/type/ruleset check for cross-definition references.

## 6. State and data flow
Authoring: `ContentCatalogAuthoringService.CreateDraftDefinition(type: BodyPart, propertiesJson: EncodeBodyPart(...))` and, separately, `CreateDraftDefinition(type: AnatomyProfile, propertiesJson: EncodeAnatomyProfile(...))` referencing the BodyPart's exact-version `ContentDefinitionRef`. Validation: `CatalogValidationService.ValidateDraftForPublish` -> `ValidateInternal` -> switch dispatches to `ValidateBodyPart`/`ValidateAnatomyProfile` (decode-only) -> `ValidateReferencesAndCycles` (unmodified) -> `CollectOutgoingRefs`'s new `AnatomyProfile` case emits each `BodyPartRef` with expected type `BodyPart` -> existence/version/type/ruleset checked exactly as any other cross-reference. Publish: `ContentCatalogLifecycleService.PublishDefinition` -> re-validates (unmodified) -> `Published`, version 1.

## 7. Error handling
`DecodeBodyPart`/`DecodeAnatomyProfile(actualType != expected, ...)` return `WrongDefinitionType` before any JSON parsing. Malformed JSON, missing/unsupported `schemaVersion`, and any constructor-validation failure (empty `BodyPartRefs`, self-referencing/out-of-range/cyclic `AttachedToIndex`) all surface as `MalformedPayload` through the same `IsMalformedPayloadException` machinery -- no new exception type, no new error code. A `BodyPartRef` that fails to resolve (missing/wrong-version/wrong-type/ruleset-incompatible) is caught by the existing, unmodified `ValidateReferencesAndCycles`, reporting `ReferenceMissing`/`ReferenceVersionMismatch`/`ReferenceWrongType`/`RulesetIncompatible` exactly as any other type's cross-reference already does.
