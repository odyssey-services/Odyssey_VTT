# ExecPlan — ODY-S07-103 Skill Catalog

## 1. Purpose
Give `ContentDefinitionType.Skill` -- today a bare, unused enum value -- a real, publishable content type through the already-existing, unmodified `SLICE-05` catalog-authoring/validation/publish pipeline, by the exact precedent `AbilityDefinition`/`EffectDefinition` (`ODY-S05-105`) already established.

## 2. Scope
`Packages/com.odyssey.domain/Runtime/Content/TypedDefinitions.cs` -- new `SkillDefinition`. `Packages/com.odyssey.application/Runtime/Content/TypedDefinitionCodec.cs` -- new `EncodeSkill`/`DecodeSkill`. `Packages/com.odyssey.application/Runtime/Content/CatalogValidationContracts.cs` -- new `ValidateSkill` branch. `TypedDefinitionCodecTests.cs` (`TC-CATALOG-113`-`116`). `MinimalTestCatalogFixtureTests.cs` (`TC-CATALOG-112`). `test-catalog.json`. `SLICE-07_IMPLEMENTATION_BACKLOG.md` (block 2 status, row 3). This task's own contract and ExecPlan.

## 3. Non-goals

Any ADR. `SLICE-05_IMPLEMENTATION_BACKLOG.md`/`SLICE-06_IMPLEMENTATION_BACKLOG.md`. The generic `ContentCatalogAuthoringService`/`ContentCatalogLifecycleService`/`CatalogValidationService` pipeline itself -- only a new type-specific branch is added.

## 4. Architecture
`SkillDefinition` (`Odyssey.Domain.Content`, `TypedDefinitions.cs`): a `sealed class`, Domain-layer, no fields beyond what `ContentDefinitionRecord`'s own generic envelope already carries -- confirmed, not assumed, by direct comparison against `AbilityDefinition`/`EffectDefinition`'s own constructors before writing it. No `MechanicsPayloadRef` (a skill is never executed as a mechanic) and no governing-attribute field (no consumer reads such a relationship) -- both withheld per the governing ТЗ's own §1 decisions, not silently omitted. `TypedDefinitionCodec.EncodeSkill`/`DecodeSkill` follow `EncodeAbility`/`DecodeAbility`'s own exact shape: `EncodeSkill` writes only the shared `schemaVersion` envelope (nothing else to write); `DecodeSkill` checks `actualType != ContentDefinitionType.Skill` first, then `JObject.Parse`/`RequireSupportedSchemaVersion` under the same `try`/`catch` over `IsMalformedPayloadException`, constructing a bare `new SkillDefinition()` on success. No new `ErrorCodes` -- `TypedDefinitionCodecFailures.WrongDefinitionType`/`MalformedPayload` are already fully generic, confirmed by direct read before writing `DecodeSkill`. `CatalogValidationContracts.ValidateSkill` calls `DecodeSkill`, reports a codec-failure issue via the existing `AddCodecFailureIssue` helper on failure, and otherwise does nothing further -- there is no field to validate beyond decodability, the same shape `ValidateAmmo` already has.

## 6. State and data flow
Authoring: `ContentCatalogAuthoringService.CreateDraftDefinition(repository, CreateDraftDefinitionRequest(type: Skill, ..., propertiesJson: TypedDefinitionCodec.EncodeSkill(new SkillDefinition())))` -> a Draft `ContentDefinitionRecord` with `DefinitionType == Skill`. Validation: `CatalogValidationService.ValidateDraftForPublish` -> `ValidateInternal` -> `switch` dispatches to the new `ValidateSkill`, which calls `TypedDefinitionCodec.DecodeSkill(record.DefinitionType, record.PropertiesJson, correlationId)` and reports any codec failure as a `CatalogValidationIssue`; `ValidateReferencesAndCycles` still runs afterward, unmodified, over the record's generic `DependencyRefsJson` (a Skill has none). Publish: `ContentCatalogLifecycleService.PublishDefinition` -> re-validates (unmodified) -> `Published`, version 1.

## 7. Error handling
`DecodeSkill(actualType != Skill, ...)` returns `WrongDefinitionType` before any JSON is parsed. Malformed JSON, a missing `schemaVersion`, or an unsupported `schemaVersion` all surface as `MalformedPayload` through the same `IsMalformedPayloadException`/`RequireSupportedSchemaVersion` machinery every other `DecodeX` already uses -- no new exception type, no new error code. `ValidateSkill` never throws; a decode failure becomes a typed `CatalogValidationIssue` via `AddCodecFailureIssue`, exactly like `ValidateAbility`/`ValidateEffect`/`ValidateAmmo`.

## 8. Test strategy
`TypedDefinitionCodecTests.cs` (pure, in-memory, no SQLite): `SkillDefinition_RoundTrips` (Encode/Decode symmetry); `DecodeSkill_AgainstEffectDefinitionType_IsRejected` (wrong-type, `ContentCatalogTypedDefinitionWrongType`); `DecodeSkill_OnMalformedJson_ReturnsSafeFailure_NotRawException` (`{ this is not valid json`, `null`); `DecodeSkill_OnPayloadMissingSchemaVersion_ReturnsSafeFailure`; `DecodeSkill_OnPayloadWithUnsupportedSchemaVersion_ReturnsSafeFailure` (`0`, `2`, `"1"`, `null`) -- each mirroring the identical-purpose `Ability`/`Item` tests already in this file line-for-line, substituting `Skill`. `MinimalTestCatalogFixtureTests.cs` (real, SQLite-backed, temp-directory campaign): `SkillFixture_PublishesEndToEnd_ThroughAuthoringValidationAndLifecycle` -- `AuthorDraft(ContentDefinitionType.Skill, "Lockpicking", EncodeSkill())`, a real `Validate` call asserting `IsValid`, then `PublishFixture`, asserting `Status == Published`/`Version == 1`. No constructor-validation test for a Skill-specific field -- `SkillDefinition` has none (governing ТЗ §4 point 6, not applicable).
