# ExecPlan — ODY-S06-108 Real MVP Content + End-to-End Two-Character Combat Scenario

Prove the whole product-owner MVP scenario really works, end-to-end, through nothing but already-accepted public production services -- the last task of the original MVP roadmap, combining blocks E ("real MVP content") and F ("end-to-end scenario test/harness") into one task per the product owner's own explicit decision (this task's own governing ТЗ §0).

## 2. Scope
One new test file, `DotNet/Tests/Odyssey.Tests.Persistence/MvpTwoCharacterCombatScenarioTests.cs` -- a single `[Test]`-class, private helpers only, mirroring `ActivateAbilityIntegrationTests.cs`/`UseItemIntegrationTests.cs`/`CoreAttackRulesEvaluatorIntegrationTests.cs`'s own established "one test class, no shared production fixture class" precedent exactly. ## 6. State and data flow
`Active("Attacker")`/`Active("Defender")` -> `InitResource`(Mana/Health for the attacker, Health for the defender) -> `GrantAttribute`(attacker, Strength, 2) -> `InitializeCharacterAnatomy`(both) -> five `AuthorDraft`+`PublishFixture` pairs (weapon, armor, instant effect, consumable item referencing the effect via `BuiltInEffectRefs`+`dependencyRefs`, self-`AdjustResource` ability) -> two `CreateInventory` -> `InventoryCreationService.CreateItemInstanceFromDefinition` (weapon, armor) / `CreateItemStackFromDefinition` (potion, quantity 2) -> `EquipmentService.Equip` (weapon into the attacker's `main_hand`, no body parts; armor into the defender's `chest_slot`, `Torso`) -> `AcquireAbility`(GMGrant)+`LinkAbilityActivationSource` -> one scene, two linked tokens (attacker at (0,0), defender at (3,0)) -> one `CombatEncounterService.Create` -> `AttackApplyService.ResolveAttack` (attack #1: distance 3 <= range 5, real armor-mitigated damage) -> `ActivateAbilityService.ActivateAbility` (self-targeted, deterministic Mana cost + self-`AdjustResource`) -> `UseItemService.UseItem` (the potion's `Instant` heal, stack quantity 2 -> 1) -> `BoardMovementService.MoveToken` (defender to (10,0), distance 10 > range 5) -> `AttackEvaluationService.EvaluateAttack` (attack #2: out of range, zero damage, defender's Health provably unchanged from attack #1).

## 7. Error handling
Every intermediate call asserts `IsSuccess` (with the failing `Error.Code` surfaced on assertion failure, matching `105`-`107`'s own established test-failure-message convention) before the scenario proceeds -- a failure at any step stops the test immediately rather than continuing on corrupted state, so a regression in ANY of the seven consumed root commands fails this test at the exact step that broke, not only at a final assertion.

## 8. Test strategy
One comprehensive scenario test (`TC-MVP-001`), asserting exact intermediate values at every step (defender Health after attack #1; attacker Mana and Health after ability activation, plus a duplicate-grant check; attacker Health and potion stack quantity after item use; attack #2's own `Range.IsInRange`/`Hit.IsHit`/`DamageDeltas`/defender Health-unchanged). No mocking anywhere -- every collaborator is a real `Sqlite*` implementation against a real temp-directory campaign, exactly like every prior `ODY-S06-10x` integration test. `FixedRandomStreamFactory(10, 20, 30, 40)` (copied verbatim from `105`/`106`'s own precedent) makes the weapon's own `1d6` term deterministic (raw 10 -> 4) for an exact, not merely range-bounded, damage assertion.
