# ExecPlan — ODY-S06-106 `ActivateAbility` Root Command

## 1. Purpose
Build `ActivateAbility`, the first command letting a character actually activate an acquired `CharacterAbility` -- authorizing the actor, charging the ability's own resource cost, interpreting `AbilityDefinition.MechanicsPayloadRef` through `ADR-030` §7's mechanics-primitive schema (the first real implementation of it anywhere in this codebase), and applying the outcome atomically, standalone from any `CombatEncounter` (`ADR-030` §9.3). Last block-A item from the product owner's explicit priority ("ability activation should work like everything else").

## 2. Scope
`MechanicsPrimitives.cs` (new, `Odyssey.Domain.Content`) -- the two-primitive schema. `MechanicsPayloadCodec.cs` (new, `Odyssey.Application.Content`) -- versioned decode/encode. `MechanicsPrimitiveInterpreter.cs` (new, `Odyssey.Rules.Mechanics`) -- pure interpreter reusing `AttackDamageFormulaParser`/`AttackRandomSample`. `ActivateAbilityContracts.cs`/`ActivateAbilityService.cs` (new, `Odyssey.Application.Persistence`) -- the command and its read/apply contracts. `SqliteActivateAbilityStateReader.cs`/`SqliteActivateAbilityRepository.cs` (new, `Odyssey.Persistence.Sqlite`) -- the implementations. `SqliteAttackApplyRepository.ApplyAttackDelta` -- visibility-only change for reuse. Nine new tests (`TC-ABILITY-001`-`009`).

**Доработка (product-owner-ordered fix, after independent verification):** `IActivateAbilityRepository.CompensateAbilityActivation` (new, additive) -- real compensating reversal of `RecordAbilityActivation`'s own committed deltas when `ApplyEffect` fails downstream. `CharacterAbility.ActivationDefinitionRef` (new field, `Ability.cs`) + `ICharacterRepository.LinkAbilityActivationSource` (new, additive, `CharacterRepositoryContracts.cs`/`SqliteCharacterRepository.cs`) -- replaces the original `SourceRef`-repurposing bridge. `ActivateAbilityIntent.ExpectedCharacterAbilitiesRevision`/`ExpectedCharacterResourcesRevision` (new required fields) + a fresh in-transaction re-check in `SqliteActivateAbilityRepository.RecordAbilityActivation`. Three new tests (`TC-ABILITY-010`-`012`).

**Вторая доработка (product-owner-ordered fix, after independent verification of the first доработка):** `CompensateAbilityActivation` extended to also remove every already-created `ActiveEffectId` via the existing, unmodified `IActiveEffectRepository.RemoveActiveEffect` (`ODY-S05-506`), BEFORE reversing resource deltas -- the first fix's own compensation only reversed resources, leaving already-created effects behind on a later-effect/later-target failure. `SqliteActivateAbilityRepository`'s constructor widened to take `IActiveEffectRepository`. One new test (`TC-ABILITY-013`).

**Третья доработка (product-owner-ordered fix, after independent verification of the second доработка targeting the idempotency requirement that same review explicitly asked to be re-checked):** a retry after an INCOMPLETE compensation attempt (`CompensateAbilityActivation` itself failing partway through) was silently reported as `Success`, since `CompensatedAt == null` alone could not distinguish that from "compensation never attempted." A new durable `CompensationStartedAt` column, set unconditionally the first time compensation is ever attempted, now lets `ActivateAbilityService`'s own idempotency check tell the two states apart -- a retry in the incomplete state resumes compensation (reading a durable `CreatedEffectIdsJson` list back, since the original in-memory list no longer exists) and always reports `Failure`. One new test (`TC-ABILITY-014`).

## 4. Architecture
`Odyssey.Domain.Content` gains `MechanicsPrimitives.cs` -- placed in Domain (not Application/Rules) since both the decode layer (Application) and the interpretation layer (Rules) need the same shape, and Rules cannot reference Application (confirmed structurally, same barrier `105` already confirmed via `.asmdef`/`.csproj`). `Odyssey.Application.Content` gains `MechanicsPayloadCodec.cs`, mirroring `TypedDefinitionCodec`'s own `RequireSupportedSchemaVersion`/exception-safe-decode pattern, versioned independently since it decodes mechanics-execution shape, not catalog shape. `Odyssey.Rules.Mechanics` (new folder, sibling to `Odyssey.Rules.Combat`) gains `MechanicsPrimitiveInterpreter.cs` -- references only `Odyssey.Rules.Combat` (`AttackDamageFormulaParser`/`AttackFormulaTerm`/`AttackFormulaTermKind`) and `Odyssey.Domain` types, never `Odyssey.Application`, verified by a scoped architecture guard test. `Odyssey.Application.Persistence` gains `ActivateAbilityContracts.cs` (interfaces/DTOs) and `ActivateAbilityService.cs` (orchestrator, mirrors `AttackEvaluationService`/`AttackApplyService`'s own shape). `Odyssey.Persistence.Sqlite` gains `SqliteActivateAbilityStateReader` (all decoding happens here, so the Rules-layer interpreter only ever receives already-decoded Domain objects -- the same resolution pattern `105` established for `CoreAttackRulesEvaluator`) and `SqliteActivateAbilityRepository` (owns a new standalone `AbilityActivation` table, reuses `SqliteAttackApplyRepository.ApplyAttackDelta` -- made `internal` -- and the shared `SqliteSavingPipeline`).

## 6. State and data flow
`ActivateAbilityService.ActivateAbility(reader, apply, catalog, effects, random, clock, campaign, keyEpochId, request)`: idempotency check first (`apply.GetActivation(campaign, request.CommandId, ...)` -- a replay returns the prior record without touching authorization, state, or RNG, **and, доработка, a replay whose own record has `CompensatedAt != null` returns a permanent honest failure instead**) -> `Authorize` (`reader.CanControlActor` or MainGM) -> `reader.Read(campaign, intent, ...)` (loads `CharacterRecord`, finds the `CharacterAbility`, resolves+decodes `AbilityDefinition` via **(доработка) `ActivationDefinitionRef`->catalog->`TypedDefinitionCodec.DecodeAbility`**, decodes `MechanicsPayloadRef` via `MechanicsPayloadCodec.DecodePrimitives` or builds an empty envelope if null) -> `ValidateTargets` (count + self-targeting against `Definition.TargetRule`) -> `RequiresDice` (parses each `AdjustResourcePrimitive.AmountFormula` via `AttackDamageFormulaParser.Parse`, checks for a `DiceGroup` term) -> if true, draw up to 4 independent RNG values via `random.Create(...)`/`RandomDecisionContext`, purpose `"ability.activation.roll"`, building one `AttackRandomSample` -> `MechanicsPrimitiveInterpreter.Interpret(primitives, actorAttributes, randomSample)` -> resolved `ResourceAdjustments`/`EffectsToApply` -> build a combined `List<AttackDelta>` (ability's own `ResourceCosts` as negative deltas on the actor, each resolved adjustment applied to every `TargetIds` entry) -> `apply.RecordAbilityActivation(..., request.Intent.ExpectedCharacterAbilitiesRevision, request.Intent.ExpectedCharacterResourcesRevision, ...)` (one SQLite transaction: **(доработка) fresh revision re-check first**; every `AttackDelta` via `SqliteAttackApplyRepository.ApplyAttackDelta`, all-or-nothing; then the durable `AbilityActivation` row; then the DomainEvent, via `SqliteSavingPipeline`) -> on success, sequential `ApplyEffect` calls per effect x target (deterministic sub-`CommandId`, catalog resolve + decode + `CreateActiveEffect`, tracking each succeeded `ActiveEffectId` into an in-memory `createdEffectIds` list -- вторая доработка) -> **if any fails, `apply.CompensateAbilityActivation(campaign, request.CommandId, createdEffectIds, request.ActorUserId, ...)` removes every already-created effect (вторая доработка) THEN reverses the just-committed resource deltas (доработка) atomically before returning failure** -> `AbilityActivationRecord` returned. **Третья доработка:** the top-of-method idempotency check now branches THREE ways instead of two: `CompensatedAt != null` -> permanent `Failure` (доработка, unchanged); `CompensationStartedAt != null && CompensatedAt == null` -> resume compensation via `apply.CompensateAbilityActivation(campaign, request.CommandId, Array.Empty<ActiveEffectId>(), ...)` and always report `Failure`; else -> the pre-existing success-replay path, unchanged.

## 7. Error handling
Any state-read failure (ability not found, not enabled, no `ActivationDefinitionRef` set, catalog lookup failure, wrong `DefinitionType`/`Status`/`Version`, incompatible `MechanicsPayloadRef` schema version) surfaces as an honest `Result` failure, never a crash -- `SqliteActivateAbilityStateReader.Read` and `MechanicsPayloadCodec.DecodePrimitives` are both exception-safe. Authorization failure and target-validation failure short-circuit before any RNG draw or transaction. **(доработка) A stale `ExpectedCharacterAbilitiesRevision`/`ExpectedCharacterResourcesRevision`, re-checked fresh inside `RecordAbilityActivation`'s own transaction, rejects the whole command before any delta is applied -- `PersistenceFailures.CharacterRevisionConflict`, reused, no new error code.** Insufficient resource for any single `AttackDelta` (the ability's own cost, or any resolved `AdjustResource` amount) rolls back the WHOLE `RecordAbilityActivation` transaction via `ApplyAttackDelta`'s own existing `OutOfRange` rejection semantics -- nothing partially applied. A retried `CommandId` short-circuits at the very first step (`apply.GetActivation`), before authorization or any RNG derivation, guaranteeing no double charge and no reroll. **`ApplyEffect` failures (after the resource-delta transaction has already committed) are no longer a disclosed-but-unfixed limitation: `CompensateAbilityActivation` genuinely reverses BOTH already-created `ActiveEffect` rows (via `IActiveEffectRepository.RemoveActiveEffect`, вторая доработка) AND already-committed resource deltas (доработка), and is itself idempotent throughout -- a retried `CommandId` after compensation is a PERMANENT honest failure (`PreviouslyCompensated`), never a silent success.** **(третья доработка, correcting this section's own prior, factually wrong claim that an incomplete effect-removal failure was "safely retryable" without qualification) if any single effect removal itself fails partway through compensation, `CompensationStartedAt` is ALREADY durably marked (set before the removal loop even starts) -- so a retry no longer mistakes this incomplete state for a fresh success; it resumes compensation, reading the durable `CreatedEffectIdsJson` list back (not the resuming caller's own, necessarily-empty, in-memory list), and always reports `Failure`, whether the resumed attempt now finishes or fails again.**

## 8. Test strategy
`ActivateAbilityIntegrationTests.cs` (`Odyssey.Tests.Persistence`): every test a real call through `ActivateAbilityService.ActivateAbility` against a real temp-directory SQLite campaign, using `ContentCatalogAuthoringService`/`ContentCatalogLifecycleService` (not raw repository calls) to author and publish real `Ability`/`Effect` content definitions, mirroring `MinimalTestCatalogFixtureTests.cs`'s own established fixture pattern. `ThrowingRandomFactory` (throws if `Create` is ever called) proves constant-only formulas never derive an RNG stream. `FixedRandomStreamFactory` (prescribed raw values per draw index) proves dice-and-attribute formulas produce an exact, hand-computed expected value. `CountingRandomFactory` (wraps a real `DeterministicRandomStreamFactory`, counts `Create` calls) proves a retried `CommandId` never re-derives randomness. All `AdjustResource` test formulas are damage-shaped (negative), since a freshly initialized `CharacterResource`'s `CurrentValue` already equals `EffectiveMaximum` (`RulesResourceInitializationRules.DefaultBaseMaximum` = 10) -- a heal-shaped formula would exceed the maximum and trigger the same `OutOfRange` rejection real overheal already triggers, a real bug this task's own test-writing found and fixed by recomputing every affected test's own expected value. `MechanicsInterpreterScopeTests.cs` (`Odyssey.Tests.Architecture`): a text scan of only `Packages/com.odyssey.rules/Runtime/Mechanics` (this task's own new folder, not the whole `Odyssey.Rules.Runtime` tree) for forbidden RNG/Application-layer substrings -- deliberately scoped narrower than `RulesScopeTests.cs`'s own whole-tree RNG-only scan, since this test's own broader forbidden list (including the bare substring `"Odyssey.Application"`) would otherwise false-positive against `105`'s own pre-existing, legitimate `CoreAttackRulesEvaluator.cs` doc comment, a file this task cannot modify.

**Вторая доработка:** `TC-ABILITY-013` publishes an ability with TWO `ApplyEffectPrimitive`s on one self-target (`PublishAbilityWithTwoApplyEffects`), archives the second effect's own `ContentDefinitionRecord` before activation (the same real-injection technique `TC-ABILITY-010` already established, extended to a second effect so the failure lands past the first, already-successful one). A new `CountStillAttached` helper filters `ListActiveEffectsByTarget`'s own results to `Active`/`Suspended` status -- a real first-draft bug was found and fixed here: that method returns every row regardless of `Status` (`ADR-012`'s append-only history keeps a `Removed` row, never deletes it), so the test's own first assertion ("the list is empty") was wrong and had to be corrected to a status-filtered count instead.

**Третья доработка:** `TC-ABILITY-014` needs a failure INSIDE compensation's own removal loop, not the original `ApplyEffect` application step (which archiving a `ContentDefinitionRef` cannot reach, since `RemoveActiveEffect` never touches the catalog at all -- confirmed by direct code read before designing this test). Since compensation runs entirely within one synchronous `ActivateAbilityService.ActivateAbility` call, there is no way to externally intervene between two already-created effects' own removal calls using only real, unassisted production code paths -- so a small, real `IActiveEffectRepository` decorator (`FailsNthRemovalActiveEffectRepository`) was written, forwarding every call to the real `SqliteActiveEffectRepository` except the Nth `RemoveActiveEffect` call, which returns a real `Result.Failure` without touching the database -- mirroring this same test file's own already-established precedent of small, real, single-behavior-controlling interface implementations (`ThrowingRandomFactory`/`FixedRandomStreamFactory`/`CountingRandomFactory`), not a mocking framework. A three-effect ability (`PublishAbilityWithThreeApplyEffects`) creates two real effects before the third fails (archived), so compensation has two removals to attempt -- the decorator fails the second. The retry then uses a SECOND `SqliteActivateAbilityRepository` built on the REAL, undecorated repository, modeling "the transient failure is gone."

## 10. Recovery and rollback
`SqliteAttackApplyRepository.ApplyAttackDelta`'s visibility change (`private` -> `internal`) is the only modification to a pre-existing file's own logic-bearing surface, and it is logic-unchanged -- `105`'s own full attack test suite re-run unmodified and green confirms this. `ICharacterRepository.LinkAbilityActivationSource` (доработка) is a new, additive interface method -- `SqliteCharacterRepository` is its only implementer (confirmed by repository-wide search), so no other implementer needed updating. No schema change to any pre-existing table beyond the additive `CompensatedAt`/`CompensationStartedAt`/`CreatedEffectIdsJson` columns on the brand-new `AbilityActivation` table (no migration needed, nothing has shipped yet). `AcquireAbility`/`AcquireAbilityViaProgressionPurchase`/`RemoveAbility` are untouched -- every existing caller keeps compiling and behaving identically; an ability acquired without a subsequent `LinkAbilityActivationSource` call simply cannot be activated (an honest rejection). **Вторая доработка:** `SqliteActivateAbilityRepository`'s own constructor signature is widened (not an additive overload) to require `IActiveEffectRepository` -- safe since this class has exactly one caller anywhere (this task's own test fixture, updated in the same commit) and is not yet merged to `main`. **Третья доработка:** `AbilityActivationRecord`'s new `CompensationStartedAt` ctor parameter is additive; every pre-existing row (from earlier tests in this same session) simply reads back with it `null`, correctly meaning "compensation never attempted." Reverting this task's source returns to the pre-`106` state: no `ActivateAbility` command exists, the mechanics-primitive schema ceases to exist, and no later task has yet been built against it (this is the first task to add it).
